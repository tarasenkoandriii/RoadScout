## Что добавлено

**Backend** (`apps/api/src/home-verification/`):
- Prisma: enum `HomeVerificationStatus` (PENDING/APPROVED/NEEDS_REVIEW/REJECTED) + модель
  `HomeAddressVerification` (адрес, координаты, фото квитанции как base64 data URL, результат
  AI-проверки, кто/когда ревьюил).
- `receipt-verification.service.ts` — `ReceiptVerificationService.verify()`: вызывает xAI/Grok

  каких сбоях (нет ключа, сетевая ошибка, невалидный JSON) — только при явном совпадении всех
  проверок.
- `home-verification.service.ts` — `HomeVerificationService`: `submit()` (с блокировкой
  повторной отправки, пока есть незавершённая заявка), `getHomeSector()` (гейт по `APPROVED`,

- `home-verification.controller.ts` — `POST /home/verify` (multipart, `multer`/

  `AdminGuard`.
- Подключено в `app.module.ts`; `multer`/`@types/multer` добавлены в `package.json`.

**Frontend** (`apps/admin/`):
- `app/my-home/page.tsx` — форма отправки (адрес + фото), статусы PENDING/NEEDS_REVIEW/APPROVED/
  REJECTED, показ сектора камер (переиспользует `SectorMap`) после одобрения.
- `app/admin/home-verifications/page.tsx` — список заявок, детальная карточка с фото квитанции
  и результатами AI-проверки, кнопки «Одобрить»/«Отклонить» (с причиной).
- Нав-ссылки в `app/page.tsx` («Мой дом») и `app/admin/layout.tsx` («Верификация «Мой дом»»).

## Найден и исправлен реальный баг (не в стабе — в самом коде)

`receipt-verification.service.ts` изначально читал `XAI_API_KEY`/`XAI_BASE_URL`/
`GROK_VISION_MODEL`/порог давности даты в **module-level `const`, вычисляемые один раз при
импорте модуля** — то есть значение примораживалось к моменту первой загрузки файла и не
реагировало на последующие изменения `process.env`. Это всплыло при тестировании (второй тест
с `XAI_API_KEY`, выставленным уже после импорта, не сработал), но потенциально является
проблемой и в реальном рантайме в любом сценарии, где модуль мог быть загружен до полной
инициализации окружения. Остальные подобные геттеры в проекте (например,
`dev-accounts.util.ts::isDevAutoLoginEnabled()`) читают `process.env` заново при каждом
вызове — **исправлено под этот же паттерн**: все четыре значения теперь читаются функциями
(`getApiKey()`, `getBaseUrl()`, `getVisionModel()`, `getMaxReceiptAgeDays()`), вызываемыми
заново на каждый `verify()`.

## Дополнение: object storage, калибровка порога, rate-limiting по IP

Три доработки поверх исходной версии — реально прогнаны тем же способом (ts-node + офлайн-стабы), не просто вычитаны.

### 1. Object storage (Vercel Blob)

`ReceiptStorageService.store()` — грузит фото в Vercel Blob (`access: 'public'`, `addRandomSuffix: true`) и хранит в БД URL вместо base64. Без `BLOB_READ_WRITE_TOKEN` — прозрачный откат на прежнее поведение (`data:`-URL в том же поле, `receiptImageUrl`); при сбое самой загрузки (сеть/квота/неверный токен) — тот же откат, не роняя заявку.

**Прогнано (3 сценария):**
1. Не настроено (`BLOB_READ_WRITE_TOKEN` не задан) → `data:`-URL. **Пройден.**
2. Настроено, `put()` успешен → реальный blob-URL, вызван с `access:'public'` и `addRandomSuffix:true`. **Пройден.**
3. Настроено, но `put()` кидает ошибку (например, квота) → откат на `data:`-URL, без исключения наружу. **Пройден.**

### 2. Калибровка порога уверенности

Порог (`HOME_VERIFICATION_MIN_CONFIDENCE`, по умолчанию `0.7`) вынесен из `ReceiptVerificationService` в env, читается функцией `getMinConfidence()` (не кэшируется). Добавлен `GET /admin/home-verifications/stats` (`HomeVerificationService.getCalibrationStats()`) — раскладывает все заявки с известным `addressMatchConfidence` по бакетам (0.0–0.5 / 0.5–0.7 / 0.7–0.9 / 0.9–1.01) и считает, сколько в каждом бакете одобрено/отклонено/на ревью вручную — админ видит на странице `/admin/home-verifications`, не завышен/занижен ли текущий порог.

**Прогнано (2 сценария):**
1. Бакетизация: 5 заявок с разными `confidence`+`status` → все 4 бакета посчитаны математически верно (проверено поштучно: total/approved/rejected по каждому диапазону), запись без `confidence` (ещё не обработана) корректно исключена. **Пройден.**
2. `currentMinConfidence` отражает `HOME_VERIFICATION_MIN_CONFIDENCE` из env "на лету" (сменили переменную между вызовами — тут же увидели новое значение). **Пройден.**

### 3. Rate-limiting по IP

`HomeVerificationService.submit()` считает заявки с того же `ipAddress` за последние `HOME_VERIFICATION_RATE_LIMIT_WINDOW_HOURS` часов (по умолчанию 24) **в БД** (не in-process — переживает холодные старты serverless), до дорогих шагов (загрузка в Blob, вызов AI). При превышении `HOME_VERIFICATION_RATE_LIMIT_MAX` (по умолчанию 3) — `HttpException` со статусом 429. IP берётся из `x-forwarded-for` (первый адрес в цепочке — исходный клиент) с фоллбэком на `req.socket.remoteAddress`; `null` IP (нет ни того, ни другого) не лимitируется вовсе.

**Прогнано (6 сценариев для лимита + 5 для парсинга IP):**
1. Первая и вторая заявки с одного IP (лимит=2) проходят. **Пройдены.**
2. Третья заявка с того же IP → `HttpException` со статусом именно `429` (не просто generic-ошибка). **Пройден.**
3. Заявка с ДРУГОГО IP не задета лимитом первого. **Пройден.**
4. `ipAddress: null` — три заявки подряд, ни одна не заблокирована. **Пройден.**
5. Заявки старше окна (24ч) не засчитываются в лимит — вручную вставлены 2 записи 48ч/30ч давности, новая заявка с того же IP всё равно прошла. **Пройден.**
6. `getClientIp()`: одиночный IP, цепочка прокси (первый побеждает), только `socket.remoteAddress`, ничего нет (`null`), обрезка пробелов вокруг адреса. **Все 5 — пройдены.**

Плюс `tsc --noEmit` по всем файлам `src/home-verification/*` вместе с `app.module.ts` — 0 ошибок в новом коде (проверено `grep` по имени модуля в выводе компилятора отдельно от неизменённых транзитивных файлов).

### Не проверено дополнительно

- Реальный аплоад в настоящий Vercel Blob (нужен реальный `BLOB_READ_WRITE_TOKEN` и сеть) — стаб `@vercel/blob` лишь повторяет публичную сигнатуру `put()`.
- Поведение `x-forwarded-for` на реальном Vercel/прокси перед API — логика написана по стандартной практике (первый IP в списке — клиент), но не сверена вживую с конкретным хостингом.
- Достаточность порога `0.7` по умолчанию и самих 4 диапазонов бакетов калибровки — это дизайнерское решение, требующее донастройки по реальным данным после первых недель эксплуатации (для этого и добавлен `/admin/home-verifications/stats`).

## Не проверено / известные ограничения

- Реальный вызов xAI/Grok vision API (сеть недоступна в этой среде) — протестирована только
  сама логика принятия решения (парсинг, все ветки авто-одобрения/ручного ревью), не факт, что
  реальная модель действительно надёжно различает "рукописную" дату от "печатной" на реальных
  фото квитанций — это зависит от качества модели, стоит откалибровать порог `0.7` и промпт по
  результатам первых реальных заявок.
- Загрузка файла (`multer`/`FileInterceptor`) не была реально прогнана (нет multer в
  установленных пакетах в этой среде) — только типизирована; сама логика чтения `file.buffer`/
  `file.mimetype` тривиальна и следует стандартному Nest-паттерну.
- `next build`/полная сборка — не прогонялась (нет доступа к npm registry), только точечные
  `tsc --noEmit` со стабами.
