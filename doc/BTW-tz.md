# Beyond the Wall — техническое задание

**Кодовое имя:** BTW
**Тип:** Telegram Mini App (Next.js 14 App Router) + NestJS + PostgreSQL/PostGIS
**Ядро:** `liveahead-core` (общий реестр камер с RoadScout)
**Версия ТЗ:** 1.1

> **Изменение в 1.1 — вычисления перенесены на устройство.** Серверный воркер `viewshed.build`, таблица `camera_viewshed` и сетевой эндпоинт сканирования упразднены. Определение окклюдера, целевой зоны, поиск и ранжирование кандидатов выполняются в Web Worker на телефоне поверх скачанных тайлов зданий и камер. На сервере остаются только выдача токенов на кадр, проверка запретных зон, размытие лиц и сборка тайлов. Затронуты §2, §4.2, §4.5, §4.7, §6, §7, §8, §9, §10, §11.2, §11.4, §14, §15.

## 1. Идея

Пользователь стоит на улице. Он поднимает телефон и **обводит им вокруг себя**. Приложение в реальном времени показывает, в каких направлениях есть публичная камера, чей обзор покрывает то, что находится **за препятствием** на линии взгляда пользователя. При совпадении направления телефона с таким направлением — на экран выводится живой кадр с этой камеры, наложенный на изображение с камеры телефона.

Метафора: **перископ / рентген**. «Что там за поворотом», «что на соседней улице», «стоит ли идти этим двором».

### 1.1. Что это НЕ

Чтобы избежать ошибки проектирования на старте:
- это **не** доступ к чужим приватным камерам и не сканер незащищённых RTSP;
- это **не** инструмент наблюдения за людьми и не «посмотреть в чужое окно»;
- это **не** дополненная реальность с 3D-реконструкцией сцены.

Источник данных — только камеры, уже публично вещающие в интернет и прошедшие модерацию в реестре LiveAhead. Всё остальное — в §11.

### 1.2. Ключевая продуктовая гипотеза

Ценность не в «увидеть стену насквозь» (буквально это невозможно), а в **мгновенном ответе на вопрос «что там, куда я смотрю»**, без карты, поиска и списков. Взгляд = запрос. Это единственный интерфейс, который быстрее карты.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Наблюдатель (O)** | пользователь: координата, высота глаз, азимут, тангаж |
| **Луч взгляда** | геодезический луч из O по азимуту `heading` |
| **Окклюдер** | первое здание/препятствие на луче взгляда, закрывающее обзор |
| **Целевая зона (T)** | область за окклюдером, которую пользователь «хочет» увидеть |
| **LOS-тест** | проверка прямой видимости «камера → конкретная точка» с учётом зданий и рельефа; считается на устройстве в момент запроса (полигоны обзора не предвычисляются, см. §4.7) |
| **Тайл** | квадрат z15 (~1.2 км) с геометрией зданий, камерами, осями улиц и рельефом; скачивается на устройство один раз |
| **Кандидат** | камера, прошедшая LOS-тест по целевой зоне T |
| **Захват (lock)** | состояние, когда телефон удерживается в направлении кандидата и открыт его поток |

## 3. Пользовательские сценарии

### 3.1. Основной: «Сканирование»
1. Пользователь открывает BTW → запрос разрешений (геолокация, датчики, камера).
2. Экран: превью камеры телефона + полупрозрачное **кольцо-радар** сверху с отметками азимутов, где есть кандидаты.
3. Пользователь поворачивается. При входе луча в конус кандидата — haptic + отметка растёт.
4. Удержание ~600 мс → **захват**: кадр камеры проявляется поверх превью (cross-fade, 400 мс), появляется подпись «450 м, за домом на Прорізній».
5. Тап → полноэкранный режим, live-видео, кнопки «сохранить точку», «поделиться».

### 3.2. Без камеры телефона (fallback)
Если `getUserMedia` недоступен (частая проблема в Telegram WebView на iOS) — вместо превью показывается затемнённая карта, ориентированная по компасу, с тем же радаром. Функциональность полная, теряется только эффект «рентгена». **Этот режим — обязательный, не опциональный.**

### 3.3. «Перископ по адресу»
Пользователь не на месте: вводит адрес/тыкает в карту → выбирает направление взгляда → тот же результат. Нужен для планирования («что у выезда со двора сейчас»).

### 3.4. Сохранённая точка наблюдения
Комбинация (позиция, азимут) сохраняется как «Мой выход из дома». Одним тапом — сразу лучший кандидат. Это основной retention-механизм: превращает разовый вау-эффект в ежедневную привычку.

### 3.5. «Что за поворотом» (пеший маршрут)
Интеграция с RoadScout: при движении пешком показывать кандидатов по ходу, а не по компасу.

## 4. Геометрическая модель и алгоритмы

### 4.1. Поза наблюдателя

```ts
interface ObserverPose {
  lat: number; lon: number;
  accuracyM: number;        // GPS accuracy
  eyeHeightM: number;       // 1.6 по умолчанию
  heading: number;          // 0..360, магнитный → истинный
  headingSigma: number;     // оценка ошибки, град
  pitch: number;            // -90..90
  floor?: number;           // если известно, +3м за этаж
  ts: number;
}
```

**Магнитное склонение:** датчики дают магнитный азимут. Для Украины склонение +7…+9°. Обязательно приводить к истинному: `trueHeading = magneticHeading + declination(lat, lon, date)`. Использовать WMM-таблицу (npm `geomagnetism`) — без этого систематическая ошибка 8° убивает точность.

### 4.2. Определение окклюдера

Вычисляется **на устройстве** (см. §4.7). Луч взгляда — отрезок длиной 400 м в локальных метрических координатах; ищем пересечения с рёбрами зданий из загруженного тайла через статический R-tree:

```ts
// buildings: Flatbush-индекс рёбер тайла, координаты в локальном ENU (метры)
function findOccluder(o: Vec2, dir: Vec2, eyeH: number, pitch: number, maxD = 400) {
  const hits = edgeIndex.search(...bboxOfRay(o, dir, maxD));   // ~5–40 рёбер
  let best = null;
  for (const e of hits) {
    const d = raySegmentIntersect(o, dir, e.a, e.b);           // null | метры
    if (d === null || d > maxD) continue;
    const losH = eyeH + d * Math.tan(pitch);
    if (e.heightM > losH && (!best || d < best.d)) best = { d, h: e.heightM, id: e.buildingId };
  }
  return best;
}
```

Это **одно** пересечение отрезков на ребро вместо марша с шагом 5 м — на порядок дешевле и точнее. Здание считается окклюдером, если его высота выше линии взгляда на этой дистанции:
`h_building > eyeHeight + d · tan(pitch)`.

Высоты: OSM `height` → `building:levels × 3.0` → дефолт по типу застройки (жилая 15 м, частная 6 м, промышленная 8 м).

**Если окклюдера нет** — пользователь смотрит вдоль открытой улицы. Продукт всё равно полезен: целевая зона ставится на 250 м вперёд («что дальше по улице»), режим помечается как `OPEN_VIEW`.

### 4.3. Целевая зона

```
d_target = min(d_occluder + 60 м, 400 м)          // 60 м — «сразу за домом»
T = ST_Buffer(destinationPoint(O, heading, d_target), r_T)
r_T = clamp(d_target · tan(θ_tol), 25 м, 120 м)
```

Формула точки назначения (сферическая):
```
φ2 = asin( sinφ1·cosδ + cosφ1·sinδ·cosθ )
λ2 = λ1 + atan2( sinθ·sinδ·cosφ1, cosδ − sinφ1·sinφ2 )
δ = d / R,  R = 6371000
```

### 4.4. Угловой допуск

```
θ_tol = clamp( atan2(accuracyM, d_target)·180/π + headingSigma, 10°, 35° )
```

Допуск **адаптивный**: чем хуже GPS и чем ближе цель, тем шире конус. Это честнее, чем фиксированные 15°, и радикально повышает match rate в плотной застройке.

### 4.5. Поиск кандидатов

Полностью **на устройстве**, без сетевого запроса на каждый скан. Работает над локально загруженными тайлами камер и зданий (§4.7).

Каскад из трёх фильтров — от дешёвого к дорогому:

**Ф1. Дистанция (R-tree, ~0.05 мс).**
Камеры в радиусе 2500 м от наблюдателя из `cameraIndex.search(bbox)`.

**Ф2. Геометрия конуса без окклюзии (~0.01 мс на камеру).**
Камера отбрасывается, если целевая зона `T` вне её сектора:
```
d_ct   = |C − T|                          // расстояние камера→цель
Δaz    = angleDiff(bearing(C → T), azimuth_C)
pass   = d_ct ≤ range_C + r_T
      && |Δaz| ≤ fov_h_C / 2 + atan2(r_T, d_ct)
```
После Ф2 обычно остаётся 3–15 камер.

**Ф3. Прямая видимость (LOS) камера→цель (~0.1–0.3 мс на камеру).**
Вместо предвычисленного полигона обзора считаем видимость **точечно, только для нужной цели**:
```ts
function isVisible(C: Cam, T: Vec2): boolean {
  const dir = normalize(sub(T, C.pos)), dist = len(sub(T, C.pos));
  for (const e of edgeIndex.search(...bboxOfSegment(C.pos, T))) {
    const d = raySegmentIntersect(C.pos, dir, e.a, e.b);
    if (d === null || d >= dist) continue;
    const losH = C.heightM + (T.groundH + 1.5 - C.heightM) * (d / dist);  // 2.5D
    if (e.heightM > losH) return false;                                    // перекрыто
  }
  return true;
}
```

**`coverage` без полигонов.** Раньше это была доля площади `T` внутри viewshed. На устройстве считаем её сэмплированием: 9 точек (центр + 8 по окружности `r_T`), `coverage = видимых / 9`. Погрешность ~11%, для ранжирования достаточно, стоимость ×9 от одного LOS.

**Бюджет:** худший случай 15 камер × 9 точек × ~30 рёбер ≈ 4000 пересечений отрезков ≈ **3–6 мс** в Web Worker на среднем Android. При 4 сканах/с — менее 2.5% CPU.

> **Ключевое упрощение:** переход на устройство позволил отказаться от полигонов видимости вообще. Предвычисление viewshed нужно было только потому, что сервер не знал заранее, о какой цели спросят. Клиент знает цель в момент вычисления — и решает задачу «видит ли камера **эту** точку» вместо «что вообще видит камера». Это на два порядка дешевле.

### 4.6. Скоринг и ранжирование

```
score = 0.35·coverage                       // доля целевой зоны в поле зрения камеры
      + 0.20·orientation_fit                // (1+cos(Δ))/2, Δ = |azimuth_cam − heading_user|
      + 0.15·freshness                      // 1 − min(1, age/120s)
      + 0.12·quality                        // разрешение × ночная пригодность
      + 0.10·proximity                      // 1 − min(1, d_cam/2500)
      + 0.08·popularity                     // сглаженный CTR камеры
```

`orientation_fit` — важнейший компонент для *ощущения* правдоподобия: камера, смотрящая примерно в ту же сторону, что и пользователь, даёт картинку, которую мозг склеивает со сценой. Камера, смотрящая навстречу, показывает «зеркальный» мир и ломает эффект. Такие кандидаты не отбрасываем, но помечаем бейджем **«встречный ракурс»** и опускаем в выдаче.

Классификация ракурса:
| Δ азимутов | Метка | UI |
|---|---|---|
| 0–45° | `ALIGNED` | «взгляд насквозь» — основной режим |
| 45–135° | `SIDE` | «сбоку» |
| 135–180° | `OPPOSING` | «встречный ракурс, вид на вас» |

### 4.7. Данные на устройстве вместо предвычисления viewshed

**Решение:** серверный воркер `viewshed.build` и таблица `camera_viewshed` **упраздняются**. Сервер отдаёт только статические тайлы; вся геометрия считается на телефоне.

#### 4.7.1. Что сервер отдаёт

| Тайл | Содержимое | Размер (z15, плотный центр) | Кэш |
|---|---|---|---|
| `buildings` | полигоны + высоты, квантованные | 40–120 КБ | 30 сут, ETag |
| `cameras` | id, позиция, высота, азимут, fov, range, тип потока, качество | 2–8 КБ | 24 ч, ETag |
| `streets` | азимуты осей улиц для snap (§У3) | 3–10 КБ | 30 сут |
| `terrain` | сетка высот 30 м из Copernicus DEM, Int16 | 2 КБ | 90 сут |

Тайлинг — **z15** (≈1.2×1.2 км в Киеве). Загружается тайл наблюдателя + 8 соседей = 9 тайлов ≈ **0.4–1.1 МБ** один раз на район. Дальше только дельты статусов.

**Формат.** Один файл **PMTiles** на город в объектном хранилище (R2/Supabase Storage), запросы через HTTP Range. Не нужен тайл-сервер — снимается ограничение Vercel Hobby. Сборка PMTiles — офлайн-скрипт из OSM-выгрузки, раз в месяц, вне продакшн-инфраструктуры.

**Компактный бинарный формат зданий** (вместо MVT — вдвое меньше и парсится без библиотеки):
```
header: u16 version | f64 tileOriginLat | f64 tileOriginLon | u16 buildingCount
per building: u8 heightM/2 | u8 vertexCount | vertices: i16 x, i16 y   // ENU-метры от origin
```
При `i16` в метрах диапазон ±32 км — с запасом; точность 1 м достаточна.

#### 4.7.2. Хранение на клиенте

- **Cache API** (`caches.open('btw-tiles-v1')`) для тайлов — переживает перезапуск, есть встроенное вытеснение.
- **IndexedDB** — распарсенные `Float32Array`/`Int16Array` и построенные Flatbush-индексы (сериализуются как `ArrayBuffer`), чтобы не перепарсивать при каждом открытии.
- `Telegram.WebApp.CloudStorage` **не использовать** для тайлов — там лимит порядка килобайт на ключ; только для настроек и списка сохранённых точек.
- Бюджет: не более 60 МБ, LRU-вытеснение по тайлам.

#### 4.7.3. Актуальность статусов камер

Статус (`ONLINE/OFFLINE/HOLD`) меняется часто, поэтому он **не** в тайле:
```
GET /btw/status?tiles=15/18752/10971,15/18753/10971
→ { "v": 8431, "off": ["a1b2…","c3d4…"], "ttl": 30 }
```
Отдаётся список выключенных (их всегда меньшинство), TTL 30 с, размер — сотни байт. Клиент фильтрует локально. Это единственный периодический сетевой вызов в режиме сканирования.

#### 4.7.4. Рельеф

Copernicus DEM 30 м, ресемплится в сетку тайла (Int16, метры) на этапе сборки PMTiles. На клиенте — билинейная интерполяция высоты земли в точке. В плотном городе влияние мало, для холмистых районов (Печерск, правый берег, пригород) — существенно.

#### 4.7.5. Что остаётся на сервере (и почему это нельзя переносить)

| Остаётся серверным | Причина |
|---|---|
| Выдача токена на кадр/поток (`/btw/lock`) | клиентский код модифицируем; токен — единственная реальная точка контроля |
| Проверка `no_target_zone` | см. §11.2 — клиенту нельзя ни доверять решение, ни отдавать геометрию зон |
| Размытие лиц и номеров | fail-closed требование §11.3 |
| Rate limit и антисталкинг | §11.4 |
| Сборка тайлов, health-мониторинг камер, модерация | инфраструктура |

**Серверный fallback сохраняется.** Эндпоинт `POST /btw/scan` не удаляется, а становится резервным путём для слабых устройств и для режима «Перископ по адресу» (§3.3), где тайлы ещё не загружены. Реализация — тот же алгоритм из §4.5 на Node (общий пакет `@btw/geometry`, изоморфный TS: один код на клиенте и на сервере, одни и те же юнит-тесты).

#### 4.7.6. Что даёт перенос

1. **Стоимость:** исчезает GPU/CPU-воркер, очередь `viewshed.build`, таблица `camera_viewshed` (~5 тыс. полигонов на город) и весь трафик сканирования. Остаётся раздача статики.
2. **Latency:** скан выполняется за 3–6 мс локально вместо 120–180 мс по сети. Радар обновляется плавно при повороте телефона — это качественно другой UX, сейчас недостижимый.
3. **Приватность — главный выигрыш.** Точные координаты и азимут наблюдателя **больше не покидают устройство**. Сервер узнаёт только целевую точку в момент захвата. Это снимает основную претензию к продукту из §11 и позволяет честно написать в онбординге: «мы не знаем, где вы стоите и куда смотрите».
4. **Офлайн:** после загрузки тайлов сканирование работает без сети; недоступен только сам живой кадр.
5. **Масштабирование:** стоимость нового города = стоимость сборки PMTiles, а не рост парка воркеров.

## 5. Проблема компаса — центральный технический риск

Магнитометр в городе даёт ошибку 10–30° (арматура, трамвайные линии, чехлы с магнитом, лифты). **Продукт нельзя строить на предположении о точном азимуте.** Стратегия — пять уровней, применяются каскадом:

### У1. Правильный источник данных
Приоритет: `Telegram.WebApp.DeviceOrientation.start({ refresh_rate: 100, need_absolute: true })`.
Telegram Bot API 8.0 добавил в Mini Apps <cite index="4-1">объекты Accelerometer, DeviceOrientation и Gyroscope, а также LocationManager для доступа к геолокации и методы requestFullscreen/exitFullscreen</cite>. Важное ограничение: <cite index="1-1">флаг absolute в событии может прийти `false` даже если абсолютные данные запрашивались — если платформа не поддерживает абсолютную ориентацию</cite>. **Обязательно проверять `absolute` в каждом событии** и при `false` уходить на У2.

Fallback-цепочка:
1. `Telegram.WebApp.DeviceOrientation` (`need_absolute: true`)
2. W3C `deviceorientationabsolute`
3. `deviceorientation` + `webkitCompassHeading` (iOS), требует `DeviceOrientationEvent.requestPermission()` **строго по жесту пользователя**
4. нет компаса → режим «ручное наведение»: пользователь сам крутит радар пальцем

Также: `Telegram.WebApp.lockOrientation()` в портрет — иначе пересчёт осей при повороте ломает азимут.

### У2. Фильтрация
Комплементарный фильтр: гироскоп даёт быстрые изменения (низкий дрейф на секундах), магнитометр — медленную коррекцию.
```
heading = α·(heading_prev + gyroZ·dt) + (1−α)·heading_mag,  α ≈ 0.94
```
Плюс медианный фильтр по окну 5 отсчётов против выбросов.

### У3. Привязка к уличной сети (главный приём)
В городе пользователь почти всегда стоит на улице и смотрит вдоль или поперёк неё. Берём из OSM азимуты ближайших сегментов дорог в радиусе 30 м → получаем 2–4 «разрешённых» направления. Если измеренный азимут попадает в ±20° от одного из них — **притягиваем к нему** (snap). Это убирает большую часть систематической ошибки бесплатно.

### У4. Калибровка по кандидату
Если пользователь вручную выбрал кандидата из списка, а не поймал его — считаем разницу между азимутом на кандидата и показанием компаса и сохраняем как персональную поправку `headingBias` на сессию (с затуханием).

### У5. Визуальная привязка (фаза 3)
Кадр с телефона + кадр с ближайшей камеры → vision-модель (Grok vision) оценивает, совпадает ли сцена, и корректирует азимут. Дорого, поэтому только: по кнопке «уточнить», не чаще 1 раза в 30 с, и только для Pro.

### У6. Дизайн, устойчивый к ошибке
Даже с У1–У5 не показывать **одного** кандидата как «единственно верного». UI показывает **ленту-веер из 3–5 кандидатов** по азимуту; захват — просто фокус на ближайшем. Пользователь листает свайпом. Это превращает неточность из бага в фичу («посмотри и соседние ракурсы»).

## 6. Схема данных

```sql
CREATE TABLE camera (
  id            uuid PRIMARY KEY,
  external_id   text,
  name          text NOT NULL,
  geom          geometry(Point,4326) NOT NULL,
  height_m      real DEFAULT 4.0,
  azimuth       real,                       -- истинный, 0..360
  azimuth_conf  real DEFAULT 0.5,           -- уверенность (из AI-vision/ручной)
  fov_h         real DEFAULT 70,
  fov_v         real DEFAULT 40,
  range_m       int  DEFAULT 300,
  is_ptz        boolean DEFAULT false,      -- PTZ → сектор считается круговым, кандидат помечается
  stream_type   text,                       -- HLS | MJPEG | SNAPSHOT | YOUTUBE
  status        text DEFAULT 'PENDING',
  publish_delay_sec int DEFAULT 0,
  city_id       uuid,
  updated_at    timestamptz DEFAULT now()
);
CREATE INDEX ON camera USING GIST (geom);
CREATE INDEX ON camera (status) WHERE status = 'ONLINE';

-- camera_viewshed УДАЛЕНА: видимость считается на устройстве (§4.7)

CREATE TABLE building (                     -- только источник для сборки тайлов,
  id        bigint PRIMARY KEY,             -- в рантайме не запрашивается
  geom      geometry(Polygon,4326) NOT NULL,
  height_m  real NOT NULL,
  src       text                            -- 'height' | 'levels' | 'default'
);
CREATE INDEX ON building USING GIST (geom);

CREATE TABLE tile_build (                   -- реестр собранных PMTiles-наборов
  city_id     uuid NOT NULL,
  layer       text NOT NULL,                -- buildings | cameras | streets | terrain
  version     int  NOT NULL,
  url         text NOT NULL,
  bytes       bigint,
  osm_snapshot date,
  built_at    timestamptz DEFAULT now(),
  PRIMARY KEY (city_id, layer, version)
);

CREATE TABLE camera_status_gen (            -- монотонный счётчик для /btw/status
  city_id  uuid PRIMARY KEY,
  version  bigint NOT NULL DEFAULT 0        -- инкремент при любой смене статуса
);

CREATE TABLE no_target_zone (               -- см. §11
  id        uuid PRIMARY KEY,
  geom      geometry(Polygon,4326) NOT NULL,
  kind      text NOT NULL,                  -- MILITARY | CRITICAL | SCHOOL | MEDICAL | PRIVACY | LEGAL
  note      text,
  created_by uuid,
  created_at timestamptz DEFAULT now()
);
CREATE INDEX ON no_target_zone USING GIST (geom);

-- Сканы больше не доходят до сервера (§4.7.6). Пишем только факт захвата.
CREATE TABLE lock_event (                   -- антисталкинг + аналитика, короткий TTL
  id         bigserial PRIMARY KEY,
  user_id    text NOT NULL,
  target_h3  text NOT NULL,                 -- цель, H3 r10 (~65 м)
  camera_id  uuid NOT NULL,
  granted    boolean NOT NULL,              -- false = отказ по зоне/лимиту
  created_at timestamptz DEFAULT now()
);
CREATE INDEX ON lock_event (user_id, target_h3, created_at);
```

`lock_event` очищается джобой старше 72 ч (см. §11.4). Позиция наблюдателя в БД **не хранится вообще** — сервер её не получает.

Клиентская телеметрия сканов (match rate, время до захвата) шлётся **агрегатами раз в сессию**, без координат: `{ scans: 42, withCandidates: 19, locks: 3, snapUsed: true }`.

## 7. API

Сканирование сетевого API **не имеет**. Клиент общается с сервером только для получения данных и токенов.

### 7.1. Тайлы (статика, CDN)
```
GET /btw/manifest?city=kyiv
→ { "layers": { "buildings": {"v":31,"url":"…/kyiv-buildings-31.pmtiles"},
                "cameras":   {"v":204,"url":"…/kyiv-cameras-204.pmtiles"},
                "streets":   {"v":31,"url":"…"},
                "terrain":   {"v":3,"url":"…"} },
    "declination": 8.2 }        // магнитное склонение для региона, §4.1
```
Сами `.pmtiles` тянутся HTTP Range-запросами напрямую из объектного хранилища, минуя backend. Immutable + версия в имени → кэшируются вечно.

### 7.2. Статусы камер (единственный периодический вызов)
```
GET /btw/status?city=kyiv&since=8431
→ { "v": 8437, "off": ["a1b2…"], "on": ["e5f6…"], "ttl": 30 }
```
Дельта от версии клиента. При `since` слишком старом — полный список `off`. Размер типично < 1 КБ.

### 7.3. Кадр и захват — единственная точка контроля
```
POST /btw/thumb   { cameraId, targetLat, targetLon }
→ { url, ttl: 60 }                      // подписанный URL превью 320px

POST /btw/lock    { cameraId, targetLat, targetLon }
→ { streamToken, ttl: 300, perspective }
→ 403 { code: "UNAVAILABLE_HERE" }      // зона запрета, §11.2 — без объяснения причины
→ 429 { code: "RATE_LIMIT" }
```
Сервер на каждом `lock`/`thumb` проверяет: (1) камера `ONLINE` и не в `HOLD`; (2) цель не в `no_target_zone`; (3) цель физически может быть в поле зрения камеры — дешёвая проверка конуса без окклюзии (защита от использования BTW как массового браузера камер); (4) лимиты и антисталкинг (§11.4).

Координаты наблюдателя в запросе **отсутствуют намеренно** — сервер их не знает и не должен знать.

### 7.4. Прочее
```
POST /btw/viewpoints        сохранить точку наблюдения (шифруется на клиенте, см. §11.4)
GET  /btw/viewpoints
POST /btw/report            жалоба на камеру/кадр
POST /btw/telemetry         агрегаты сессии, без координат
GET  /btw/coverage?bbox=    тепловая карта покрытия (онбординг «где это работает»)
POST /btw/scan              ФОЛЛБЭК: серверный расчёт для слабых устройств и режима §3.3
```

Аутентификация — `X-Telegram-Init-Data` (HMAC-валидация; `signature` исключается из `data_check_string`).

## 8. Клиент

### 8.1. Стек
- Next.js 14 App Router, TMA SDK, Zustand для позы и кандидатов.
- **Геометрический движок — в Web Worker.** Главный поток только рисует; воркер держит тайлы, Flatbush-индексы и считает §4.2–4.6. Обмен через `postMessage` с `Transferable` буферами (без копирования).
- Индексы: `flatbush` (статический R-tree на типизированных массивах, ~0.1 мс на построение для 2 тыс. рёбер).
- Тайлы: `pmtiles` (JS-клиент, Range-запросы), парсинг бинарного формата зданий — вручную через `DataView`.
- Вся математика — в локальных ENU-метрах `Float32Array`, геодезия только на границах (вход позы, выход целевой точки).
- Общий изоморфный пакет `@btw/geometry` — один и тот же код в воркере и в серверном фоллбэке `/btw/scan`.
- Рендер радара — Canvas 2D (не WebGL: меньше расход батареи, достаточно).
- Превью телефона — `<video>` c `getUserMedia({ video: { facingMode: 'environment' } })`, `playsInline`.
- Оверлей кадра камеры — `<img>`/`<canvas>` поверх видео с `mix-blend-mode: screen` и настраиваемой прозрачностью (слайдер «рентген» 0–100%) — это и есть главный вау-эффект.
- `Telegram.WebApp.requestFullscreen()` + `lockOrientation()` при входе в режим сканирования.
- Haptic: `HapticFeedback.impactOccurred('light')` при входе в конус, `'medium'` при захвате.

### 8.2. Разрешения — порядок важен
1. Экран-объяснение (зачем нужны датчики) → **кнопка**.
2. По жесту: `LocationManager.init()` → `DeviceOrientation.start({need_absolute:true})` → `getUserMedia`.
3. Любой отказ → деградация, а не блокировка: без камеры → карта-режим; без ориентации → ручной радар; без геолокации → выбор точки на карте.

### 8.3. Загрузка тайлов
- При первом запуске: определяем город → `manifest` → тянем 9 тайлов z15 вокруг позиции с индикатором прогресса («готовим карту района, 0.8 МБ»).
- Префетч соседнего кольца тайлов в `requestIdleCallback` при движении к границе текущего.
- Тайлы вокруг сохранённых точек (§3.4) прогреваются заранее — сценарий «вышел из дома» работает мгновенно и офлайн.
- Проверка версий из `manifest` — раз в 24 ч, обновление тайлов в фоне.
- На `saveData: true` (Network Information API) или медленной сети — спросить пользователя перед загрузкой.

### 8.4. Батарея и трафик
- Датчики: `refresh_rate: 100` мс во время сканирования, `stop()` при `lock` и при уходе экрана (`visibilitychange`).
- Пересчёт кандидатов не чаще 8 Гц и только при Δheading > 3° или Δposition > 10 м; иначе — интерполяция радара по последнему результату.
- Превью телефона на 640×480, 15 fps.
- Кадры кандидатов — только thumbnail 320 px до захвата; полный поток только после `lock`.
- Автовыход из сканирования после 90 с бездействия.
- Трафик в режиме сканирования после загрузки тайлов: ~1 КБ / 30 с (`/btw/status`) + превью только для видимых кандидатов.

## 9. Производительность

Целевые показатели после переноса на устройство:

| Показатель | Цель | Где меряем |
|---|---|---|
| Один скан (Ф1–Ф3, §4.5) | < 8 мс p95 | Web Worker, средний Android 2021 г. |
| Задержка радара при повороте | < 120 мс | от события датчика до кадра Canvas |
| Первая загрузка тайлов района | < 6 с на 4G | 9 тайлов z15 |
| TTF полного кадра после `lock` | < 1.5 с p75 | сеть |
| `p95(/btw/lock)` | < 120 мс | сервер |

**Бенчмарк — обязательная часть M1.** Прогон §4.5 на наборе из 200 реальных поз в центре Киева, на трёх устройствах (низ/середина/верх). Если p95 > 15 мс — переписать `isVisible` на Rust→WASM (ожидаемый выигрыш ×4–6); архитектуру это не меняет, интерфейс `@btw/geometry` тот же.

**Деградация на слабых устройствах.** Клиент замеряет время первых 20 сканов; при медиане > 25 мс автоматически: снижает частоту до 3 Гц → уменьшает `coverage`-сэмплирование с 9 точек до 3 → переключается на серверный `/btw/scan`. Переключение прозрачно для пользователя.

**Серверная нагрузка.** Исчезла целиком: вместо N запросов/с на сканирование остаётся раздача immutable-статики через CDN и редкие `lock`. Redis-кэш сканов и его TTL-логика **не нужны**.

**Ограничения Vercel Hobby.** На Vercel — Next.js-фронт и `manifest`/`status` (лёгкие, кэшируемые). PMTiles — в R2/Supabase Storage напрямую. На отдельном сервере остаются: `/btw/lock`, прокси потоков, размытие лиц (GPU), health-мониторинг камер, сборка тайлов. Планировщик — Supabase `pg_cron`.

**Rate limits.** Сканы не лимитируются вообще (они локальные и бесплатны для нас — это ещё и лучше для UX). Лимитируются `thumb` (60/мин) и `lock` (20/час для Free).

## 11. Приватность, безопасность, право — обязательные требования

Функция «посмотреть за стену» по умолчанию читается как слежка. Ограничения ниже — **не опция**, они реализуются до публичного релиза, иначе продукт нежизнеспособен репутационно и юридически.

### 11.1. Источники
- Только камеры из реестра LiveAhead со статусом `VERIFIED`: публично вещающие, размещённые владельцем для публичного просмотра.
- **Запрещено:** сканирование интернета на открытые RTSP/ONVIF, использование агрегаторов незащищённых камер, любой доступ по дефолтным учётным данным. Это уголовно наказуемо (ст. 361 КК України) и не подлежит обсуждению как источник.
- Камера удаляется по первому требованию владельца, без разбирательства.

### 11.2. Зоны, запрещённые как цель (`no_target_zone`)
Если целевая зона `T` пересекает такой полигон — **кадр не выдаётся**, с нейтральным сообщением «здесь просмотр недоступен» (без объяснения причины — иначе карта запретов утекает).

> **Критично при вычислениях на устройстве.** Полигоны `no_target_zone` **никогда не попадают в тайлы и не отдаются клиенту** — они содержат карту военных и критических объектов, их утечка опаснее самого продукта. Поэтому применяется двухуровневая защита:
>
> 1. **Редакция на этапе сборки тайлов.** Камеры, чей сектор обзора пересекает зону `MILITARY` или `CRITICAL`, **не включаются в `cameras`-тайл вообще**. Для клиента их просто не существует — это неотличимо от честного отсутствия камер и ничего не выдаёт. То же для зданий не делаем (застройка и так публична в OSM).
> 2. **Проверка на сервере при выдаче кадра.** Зоны `SCHOOL/MEDICAL/PRIVACY/LEGAL` и оперативные добавления проверяются в `/btw/thumb` и `/btw/lock` по фактической цели. Клиент может «увидеть» кандидата в радаре, но кадра не получит.
>
> Клиентский код модифицируем, поэтому решение о выдаче принимает **только сервер**. Всё, что клиент считает локально, — это подсказка «куда повернуть телефон», а не право доступа.

| kind | Содержимое |
|---|---|
| `MILITARY` | военные объекты, блокпосты, позиции ПВО, места прилётов |
| `CRITICAL` | энергетика, связь, ж/д узлы, водоканал |
| `SCHOOL` | школы, детсады, площадки — жёсткий запрет наведения |
| `MEDICAL` | больницы, реабилитационные центры |
| `PRIVACY` | жилые дворы, окна, приюты, кризисные центры |
| `LEGAL` | по требованию суда/владельца |

### 11.3. Обработка кадра
- **Обязательное** размытие лиц и госномеров на всех кадрах перед отдачей. Fail-closed: модель недоступна → кадр не отдаётся.
- Запрет распознавания лиц, повторной идентификации, трекинга людей между камерами — на уровне архитектуры (такие сервисы не подключаются).
- Кадры не сохраняются дольше 15 мин; Pro-«лента прошлого» — 60 мин, только обезличенные.
- Запрет скриншотов не реализуем технически, но: водяной знак с меткой времени на кадре + предупреждение о запрете распространения.

### 11.4. Антисталкинг
- Если один пользователь запрашивает кадр по одной и той же целевой H3-ячейке r10 более 10 раз за 24 ч — soft-block этой ячейки для него на 24 ч + флаг модератору. Счёт ведётся по `lock_event`, т.е. по фактическим просмотрам, а не по сканам.
- `lock_event` хранит только цель (H3 r10) и удаляется через 72 ч. **Позиция наблюдателя не собирается вообще** — сканирование происходит на устройстве и координаты никуда не отправляются (§4.7.6).
- Сохранённые точки наблюдения (`viewpoints`) — самые чувствительные данные (фактически домашний адрес). Хранятся зашифрованными ключом, производным от `telegram_id` + серверной соли, расшифровываются только на клиенте; сервер видит шифротекст. Прогрев тайлов для них делает клиент, не сервер.
- Нет функции «подписаться на точку и получать уведомления об изменениях» для произвольного адреса — только для собственных верифицированных точек (дом/работа).
- Нет и не будет: истории по адресу, поиска «покажи двор по адресу X во времени», экспорта кадров.

### 11.5. Военное положение (Украина)
- Kill-switch: отключение выдачи по области одной операцией.
- `publish_delay_sec` 10–30 мин для чувствительных локаций — сохраняет бытовую пользу, обесценивает для корректировки огня.
- AI-фильтр кадра: детект военной техники/формы/последствий прилёта → кадр не публикуется, камера в `HOLD`.
- Запрет массовой выгрузки: API не отдаёт списки камер с азимутами без строгого rate-limit и не поддерживает bbox-выгрузку крупнее 2 км².
- **До релиза — юридическая консультация** по ЗУ «Про захист персональних даних», нормам о видеонаблюдении и режиму воєнного стану. Заложить в план как блокирующую задачу.

### 11.6. Прозрачность для пользователя
Онбординг явно сообщает: показываются только публичные камеры, лица размыты, наведение на жильё и соцобъекты заблокировано, история не хранится. Кнопка «пожаловаться» на каждом кадре.

## 12. Модерация

- Очередь заявок на камеры: автопроба потока → AI-vision определяет азимут и тип сцены → ручное подтверждение.
- Проверка на пересечение с `no_target_zone` при каждом изменении полигонов зон (джоба `zones.revalidate`).
- Разбор жалоб: SLA 24 ч, при жалобе камера немедленно в `HOLD` до решения.
- Журнал всех действий модератора (кто, что, когда) — неизменяемый.

## 13. Метрики

| Метрика | Целевое |
|---|---|
| **Match rate** — доля сканов с ≥1 кандидатом | > 45% в центре Киева на старте |
| Lock rate — доля сканов, дошедших до захвата | > 20% |
| TTF кадра после захвата | < 1.5 с p75 |
| Heading correction rate — доля сессий, где сработал snap У3 | трекать, ожидаем > 50% |
| Доля сессий в fallback-режиме (без камеры телефона) | < 30%, иначе приоритизировать фикс WebView |
| D7 retention | > 20% |
| Доля пользователей с ≥1 сохранённой точкой | > 35% (главный предиктор удержания) |
| Жалоб на 1000 захватов | < 1 |

Match rate — **главная метрика жизнеспособности**. Если ниже 25%, продукт ощущается сломанным; тогда решение — не улучшать компас, а расширять целевую зону и переходить к формату «камеры вокруг меня» вместо «строго туда, куда смотрю».

## 15. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Компас непригоден в целевых устройствах | высокая | M0-спайк; веер кандидатов вместо одного; snap к улицам; ручной режим |
| `getUserMedia` не работает в TMA на iOS | средняя-высокая | fallback-режим карты обязателен с первого дня; запасной вариант — обычное web-приложение вне Telegram |
| Плотность камер недостаточна → match rate < 25% | высокая | старт в одном районе одного города; расширение целевой зоны; supply-механика из RoadScout (§7) |
| Репутационный удар «приложение для слежки» | средняя | §11 реализуется в M4, до публичного релиза; публичная политика приватности; пресейл-коммуникация как «городской перископ», не «рентген для дворов» |
| Юридические претензии в режиме воєнного стану | средняя | fail-closed зоны, kill-switch, задержка публикации, юрист до релиза |
| Стоимость размытия лиц (GPU) | средняя | размывать только отдаваемые кадры, кэш по `(camera, second)`, лёгкая модель (YOLOv8n-face) на CPU при малой нагрузке |
| **Слабые устройства не тянут расчёт** | средняя | бенчмарк в M0; Web Worker; авто-деградация 8→3 Гц → 3 сэмпла → серверный фоллбэк; WASM как запасной ход |
| **Объём тайлов отпугивает на первом запуске** | средняя | бинарный формат вместо MVT (×2 экономия); загрузка только 9 тайлов z15; прогресс-экран с объяснением; уважение к `saveData` |
| **Устаревшие тайлы → «камера есть, а кадра нет»** | средняя | `/btw/status` каждые 30 с; проверка версии манифеста раз в сутки; при 404/403 на `thumb` — камера сразу гасится в локальном индексе |
| **Модификация клиента для обхода ограничений** | средняя | все решения о выдаче — на сервере (§11.2); камеры чувствительных зон вырезаны на этапе сборки тайлов; лимиты по `lock_event` |
| **Утечка карты запретных зон через тайлы** | низкая, но критичная по последствиям | зоны никогда не отдаются клиенту; редакция на сборке; отказ без объяснения причины |
