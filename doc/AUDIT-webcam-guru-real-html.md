# Аудит: `WebcamGuruAdapter` переписан під реальну розмітку `webcam.guru.ua`

## Контекст

П0.1 (`doc/TZ-parser-import-improvements.md`) увесь час був позначений як "не перевірено —
немає доступу в інтернет". Користувач надав **реальний HTML** з живого сайту в трьох частинах:
1. Сторінка списку камер міста (Київ) — `<ol class="red padd">...`.
2. Скріншот сторінки конкретної камери (заголовок + «Источник: youtube.com/...»).
3. Точний HTML-фрагмент заголовка (`<h1>`) і посилання-джерела з тієї ж сторінки.

## Що показали реальні дані

Структура сайту виявилась **повністю іншою** за всі 4 попередні здогадки
(`.webcam-card`, `.camera-item`, generic `.card`, generic iframe-based fallback) — жодна з них
не могла спрацювати, бо сайт **не використовує CSS-класи для карток камер узагалі**. Реальна
структура — **двофазна**:

1. **Сторінка міста** (`/city/{slug}/`) — простий список без потоку/адреси:
   ```html
   <ol class="red padd"><li><a href="/city/Kiev/609/">Софійська площа</a></li>...</ol>
   ```
2. **Сторінка окремої камери** (`/city/Kiev/{id}/`) — тут і тільки тут є посилання на потік:
   ```html
   <h1 style="display:inline;">Веб камера {Назва} Киев</h1>
   ...
   <a href="http://www.youtube.com/channel/..." target="_blank">...</a>
   ```
   Окремого поля «адреса» немає взагалі — назва камери сама по собі є орієнтиром/адресою
   («Перехрестя б-ру Шевченка та вул. Володимирської»).

## Що зроблено

`apps/api/src/scraper/providers/webcam-guru.adapter.ts` переписаний повністю:
- Прибрано весь код на основі 4 здогадок-стратегій (`SELECTOR_STRATEGIES`).
- `discover()` тепер робить **1 + N запитів**: один на список міста, потім по одному на кожну
  знайдену камеру (щоб дістати `streamUrl`).
- `parseList()` — `ol.red.padd > li > a`, `externalId` — останній сегмент шляху `href`.
- `parseDetail()` — заголовок з `<h1>` (обрізається префікс «Веб камера »), джерело — перше
  посилання з `target="_blank"`, чий `href` не містить `guru.ua` (зовнішнє посилання — і є
  потоком; власні посилання сайту такого атрибута не мають, підтверджено реальними зразками).
- `locationText` = очищений заголовок (той самий текст, що й `title`) — на цьому сайті це і є
  єдиний доступний орієнтир для геокодингу.
- Класифікація `streamType`: `youtube.com` у посиланні → `YOUTUBE_LIVE`, інакше → `IFRAME`.
- Добавлено `PARSER_DETAIL_FETCH_DELAY_MS` (за замовчуванням 300мс) — пауза між дозапитами
  окремих сторінок камер, ввічливість щодо сайту-джерела.
- `ScraperService` — прибрано посилання на застарілу концепцію "стратегій" у тексті логу
  (`diagnostics.matchedStrategy` більше не існує в новій структурі `diagnostics`).

## Реально прогнані тести

Оскільки в цьому середовищі немає справжнього `cheerio` (немає мережі для встановлення), CSS-
селектор-залежну частину (`ol.red.padd > li > a`, `h1`, `a[target="_blank"]`) не вдалося
перевірити виконанням реального парсера — це чесно визнане обмеження. Натомість **реально
протестована чиста (без cheerio) логіка** — 8 перевірок, **проти точних рядків, які прислав
користувач**, не вигаданих:
1. `extractExternalId()` на всіх 4 реальних `href` зі списку камер Києва (`/city/Kiev/609/` →
   `"609"` і т.д.) — **пройдено**.
2. `cleanTitle()` на обох реальних заголовках (`"Веб камера Перехрестя ... Киев"` →
   `"Перехрестя ... Киев"`) — **пройдено**.
3. `classifyStreamType()` на реальному `http://www.youtube.com/channel/UC13xO4_2rnO7-FuJ8ne78_g`
   → `YOUTUBE_LIVE` — **пройдено**.
4. Перевірка, що фільтр «не містить guru.ua» коректно приймає реальне посилання-джерело і
   відхиляє посилання на власний домен сайту — **пройдено**.

Плюс `tsc --noEmit` ізольовано по обох змінених файлах (`webcam-guru.adapter.ts`,
`provider-adapter.interface.ts`) разом з `RegistryProxyService` — 0 помилок.

## Не перевірено / відомі обмеження

- **Сам cheerio-селекторний рушій не перевірений виконанням** у цьому середовищі (немає
  мережі для встановлення реального пакета) — покладаємось на те, що cheerio/css-select —
  зріла, широко використовувана бібліотека, що коректно реалізує стандартні CSS-селектори;
  ризик — у МОЇХ рядках селекторів, які саме тому звірені вручну посимвольно проти реальних
  HTML-фрагментів користувача (задокументовано вище).
- **Продуктивність двофазного `discover()` при великій кількості камер у місті** — якщо у
  Києві виявиться, скажімо, 50+ камер, `discover()` робитиме 50+ послідовних запитів ще ДО
  того, як спрацює вже наявний бюджет часу на прохід (`PARSER_RUN_TIME_BUDGET_MS`, П3.2, — той
  перевіряється МІЖ обробкою вже знайдених елементів, не всередині самого `discover()`). Якщо
  це підтвердиться на практиці — правильне рішення: перенести дозапит сторінки камери всередину
  `processItem()` (тоді він природно потрапить під вже наявну перевірку бюджету на кожній
  ітерації), а не робити це одним блоком до повернення результату з `discover()`. Явно
  задокументовано в коді як відоме обмеження, не приховано.
- Інші поля (`title`/`locationText`) для камер з НЕ-youtube джерелами (MJPEG/HLS/інші відео-
  хостинги) — реальний зразок був лише для одного джерела (YouTube-канал); чи однаковий патерн
  `a[target="_blank"]` спрацює для інших типів джерел — не перевірено, потрібні додаткові
  реальні приклади, якщо перші реальні прогони покажуть інакше.

## Оновлення: ризик підтвердився на реальних даних і виправлений

Пункт «Не перевірено / відомі обмеження» вище про продуктивність двофазного `discover()` —
**підтвердився в точності** на реальному прогоні (Київ, 31.07.2026, надано користувачем):

```
discoveredCount: 50, newCount: 0, autoImportedCount: 0, needsReviewCount: 0
status: PARTIAL, durationMs: 25263 (майже точно = PARSER_RUN_TIME_BUDGET_MS)
```

Тобто фаза 1 (список) відпрацювала правильно (знайдено 50 камер), але **жодна не була
оброблена жодного разу** — весь бюджет часу пішов на 50 послідовних дозапитів сторінок камер
ВСЕРЕДИНІ `discover()`, ще до того, як цикл обробки елементів у `runForProvider()` (де й
перевіряється бюджет) взагалі встиг зробити першу ітерацію.

**Виправлення**: `discover()` тепер робить **тільки фазу 1** (список, один швидкий запит) і
одразу повертає елементи-заглушки (`streamUrl: ''`). Фаза 2 (дозапит сторінки конкретної
камери) винесена в окремий необов'язковий метод `ProviderAdapter.fetchDetails()`, який
`ScraperService` викликає **по одному елементу за раз**, всередині циклу, що вже перевіряє
бюджет часу перед кожною ітерацією (`resolveItemDetails()` → `processItem()`). Адаптери, які
й так віддають усе одним запитом (майбутні однофазні джерела), цей метод просто не реалізують.

**Реально протестовано** (відтворення точного сценарію зі скріншотів):
- 50 елементів-заглушок від `discover()`, `fetchDetails()` дозапитує кожен окремо →
  **`newCount: 50`, `autoImportedCount: 50`, `status: SUCCESS`** (замість `0`/`0`/`PARTIAL` до
  фіксу) — головна перевірка, що напряму відтворює й підтверджує вирішення реального бага.
  **Пройдено.**
- Окремо перевірено, що бюджет часу (П3.2) і далі коректно працює в новій архітектурі: з
  навмисно жорстким бюджетом і повільним фейковим `fetchDetails()` — оброблено 3 з 20
  елементів (реальний прогрес є, на відміну від старого бага), статус `PARTIAL`, є явний запис
  у логі з причиною зупинки. **Пройдено.**

## Наступний крок

Реальний повторний запуск (`/admin/parser` → «Запустить сейчас» для Києва) на справжньому
сервері — це й покаже, чи справді 50 камер тепер реально імпортуються/йдуть на ревью (а не
просто знаходяться в списку). Про результат бажано повідомити — якщо щось не так на реальному
сайті (наприклад, `fetchDetails()` не знаходить `<h1>`/посилання-джерело на якійсь конкретній
сторінці камери), знадобиться ще один реальний фрагмент HTML з тієї сторінки.
