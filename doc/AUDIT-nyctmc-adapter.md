# Аудит: NYC DOT Traffic Cameras (NycTmcAdapter) — перший у списку парсерів

## Контекст

Прямий запит користувача: сайт `https://webcams.nyctmc.org/cameras-list`, знайдений і
підтверджений як реально існуючий (перевірено пошуком), не відкривався в браузері
користувача (найімовірніше — JS-застосунок (SPA), заблокований розширенням/налаштуванням
браузера). За результатом — накидати адаптер під цей API, додати першим у список парсерів.

## Дослідження реальної структури API

Офіційної публічної документації NYC DOT для цього конкретного ендпоінту не знайдено —
структура звірена з двома незалежними технічними джерелами:
1. Блог-пост про скрапінг цього самого API (`wttdotm.com/blog/tcpb_part_2.html`) — детально
   описує послідовність: `/map` → `/api/cameras/{id}/image` → `/api/cameras/{id}` (JSON з
   полями `id`/`name`/`latitude`/`longitude`/`area`/`isOnline`/`imageURL`) →
   `/api/cameras` (масив усіх камер одразу).
2. Відкритий репозиторій `github.com/wttdotm/traffic_cam_photobooth` — реальний приклад
   JSON-відповіді з конкретними id/координатами/назвами камер, використаний як тестові дані.

## Що зроблено

### `NycTmcAdapter`

- `GET https://webcams.nyctmc.org/api/cameras` — один виклик, масив усіх камер (сотні
  записів). Без ключа, без відомого ліміту квоти.
- `streamType: 'MJPEG_SNAPSHOT'` (пряме посилання на JPEG-знімок,
  `imageUrl`/`/api/cameras/{id}/image`) — перший реальний адаптер проєкту, що використовує це
  значення enum (раніше існувало в схемі, але жоден адаптер його фактично не створював).
- Захисна фільтрація: камери без `id` або без числових `latitude`/`longitude` пропускаються
  (реальний випадок — деякі камери в системі позначені offline і можуть мати неповні дані).

### Новий загальний механізм — `RawCameraItem.suggestedLat`/`suggestedLng`

Не специфічний для NYC TMC — будь-який майбутній адаптер зі структурованими координатами
(не тільки текстовою адресою) може передати їх напряму. `ScraperService.processItem()`
перевіряє наявність цих полів **перед** викликом `GeocodingService.geocode()` — якщо є,
геокодинг тексту повністю обходиться (`confidence: 1`, джерело авторитетне), і в журналі
імпорту явно записується «координати отримані напряму від источника», а не «геокодинг».
Це надійніше за спробу геокодити короткі технічні описи на кшталт «WBB - 2 NOR @ ABOVE
BEDFORD AVE & S 5 St», які звичайний геокодер міг би розпізнати неправильно.

### «Перший у списку парсерів»

Реалізовано двома незалежними шляхами (не покладаючись на один крихкий механізм):
1. `sql/nyctmc-provider-seed.sql` підключений **першим** у `docker-entrypoint.sh` (перед усіма
   іншими сідами).
2. **Знайдена й виправлена структурна прогалина**: у моделі `CameraProvider` не було поля
   `createdAt` взагалі — без нього порядок `findMany()` без `orderBy` у Postgres хоч і
   зазвичай збігається з порядком вставки рядків для простого сканування, це не гарантія, а
   побічний ефект плану виконання запиту. Додано `CameraProvider.createdAt DateTime
   @default(now())`, і — оскільки всі вже існуючі провайдери отримають `now()` в момент
   застосування міграції, а сід NYC TMC виконується ПІСЛЯ міграції (тобто з пізнішим `now()`,
   що звело б нанівець спробу бути «першим») — у самому сіді `createdAt` встановлено явно на
   штучно ранню дату (`2000-01-01`), що гарантує коректний порядок незалежно від точного часу
   виконання. Ендпоінт `/admin/parser/stats/summary` тепер явно `orderBy: { createdAt: 'asc' }`.

### Взаємне виключення — NYC TMC НЕ виключений

На відміну від YouTube/Google/Windy (усі коштують реальну квоту чи платні AI-виклики), NYC
TMC — безкоштовний API без відомого ліміту, тому свідомо залишений у загальному `run-all()`
без винятку — працює на тому самому частому розкладі, що webcam.guru.ua, без потреби в
окремому cron-job/endpoint.

## Реально прогнані тести (ts-node, справжнє виконання)

**`NycTmcAdapter`** (12 перевірок, на РЕАЛЬНИХ даних з дослідженого прикладу відповіді API):
коректний URL запиту; **точний реальний приклад камери** (`8d2b3ae9-da68-4d37-8ae2-d3bc014f827b`,
«WBB - 2 NOR @ ABOVE BEDFORD AVE & S 5 St», координати `40.710983, -73.963168`) — коректний
парсинг `externalId`/`streamType`/`streamUrl`/`title`/`suggestedLat`/`suggestedLng`/
`locationText`; камера без координат коректно відфільтрована (захисний випадок); не-200 статус
і мережева помилка → порожній результат без падіння; VPN-проксі дійсно використовується, коли
переданий.

**Обхід геокодингу тексту** (5 перевірок): наскрізний прогін через реальний
`ScraperService.runForProvider()` — **`GeocodingService.geocode()` жодного разу НЕ
викликається**, коли адаптер надає `suggestedLat`/`suggestedLng`; камера створюється з
точними координатами напряму з джерела; журнал імпорту коректно розрізняє «координати
напряму» від «геокодинг».

Разом **17 нових перевірок**, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку —
0 помилок у змінених файлах (2 залишкові — той самий, вже неодноразово підтверджений
артефакт спрощеної заглушки типів у `lookahead.controller.ts`/`monitoring.controller.ts`).

## Не перевірено / відомі обмеження

- **Реальний виклик `webcams.nyctmc.org/api/cameras` з живою мережею** — недоступна в цій
  пісочниці; структура відповіді звірена лише з незалежними технічними джерелами (блог-пост +
  приклад із GitHub-репозиторію), не з офіційною документацією NYC DOT (публічно її для цього
  ендпоінту не знайдено) — перед продакшеном варто перевірити один живий виклик, той самий
  принцип, що вже застосований для webcam.guru.ua/Windy.
- **Порядок «першим у списку»** — гарантований на рівні коду (`orderBy`+явна рання дата), але
  не перевірений на реальному запуску `docker compose up` з `prisma db push` (немає
  Docker/мережі в цій пісочниці).
- Кількість повернутих API камер (969 за одним зі спостережень, 963 за іншим — число
  коливається природно) означає потенційно велику кількість нових `CameraSourceRaw`-записів
  за один прохід — жодних окремих обмежень на це не додано (той самий принцип бюджету часу
  П3.2, що вже захищає інші адаптери, застосовується і тут автоматично через спільний цикл
  `ScraperService.runForProvider()`).

## Оновлення: реальний прогін показав 0 камер — знайдено і виправлено

Користувач реально запустив адаптер проти живого API — журнал імпорту показав WARN «Источник
не вернул ни одной камеры». Розбір показав дві окремі проблеми:

### 1. Найімовірніша реальна причина — відсутній User-Agent

На відміну від **усіх** інших адаптерів проєкту (webcam-guru/google-web-camera-search/
aggregator-discovery — всі явно ставлять описовий `User-Agent`), `NycTmcAdapter` спочатку
робив запит із дефолтним User-Agent axios (`axios/1.x.x`) — поширеним сигналом для WAF/бот-
захисту, через який запит міг тихо відхилятися чи повертати інший вміст замість реального
JSON. Додано той самий `User-Agent`, що вже використовується деінде в проєкті, і заголовок
`Accept: application/json`.

### 2. Узагальнене повідомлення журналу вводило в оману

Повідомлення «Источник не вернул ни одной камеры — проверьте вёрстку страницы» було написане
ще тоді, коли існував лише один, HTML-скрапінговий адаптер (webcam-guru) — тепер API-адаптерів
(YouTube/Google/Windy/NYC TMC) більше, ніж HTML-скрапінгових, і порада «перевірте вёрстку»
для них фактично невірна (немає жодної вёрстки, є тільки відповідь API). Формулювання в
`ScraperService` зроблено нейтральним до типу джерела, з підстановкою `diagnostics.reason`
безпосередньо в повідомлення, коли адаптер його заповнив.

### 3. Розширена діагностика `NycTmcAdapter` — три окремі, розрізнювані причини порожнього результату

Раніше «status 200, але тіло — не масив» і «джерело реально порожнє» виглядали в діагностиці
однаково (`foundCount: 0`). Тепер три випадки розрізняються явно:
- Статус 200, тіло — НЕ масив (можлива WAF/CAPTCHA-заглушка замість JSON) — `diagnostics.reason`
  + обрізаний фрагмент реальної відповіді (`responseSnippet`) для діагностики без відтворення.
- Масив непорожній, але жоден запис не має валідних `id`/`latitude`/`longitude` (можлива зміна
  структури полів API) — `diagnostics.reason` + приклад проблемного запису (`sampleRecord`).
- Дійсно порожній масив (джерело легітимно не має камер зараз) — звичайна діагностика без
  тривожного `reason`.

### Реально протестовано (9 нових перевірок)
User-Agent і Accept тепер справді встановлюються; усі три сценарії порожнього результату дають
чітко розрізнювані `diagnostics.reason`; звичайний успішний випадок не зламаний змінами.

## Виправлення: React-ворнінг "Each child in a list should have a unique key"

Окрема, незалежна знахідка того самого скріншота — `ImportLogPage`
(`/admin/parser/log`) використовував короткий синтаксис фрагмента `<>...</>` як прямий елемент
масиву в `.map()`, з `key` на ВНУТРІШНЬОМУ `<tr>` замість самого фрагмента. Короткий синтаксис
фрагмента **не підтримує `key` взагалі** — React бачив масив елементів без ключів на
верхньому рівні. Виправлено заміною на явний `<Fragment key={e.id}>...</Fragment>`.

**Перевірено, що це не системна проблема** — систематичний пошук усіх інших використань `<>`
у проєкті (5 файлів) підтвердив: жодне інше входження не знаходиться всередині `.map()` (усі —
умовний рендеринг через `&&`/тернарний оператор, де ключ не потрібен) — виправлення потрібне
було лише в цьому одному файлі.

## Оновлення 2: MJPEG_SNAPSHOT помилково вважався недоступним для прев'ю/автокалібрування

Реальний скріншот показав перший реально імпортований запис NYC TMC (камера «MHB-19 Manh N
URDW @ Anch», координати `40.710705, -73.992304`) — і одразу дві помилки, обидві з тієї самої
першопричини: `MJPEG_SNAPSHOT` (пряме посилання на статичний JPEG-знімок) помилково
трактувався як «потребує headless-браузера/плеєра», хоча насправді це **найпростіший** з усіх
типів для показу — звичайний `<img>`, простіше навіть за `<iframe>`.

### 1. Автокалібрування (`GrokCameraAssistService.suggestAzimuthFov()`)

Раніше: `imageUrl` обчислювався тільки для `YOUTUBE_LIVE` (через витяг мініатюри), для решти
типів — завжди `null`, з повідомленням «нужен headless-браузер». Виправлено: для
`MJPEG_SNAPSHOT` `streamUrl` тепер використовується напряму як `imageUrl` — жодного витягу не
потрібно, vision-модель отримує реальний знімок одразу.

### 2. Прев'ю трансляції (і на екрані калібрування, і в публічному embed-віджеті)

Той самий недогляд — `MJPEG_SNAPSHOT` був згрупований разом із `HLS` («обидва потребують
плеєра»), хоча HLS дійсно потребує (`hls.js`), а MJPEG_SNAPSHOT — ні. Новий хелпер
`canShowAsImage()` у `lib/embeddable.ts`, рендер через звичайний `<img>` з періодичним
cache-bust оновленням (кожні 3с — реальна камера оновлює знімок що ~2с за спостереженнями
спільноти, див. основний розділ цього документа) в обох місцях.

### Реально прогнані тести (11 нових перевірок)

`canShowAsImage()` (5): точний реальний URL з NYC TMC → `true`; IFRAME/YOUTUBE_LIVE/HLS → всі
коректно `false` (різні шляхи рендеру); той самий захист голого кореня домену, що вже є в
`looksEmbeddable()`, застосовується і тут. `suggestAzimuthFov()` (6): **точний реальний
сценарій зі скріншота** — `imageAvailable: true` замість попереднього `false`, `imageUrl`
дорівнює `streamUrl` напряму (без витягу); vision-модель реально викликається з цим прямим
URL; **HLS і далі коректно недоступний** (не зайва корекція — це справжнє обмеження, не
регресія).

## Оновлення 3: реальний скріншот показав "—" у колонках Город/Страна для всіх камер NYC TMC

Користувач реально запустив парсер (після фіксу продуктивності — камери імпортувались швидко
й успішно!), але колонки «Город»/«Страна» на `/admin/cameras` показували «—» для **усіх**
камер NYC TMC.

### Причина — дві окремі, повʼязані помилки

1. **`nyctmc-provider-seed.sql` мав `cityId = NULL`** — свідоме на той момент рішення
   («адаптеру City не потрібне для побудови запиту»), яке не врахувало, що
   `ScraperService.processItem()` **успадковує `provider.cityId`** для кожної створеної
   камери (`Camera.create({ data: { cityId, ... } })`). З `NULL` у провайдера — усі камери
   NYC TMC назавжди залишались без City взагалі, незалежно від того, що самі координати
   (`suggestedLat`/`suggestedLng`) були точними.
2. **Ще важливіше — `sql/cities-seed-developed-countries.sql` (містить сам запис City для
   New York) НІКОЛИ не був підключений у `docker-entrypoint.sh`** — суто структурне
   упущення при попередній роботі над світовою картою: файл був створений, але не доданий у
   ланцюг `run_sql`. Навіть якби `nyctmc-provider-seed.sql` посилався на правильний `cityId`
   із самого початку, City-рядок "New York" міг просто не існувати в базі.

### Виправлення

- **`nyctmc-provider-seed.sql`** — тепер `cityId: 'city_us_new_york'`, і
  `ON CONFLICT DO UPDATE SET "cityId" = EXCLUDED."cityId"` (не `DO NOTHING`, як раніше) —
  щоб фікс застосувався навіть до вже існуючого рядка провайдера без потреби видаляти й
  пересоздавати його.
- **`docker-entrypoint.sh`** — виправлено порядок: `cities-seed-developed-countries.sql`
  тепер підключений і виконується **до** `nyctmc-provider-seed.sql` (який на нього
  посилається), і до `youtube-search-providers-seed.sql`/`web-search-providers-seed.sql`/
  `windy-webcams-providers-seed.sql` — **той самий структурний фікс попутно вирішує ще одну
  приховану проблему**: провайдери YouTube/Google-пошуку/Windy для міст технологічно
  розвинених країн (Нью-Йорк, Берлін, Токіо тощо) теж ніколи не створювались автоматично,
  оскільки самих City-рядків не існувало на момент їх сідів.
- **Новий `sql/nyctmc-backfill-city-fix.sql`** — окремий бекфіл-скрипт для КАМЕР, уже
  імпортованих ДО цього фіксу (як на скріншоті користувача) — оновлює `cityId` заднім числом
  для всіх активних (не soft-deleted) камер провайдера `nyctmc`, де `cityId IS NULL`.

### Практичні кроки для застосування фіксу на вже працюючій системі

Оскільки сіди виконуються автоматично лише при старті контейнера (`docker-entrypoint.sh`),
для вже запущеної системи потрібно прогнати SQL вручну (в цьому саме порядку):

```bash
docker compose exec api npx prisma db execute --file sql/cities-seed-developed-countries.sql --schema prisma/schema.prisma
docker compose exec api npx prisma db execute --file sql/nyctmc-provider-seed.sql --schema prisma/schema.prisma
docker compose exec api npx prisma db execute --file sql/nyctmc-backfill-city-fix.sql --schema prisma/schema.prisma
```

Після цього колонки «Город»/«Страна» для вже імпортованих камер NYC TMC мають показати «New
York»/«United States», і фільтр по країні на `/admin/cameras` побачить їх коректно.



## Оновлення 4: оцінка дальності обзору + звірка з поточним сектором на карті

За прямим запитом користувача, реальний привід — скріншот з успішним автокалібруванням
камери NYC TMC («5 Ave @ 34 St», азимут 0°/FOV 100°/впевненість 100%, коректно розпізнане
«Facing North» з накладеного тексту на кадрі).

### 1. Оцінка дальності обзору (`suggestedRangeMeters`)

`GrokCameraAssistService.suggestAzimuthFov()` тепер також просить vision-модель оцінити
дальність обзору в метрах — за видимими орієнтирами для масштабу (відстань до перехрестя/
кінця вулиці/помітної будівлі, типові розміри міських кварталів). Той самий чесний принцип,
що вже є для азимута/FOV — `null`, якщо за кадром неможливо оцінити, не вигадана цифра.
Валідація діапазону (20-1000м, той самий орієнтир, що вже прийнятий у
`DEFAULT_RANGE_BY_HINT` для евристики) — нереалістичне значення (перевірено тестом: 50км)
відхиляється як `null`, не сліпо довіряється.

### 2. Звірка з поточним сектором на карті

Новий опціональний параметр `current: {azimuth, fovAngle, rangeMeters}` — поточні (можливо, ще
не збережені) значення сектора передаються в промпт як контекст. **Важливо**: модель
явно просять оцінити сцену НЕЗАЛЕЖНО від цих чисел (не підганяти відповідь під уже виставлені
значення), але в полі `reasoning` — прямо вказати, чи узгоджується її власна візуальна оцінка
з поточним сектором, чи розходиться. Кнопка «Применить» на калібруванні тепер застосовує й
запропоновану дальність, не тільки азимут/FOV.

### Реально прогнані тести (8 нових перевірок)

На точних реальних значеннях зі скріншота (координати `40.748444, -73.984560`, поточний
сектор азимут=0°/FOV=100°/дальність=80м): промпт справді містить ці числа для звірки;
формулювання явно просить порівняння, не просте повторення; `suggestedRangeMeters` коректно
парситься (250м); нереалістичне значення (50000м) від моделі відхиляється як `null`, при
цьому азимут/FOV з ТІЄЇ Ж відповіді парсяться коректно (валідація по кожному полю окремо,
не «все або нічого»); чесна відповідь моделі "не можу оцінити дальність" (`null`) зберігається
як `null`, не перезаписується вигаданим значенням.

Плюс `tsc --noEmit` по всьому графу застосунку — 0 помилок у змінених файлах (2 залишкові —
той самий, вже неодноразово підтверджений артефакт спрощеної заглушки типів).

### Не перевірено

Реальна якість оцінки дальності обзору vision-моделлю на живих кадрах — не перевірялась
(немає мережі в пісочниці); це складніша задача для vision-моделі, ніж азимут (потребує
оцінки масштабу сцени без відомої точки відліку) — очікувано менш надійна, ніж азимут/FOV,
тому й позначена тим самим чесним принципом «null, якщо не впевнена», а не завжди повертає
число.
