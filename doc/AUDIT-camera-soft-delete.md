# Аудит: soft delete камер по всьому проєкту + масове «Удалить нерабочие»

## Контекст

Прямий запит користувача: (1) кнопка над усім списком камер — «Удалить нерабочие»; (2) по
всьому проєкту камери при видаленні мають позначатись видаленими (soft delete), не видалятись
фізично.

## Що зроблено

### Схема

`Camera.deletedAt DateTime?` (+ індекс) — `null` = активна камера, timestamp = коли позначена
видаленою.

### `CamerasService.remove()` — перетворено на soft delete

Було: `prisma.camera.delete({ where: { id } })` (фізичне видалення).
Стало: `prisma.camera.update({ where: { id }, data: { deletedAt: new Date() } })`.

Причини свідомого вибору саме soft delete (а не просто виконання прямого запиту користувача
без пояснення): `CameraSourceRaw.cameraId` і `CameraSubmission.createdCameraId` — обидва
посилаються на `Camera.id` — фізичне видалення або впало б на обмеженні зовнішнього ключа (якщо
воно є), або залишило б биті посилання (якщо його немає) в записах, які документують історію
імпорту/модерації цієї камери.

### Масове «Удалить нерабочие»

- `CamerasService.removeAllOffline()` — `updateMany({ where: { status: 'OFFLINE', deletedAt:
  null }, data: { deletedAt: new Date() } })`. Свідомо виключає `DISABLED_SECURITY` (ручний
  оверрайд власника — не «не працює») і вже видалені камери.
- `POST /admin/cameras/delete-offline` — навмисно `POST`, не `DELETE`, щоб не конфліктувати з
  маршрутом `DELETE /admin/cameras/:id` (інакше рядок `delete-offline` спробував би
  зматчитись як `:id`).
- Кнопка «Удалить нерабочие (N)» над списком камер (`/admin/cameras`) — показує реальну
  кількість `OFFLINE`-камер, вимкнена, якщо їх 0.

## Реально прогнані тести (ts-node, справжнє виконання)

**Частина 1** (7 перевірок): `remove()` — запис ФІЗИЧНО лишається в фейковій БД, `deletedAt`
стає справжньою датою (не просто прапорцем); `findAll()` коректно виключає видалену камеру;
`removeAllOffline()` торкається лише активних `OFFLINE`-камер (не чіпає вже видалену, не чіпає
`ONLINE`).

**Частина 2** (3 перевірки): `findAtPoint()` (JS-фолбек шлях, коли PostGIS недоступний)
коректно виключає soft-видалену камеру з результатів пошуку; `findIndoorNearby()` те саме для
indoor-камер, активна indoor-камера лишається в результатах.

**Частина 3** (4 перевірки): `checkContentAvailability()` і `checkAll()` в `MonitoringService`
обидва коректно виключають видалені камери з проходу; `AlertsService.subscribe()` кидає
`NotFoundException` при спробі підписатись на видалену камеру (не мовчки створює биту
підписку); `checkCameraStatus()` (приватний метод, викликаний напряму для тесту) коректно
трактує видалену камеру як відсутню — повертає `false`, не намагається зіставити застарілий
статус.

**Embed-info** (3 перевірки): активна камера — звичайна відповідь; **видалена камера —
`embedInfo()` кидає саме `NotFoundException`** (перевірено конструктор помилки, не просто факт
кидання) — публічний віджет коректно 404-ить, не показує видалену камеру мовчки.

Разом **17 нових перевірок**, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку —
0 помилок у змінених файлах (залишкові 2 помилки в `lookahead.controller.ts` — той самий,
неодноразово підтверджений у попередніх аудитах цього проєкту артефакт спрощеної заглушки
Prisma-типів у пісочниці, не пов'язаний з однорядковим додаванням `deletedAt: null` до `where`).

## Не перевірено / відомі обмеження

- **Реальний `prisma db push` з новим полем `deletedAt`** — не прогонявся проти справжнього
  Postgres; поле опціональне (nullable), зворотна сумісність по побудові (усі існуючі записи
  автоматично отримають `NULL` = активна камера), але не перевірено вживу.
- **`findOne()` і `runForCamera()` свідомо не фільтрують по `deletedAt`** — це архітектурне
  рішення (не помилка), обґрунтоване в таблиці вище, але варто мати на увазі: пряме посилання
  на видалену камеру (наприклад, старий закладка в браузері адміна) технічно й далі відкриє
  сторінку калібрування для неї — тільки публічні/пошукові шляхи гарантовано ховають видалені
  камери.
- Немає окремого UI для перегляду списку вже видалених камер чи їх «відновлення» — тільки сама
  можливість зробити це на рівні БД/API (`Camera.deletedAt` можна вручну скинути в `null`) —
  повноцінна функція відновлення не була частиною цього запиту, поза обсягом цього кроку.
- Фронтенд-зміни (кнопка над списком камер) — перевірені балансом дужок і вручну вичитані, не
  прогонялись через `tsc`/візуально в браузері (та сама, вже неодноразово задокументована
  причина нестабільності заглушки `@types/react` у цій конкретній пісочниці).
