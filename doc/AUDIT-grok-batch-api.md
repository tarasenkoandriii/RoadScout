# Аудит: Batch API xAI для фонових Grok-викликів (aggregator-discovery)

## Контекст

Прямий запит користувача (зі скріншота консолі xAI Batch API): «для экономии бюджета и
производительности для Grok AI также используй батч».

## Ключове дослідження ПЕРЕД реалізацією — чому НЕ для авто-калібрування

Документація xAI (docs.x.ai/developers/advanced-api-usage/batch-api, підтверджено кількома
незалежними джерелами): Batch API дає знижку **20-50%** на вартість запитів, але результати
повертаються **асинхронно, «найкраще зусилля», типово до 24 годин** (жодних гарантій швидшого
часу). Це фундаментально несумісно з авто-калібруванням камер (`autoCalibrateBatch()`) —
інтерактивною функцією, де адмін натискає кнопку й очікує результат на екрані за секунди (щойно
оптимізовано з ~100с до ~10с через конкурентність). Переведення її на Batch API означало б
«натиснув — і, можливо, побачив результат за кілька годин чи наступного дня» — це зламало б
саму суть функції.

**Користувач це підтвердив і явно попросив застосувати Batch API саме до фонових Grok-викликів
у парсері** (`AggregatorDiscoveryService`), де це дійсно доречно — пошук сайтів-агрегаторів і
так уже виконується вночі за розкладом (04:00), жодна людина не чекає результат у реальному
часі.

## Реалізовано — тільки для `AggregatorDiscoveryService`

Свідомо НЕ застосовано до `GoogleWebCameraSearchAdapter`/`isLikelyCityCamera` (окремі камери,
релевантність) — вони викликаються ВСЕРЕДИНІ синхронного циклу `ScraperService.processItem()`,
де результат потрібен одразу, щоб вирішити, чи створювати `CameraSourceRaw` для цього
конкретного елемента ПРЯМО ЗАРАЗ. Переведення їх на асинхронний Batch API вимагало б куди
глибшої переробки самого пайплайну парсера (відкласти рішення "створювати чи ні" на
невизначений час) — окрема, значно більша робота, не зроблена в цьому кроці.

`AggregatorDiscoveryService` — ідеальний перший кандидат: результат (список
`AggregatorSiteCandidate`) і так лише зберігається в БД для подальшого ручного огляду адміном,
без жодної залежності від негайного результату.

### Нова модель `GrokBatchJob`

Один рядок = один пакет, поданий до xAI, з `requestMap` (JSON: `batch_request_id → {cityId,
cityName}`) для зіставлення результатів назад із конкретним містом, коли вони стануть готові.

### Нові методи `GrokCameraAssistService`

- `submitAggregatorSearchBatch(cities)` — `POST /v1/batches` (створення) →
  `POST /v1/batches/{id}/requests` (додавання запитів, по одному на місто, з тим самим
  промптом і `web_search` tool, що вже є в синхронному `searchAggregatorSites()`).
- `getBatchStatus(xaiBatchId)` — `GET /v1/batches/{id}`.
- `getBatchResults(xaiBatchId)` — `GET /v1/batches/{id}/requests` (з пагінацією), парсить
  кожен завершений запит тим самим чином, що синхронний шлях.

### Нові методи `AggregatorDiscoveryService`

- `submitBatchDiscovery()` — подає ВСІ міста одним пакетом, зберігає `GrokBatchJob`, повертається
  одразу (не чекає результатів).
- `processPendingBatches()` — викликається з окремого cron (щогодини), перевіряє статус кожного
  ще не обробленого `GrokBatchJob`, і якщо `completed` — забирає результати, створює
  `AggregatorSiteCandidate` (та сама дедуплікація за URL, що вже є в синхронному шляху —
  **включно з дедуплікацією МІЖ синхронним і batch-шляхами**, якщо той самий сайт вже був
  знайдений одним із них раніше).

### Нові ендпоінти + cron

`POST /admin/aggregator-sites/submit-batch` (ручний запуск), `POST
/internal/aggregator-discovery/submit-batch` (cron, той самий розклад — раз на 3 дні, о 04:30,
трохи пізніше за синхронний шлях), `POST /internal/aggregator-discovery/process-pending-batches`
(cron, щогодини — Batch API типово до 24 годин, частіше опитувати немає сенсу).

### Frontend

Нова кнопка «🕐 Пакетный запрос (дешевле)» на `/admin/aggregator-sites`, поруч із існуючою
синхронною — з явним попередженням у `confirm()`, що результати з'являться не одразу.

## Реально прогнані тести (ts-node, справжнє виконання)

**`GrokCameraAssistService` — 11 перевірок**: реальна структура запитів підтверджена (виклик
`/batches` для створення, `/batches/{id}/requests` для додавання, коректний `web_search` tool
у кожному запиті, промпт містить правильні місто+країну); без ключа API — жодного мережевого
виклику; статус і результати коректно парсяться, включно з правильною кореляцією за
`batch_request_id` (місто з реальними сайтами і місто з порожнім результатом — обидва коректно
присутні, не втрачені).

**`AggregatorDiscoveryService` — 10 перевірок**: повний цикл обробки завершеного пакета
(кандидати створені, коректно зіставлені з правильним `cityId` через `requestMap`,
`estimationMethod` коректний); пакет, що ще не завершився — коректно НЕ оброблюється, не
позначається завершеним передчасно; **дедуплікація МІЖ синхронним і batch-шляхами
підтверджена** — сайт, уже знайдений раніше (синхронним шляхом чи попереднім пакетом), не
створюється вдруге, коли той самий URL приходить через batch-результат.

Разом **21 нова перевірка**, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку —
0 помилок у змінених файлах (2 залишкові — той самий, вже неодноразово підтверджений
артефакт спрощеної заглушки типів).

## ⚠️ Чесно — не перевірено / відомі обмеження

- **Реальний виклик xAI Batch API з живим ключем не виконувався** (немає мережі в цій
  пісочниці) — структура ендпоінтів звірена лише з офіційною документацією
  (docs.x.ai/developers/advanced-api-usage/batch-api), не живим викликом. Перед продакшеном
  варто перевірити один реальний прохід (той самий принцип, що вже застосований для
  webcam.guru.ua/Windy/NYC TMC свого часу).
- **Точний перелік можливих значень `status`** (`pending`/`processing`/`completed`/`failed`)
  для xAI Batch API конкретно **не підтверджений** — виведений за аналогією з іншими batch API
  (OpenAI/Mistral/Kimi показують схожі, але не ідентичні набори статусів). Код у
  `processPendingBatches()` трактує будь-що, крім `completed`, як «ще не готово» — це має
  працювати навіть якщо точна назва проміжного статусу відрізняється, але варто звірити на
  практиці.
- **Пагінація результатів** (`GET /batches/{id}/requests` з `after`/`has_more`) — структура
  параметрів пагінації виведена з загального патерну (схожого на інші list-ендпоінти xAI), не
  підтверджена для ЦЬОГО конкретного ендпоінту офіційною документацією напряму — можливо,
  реальні назви параметрів відрізняються (наприклад, `pagination_token`, як у Python SDK, а не
  `after`, як у REST-прикладі для ІНШОГО ендпоінту).
- Реальний розмір знижки для конкретних моделей (`grok-4`) — не перевірявся, документація
  вказує «варіюється залежно від моделі, 20-50%».

## Оновлення: розширення на групову калібровку камер (за прямим запитом користувача)

Користувач, ознайомившись із фундаментальною несумісністю Batch API (типово до 24 годин) з
інтерактивним автокалібруванням, свідомо обрав компроміс: **додатковий, окремий шлях** для
пакетної калібровки 50 камер через xAI Batch API — не заміна синхронної
`autoCalibrateBatch()` (та лишається без змін, кнопка «🤖 Автокалибровка (50 камер)», результат
за секунди), а альтернатива для тих, хто свідомо готовий почекати довше заради знижки 20-50%.

### Нове — перевірка стану пакетів при відкритті сторінок

За прямим запитом користувача: при завантаженні `/admin/cameras` (і, за тим самим принципом,
`/admin/aggregator-sites`) сторінка автоматично перевіряє стан УСІХ ще не оброблених пакетів
(і калібрування камер, і пошуку сайтів-агрегаторів) і оновлює таблицю, ТІЛЬКИ якщо щось
реально щойно завершилось — не зайвий перезапит БД, якщо всі пакети й далі просто в очікуванні.

### Що реалізовано

- `GrokCameraAssistService.submitAzimuthFovBatch()`/`getAzimuthFovBatchResults()` —
  той самий принцип, що вже є для сайтів-агрегаторів, але для vision-запитів (текст+
  зображення). **⚠️ Найбільш непідтверджена частина**: точний формат мультимодального
  (зображення) запиту ВСЕРЕДИНІ Batch API не підтверджений офіційною документацією напряму —
  використана та сама структура content-частин, що вже перевірена для звичайного
  `/v1/chat/completions` виклику, обгорнута в те саме поле `"responses"`, що для текстового
  batch-запиту сайтів-агрегаторів.
- `CamerasService.submitCalibrationBatch()` — той самий вибір камер (ESTIMATED, ніколи не
  пробувані спершу), що синхронний шлях, але позначає `lastAutoCalibrationAttemptAt`
  ОДРАЗУ ПРИ ПОДАЧІ (не при отриманні результату) — інакше ті самі камери потрапили б у ЩЕ
  ОДИН пакет до завершення першого.
- `CamerasService.processPendingCalibrationBatches()` — та сама логіка застосування (100%
  впевненість + усі три значення → `VERIFIED`, координати оновлені, `syncCameraPolygon()`),
  що синхронний шлях — обидва шляхи довіряють AI однаково обережно.
- Кнопка «🕐 Пакетная калибровка (дешевле)» поруч із існуючою синхронною.
- Окремий hourly cron (`camera-calibration-process-pending-batches-hourly`).

### Реально прогнані тести (18 нових)

`GrokCameraAssistService` (9): batch-запит коректно містить і текстову, і `image_url` частину;
камера без доступного зображення (HLS) коректно відфільтрована з пакета; пакет з нульовою
кількістю придатних камер не створюється взагалі; результати коректно розкладені по
`batch_request_id`, включно з випадком низької впевненості (усі значення `null`, не крашиться).

`CamerasService` (9): **позначення `lastAutoCalibrationAttemptAt` ОДРАЗУ при поданні пакета
підтверджено** (не чекаючи результату); повний цикл обробки завершеного пакета — камера зі
100% впевненістю отримує `VERIFIED` + оновлені координати, камера з 60% (нижче порогу)
лишається недоторканою.

Плюс `tsc --noEmit` по всьому графу застосунку — чисто.

### ⚠️ Ще раз чесно

Найбільш непевна частина цієї реалізації — мультимодальний (з зображенням) запит усередині
Batch API. Текстові batch-запити (сайти-агрегатори) підтверджені офіційними прикладами
документації; для запитів із зображенням такого підтвердженого прикладу знайти не вдалось —
використана обґрунтована, але не перевірена жодним прямим прикладом структура. Це перший
пункт для перевірки живим викликом перед активним використанням цієї функції в продакшені.

## Оновлення: реальна помилка на живому сервері — покращена діагностика

Користувач реально натиснув «Пакетная калибровка» — фронтенд показав узагальнене «Не удалось
создать batch (нет ключа API, нет камер с доступным кадром, или ошибка запроса к xAI)», без
конкретної причини з трьох. Той самий клас проблеми, що вже виправлявся для NycTmcAdapter.

### Виправлення

`submitAzimuthFovBatch()`/`submitAggregatorSearchBatch()` тепер повертають дискримінований
union (`{xaiBatchId, requestMap} | {error: string}`) замість голого `null` — кожна з причин
(відсутній ключ, немає камер з доступним кадром, неочікувана форма відповіді xAI, реальне
тіло помилки від xAI) повертає СВІЙ окремий, конкретний текст — і в лог сервера, і на
фронтенд.

### Реально прогнані тести (4 нові, кожен — окремий реалістичний сценарій)

Відсутній ключ API → конкретна згадка `XAI_API_KEY`; жодної камери з доступним кадром (усі
HLS) → конкретна згадка HLS/headless-браузера; **реалістичний сценарій «Batch API не
увімкнено для цього тарифу акаунту» (403 з тілом помилки від xAI)** → реальне тіло помилки
xAI тепер видно, не узагальнене повідомлення; неочікувана форма відповіді (200, але без полів
`id`/`batch_id`) → показує сам отриманий JSON для діагностики.

**Практична порада користувачу**: перевірений сценарій «Batch API is not enabled for this
account tier» — цілком реалістична причина для нового акаунту/ключа xAI, які функцію Batch API
могли ще не активувати за замовчуванням. Наступний реальний виклик тепер покаже це прямо в
UI, не приховано за узагальненим повідомленням.

## Оновлення: два реальних інциденти зі скріншотів — знайдено й виправлено

### 1. Реальний 404 — відсутній admin-ендпоінт

`AggregatorDiscoveryController` мав `POST /internal/aggregator-discovery/process-pending-batches`
(cron-guarded), але фронтенд (обидві сторінки — камери й сайти-агрегатори — перевірка при
відкритті) викликає `POST /admin/aggregator-sites/process-pending-batches` — admin-guarded
шлях, якого просто не існувало. Додано.

### 2. Найважливіший знайдений інцидент — batch реально створювався в xAI, але "No requests in batch"

Скріншот консолі xAI показав: пакет `camera-calibration-...` реально існує, але
**"No requests in batch"** — запити НЕ додались, хоча фронтенд бачив "успіх". Причина:
попередній код робив `POST /batches/{id}/requests` і НЕ перевіряв, що запити реально
прикріпились — axios не кидав виняток (сервер відповідав 2xx), тому будь-яка невідповідність
формату запиту, яку xAI мовчки ігнорував замість явної помилки, проходила непоміченою.

**Виправлення**: після подачі запитів тепер явно викликається `getBatchStatus()` і
перевіряється, що `totalCount` дорівнює кількості реально відправлених запитів. Якщо ні —
це трактується як помилка (з деталями: скільки очікувалось, скільки xAI повідомляє, сама
відповідь на додавання) — і в `AggregatorDiscoveryService`, і в `CamerasService` (обидва
місця, той самий клас проблеми).

### Реально прогнані тести (4 нові)

**Точна симуляція реального інциденту зі скріншота** — batch створюється, додавання запитів
повертає 200 без винятку, але статус після показує 0 замість очікуваної кількості —
підтверджено: тепер це коректно ловиться як помилка з чітким поясненням, а не мовчки
повідомляється як успіх. Окремо підтверджено, що ГЕНУЇННО успішний випадок (кількість
збігається) і далі коректно повертає успіх — фікс не створює хибних спрацювань.

### Ключовий висновок для подальшої роботи

Той факт, що batch реально СТВОРЮЄТЬСЯ (підтверджено консоллю xAI), але запити до нього НЕ
додаються — сильний сигнал, що структура тіла запиту до `POST /batches/{id}/requests` (поле
`batch_requests`, вкладена структура `batch_request.responses`) відрізняється від того, що
реально очікує xAI. Це перший конкретний пункт для перевірки: спробувати альтернативні
формати (наприклад, `requests` замість `batch_requests`, чи інша назва вкладеного поля) при
наступній спробі, звіряючись із повідомленням про помилку, яке тепер видно завдяки цьому
фіксу.

## Оновлення: точна причина знайдена й виправлена завдяки покращеній діагностиці

Попередній фікс (перевірка кількості запитів після подачі) спрацював саме так, як задумано —
замість мовчазного "успіху" фронтенд показав ТОЧНУ помилку від xAI:

> Failed to deserialize the JSON body into the target type:
> batch_requests[0].batch_request.responses.input: data did not match any variant of
> untagged enum ModelInput at line 1 column 3638

### Причина — підтверджена документацією OpenAI/xAI Responses API

`/v1/responses` (яким є `batch_request.responses`) використовує ІНШІ назви частин
мультимодального контенту, ніж `/v1/chat/completions`:
- `/v1/chat/completions` (синхронний `suggestAzimuthFov()` — **лишається без змін, він
  коректний**): `{type: 'text', text: ...}` + `{type: 'image_url', image_url: {url: ...}}`
  (вкладений об'єкт).
- `/v1/responses` (Batch API для калібрування камер): **потрібно** `{type: 'input_text',
  text: ...}` + `{type: 'input_image', image_url: ...}` — і `image_url` тут **пряма
  стрічка**, не вкладений об'єкт `{url: ...}`.

Підтверджено офіційною документацією OpenAI Responses API (яку xAI явно позиціонує як
сумісну — "Responses API (NEW!): xAI's modern agentic tools API").

### Виправлення

Змінено ТІЛЬКИ вміст `submitAzimuthFovBatch()` (текстовий `submitAggregatorSearchBatch()` не

Підтверджено: текстова частина тепер має `type: 'input_text'` (не `'text'`); зображення —
`type: 'input_image'` з `image_url` як прямою стрічкою (не вкладеним об'єктом,
**точно відтворює й виправляє знайдену помилку**); текст промпту й далі коректно присутній.

### Практичний висновок

## Оновлення: race condition у власній перевірці — знайдено й виправлено

Формат мультимодального запиту (попереднє оновлення) справді був виправлений правильно —

Перевірка кількості запитів (`getBatchStatus()`) викликалась ОДРАЗУ після

як "0 запросов" одразу після подачі, за хвилину показував 22/50, а ще за хвилину — 50/50.
Перевірка була занадто нетерплячою і хибно визнала успішну подачу провалом.

пакетної калібровки підхопить їх знову, коректно. Єдиний практичний наслідок — витрачені
даремно AI-виклики за два "осиротілі" пакети (не критично, невелика витрата).

### Виправлення

Новий `verifyBatchRequestCountWithRetries()` — замість одноразової миттєвої перевірки, кілька
спроб із паузами (1с, 2с, 3с — сукупно до ~6с) перш ніж дійсно визнати провал.

### Реально прогнані тести (4 нові)

**Точна симуляція реального сценарію зі скріншотів** (0 → 22/50 → 50/50 за кілька спроб
опитування) — підтверджено: тепер коректно розпізнається як УСПІХ, не хибний провал; реально
підтверджено виконання кількох спроб опитування з паузами (не миттєва єдина перевірка).
Окремо підтверджено: СПРАВЖНІЙ, стійкий провал (кількість ніколи не досягає очікуваної)
і далі коректно ловиться як помилка — фікс не приховує реальні проблеми, лише усуває
хибні спрацювання через передчасну перевірку.

## Оновлення: реальна причина, чому VERIFIED так і не з'явився — знайдено й виправлено

Скріншот консолі xAI показав **3 пакети з прогресом 50/50** (реально завершені), і Network
tab підтвердив: `process-pending-calibration-batches` реально викликається при відкритті
сторінки (статус 201). Але жодна камера не оновилась.

### Причина

Код чекав РІВНО на рядок `status === 'completed'`, щоб вважати пакет готовим до обробки. Але
точне слово, яке xAI повертає в полі `status` для дійсно завершеного пакета, **ніколи не було
підтверджено живим викликом** — можливо, це "created" (той самий рядок, що й одразу після
створення) або якесь інше слово, яке НЕ дорівнює буквально `"completed"`. Якщо так — код
назавжди трактував завершений пакет як "ще не готовий", попри те, що `completed_count`
фактично дорівнював `request_count` (як 50/50 на екрані).

Той самий клас проблеми виявлено і на рівні ОКРЕМОГО запиту всередині пачки (`item.status
!== 'completed'` при парсингу результатів).

### Виправлення

Замінено перевірку за точним словом статусу на перевірку **за кількістю** —
`completedCount === totalCount && totalCount > 0` — що не залежить від невідомого словника
статусів xAI. На рівні окремого запиту — довіра до **наявності самого тексту відповіді**,
а не до назви статусу цього запиту. Додано діагностичне логування сирої відповіді
`getBatchStatus()`, якщо кількість несподівано виявляється нульовою — щоб наступного разу
було видно РЕАЛЬНІ назви полів у логах сервера, а не гадати про них знову.

### Реально прогнані тести (6 нових)

Точна симуляція реального сценарію (`status: 'created'` при `completed_count === request_count
=== 50`) — підтверджено: тепер коректно визнається завершеним; окремо підтверджено повний
цикл `processPendingCalibrationBatches()` — камера дійсно отримує `VERIFIED` і нові координати
попри те, що слово статусу не дорівнювало буквально "completed"; результат окремого запиту
парситься за наявністю тексту відповіді, не за назвою статусу; запит, що дійсно ще не має
відповіді, і далі коректно пропускається (не хибно оброблюється як готовий).

## Оновлення: ТОЧНА реальна структура API отримана з логів сервера — виправлено остаточно

Користувач надав реальні логи з `getBatchStatus()` для завершеного batch (`batch_eafccc38...`,
дійсно 50/50 у консолі xAI). Реальна відповідь xAI:

```json

  "create_api_key_id": "...", "cancel_time": null, "cancel_by_xai_message": null,
```

### Ключове відкриття

**Жодного плоского поля `status` немає взагалі** — усі попередні здогадки

`getBatchStatus()` тепер повертає `{ totalCount: state.num_requests, completedCount:

завершеним.

підтверджена реальним викликом, не здогадкою.

## Оновлення: КРИТИЧНИЙ фікс — job "губився" назавжди при провалі парсингу

Реальний інцидент: `getAzimuthFovBatchResults` жодного разу не з'явився в логах на повторний
запит користувача — тому що job уже був позначений `completed` у БД при попередньому проході

### Причина

Код позначав job як `completed` ОДРАЗУ після визначення, що batch завершився на боці xAI
(`pendingCount === 0`) — **незалежно від того, чи вдалось витягти хоч один результат**. Якщо
парсинг результатів ламався (структура відповіді не та) — job назавжди "губився": позначений
завершеним, хоча жодна камера так і не отримала результат, і жодна подальша спроба вже не
могла його підхопити, навіть ПІСЛЯ виправлення парсингу.

### Виправлення

Тепер: якщо batch дійсно завершений, але `resultsByRequestId` виявився ПОРОЖНІМ (0 ключів)
попри непорожній `requestMap` — це трактується як сигнал зламаного парсингу (не "AI не був
упевнений для ВСІХ камер одразу"), і job лишається в стані `processing` (НЕ `completed`) —
щоб наступний прохід спробував ще раз, коли парсинг буде виправлено. Той самий фікс
застосовано і до `AggregatorDiscoveryService.processPendingBatches()`.

### Реально прогнані тести (5 нових) — найважливіший тест цього документа

**Точна симуляція реального інциденту**: batch готовий, `getAzimuthFovBatchResults()`
повертає порожній об'єкт — підтверджено: job коректно лишається `processing` (НЕ
`completed`), камера не зачеплена (без втрати даних). **Критичний тест**: та сама job
СИМУЛЬОВАНА вдруге — цього разу з "виправленим" парсингом, що реально повертає результат —
підтверджено: **job і далі доступний для повторної обробки** (не втрачений назавжди), камера
успішно отримує `VERIFIED`.

Конкретний batch із попереднього кроку (`batch_eafccc38-01b3-4d2d-bbb5-63646403e833`) уже
позначений `completed` у БД користувача ДО цього фіксу — новий код його автоматично не
підхопить. Потрібно скинути статус вручну:

Або ширше — скинути ВСІ `completed` job'и типу `camera-calibration` (безпечно: повторна

```sql
UPDATE "GrokBatchJob" SET status = 'processing' WHERE "jobType" = 'camera-calibration' AND status = 'completed';
```

## Оновлення: точна причина знайдена — неправильний ендпоінт для результатів

Користувач надав реальний лог `getAzimuthFovBatchResults` — і завдяки попередньому фіксу
(job більше не "губиться") ми побачили СПРАВЖНЮ структуру:

```json
{
  "batch_request_metadata": [
    {"batch_request_id": "cam_0_...", "endpoint": "xai_api.Chat/GetCompletion", "model": "grok-4", "state": "succeeded", "create_time": "...", "finish_time": "..."},
    ...
  ]
}
```

### Ключове відкриття

`GET /batches/{id}/requests` (ендпоінт, який використовувався весь цей час) повертає **лише
метадані** про кожен запит (id, статус, час) — **жодного поля з фактичною відповіддю AI
взагалі немає**. Це не структурна проблема (не інші назви полів) — це просто ІНШИЙ, окремий
ендпоінт, призначений тільки для перегляду прогресу/статусу, не для отримання результатів.

Пошук документації підтвердив: Python SDK xAI має **окремий метод** саме для результатів —
`client.batch.list_batch_results(batch_id, limit, pagination_token)`, з окремими
`.succeeded`/`.failed` списками. За конвенцією найменування цього ж API — REST-еквівалент:
`GET /batches/{id}/results` (не `/requests`).

### Виправлення

Обидва методи (`getAzimuthFovBatchResults()`/`getBatchResults()`) тепер звертаються до
`/results`, з парсингом `{succeeded: [...], failed: [...], pagination_token}` — за прикладом
з документації Python SDK. Пагінація тепер через `pagination_token` (не `after`/`has_more`,
як помилково передбачалось раніше).

⚠️ **Ще не підтверджено живим викликом** — цей самий метод (реальний лог → фікс) застосовано
вже вдруге поспіль для цього API; діагностичне логування сирої відповіді залишено на місці,
про всяк випадок, якщо і ЦЕЙ ендпоінт/структура виявляться не зовсім точними.

### Реально прогнані тести (5 нових)

Підтверджено: викликається саме `/results`, не `/requests`; структура `succeeded`/`failed`
коректно парситься (успішний запит дає результат, неуспішний коректно ігнорується без
крашу); пагінація через `pagination_token` коректно передається в наступний запит і обидві
сторінки результатів комбінуються правильно.

## Оновлення: ДВІ окремі критичні проблеми знайдено й виправлено з повного реального лога

Користувач надав повний реальний лог з реальними даними камери (Lexington Ave, E 110 St).
Це дало остаточну ясність по ДВОХ окремих проблемах одночасно.

### Проблема 1 — точна структура відповіді (нарешті остаточно підтверджена)

```json
{
  "results": [
    {
      "batch_request_id": "cam_0_...",
      "batch_result": {
        "response": {
          "chat_get_completion": {
            "choices": [{"message": {"content": "{...JSON з азимутом/FOV/впевненістю...}"}}]
          }
        }
      }
    }
  ]
}
```

Топ-рівень ключ — **`results`** (не `succeeded`/`failed`, як передбачалось на попередньому
кроці). Структура самої відповіді — **Chat Completions формат**
(`choices[0].message.content`), НЕ Responses API формат (`output_text`), попри те, що запит
подавався через поле `"responses"`. Додано окремий, спеціальний екстрактор
`extractBatchResultText()` саме під цю структуру.

### Проблема 2 — критичний баг шкали впевненості (виявлений паралельно, незалежний від структури)

Реальна відповідь моделі: **`"confidence": 45`** — модель відповідає в шкалі 0-100
(відсоток), а не 0-1 (частка), як було запитано в промпті (нечітко сформульовано:
`"confidence": number` — без явної вказівки шкали). Попередній код:
`Math.max(0, Math.min(1, confidence))` — **сліпо обрізав БУДЬ-ЯКЕ значення ≥1 до рівно 1.0**.
Це означало б, що впевненість 45% помилково трактувалась би як 100% і калібрування
застосовувалось би автоматично з false-positive "повною впевненістю".

### Виправлення

1. Промпт уточнено явно: `"confidence": number (от 0 до 1, ДОЛЯ, не процент — например 0.45,
   а НЕ 45)`.
2. Захисна нормалізація в парсері: якщо сире значення > 1, спершу ділимо на 100 (трактуючи
   як відсоток), і ЛИШЕ ПОТІМ обрізаємо до [0,1] — так 45 коректно стає 0.45, а 100 коректно
   стає 1.0.

### Реально прогнані тести (8 нових) — з ТОЧНИМИ реальними даними користувача

Підтверджено: точна реальна структура (Lexington Ave, E 110 St, `confidence: 45`) тепер
коректно парситься; азимут/FOV/дальність коректно витягуються; **критично — впевненість 45
коректно нормалізується до 0.45, НЕ обрізається до 1.0**; підтверджено, що ЦЕЙ конкретний
результат коректно НЕ спрацював би автоматичне застосування (0.45 < 1). Окремо перевірено:
генуїнна впевненість 100 (0-100 шкала) коректно нормалізується до 1.0; генуїнна впевненість 1
(уже правильна 0-1 шкала) НЕ ділиться вдруге помилково.

### Практичний висновок

Цей баг зі шкалою впевненості міг би реально впливати на ЯКІСТЬ калібрування ще ДО того, як
взагалі вдалось виправити структуру парсингу — модель РЕГУЛЯРНО відповідає в шкалі 0-100
(судячи з прикладу), тому без цього фіксу практично КОЖЕН результат із будь-якою впевненістю
≥1% на 100-бальній шкалі помилково трактувався б як "100% впевненість AI" і одразу
застосовувався б до камери зі статусом VERIFIED — навіть якщо реальна впевненість була
низькою.
