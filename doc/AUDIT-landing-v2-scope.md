# AUDIT — реалізація `apps/landing` відносно `doc/TZ-apps-landing-v2-audit.md`

За прямим запитом користувача реалізовано лендинг у `apps/landing` (окремий Next.js-проєкт,
той самий патерн деплою, що вже перевірений для `apps/admin`/`apps/btw`/`apps/api` — окремий
Vercel-проєкт із власним Root Directory). Нижче — чесний звіт, що саме з рекомендацій
v2-аудиту застосовано, а що свідомо відкладено, і чому.

## Застосовано повністю (дешево, реальна користь без інфраструктурних витрат)

- **Security-заголовки** — CSP (м'який, `unsafe-inline` для скриптів/стилів — суворіший
  зламав би Next.js-гідратацію без nonce-інфраструктури, якої немає сенсу городити для
  статичного лендингу), X-Frame-Options, X-Content-Type-Options, Referrer-Policy,
  Permissions-Policy — усе через `next.config.js` `headers()`.
- **SEO** — `robots.ts`/`sitemap.ts` (динамічні, App Router-конвенція, читають реальний
  домен з `NEXT_PUBLIC_SITE_URL`, не захардкоджена заглушка), canonical URL, повні
  OpenGraph/Twitter Card метадані, JSON-LD (Organization/WebSite).
- **Accessibility** — `TypeScript strict` (уже було в базовому `tsconfig.json`, той самий,
  що в `apps/btw`), skip-link для клавіатурної навігації, семантична розмітка (`<ol>` для
  послідовних кроків, нативний `<details>/<summary>` для FAQ — доступність з коробки, без
  жодного JS), `prefers-reduced-motion` враховано в `globals.css`, `alt`/`role="presentation"`
  на декоративних ілюстраціях.
- **Browser Support** — Next.js 14 + Tailwind за замовчуванням покривають Chrome/Edge/
  Firefox/Safari останні версії без додаткових налаштувань.

## Свідомо НЕ застосовано (реальне обґрунтування, не недбалість)

- **Vitest/Playwright/Lighthouse CI, Husky/lint-staged, повний CI/CD-пайплайн** — жоден з
  інших застосунків цього проєкту (`apps/admin`, `apps/btw`, `apps/api`) не має тестового
  стеку чи CI/CD-контурів. Додавати їх лише для лендингу означало б підтримувати
  інфраструктуру, якої немає більше ніде в проєкті — реальна вартість (налаштування,
  підтримка, час на проходження пайплайну при кожному коміті) без відповідної користі на
  цьому MVP-етапі одноосібної розробки. Якщо/коли проєкт виросте до команди з кількома
  контриб'юторами — тоді це варто переглянути для ВСІХ застосунків одночасно, не вибірково
  для одного лендингу.
- **ADR, Conventional Commits, SemVer, Dependabot/Renovate** — процесні практики для команди,
  не для соло-розробки одним репозиторієм.
- **Cookie policy** — застосовується лише якщо/коли підключиться аналітика (Google Analytics/
  Plausible тощо) — на цьому етапі жодної аналітики немає взагалі, тому й політика поки
  нічого не регулювала б.
- **i18n roadmap** — сторінка поки що одномовна (російська, як і решта UI проєкту) — той
  самий вибір мови, що вже усталений у `apps/admin`/`apps/btw`.
- **Error page 404/500** — Next.js має розумні дефолтні сторінки з коробки; кастомізація —
  дешевий, але не критичний штрих, можна додати окремим невеликим кроком пізніше.

## Реалізовані ілюстрації

Використано готовий набір із `btw-illustrations.zip` (авторський вихідний проєкт збережено
повністю в `apps/landing/design-source/btw-illustrations/` для майбутнього редагування;
у `public/` — лише фінальні файли, що реально йдуть у веб): hero (десктоп+мобільна версія),
privacy (десктоп+мобільна версія), 4 core-іконки для секції «Як це працює» (open/point/
detect/warning — розфарбовані через CSS `mask-image`, а не `<img>`, оскільки `currentColor`
не працює через зовнішнє посилання на файл — реальний баг, знайдений і виправлений під час
імплементації), повний набір favicon (ico + PNG різних розмірів + Safari pinned tab), OG-
зображення.

## Мультиязичність (за прямим запитом користувача, за зразком ОРБІТА/apps/admin)

Реалізовано той самий патерн, що вже є в `apps/admin` (сам код там позначений коментарем "за
аналогією ATM-travel.org/ОРБІТА") — той самий набір 10 мов, той самий принцип
`Dictionary`-інтерфейсу, що TypeScript-компілятор змушує тримати ідентичний набір ключів у
всіх 10 файлах словника (реально перевірено — `tsc --noEmit` пройшов чисто по всіх 10, це не
голослівна обіцянка в коментарі).

**Дві свідомі відмінності від патерну `apps/admin`, за прямим запитом користувача:**
1. **Детекція мови** — з заголовка `x-vercel-ip-country` (країна за IP, який Vercel сам
   підставляє на кожен запит), а не з `Accept-Language` браузера, як в admin. Пріоритети:
   збережена cookie → країна з Vercel-заголовка → мова за замовчуванням (українська).
2. **Селектор** — кастомний вертикальний dropdown із прапорцями (кнопка + панель), а не
   нативний `<select>`, як в admin. Доступність відтворена вручну: `aria-haspopup`/
   `aria-expanded`, закриття по Escape і кліку поза межами, фокус повертається на кнопку.

**Оновлено — URL-based мультимовний SEO реалізовано повністю:** попереднє обмеження (мова
визначалась лише через cookie/заголовок на ОДНІЙ URL-адресі, без hreflang-альтернатив) —
усунено за прямим наступним запитом користувача. Тепер:

- **Справжні окремі маршрути** для кожної мови: `/uk`, `/en`, `/pl`, `/sk`, `/hu`, `/ro`,
  `/de`, `/fr`, `/es`, `/it` — через динамічний сегмент `app/[lang]/`, зі статичною
  попередньою генерацією всіх 10 (`generateStaticParams()`), не лише за першим живим
  запитом.
- **`middleware.ts`** — редиректить будь-який запит без мовного префікса (найчастіше просто
  `/`) на конкретний `/{lang}` ДО маршрутизації App Router, за тим самим пріоритетом, що й
  раніше (збережена cookie → країна з `x-vercel-ip-country` → мова за замовчуванням).
- **Повні hreflang-альтернативи** — кожна мовна сторінка через Next.js Metadata API
  (`alternates.languages`) оголошує посилання на всі інші 9 мовних версій одразу + `x-default`
  — пошуковий краулер бачить повний набір при кожному обході, не одну випадкову мову залежно
  від IP.
- **`sitemap.xml`** тепер містить усі 10 мовних URL, кожен із власним набором
  hreflang-альтернатив.
- **Перемикач мови** — тепер справжня навігація (`next/navigation`, заміна першого сегмента
  шляху), не мутація React-стану на тій самій адресі; cookie й далі зберігається — вирішує,
  куди редиректить НАСТУПНИЙ візит на голий `/`.
- Некоректний/непідтримуваний мовний код у шляху (напр. хтось вручну набрав `/zz`) коректно
  віддає справжній `404` (`notFound()`), не мовчазний рендер зі сміттєвим значенням.

## Аудит і виправлення (за прямим запитом користувача)

Проведено окрему перевірку вже реалізованого лендингу, знайдено й виправлено 4 реальні
недоліки:

1. **Title був однаковий для всіх 10 мов** — `description` уже коректно брав переклад з
   `dict.hero_subtitle`, а `title` (і в `<head>`, і в OpenGraph, і в Twitter Card) залишався
   захардкодженим "Beyond the Wall" незалежно від мови. Виправлено — зібраний з уже наявних
   ключів словника (`hero_title_line1`/`hero_title_line2`), без потреби додавати новий ключ у
   всі 10 файлів.
2. **Відсутній `dynamicParams = false`** — без цього Next.js за замовчуванням намагався б
   ДИНАМІЧНО відрендерити будь-яке значення `[lang]`, якого немає в `generateStaticParams`
   (напр. хтось вручну набрав `/zz`), і лише ПІСЛЯ спроби рендеру falling back на `notFound()`
   всередині layout — зайва витрата. Тепер Next.js одразу віддає 404 на рівні маршрутизації.
3. **`og:locale` у неправильному форматі** — специфікація Open Graph очікує код формату
   "мова_РЕГІОН" (напр. `en_US`, `de_DE`), а не голий ISO 639-1 код мови, який там був
   (`en`, `de`). Додано окрему мапу мова→og-локаль, HTML-атрибут `lang` (де якраз правильний
   голий код) не зачеплено.
4. **Акордеон FAQ не ховав маркер розкриття в старішому Safari** — Tailwind-утиліта
   `marker:content-none` ховає лише стандартний `::marker` (Chrome/Firefox); старіший Safari
   використовує окремий `::-webkit-details-marker`, для якого потрібне власне CSS-правило —
   без нього трикутник розкриття лишався б видимим саме в Safari, всупереч заявленій
   підтримці браузерів.

Реально протестовано (`tsc --noEmit` після кожного виправлення) — чисто.

### Оновлення — реальна помилка збірки (`next build`), знайдена користувачем

5. **Space Grotesk не має кириличної підмножини символів взагалі** — офіційний список
   підмножин шрифту: лише `latin`/`latin-ext`/`vietnamese`. Українська (одна з 10 мов сайту)
   — кирилична, тому `next build` коректно впав з помилкою `Unknown subset "cyrillic"`.
   Просте прибирання `cyrillic` з конфігу зробило б білд успішним, але МОВЧКИ зламало б
   заголовки саме для української версії (кириличні символи впали б на інший, невибраний
   шрифт — типовий "тихий" клас багів, який build-помилка випадково відловила раніше, ніж
   він проявився б візуально). Замінено на **Unbounded** — той самий геометричний, "дисплейний"
   характер (і ті самі ваги 500/700), з повною кириличною підтримкою.
6. **JetBrains Mono — та сама помилка, без явного збою збірки** — конфіг запитував лише
   `latin`-підмножину, хоча "телеметрійні" лейбли (напр. `'// приватність'` в uk-словнику)
   реально містять кирилицю. Build не падав (оскільки `latin` — валідна підмножина для цього
   шрифту), але ті самі кириличні лейбли мовчки рендерились би не тим шрифтом. JetBrains Mono
   РЕАЛЬНО підтримує cyrillic — досить було додати підмножину в запит, не міняти шрифт.

Реально протестовано (`tsc --noEmit`) — чисто.

### Оновлення — `MIDDLEWARE_INVOCATION_FAILED` на проді, знайдено користувачем

7. **`ReferenceError: __dirname is not defined` у middleware на Vercel** — задокументований
   баг самого Next.js (vercel/next.js#53968, #58140, той самий клас помилки в next-intl і
   `@supabase/ssr`): сам ІМПОРТ із `'next/server'` (навіть лише типів
   `NextRequest`/`NextResponse`) тягне за собою внутрішній `ua-parser-js`, який звертається
   до `__dirname` при завантаженні модуля — і падає саме на Edge Runtime (локально не
   відтворюється, тому й не було спіймано раніше, попри `tsc --noEmit`, який лише перевіряє
   типи, не поведінку на реальному рантаймі). Виправлено — `middleware.ts` переписано без
   жодного імпорту з `'next/server'`, лише стандартні Web API (`Request`/`Response`/`URL`,
   ручний парсинг cookie з заголовка) — усі нативно підтримувані Edge Runtime без внутрішніх
   залежностей Next.js.

Реально протестовано (`tsc --noEmit`, і окремо перевірено — у всьому проєкті це був
ЄДИНИЙ імпорт з `'next/server'`, більше ніде такого ризику немає).

## Що потрібно налаштувати перед реальним деплоєм


- `NEXT_PUBLIC_SITE_URL` — реальний домен деплою (для OG/canonical/sitemap).
- `NEXT_PUBLIC_TELEGRAM_MINIAPP_URL` — реальний deep-лінк мініаппа (`https://t.me/<bot>/<app_short_name>`,
  short_name — через BotFather `/newapp`).
- Новий Vercel-проєкт із Root Directory = `apps/landing` (той самий процес, що вже
  відпрацьований для `apps/admin`/`apps/btw` — включно з тим, що Framework Preset має
  розпізнатись як Next.js автоматично; якщо ні — див. `doc/AUDIT-vercel-hobby.md`, той самий
  клас проблеми, що вже траплявся раніше).
- Реальні скріншоти інтерфейсу `apps/btw` для секції «Демо» (`doc/TZ-btw-landing.md`, §2.5)
  — не додані в цьому кроці (потрібні знімки РЕАЛЬНОГО працюючого інтерфейсу, не ілюстрації).
