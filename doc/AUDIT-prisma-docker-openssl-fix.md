# Аудит: "Could not parse schema engine response" (Prisma + Alpine + OpenSSL)

## Диагноз

Пользователь прислал реальный лог падения контейнера `api`:

```
prisma:warn Prisma failed to detect the libssl/openssl version to use, and may not work as
expected. Defaulting to "openssl-1.1.x".
...
Error: Could not parse schema engine response: SyntaxError: Unexpected token 'E', "Error load"...
is not valid JSON
```

Это не наш баг в коде проекта, а классическая, хорошо задокументированная в issue-трекере Prisma
несовместимость с `node:*-alpine` образами: Alpine использует musl libc (не glibc), и Prisma
исторически хуже поддерживает musl-таргеты движков, особенно на новых версиях Alpine с
OpenSSL 3.x. Цепочка событий:

1. Prisma не может надёжно определить установленную версию OpenSSL внутри Alpine-контейнера →
   гадает ("Defaulting to openssl-1.1.x").
2. Скачанный/сгенерированный под это предположение бинарник schema-engine не может
   стартовать (реально нужных .so-библиотек либо нет, либо не та версия).
3. Сам движок при попытке запуска печатает **не JSON**, а обычный текст ошибки загрузки
   библиотеки (что-то вида `Error loading shared library libssl.so.1.1...`).
4. Node-обвязка Prisma ожидает JSON на этом канале и падает на парсинге с этим самым
   `SyntaxError: Unexpected token 'E', "Error load"...`.

Причина, по которой это не было поймано раньше в этой сессии: вся работа в песочнице шла через
`ts-node`+ручные офлайн-стабы (нет доступа к npm registry/Docker), без реальной сборки образа —
эта категория багов принципиально не воспроизводима таким способом, только реальным
`docker compose up --build`, который смог прогнать только сам пользователь.

## Исправление

- **`apps/api/Dockerfile.dev`** — база образа `node:20-alpine` → `node:20-slim` (Debian, glibc).
  Debian — комбинация, которую сама Prisma документирует как надёжную (в отличие от
  musl-таргетов, поддержка которых второго сорта). Дополнительно явно ставится `openssl` +
  `ca-certificates` (`apt-get install`) — Debian slim-образы не всегда несут их по умолчанию,
  а `ca-certificates` нужен для исходящих HTTPS-вызовов самого приложения (геокодинг,
  Open-Meteo, xAI, Telegram) на "голом" slim-образе.
- **`prisma/schema.prisma`** — `generator client` теперь с явным
  `binaryTargets = ["native", "debian-openssl-3.0.x"]` вместо автоопределения. `native` — для
  локальной разработки вне контейнера (хост-машина разработчика), `debian-openssl-3.0.x` — под
  контейнер `api`. Явное перечисление — чтобы Prisma не гадала о платформе/OpenSSL вообще,
  устраняя первопричину, а не просто меняя окружение, в котором гадание случайно работает.
- **`docker-compose.yml`** — команда запуска `api` теперь явно выполняет `npx prisma generate`
  перед `db push --skip-generate` (раньше generate не запускался при старте контейнера вообще,
  только один раз при сборке образа в Dockerfile). Это самовосстанавливающееся поведение: именованный
  volume `api_node_modules` переживает пересборку образа (`--build`), так что при первом
  создании volume ДО этого исправления в нём мог остаться Prisma-клиент, сгенерированный под
  старый Alpine-образ — теперь клиент перегенерируется при каждом старте контейнера, а не
  полагается на то, что кто-то вручную снесёт volume.
- **`doc/README.md`** — новый подраздел "Известная проблема" в разделе "Локальная разработка" с
  точным текстом ошибки (чтобы находилось поиском) и инструкцией `docker compose down -v`
  (обязательно с `-v` — без этого старый volume всё равно переживёт пересборку и проблема
  вернётся, даже после всех остальных исправлений выше).

## Не проверено (ограничение аудита)

Реальная пересборка (`docker compose up --build`) и повторный прогон в среде пользователя — в
этой песочнице нет Docker/сети для воспроизведения. Исправление основано на:
- точном совпадении симптома с задокументированным классом проблем Prisma (не догадка "наугад
  попробовать что-то с Docker");
- официально рекомендуемой Prisma комбинации (Debian + явные `binaryTargets`) как способе её
  устранения, а не обхода.

Если после `docker compose down -v && docker compose up --build` ошибка всё ещё воспроизводится
— следующий шаг диагностики: `docker compose exec api npx prisma generate --schema prisma/schema.prisma`
вручную внутри контейнера, чтобы увидеть, стартует ли схема-движок вообще с подробным выводом
(без обёртки Nest/npm-скриптов, глотающей стектрейс).
