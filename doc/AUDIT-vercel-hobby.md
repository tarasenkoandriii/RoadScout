# Аудит: деплой на Vercel Hobby

Проверено по официальной документации Vercel (актуально на июль 2026). Вывод: **деплоится**, но с несколькими обязательными оговорками ниже — без них парсер либо не запустится, либо будет падать по таймауту/коннектам к БД.

---

## 1. NestJS деплоится нативно, без обвязки

Vercel поддерживает NestJS zero-config: приложение оборачивается в один Vercel Function на Fluid Compute автоматически, если entrypoint называется одним из ожидаемых имён — `src/main.ts` (наш случай) подходит без правок. Никакой самодельный `api/index.ts`-wrapper с ручным `builds` в `vercel.json` не нужен — это устаревший паттерн из старых гайдов.

Значит `apps/api` деплоится как есть: `vercel.json` в проекте нужен только чтобы явно задать `maxDuration` (см. п.2) — уже добавлен.

## 2. Максимальная длительность функции — 300 секунд, но её нужно задать явно

Текущий официальный лимит Hobby — **300 секунд (5 минут)** на функцию (это не старые 10с из более ранних версий документации Vercel, которые до сих пор гуляют по гайдам в интернете). Этого с запасом хватает на один проход парсера по одному источнику.

**⚠️ ИСПРАВЛЕНО (реальная ошибка, найденная на живом деплое пользователя) —**
раньше здесь было написано, что `maxDuration` задаётся через `apps/api/vercel.json`
(`{"functions": {"src/main.ts": {"maxDuration": 300}}}`). Это оказалось НЕВЕРНО: реальный
деплой упал с ошибкой `The pattern "src/main.ts" defined in \`functions\` doesn't match any
Serverless Functions inside the \`api\` directory`. Причина — при zero-config деплое NestJS
Vercel оборачивает всё приложение в ОДНУ функцию, но реальный путь этой функции ПОСЛЕ сборки
не совпадает с исходным файлом `src/main.ts` (подтверждено официальной документацией Vercel:
"With Fluid compute enabled, set memory in the Functions section of your project dashboard,
not in vercel.json" — тот же принцип применим и к длительности для zero-config бэкендов).

**Правильный способ** — `apps/api/vercel.json` теперь пустой (только `$schema`), а
`maxDuration` задаётся через **Project Settings → Functions** в дашборде Vercel (поле Default
Function Duration/аналог) — 300 секунд, тот же лимит Hobby, что и раньше, просто через
правильный интерфейс.

**Что может не влезть в 300с:** `processItem()` в `scraper.service.ts` обрабатывает камеры последовательно (discover → geocode → Overpass-эвристика на каждую), без параллелизма. Если один каталог отдаёт много новых камер за один проход — суммарное время может приблизиться к лимиту. Пока в MVP это не проблема (ожидаемые объёмы небольшие), но при росте реестра стоит либо ограничить число обрабатываемых айтемов за один вызов (пагинация discover + несколько последовательных cron-хитов), либо распараллелить geocode/Overpass-запросы с `Promise.all` батчами.

## 3. Не использовать встроенный Vercel Cron — уже учтено

Собственный cron у Vercel на Hobby ограничен **одним запуском в сутки** и точностью «в течение часа» — для регулярного парсинга источников каждые 24ч этого достаточно по частоте, но не по гибкости (нельзя быстро прогнать вручную несколько раз для отладки без редеплоя, и нельзя позже перейти на более частые прогоны без Pro).

Мы это обходим осознанно: планирование идёт через **Supabase `pg_cron` + `pg_net`** (см. `sql/pg_cron-schedule.sql`), который дёргает наш собственный HTTP-эндпоинт `POST /internal/parser/run/:providerId`. Это не завязано на лимиты Vercel Cron вообще — просто обычный вызов обычного роута. Дополнительно оставлена ручная кнопка «Запустить сейчас» в админке (`POST /admin/parser/run/:providerId`) для отладки без ожидания расписания.

## 4. Prisma + Supabase: обязательно через пулер соединений

Каждый вызов serverless-функции может открыть новое соединение к Postgres. Без пулера под нагрузкой это быстро упрётся в лимит соединений Supabase. В `.env.example` уже разведено:

- `DATABASE_URL` — через Supabase PgBouncer, порт **6543**, с `?pgbouncer=true` — используется в рантайме;
- `DIRECT_URL` — порт **5432**, только для `prisma migrate deploy`.

Это уже отражено в `schema.prisma` (`directUrl = env("DIRECT_URL")`). Если задеплоить только с `DATABASE_URL` без пулера — сначала всё будет работать, но начнёт рваться под конкурентными запросами крона + админки.

## 5. Ограничение размера бандла — актуально, если позже понадобится Playwright

Стандартный лимит — **250 МБ** на функцию (до 5 ГБ в бете Large Functions на Fluid Compute). Наш текущий адаптер (`webcam-guru.adapter.ts`) — `axios` + `cheerio`, это лёгкий HTML-парсинг, укладывается в лимит без вопросов.

**Если один из источников окажется client-side rendered** (данные подгружаются JS, cheerio не увидит их в исходном HTML) и придётся подключать Playwright/Puppeteer с headless Chromium — бинарник браузера сам по себе весит больше стандартного лимита. В этом случае **не пытаться впихнуть headless-браузер в эту же Vercel-функцию** — вынести конкретно этот адаптер во внешний воркер (например, лёгкая VM на Fly.io/Railway или scheduled GitHub Actions job), который пишет результат напрямую в ту же Supabase Postgres, а публичный API и админка остаются на Vercel как есть.

## 6. Итог

| Проверка | Статус |

## Оновлення — за прямим запитом користувача: аудит нового модуля Beyond the Wall (BTW)

Перевірено окремо, оскільки BTW (`apps/btw`, `src/btw/*`) додавався пізніше й має принципово
іншу поведінку — частий поллінг (`/btw/scan` кожні ~2с при активному скануванні), на відміну
від разового парсингу камер.

### 1. `apps/btw` — новий Next.js-застосунок, деплой аналогічний `apps/admin`

Той самий підхід, що вже перевірений для `apps/admin` — Next.js на Vercel не потребує
власного `vercel.json` (на відміну від `apps/api`). **Обов'язково перед деплоєм**: окремий
Vercel-проєкт для `apps/btw`, і `NEST_API_URL` у змінних середовища має вказувати на РЕАЛЬНИЙ
URL задеплоєного API (`https://your-api.vercel.app`), а не `http://api:3000` (це працює лише
всередині `docker-compose.yml`).

### 2. 🔴 Знайдено й виправлено: rate-limit для У5 (vision-уточнення) не пережив би serverless

`BtwService.refineHeading()` мав `private readonly lastRefineAtByUser = new Map<...>()` —
той самий клас проблеми, що вже задокументований у п.36 README для кешу позицій, але тут
НАБАГАТО серйозніше: це не просто оптимізаційний кеш, а **захист від зайвих платних викликів
vision AI**. На serverless кожен виклик функції може потрапити на інший/холодний інстанс із
власною порожньою `Map` — rate-limit міг мовчки НЕ спрацьовувати, дозволяючи частіші виклики,
ніж заплановані "1 раз на 30с", і непередбачувано зростаючи витрати на AI.

**Виправлено**: перевірка тепер через нову таблицю `BtwRefineEvent` — той самий надійний
принцип, що вже застосований для антисталкінгу в `BtwLockEvent`. Реально протестовано
(2 перевірки): rate-limit коректно спрацьовує навіть коли виклик робиться через ЗОВСІМ НОВИЙ
екземпляр сервісу (симулює холодний/інший інстанс) — та сама БД, той самий результат.

### 2а. Кеш позицій (`AzimuthHeuristicService`) — той самий клас обмеження, вже задокументований

`this.cache`/новий `this.streetAzimuthCache` — in-process `Map`. На serverless це коректно
працює в межах одного "теплого" інстансу, але не розділяється між кількома одночасними
інстансами — той самий компроміс, що вже прийнятий і задокументований у README для
позиційного кешу (п.36). Для росту навантаження — Redis/Supabase-таблиця замість `Map`.

### 3. 🔴 Знайдено й виправлено: `getNearbyStreetAzimuths()` (У3) не мав кешування ВЗАГАЛІ

Реальна розбіжність між коментарем і кодом: у `btw.service.ts::scan()` коментар СТВЕРДЖУВАВ
"живий Overpass-запит (з кешем по сітці всередині AzimuthHeuristicService...)" — але сам
метод `getNearbyStreetAzimuths()` РЕАЛЬНО не звертався до жодного кешу, кожен виклик бив
Overpass наново. Оскільки `/btw/scan` викликається кожні ~2с при активному скануванні — це
означало повторний, повністю некешований запит до зовнішнього Overpass API на КОЖЕН тик.

**Чому це критично саме для BTW** (на відміну від RoadScout, де ця сама інфраструктура
використовується лише рідко, під час одноразового калібрування камери): Overpass Foundation
має власні правила добросовісного використання і може заблокувати IP за надмірну частоту
запитів — сталий поллінг кожні 2с від багатьох одночасних користувачів реально ризикує
заблокувати вихідний IP сервера в Overpass, ламаючи ОБИДВІ функції одночасно (і BTW, і
автокалібрування камер RoadScout, що використовує той самий сервіс).

**Виправлено**: додано реальний кеш (`streetAzimuthCache`, той самий gridKey-принцип, що вже
є для `guessForPoint()`) — сусідні скани тієї самої області тепер справді не б'ють Overpass
повторно. Реально протестовано: другий виклик для тієї самої області коректно обслуговується
з кешу (0 додаткових мережевих викликів), результат ідентичний.

**Залишковий ризик, не усунений повністю**: `OcclusionService.isPossiblyBlocked()` (LOS-
перевірка, Ф3) явно позначений у власному коментарі як `"NOTE: not cached across requests in
this MVP"` — і викликається аж 9 разів НА КОЖНОГО кандидата-камеру НА КОЖЕН скан (для 9 точок
сэмплювання coverage). За наявності кількох кандидатів у пачці це швидко перетворюється на
десятки некешованих Overpass-запитів на один тик сканування. Це вже наявне обмеження
(введене до цього кроку, не BTW-специфічне), але поллінг-патерн BTW навантажує його НАБАГАТО
інтенсивніше, ніж будь-яке інше використання цього сервісу в проєкті. **Рекомендація на
майбутнє** (не виправлено в цьому кроці — більший обсяг роботи): додати аналогічне кешування
по сітці для `isPossiblyBlocked()`, або (краще) знизити частоту реального виклику `/btw/scan`
на клієнті нижче поточних 2с при повторюваних майже ідентичних позиціях/азимутах.

### 4. ⚠️ Розмір тіла запиту — `/btw/refine` надсилає base64-зображення в JSON

README уже документує аналогічну проблему для іншої функції: **"Лимит файла — 4 МБ (с
запасом под потолок тела запроса на Vercel Hobby, ~4.5 МБ)"** (квитанції home-verification).
`/btw/refine` надсилає `phoneImageDataUrl` — кадр із `canvas.toDataURL('image/jpeg', 0.7)` —
ТОЧНО ТОЙ САМИЙ клас ризику, і в цьому кроці НЕ перевірявся явно проти ліміту. За типового
дозволу камери телефону (напр. 1920×1080+) навіть стиснутий JPEG у форматі base64 (+33%
накладних витрат кодування) може наблизитись до чи перевищити ліміт Vercel Hobby — це
призвело б до помилки запиту (413/аналог), яку користувач побачить як загадкове "Ошибка
уточнения" (загальний catch-блок на клієнті, без розрізнення причини).

**Не виправлено в цьому кроці** (не було явно узгоджено з користувачем) — рекомендація:
явно обмежити роздільну здатність кадру перед `canvas.toDataURL()` (напр. `canvas.width =
Math.min(videoRef.current.videoWidth, 1280)`, пропорційно), а не покладатись лише на якість
JPEG-стиснення.

### 5. ✅ Позитивна знахідка: HTTPS від Vercel вирішує раніше названу прогалину М0-спайку

`DeviceOrientationEvent`/`DeviceMotionEvent`/`getUserMedia` вимагають HTTPS-контексту — саме
це раніше було названо як передумова категорії А ("потребує ваших дій поза кодом") для
реального польового тесту. Vercel видає HTTPS-домен безкоштовно й автоматично для будь-якого
деплою — ця конкретна передумова повністю вирішується самим фактом деплою на Vercel, без
додаткових дій (ngrok/Cloudflare Tunnel більше не потрібні для цієї конкретної мети).

### 6. Нові Prisma-моделі BTW потребують міграції — той самий чекліст, що й раніше

`NoTargetZone`, `BtwLockEvent`, `BtwViewpoint`, `BtwReport`, `BtwDevLocationOverride`,
`BtwTelemetryEvent`, `BtwRefineEvent` — усі потребують `prisma generate` + `prisma db push`/
`migrate deploy` (через `DIRECT_URL`, порт 5432, не пулер) перед першим використанням у
задеплоєному середовищі — та сама вимога, що вже сформульована в п.4 вище для
`GrokBatchJob` та інших попередніх моделей.

## Оновлення — за прямим запитом користувача: усунено залишковий ризик LOS-перевірки (Ф3)

`OcclusionService.isPossiblyBlocked()` раніше явно був позначений власним коментарем як
`"NOTE: not cached across requests in this MVP"` — і викликався 9 разів НА КОЖНОГО кандидата-
камеру НА КОЖЕН тик сканування BTW (кожні ~2с), повністю некешовано.

### Виправлення

Додано `buildingCache` — той самий гридключ-принцип (~100м сітка), що вже перевірений в
`AzimuthHeuristicService`, з ключовою оптимізацією: радіус округлюється ВГОРУ до найближчих
100м, тому набір будівель, отриманий на ширшому радіусі, безпечно перевикористовується для
запитів із меншим фактичним радіусом (геометрично коректна надмножина). Оскільки всі 9 точок
сэмплювання для ОДНОГО кандидата мають той самий `center` (саму камеру, не міняється між
точками) і практично однаковий округлений радіус (обмежений зверху 300м у `BtwService`) — усі
9 запитів тепер фактично діляться ОДНИМ кеш-записом.

### Реально прогнана перевірка (3 нові)

Підтверджено точним реальним сценарієм: 9 точок сэмплювання для одного кандидата тепер
призводять лише до 1 Overpass-запиту (було 9); геть інша камера (інше місто) коректно
отримує ОКРЕМИЙ кеш-запис, не плутається з першою; 5 послідовних тиків сканування (кожні
~2с, симуляція реального патерну активного сканування) для ТІЄЇ САМОЇ камери-кандидата
призводять лише до 1 запиту сумарно, не 5 і не 45.

Технічний борг, названий у попередньому аудиті, закрито.
