# Аудит: мультиязычность (10 языков, аналогично ОРБІТА)

## Что добавлено

**Backend не тронут** — вся фича целиком на фронтенде (`apps/admin`), серверная логика ограничена одним `app/layout.tsx` (серверный компонент), читающим `Accept-Language`/cookie.

- `lib/i18n/languages.ts` — список 10 языков (код, нативное название, флаг-эмодзи), `DEFAULT_LANGUAGE = 'uk'`.
- `lib/i18n/dictionary.types.ts` — единый TS-интерфейс `Dictionary` (~50 ключей: общие/поиск/статусы камер/погода/«Мой дом»/AuthGate).
- `lib/i18n/dictionaries/{uk,en,pl,sk,hu,ro,de,fr,es,it}.ts` — по одному словарю на язык, каждый `const dict: Dictionary = {...}`.
- `lib/i18n/detect.ts` — `parseAcceptLanguage()`/`detectLanguageFromAcceptHeader()`.
- `lib/i18n/index.ts` — реестр словарей + `interpolate()`.
- `components/I18nProvider.tsx` — React-контекст, `useI18n()` хук, cookie-персистентность выбора.
- `components/LanguageSelector.tsx` — `<select>` с флагами.
- `app/layout.tsx` — определяет язык на сервере (cookie → иначе `Accept-Language`), оборачивает всё дерево в `I18nProvider`.
- Переведены: `app/page.tsx`, `app/my-home/page.tsx`, `components/AuthGate.tsx` (публичные строки), `components/LogoutButton.tsx`.

## Реально прогнанные тесты

**Полнота словарей (самое важное для "полные словари для всех языков")**: реальный `tsc --noEmit --strict` над `dictionary.types.ts` + всеми 10 файлов `dictionaries/*.ts` вместе — **0 ошибок**. Поскольку каждый файл делает `const dict: Dictionary = {...}` (прямое присваивание объектного литерала типизированной переменной), TS проверяет одновременно и отсутствие недостающих ключей, и отсутствие лишних/опечатанных — это не ручная проверка, а гарантия компилятора. Если бы, скажем, в `it.ts` не хватало ключа `myHome_submitButton` или он назывался `myHome_submitBtn` — сборка бы упала именно на этом файле с конкретной строкой.

**`detectLanguageFromAcceptHeader()`/`parseAcceptLanguage()`** (ts-node, реальное выполнение, 6 сценариев):
1. Стандартный многоязычный заголовок (`uk-UA,uk;q=0.9,en-US;q=0.8,en;q=0.7`) — правильный порядок приоритета. **Пройден.**
2. Заголовок с явными `q`-весами (`de-DE,de;q=0.9,fr;q=0.8`) — выбирается язык с наивысшим приоритетом. **Пройден.**
3. Заголовок из ТОЛЬКО неподдерживаемых языков (`ja-JP`, `zh`) — корректный фоллбэк на `uk`. **Пройден.**
4. `null`/пустая строка — фоллбэк на `uk`, без падения. **Пройден.**
5. Смешанный список, где первый (наивысший приоритет) язык не поддержан, а более поздний — да (`ja,ja;q=0.9,pl;q=0.5`) — выбирается первый ПОДДЕРЖИВАЕМЫЙ по порядку, а не просто первый в списке. **Пройден.**
6. Регионные варианты и регистронезависимость для всех значимых языков (`sk-SK`, `HU-hu`, `ro-RO`, `es-419`, `it-IT`) — все 5 сверены поштучно. **Пройден.**

**`interpolate()`** (4 сценария): обычная подстановка, отсутствие параметров (строка возвращается как есть), отсутствующий в `params` ключ (плейсхолдер остаётся буквально, не превращается в пустоту — сознательное поведение, чтобы ошибка в вызывающем коде была заметна, а не тихо проглатывалась), повторное использование одного и того же ключа дважды в шаблоне. **Все 4 — пройдены.**

## Найдена (и НЕ являющаяся багом) путаница со стендом

При попытке протипчекать JSX-файлы (`page.tsx`, `my-home/page.tsx`, `layout.tsx`, `AuthGate.tsx`) через самодельную заглушку `@types/react` несколько раз подряд натыкался на ошибки вида `Cannot find namespace 'JSX'`/`Property 'X' is missing... from type 'I18nContextValue'`. Каждый раз причина оказывалась в моей же заглушке (нарушение UMD-паттерна `export as namespace React` при вложении в `declare module 'react' {}`, отсутствие phantom-типа в `Context<T>` и т.п.), а не в реальном коде — подтверждено:
1. Изолированным минимальным репро с ПРАВИЛЬНОЙ структурой типов (top-level `declare namespace React {} export = React; export as namespace React;`, как в настоящем `@types/react`) — тот же паттерн `createContext`/`useContext`/`React.ReactNode`, что в `I18nProvider.tsx`, скомпилировался с 0 ошибок.
2. В последней попытке та же ошибка `JSX.IntrinsicElements` вылезла у ВСЕХ файлов проекта одновременно, включая давно существующие и не тронутые в этой сессии (`SituationalMap.tsx`, `app/admin/*`) — это доказывает проблему именно в конкретном прогоне стенда, а не в новом коде конкретно.

**Вывод**: содержательная (не стендовая) валидация полноты словарей и логики детекта языка — сделана и прошла полностью. Финальную сборку `next build`/`tsc` по факту в среде с реальными пакетами стоит прогнать перед деплоем (как и во всех предыдущих аудитах в этом проекте — нет доступа к npm registry в этой песочнице).

## Не проверено (ограничение аудита)

- Реальный рендер в браузере — переключение языка, cookie-персистентность между визитами, SSR без "мигания" — не проверялись визуально (нет браузера в этой среде).
- Качество переводов не проверено носителями языка — переводы (9 языков помимо базового украинского/русского оригинала) сделаны по общим знаниям соответствующих языков, стоит дать на вычитку носителю перед продакшеном, особенно для юридически значимых формулировок (например, текст о рукописной дате на квитанции в `myHome_dateWarningText`).
- `next build` целиком (production build, включая генерацию статики) — не прогонялся.
