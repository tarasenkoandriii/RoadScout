# Аудит: реальний інцидент — `prisma db push` падав у нескінченний цикл рестарту

## Контекст

Реальні логи контейнера `api`, надані користувачем, показали чіткий цикл: `db push` падає з
помилкою `Error: Use the --accept-data-loss flag...`, скрипт (`set -e`) завершується з
помилкою, Docker перезапускає контейнер, `entrypoint.sh` виконується заново з початку, той самий
крок знову падає — нескінченний цикл рестарту, бекенд ніколи не встигає дійти до
`npm run start:dev`. Саме тому впали навіть базові `/api/auth/me`/`/api/auth/dev-accounts` —
бекенд у принципі не був живий, це не проблема конкретно тих ендпоінтів.

## Діагноз

`Camera.fov_polygon` і `Camera.route_buffer_polygon` (плюс `route_line`) — сирі PostGIS-колонки
типу `geometry(...)`, якими Prisma нативно не вміє керувати; вони створюються і підтримуються
виключно через `sql/geo-migration.sql`/`sql/route-migration.sql` і пряме читання/запис через
`$executeRawUnsafe`/`$queryRaw` (`syncCameraPolygon()`/`syncCameraRoutePolygon()`,
`CamerasService.findCandidatesNearPoint()`).

**Ці колонки ніколи не були оголошені в моделі `Camera` у `schema.prisma`.** Через це кожен
запуск `prisma db push` бачив їх як "зайві" стовпці, що не описані в схемі, і намагався їх
**видалити** — щоб привести реальну структуру БД у повну відповідність зі схемою. Поки таблиця
була порожньою/усі значення `fov_polygon` були `NULL`, це відбувалося мовчки, без жодного
попередження (видалення порожньої/всюди-`NULL` колонки Prisma не вважає "втратою даних"). Тільки
після кількох сесій реального імпорту камер (і накопичення **16 непорожніх значень
`fov_polygon`**) Prisma нарешті коректно розпізнала реальну втрату даних і — цілком правильно —
відмовилась виконувати операцію без явного підтвердження прапорцем `--accept-data-loss`.

**Важливо: `--accept-data-loss` був би НЕПРАВИЛЬНИМ фіксом**, попри те, що саме на нього
натякає повідомлення про помилку — він би тихо видалив саму колонку геопошуку для всіх 16 уже
імпортованих камер (`fov_polygon` заново створюється порожньою `route-migration.sql`, і жодного
автоматичного механізму перерахунку сектору для ВЖЕ ІСНУЮЧИХ камер під час старту контейнера
немає) — усі раніше імпортовані вуличні камери (Tetris Hall, Протасів Яр тощо) миттєво зникли б
з пошуку за адресою після першого ж рестарту з цим прапорцем, і про це ніхто б не дізнався без
окремої перевірки.

## Виправлення

Додано три поля в модель `Camera` в `schema.prisma` через офіційний механізм Prisma
`Unsupported("...")` — спосіб сказати "ця колонка існує в БД навмисно, з таким сирим типом, не
чіпай її при `db push`, просто не давай типізованого доступу через клієнт":

```prisma
fov_polygon           Unsupported("geometry(Polygon, 4326)")?
route_buffer_polygon  Unsupported("geometry(Polygon, 4326)")?
route_line            Unsupported("geometry(LineString, 4326)")?
```

Типи звірені точно з реальними SQL-визначеннями в `sql/geo-migration.sql`/
`sql/route-migration.sql` (`geometry(Polygon, 4326)`/`geometry(LineString, 4326)`). Це **не
одноразовий обхідний шлях, а постійне, правильне рішення** — з цього моменту `prisma db push`
буде коректно розпізнавати ці колонки як навмисну частину схеми й ніколи більше не
намагатиметься їх видалити, незалежно від того, скільки в них реальних даних.

## Реально перевірено

- Структурна цілісність `schema.prisma` — баланс дужок після додавання нових полів, немає
  дублікатів імен моделей/enum-ів. **Чисто.**
- Типи `Unsupported(...)` звірені посимвольно з реальними SQL-визначеннями стовпців у обох
  міграційних файлах — збігаються точно.
- Підтверджено, що `apps/api/scripts/docker-entrypoint.sh` НЕ містить прапорця
  `--accept-data-loss` як тимчасового обхідного шляху — команда `db push` лишається чистою,
  без ризикованих прапорців, оскільки справжня причина усунена на рівні схеми, а не замаскована
  прапорцем.

## Не перевірено / відомі обмеження

- **Реальний прогін `prisma db push` проти живої бази з цим фіксом** — мережа/Docker недоступні
  в цій пісочниці; перевірена лише коректність оголошення `Unsupported(...)` синтаксично і
  відповідність типів реальним SQL-визначенням, не фактична поведінка Prisma CLI проти реальної
  БД з існуючими 16 непорожніми записами `fov_polygon`.
- Якщо колись у майбутньому знадобиться ЗМІНИТИ (не просто зберегти) тип цих геометричних
  стовпців — це все одно доведеться робити через окрему сиру SQL-міграцію (як і раніше), `db
  push`/`migrate` самі по собі не вміють генерувати ALTER для `Unsupported`-полів; `Unsupported`
  лише зупиняє їх ВИДАЛЕННЯ, не бере на себе повне керування.

## Що потрібно зробити користувачу

Після оновлення коду з цим фіксом — просто перезапустити контейнер `api` звичайним чином
(`docker compose restart api` або новий `docker compose up --build`, volume з БД видаляти
**не потрібно** — усі 16 уже імпортованих камер і їхні `fov_polygon` лишаться недоторканими).
`db push` тепер має пройти без помилок і без нескінченного циклу рестарту.
