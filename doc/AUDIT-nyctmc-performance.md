# Аудит: чому NYC DOT Traffic Cameras (RTTI) — дуже повільний парсер

## Контекст

Прямий запит користувача: NYC TMC працює дуже повільно, провести аудит, можливо додати
багатопотоковість.

## Діагноз — знайдено конкретну, кількісно оцінювану причину

### Перший підозрюваний (перевірений і виправлений раніше) — не є основною причиною

Раніше вже виправили відсутній `User-Agent` (див. `doc/AUDIT-nyctmc-adapter.md`) — це
впливало на те, чи `discover()` (ОДИН запит до `/api/cameras`) взагалі повертав дані. Це не
стосується швидкості ОБРОБКИ вже отриманих даних — саме про це цей аудит.

### Реальна причина — `AzimuthHeuristicService.guessForPoint()` робить живий мережевий запит до Overpass API (OpenStreetMap) на КОЖНУ камеру

`discover()` NYC TMC повертає ~900-969 камер **одним** HTTP-викликом (швидко). Але далі кожен
з цих ~900+ елементів проходить через `ScraperService.processItem()`, де для кожної камери
без вже відомого азимута викликається `AzimuthHeuristicService.guessForPoint(lat, lng)` —
**реальний живий запит до публічного Overpass API** (спільний, часто повільний геосервіс),
щоб знайти найближчу дорогу для евристики напрямку огляду. Кеш там — по сітці лише ~100
метрів; для камер NYC TMC, розкиданих по всьому місту (Мангеттен/Бруклін/Квінс/Бронкс/
Стейтен-Айленд), переважна більшість опиняється в РІЗНИХ клітинках сітки — кеш майже ніколи
не спрацьовує для цього конкретного набору даних.

### Кількісна оцінка (чому "дуже повільно" — не суб'єктивне відчуття)

Цикл обробки раніше йшов **строго послідовно**, один елемент за раз, і зупинявся за
бюджетом часу (`PARSER_RUN_TIME_BUDGET_MS`, за замовчуванням **25 секунд**). Якщо кожен
Overpass-запит займає навіть 1-3 секунди (типово для публічного, спільного сервісу під
навантаженням) — плюс ще й фіксована пауза `PARSER_DETAIL_FETCH_DELAY_MS` (300мс) **після
кожного елемента, незалежно від того, чи адаптер взагалі робив додатковий запит до сайту-
джерела** (реальна знахідка — ця пауза була написана саме під webcam.guru.ua, де вона
захищає САЙТ-ДЖЕРЕЛО від паралельних запитів; для NYC TMC вона не захищає нікого, оскільки
сам NYC TMC вже опитаний один раз у `discover()`) — за 25 секунд встигало обробити
орієнтовно **8-25 камер за один прохід**. NYC TMC ганяється на тому самому щоденному
розкладі, що й `webcam-guru` (не виключений з квотних міркувань — див.
`doc/AUDIT-nyctmc-adapter.md`) — тобто **повний імпорт ~900+ камер зайняв би 40-100+ днів**.

## Що зроблено

### "Многопоточність" у Node.js для I/O-навантаженої роботи — це не OS-потоки

Важливе уточнення (пояснено і в самому коді): вузьке місце тут — очікування мережі
(Overpass-запит), не обчислення на CPU. `worker_threads` (справжні OS-потоки Node.js) не дали
б виграшу — вони потрібні для CPU-важких задач, а тут CPU майже не завантажений, більшість
часу йде на очікування відповіді зовнішнього сервера. Правильний, ідіоматичний для Node.js
відповідник "багатопотоковості" для I/O-навантаженої роботи — **конкурентні проміси**:
кілька елементів обробляються ПАРАЛЕЛЬНО через `Promise.all()`, поки кожен окремо чекає на
свою мережеву відповідь — саме це й реалізовано.

### Рефакторинг циклу обробки — пачки з конкурентністю, що залежить від типу адаптера

- **Концептуально важлива обережність**: конкурентність **безпечна не для всіх адаптерів
  однаково**. Двофазні HTML-скрапінгові адаптери (`webcam-guru`, `google-web-camera-search`)
  самі роблять по одному мережевому запиту НА КОЖЕН елемент — САМЕ до сайту-джерела (через
  `fetchDetails()`). Паралелити ці запити означало б одночасно бомбардувати чужий сайт
  кількома запитами замість ввічливого одного за раз — свідомий вибір із самого початку
  проєкту (див. `PARSER_DETAIL_FETCH_DELAY_MS`).
- Тому: **конкурентність = 1 (стара поведінка, без змін) для адаптерів із `fetchDetails()`**,
  і **конкурентність = `PARSER_ITEM_CONCURRENCY` (новий, за замовчуванням 8) для адаптерів БЕЗ
  `fetchDetails()`** (NYC TMC, Windy, YouTube-пошук — усі вже мають повні дані з одного
  виклику `discover()`, єдиний реальний per-item мережевий виклик — Overpass, сторонній
  спільний сервіс, не сайт-джерело, тому паралельна обробка не шкодить jerelu).
- Пауза `PARSER_DETAIL_FETCH_DELAY_MS` тепер теж **умовна** — застосовується лише коли
  `adapter.fetchDetails` реально існує (для NYC TMC й подібних вона більше не додає 300мс
  марного очікування на кожен елемент без жодної практичної користі).
- Бюджет часу (`PARSER_RUN_TIME_BUDGET_MS`) перевіряється **між пачками**, не між кожним
  елементом — та сама гарантія (акуратна зупинка, збережений прогрес, чіткий лог), просто
  на рівні пачки.

## Реально прогнані тести (ts-node, справжнє виконання)

**7 нових перевірок**, усі пройшли:
- **Реально виміряний виграш у часі**: 24 елементи з симульованою мережевою затримкою 50мс
  кожен, конкурентність 8 → **179-182мс** замість очікуваних ~1200мс при строго послідовній
  обробці (**~6.5x швидше**, близько до теоретичного максимуму 8x з урахуванням накладних
  витрат).
- **Усі 24 елементи реально оброблені** (не втрачені при паралелізації).
- **Адаптер із `fetchDetails()` і далі обробляється строго послідовно** — перевірено порядок
  подій (`start-X` завжди одразу за ним `end-X`, без переплетення з іншими елементами) —
  підтверджує, що webcam-guru-подібні адаптери НЕ паралеляться (свідома, збережена гарантія).
- **Бюджет часу коректно зупиняє цикл пачок** навіть при дуже жорсткому ліміті (50мс) — не всі
  20 елементів оброблені, але реальний прогрес зроблений (не нуль — той самий принцип, що вже
  перевірений раніше для П3.2 у попередньому інциденті бюджету часу).

Плюс `tsc --noEmit` по всьому графу застосунку — 0 помилок у змінених файлах (2 залишкові —
той самий, вже неодноразово підтверджений артефакт спрощеної заглушки типів у
`lookahead.controller.ts`/`monitoring.controller.ts`).

## Не перевірено / відомі обмеження

- **Реальна поведінка Overpass API під конкурентним навантаженням** (8 одночасних запитів) —
  недоступна в цій пісочниці (немає мережі); Overpass загалом розрахований на конкурентні
  гео-запити, але при рейт-лімітуванні (HTTP 429) варто зменшити `PARSER_ITEM_CONCURRENCY`
  через env — жодного окремого retry/backoff механізму саме під це поки не додано.
- **Подальше, більш глибоке покращення (поза обсягом цього кроку)**: Overpass підтримує
  запити з КІЛЬКОМА `around`-регіонами в ОДНОМУ HTTP-виклику — теоретично можна було б
  групувати десятки координат в один запит замість N окремих, що дало б набагато більший
  виграш, ніж просто конкурентність окремих викликів. Це вимагає суттєвої переробки
  `AzimuthHeuristicService` (зараз спроєктований як `guessForPoint()` по одній точці) — не
  зроблено в цьому кроці через ризик і обсяг зміни центрального, вже давно стабільного
  сервісу, яким користуються ВСІ адаптери, не лише NYC TMC.
- Бюджет часу (`PARSER_RUN_TIME_BUDGET_MS`) лишився ГЛОБАЛЬНИМ (спільним для всіх провайдерів)
  — не зроблено адаптер-специфічним; збільшення цього значення для пришвидшення повного
  імпорту NYC TMC вплинуло б і на webcam-guru — свідомо не змінено без явного рішення
  оператора (можна підняти вручну через env, якщо серверless-таймаут дозволяє довший прохід).
