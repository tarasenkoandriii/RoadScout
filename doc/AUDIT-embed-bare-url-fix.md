# Аудит: реальний інцидент — «биту» посилання на потік ламало embed-віджет

## Контекст

Реальний скріншот `/admin/cameras/:id/calibrate` (камера «Шулявка реконструкція») показав дві
пов'язані помилки в консолі браузера:
1. `Refused to display 'https://www.youtube.com/' in a frame because it set 'X-Frame-Options'
   to 'sameorigin'.`
2. Повідомлення AI-автокалібрування: `Автоматический захват кадра для типа потока "IFRAME" не
   реализован`.

## Діагноз

Ці два повідомлення разом видали точну причину: `streamUrl` цієї камери — буквально
**`https://www.youtube.com/`** (гола головна сторінка YouTube), а `streamType` збережений як
**`IFRAME`**, хоча посилання явно про YouTube. Це несумісна пара: `<iframe src="https://www.youtube.com/">`
намагається вбудувати головну сторінку YouTube, яка (на відміну від справжніх embed/watch-
посилань) забороняє вбудовування через `X-Frame-Options: sameorigin`.

Найімовірніше походження: ця камера пройшла через **ручне резолвлення в черзі ревʼю**
(автогеокодинг спочатку провалився — цю саму камеру видно в попередніх скріншотах реального
журналу імпорту як `NEEDS_REVIEW`). Форма ревʼю ЗАВЖДИ відкривалась із жорстко закодованим
`streamType: 'IFRAME'` за замовчуванням, незалежно від реального `rawStreamUrl` — адмін,
найімовірніше, не звернув уваги на випадаючий список і зберіг з дефолтним (невірним) значенням.

## Виправлення (три рівні захисту)

### 1. `/embed/[id]` — захисна перевірка форми URL

Нова функція `looksEmbeddable(url)`: голий корінь домену (шлях `/` або порожньо, без
query/hash) вважається **не** вбудовуваним **незалежно від `streamType`** — навіть якщо тип
формально «IFRAME»/«YOUTUBE_LIVE», порожнє посилання на корінь домену майже напевно бите/
неповне. Замість спроби показати биту трансляцію — зрозуміле повідомлення «Ссылка на поток
выглядит неполной» + пряме посилання.

### 2. Усунення першопричини — автовизначення типу потоку у формах

`/admin/parser/review` і `/admin/camera-submissions` — обидві форми тепер вгадують
`streamType` за самим посиланням при відкритті картки (`inferStreamType()`:
`youtube.com`/`youtu.be` → `YOUTUBE_LIVE`, інакше `IFRAME`) замість жорсткого дефолту
`'IFRAME'`. Це не гарантія (адмін усе одно може вручну обрати неправильний варіант), але різко
знижує шанс повторення саме цієї помилки.

### 3. Можливість виправити вже існуючі биті камери

Раніше `streamUrl`/`streamType` взагалі не редагувалися після створення камери — єдиний спосіб
виправити вже існуючу биту камеру (як цю саму «Шулявку») був прямий доступ до БД.
`CalibrateCameraDto` доповнений опціональними полями `streamUrl`/`streamType`; інструмент
калібрування тепер показує їх як звичайні редаговані поля форми.

## Реально прогнані тести (справжнє виконання)

**`looksEmbeddable()`** (9 перевірок): **точний реальний випадок** (`https://www.youtube.com/`)
→ `false`; той самий домен без кінцевого слеша → теж `false`; справжні watch/embed-посилання
YouTube → `true`; звичайний iframe-URL зі шляхом → `true`; голий корінь довільного домену →
`false`; URL лише з query (без шляху) → `true` (є query — це вже не голий корінь); зіпсований
рядок (не URL взагалі) → `false` без падіння; порожній рядок → `false` без падіння. Усі 9 —
**пройдені**.

**`inferStreamType()`** (5 перевірок): watch-посилання YouTube → `YOUTUBE_LIVE`; **точний
реальний бітий URL (`https://www.youtube.com/`) → все одно правильно `YOUTUBE_LIVE`**
(підтверджує, що визначення типу і перевірка вбудовуваності — дві незалежні, доповняльні
перевірки, не одна й та сама); короткі `youtu.be`-посилання → `YOUTUBE_LIVE`; звичайний iframe-
URL → `IFRAME`; відсутнє посилання → дефолт `IFRAME`. Усі 5 — **пройдені**.

Разом 14 нових перевірок, усі пройшли. Плюс `tsc --noEmit` по оновленому
`CalibrateCameraDto`/`CreateCameraDto` — 0 помилок; баланс дужок усіх 4 змінених фронтенд-файлів
— чисто.

## Оновлення: та сама помилка залишалась навіть після виправлення URL у формі

Другий реальний скріншот (той самий, "Шулявка реконструкція") показав: користувач уже виправив
`streamUrl` на справжнє watch-посилання (`https://www.youtube.com/watch?v=bK_oTZcHEW...`) прямо
у формі калібрування, **але консоль браузера все одно показувала ту саму помилку**
`X-Frame-Options: sameorigin`. Причина: превʼю рендерилось через
`<iframe src="/embed/{camera.id}">` — окремий запит до сервера, що повертає **збережений** стан
камери (з БД), а не те, що адмін щойно ввів у поле форми без збереження. Тобто виправлення поля
реально спрацювало б, але превʼю продовжувало тягнути стару, ще не збережену биту адресу —
вводило в оману, ніби фікс не подіяв.

### Виправлення

- Спільна логіка `looksEmbeddable()`/`canEmbedStream()` винесена в
  `apps/admin/lib/embeddable.ts` — використовується і в `/embed/[id]`, і в новому
  live-превʼю, щоб не розійтися при майбутніх правках.
- Превʼю на екрані калібрування тепер рендериться **напряму з поточного стану форми**
  (`camera.streamUrl`/`camera.streamType`), без походу на сервер — правка поля миттєво
  відображається в превʼю, без потреби спочатку натискати «Сохранить».

### Реально прогнані тести

5 перевірок, включно з **точним відтворенням стану користувача зі скріншота**: watch-посилання
вже введене в поле, але `streamType` все ще `IFRAME` (не змінений на `YOUTUBE_LIVE`) →
`canEmbedStream()` **правильно повертає `true`** — підтверджує, що після цього фіксу превʼю
запрацює одразу, ще до зміни випадаючого списку типу чи натискання «Сохранить». Окремо
перевірено: старий биний стан (голий корінь) → `false`; той самий голий корінь з
`YOUTUBE_LIVE` → все одно `false` (перевірка форми URL не залежить від заявленого типу); валідний
URL з несумісним типом (`HLS`) → `false` (сам тип не підтримує вбудовування). Усі 5 —
**пройдені**.

Плюс перевірено обчисленням, що відносні шляхи імпорту (`../../../lib/embeddable` для
`/embed/[id]`, `../../../../../lib/embeddable` для калібрування) точно відповідають реальній
глибині директорій — звірено програмно через `os.path.relpath()`, не на око.

## Оновлення 2: та сама помилка навіть на справжньому watch-посиланні з конкретним відео

Користувач сам правильно визначив напрям: третій скріншот показав, що конкретне відео за цим
id справді **більше не доступне на YouTube** («Це відео більше не доступне»). Але навіть якби
воно було доступне — проблема лишилась би: **сторінки `youtube.com/watch?v=...` в принципі не
призначені для вбудовування в чужий `<iframe>`** — `X-Frame-Options: sameorigin` стоїть на них
завжди, незалежно від доступності відео. Тільки `youtube.com/embed/{id}` спеціально
спроєктований для показу в чужих фреймах — включно з коректним показом «відео недоступне»
**всередині самого фрейму** (не блокується браузером), якщо відео дійсно видалене/приватне.

### Виправлення

- `toEmbeddableUrl(streamUrl)` (`lib/embeddable.ts`) — розпізнає будь-який формат посилання на
  YouTube (`watch?v=`/`youtu.be/`/`live/`/вже-`embed/`) і конвертує в канонічний
  `youtube.com/embed/{id}` — використовується ТІЛЬКИ для `src` самого iframe, не для посилання
  «відкрити в новій вкладці» (там потрібен звичайний watch-адрес, повний інтерфейс YouTube).
- **Свідомо не покладається строго на `streamType === 'YOUTUBE_LIVE'`** — оскільки ми вже двічі
  зустріли розсинхронізацію типу й посилання для цієї ж камери (`streamType` лишався `IFRAME`,
  хоча посилання вело на YouTube), конвертація спрацьовує, якщо з самого `streamUrl` вдається
  видобути id відео, **незалежно від заявленого типу потоку**.

### Реально прогнані тести

6 перевірок, включно з **точним поточним станом користувача**: `streamType` все ще `IFRAME` (не
перемкнутий на `YOUTUBE_LIVE`) + реальне watch-посилання з відео `bK_oTZcHEWY` →
**конвертація все одно спрацьовує коректно**, `toEmbeddableUrl()` повертає
`https://www.youtube.com/embed/bK_oTZcHEWY`. Окремо перевірено: короткі `youtu.be`-посилання;
вже-`embed`-посилання лишається незмінним (ідемпотентність); не-YouTube URL не чіпається;
посилання на канал цілком (без id відео) і голий корінь домену — обидва коректно повертаються
без змін (нема з чого видобути id, конвертувати нема сенсу). Усі 6 — **пройдені**.

## Не перевірено / відомі обмеження (оновлення 2)

- **Саме те конкретне відео дійсно недоступне** (підтверджено користувачем напряму на
  YouTube) — навіть з правильним `/embed/` форматом, YouTube покаже «відео недоступне»
  всередині фрейму замість трансляції; це не помилка коду, а стан самого джерела — камеру
  варто перевірити/оновити посилання на актуальне.
- **Сама камера «Шулявка реконструкція» в реальній БД користувача не виправлена автоматично**
  цим фіксом — потрібно зайти в `/admin/cameras/:id/calibrate` для неї і вручну замінити
  `streamUrl`/`streamType` на правильні значення (тепер це можливо через форму, раніше не було).
- `inferStreamType()` — проста регулярка за доменом, не універсальна: не розпізнає інші відео-
  хостинги (Vimeo, власні RTMP-плеєри тощо) як щось окреме від `IFRAME` — це прийнятний
  компроміс (той самий принцип, що вже використовується в `WebcamGuruAdapter.fetchDetails()`),
  не намагається вирішити загальну задачу класифікації всіх можливих типів потоків.
- Фронтенд-зміни — перевірені балансом дужок і вручну вичитані, не прогонялись через `tsc`/
  візуально в браузері (та сама, вже неодноразово задокументована причина нестабільності
  заглушки `@types/react` у цій конкретній пісочниці).
