# Аудит: реализация П2 (надёжность эвристики азимута, охват всех городов, health-сигнал) из `doc/TZ-parser-import-improvements.md`

## Что сделано

### П2.1 — надёжность эвристики азимута

- `AzimuthHeuristicService` переписан:
  - **Кэш по координатной сетке** (~100м, `AZIMUTH_HEURISTIC_CACHE_TTL_HOURS`, по умолчанию
    24ч) — соседние камеры на одной улице переиспользуют один и тот же результат Overpass-
    запроса вместо отдельного запроса на каждую.
  - **Явный клиентский таймаут** через `AbortController` (`AZIMUTH_HEURISTIC_TIMEOUT_MS`, по
    умолчанию 8с) — раньше `fetch()` не имел ограничения по времени со стороны клиента вообще
    (только `timeout:10` внутри самого Overpass-запроса, который ничего не гарантирует, если
    сервер зависает на уровне сети, а не отвечает вовремя ошибкой).
  - `AzimuthGuess` теперь содержит явное поле `source: 'heuristic' | 'fallback'`.
- **Найден и исправлен реальный баг**, обнаруженный в процессе доработки (не был в исходном
  ТЗ): раньше `ScraperService` угадывал "это фолбэк?" по магическим значениям
  (`azimuth === 0 && rangeHint === 'yard'`). Это ошибочно классифицировало бы **настоящий**
  результат эвристики (дорога, идущая точно на север, классифицированная как "двор" — редкий,
  но реальный случай) как фолбэк. Исправлено: сервис сообщает источник напрямую, никакого
  угадывания по значениям.
- `Camera.azimuthSource` — новое персистентное поле (не только в транзиентном
  `ImportLogEntry.metadata`, как было после П1.2) — проставляется во всех трёх местах, где
  создаётся/обновляется азимут камеры: авто-импорт (`processItem`, `'heuristic'`/`'fallback'`),
  ручное разрешение из очереди ревью (`resolveSourceRaw`, всегда `'manual'`), ручная калибровка
  (`CamerasService.calibrate`, тоже `'manual'`).
- `GET /admin/parser/stats/summary` дополнен `azimuthFallbackCount`/`azimuthHeuristicCount` на
  провайдера — видно агрегированно в таблице `/admin/parser`, не только в логе по одной камере.

### П2.2 — охват всех городов

- `ScraperService.runAll(triggeredBy)` — обходит **все** строки `CameraProvider` (без
  предварительной фильтрации по `adapterKey` — `resolveAdapter()` внутри `runForProvider()` сам
  решает, поддержан ли адаптер, что не дублирует эту логику в двух местах), с задержкой между
  провайдерами (`PARSER_RUN_ALL_DELAY_MS`, по умолчанию 2с).
- `POST /internal/parser/run-all` (под `CronSecretGuard`) и `POST /admin/parser/run-all` (под
  `AdminGuard`, кнопка «Запустить все источники» в админке).
- `sql/pg_cron-schedule.sql` — единственный захардкоженный `<webcam-guru-provider-id>` заменён
  на один job, бьющий по `/internal/parser/run-all`.

### П2.3 — health-сигнал

- `ParserRunLog.anomalyFlag` — `detectAnomaly()` сравнивает `discoveredCount` текущего прохода
  со скользящим средним последних `PARSER_ANOMALY_HISTORY_SIZE` (по умолчанию 5) успешных/
  частично успешных проходов **того же провайдера**; при отклонении больше
  `PARSER_ANOMALY_THRESHOLD` (по умолчанию 0.5 = 50%) в любую сторону — флаг `true`. Не
  срабатывает, если истории меньше `PARSER_ANOMALY_MIN_HISTORY` (по умолчанию 3, чтобы не
  поднимать тревогу на первых проходах источника) или если само скользящее среднее равно 0
  (источник и раньше стабильно ничего не находил — не "новая" аномалия).
- Визуальная пометка ⚠️ в таблице проходов на `/admin/parser`.

## Реально прогнанные тесты (ts-node, настоящее выполнение логики)

**`AzimuthHeuristicService`** (6 сценариев):
1. Реальная дорога найдена → `source: 'heuristic'`, корректный азимут/классификация по тегу
   `highway`. **Пройден.**
2. **Ключевая проверка бага**: реальный результат эвристики, который *случайно* равен
   `azimuth: 0, rangeHint: 'yard'` (дорога точно на север без тега `highway`) — подтверждено,
   что источник всё равно правильно определяется как `'heuristic'`, не `'fallback'` по старой
   магической логике. **Пройден.**
3. Дорога не найдена рядом → `source: 'fallback'`. **Пройден.**
4. Сетевая ошибка → `source: 'fallback'`, исключение не пробрасывается наружу. **Пройден.**
5. Кэш: повторный запрос для близкой точки (та же ячейка сетки) не делает новый fetch.
   **Пройден.**
6. Кэш: запрос для далёкой точки (другая ячейка сетки) делает новый fetch. **Пройден.**

**`ScraperService.detectAnomaly()`** (5 сценариев):
1. Недостаточно истории у нового провайдера → `anomalyFlag: false` независимо от значения.
   **Пройден.**
2. Обычное отклонение (20 против среднего ~20) → `false`. **Пройден.**
3. Резкое падение (0 против среднего ~20, имитация "селекторы сломались") → `true`. **Пройден.**
4. Резкий скачок (500 против среднего ~20, имитация бага дублирования) → тоже `true`.
   **Пройден.**
5. Базовое среднее само равно 0 (источник и раньше ничего не находил) → `false`, без ложной
   повторной тревоги. **Пройден.**

**`ScraperService.runAll()`** (1 комплексный сценарий): обход 3 провайдеров, включая один с
незарегистрированным `adapterKey` — подтверждено, что все 3 попытки выполняются (не прерывается
на первой ошибке), два рабочих корректно завершаются `SUCCESS`, проблемный — `FAILED` (изящно,
не роняя весь `runAll()`), и что между вызовами реально прошла заданная задержка. **Пройден.**

Итого 12 сценариев, все прошли. Плюс `tsc --noEmit` над изменёнными файлами модуля scraper —
0 ошибок, относящихся к этим файлам (единственные найденные ошибки — в `cameras.service.ts`,
но относятся к полям DTO, не тронутым в этом шаге, артефакт неполной заглушки `class-validator`
в этом конкретном прогоне, не связанный с добавлением `azimuthSource: 'manual'` в `calibrate()`).

## Не проверено / известные ограничения

- Фронтенд-изменения (`/admin/parser` — кнопка «Запустить все источники», колонка азимута,
  бейдж аномалии) — проверены балансом скобок и вручную вычитаны, не прогонялись через `tsc`/
  визуально в браузере (та же, уже неоднократно задокументированная причина нестабильности
  самодельной заглушки `@types/react` в этой песочнице).
- Реальный `prisma db push` с новыми полями (`Camera.azimuthSource`, `ParserRunLog.anomalyFlag`)
  — не прогонялся против настоящего Postgres; оба поля опциональные/со значением по умолчанию,
  обратная совместимость по построению, но не проверено вживую.
- Пороговые значения аномалии (50% отклонение, минимум 3 прохода истории, сравнение с 5
  последними) — как и отмечалось в самом ТЗ, это стартовые значения "на глаз", подлежат
  эмпирической донастройке после первых недель работы с реальными данными.
- Реальный вызов Overpass API с новым таймаутом/кэшем — сеть недоступна в этой среде; проверена
  только сама логика (таймаут через `AbortController`, кэш по сетке), не фактическое поведение
  реального API под нагрузкой.
