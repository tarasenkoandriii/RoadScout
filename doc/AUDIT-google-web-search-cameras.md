# Аудит: пошук через Google (окремо камер, окремо сайтів-агрегаторів) + VPN

## Контекст

Прямий запит користувача: додати пошук через Google (з VPN) для (1) окремих камер, (2) сайтів-
агрегаторів (з новою вкладкою в адмінці, таблиця URL + орієнтовна кількість камер).

## Ключова архітектурна знахідка (перед реалізацією)

**Google Custom Search JSON API закритий для нових клієнтів з 2025 року** (підтверджено
офіційною документацією Google) — не можна отримати новий ключ/Search Engine ID. Замінено
**вбудованим `web_search` tool xAI/Grok** (`/v1/responses`, той самий `XAI_API_KEY`, що вже є
в проєкті) — жодного нового провайдера/ключа заводити не довелось.

**Важливий наслідок для VPN**: пошук через `web_search` виконується на серверах xAI (Grok сам
робить запит до Google), не з нашого сервера — `RegistryProxyService` (VPN) до цього КРОКУ не
застосовний. VPN залишається доречним і реально використаний окремо — там, де наш сервер САМ
робить HTTP-запит: `fetchDetails()` в `GoogleWebCameraSearchAdapter` (відвідування знайденої
сторінки камери) і `AggregatorDiscoveryService.refineEstimate()` (відвідування сайту-
агрегатора для уточнення оцінки).

## Що зроблено

### Частина 1 — окремі камери (`GoogleWebCameraSearchAdapter`)
- `GrokCameraAssistService.searchCameraPages(cityName)` — новий метод, `/v1/responses` +
  `web_search` tool, повертає список `{url, title}`.
- `GoogleWebCameraSearchAdapter` (`adapterKey: web-search-{citySlug}`) — той самий двофазний
  принцип, що `WebcamGuruAdapter`: `discover()` — плейсхолдери (сторінка знайдена пошуком,
  реальний stream ще невідомий), `fetchDetails()` — наш сервер (VPN застосовний) відвідує
  сторінку, шукає `<iframe src=...>`/YouTube-посилання/`.m3u8` у HTML, з фолбеком на саму
  сторінку, якщо нічого розпізнати не вдалось.
- `isRelevant()` — той самий AI-фільтр шуму, що `YoutubeSearchAdapter`.

### Частина 2 — сайти-агрегатори (`AggregatorDiscoveryService`)
- Нова модель `AggregatorSiteCandidate` — url (унікальний), назва, місто, оцінка кількості
  камер, метод оцінки (`search_snippet` / `page_visit`), статус.
- `GrokCameraAssistService.searchAggregatorSites(cityName)` — та сама `web_search` схема,
  інший промпт (шукає каталоги, не окремі камери), повертає оцінку кількості зі сніпета, якщо
  видно.
- `AggregatorDiscoveryService.discoverForAllCities()` — для кожного українського міста,
  дедуплікація за URL (вже знайдені раніше сайти не перезаписуються).
- `AggregatorDiscoveryService.refineEstimate(id)` — реальне відвідування сайту через VPN,
  евристичний підрахунок посилань, що виглядають як окремі камери.
- Нова вкладка адмінки `/admin/aggregator-sites` — таблиця URL/місто/оцінка/дата, кнопка
  «Уточнить» (запускає `refineEstimate()`).

### Взаємне виключення (розширено з двох сімейств до трьох)
`ScraperService.runAll()` тепер приймає масив `excludeAdapterKeyPrefix` — загальний `run-all`
явно виключає і `youtube-search-*`, і `web-search-*`; кожне з трьох сімейств
(`webcam-guru-*`/`youtube-search-*`/`web-search-*`) має власний, окремий endpoint і cron-час
(03:00 → 03:15 → 03:45, знайдена й виправлена колізія з `camera-content-availability-daily` о
03:30 під час реалізації).

## Реально прогнані тести (ts-node, справжнє виконання)

**Grok web-search методи** (9 перевірок): запит справді йде на `/v1/responses`, не
`/chat/completions`; включає `web_search` tool; коректний парсинг обох форматів відповіді
(`output[].content[].text` і скорочений `output_text`); відсутність ключа → порожні масиви без
мережевих викликів; зіпсована/порожня відповідь і мережева помилка → безпечні фолбеки без
падіння.

**`GoogleWebCameraSearchAdapter`** (11 перевірок): `discover()` повертає коректні плейсхолдери
зі стабільним `externalId` (той самий URL → той самий хеш, дедуплікація нижче за течією);
`fetchDetails()` коректно витягує iframe (звичайний і YouTube-специфічний → правильна
класифікація `streamType`), `.m3u8`-посилання (→ `HLS`), коректний фолбек на саму сторінку,
коли нічого не знайдено; мережева помилка → `null`, не падіння; `isRelevant()` коректно
делегує в `isLikelyCityCamera()`.

**`AggregatorDiscoveryService`** (11 перевірок): пошук по всіх містах; **коректна
дедуплікація за URL навіть між РІЗНИМИ містами** (той самий сайт, знайдений для двох міст
поспіль, створює лише один запис); повторний запуск не дублює вже відомі кандидати;
`estimationMethod` коректно `search_snippet`/`null` залежно від наявності оцінки в сніпеті;
**`refineEstimate()` реально відвідує URL кандидата через проксі-обгортку**, коректний
евристичний підрахунок (3 з 5 тестових посилань розпізнані як камероподібні), правильно
встановлює `page_visit`/`lastCheckedAt`; невідомий id → `null` без падіння.

**Знайдена й виправлена помилка тестового фікстуру** (не реального коду) — під час тестування
`refineEstimate()` спочатку провалився через те, що тестова заглушка `findUnique` шукала лише
за `url`, а метод шукає за `id` — підтверджено окремим налагоджувальним скриптом, що сама
реалізація коректна, виправлено тестовий фікстур.

**Тримаоронне взаємне виключення** (4 перевірки): загальний `run-all` (виключає обидва нові
сімейства) торкається лише `webcam-guru`; youtube- і web-специфічні виклики торкаються лише
свого сімейства; **усі три провайдери спрацьовують рівно по одному разу сукупно** — жодного
подвійного чи пропущеного запуску.

Разом **35 нових перевірок**, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку — 0
помилок у змінених файлах (2 залишкові — той самий, вже неодноразово підтверджений артефакт
спрощеної заглушки типів у `lookahead.controller.ts`/`monitoring.controller.ts`).

## Не перевірено / відомі обмеження

- **Реальний виклик `/v1/responses` з живим ключем** — мережа недоступна в цій пісочниці;
  перевірена лише логіка парсингу відповіді й обробки помилок, не фактична якість/повнота
  результатів пошуку Grok на реальних українських містах.
- **Евристика підрахунку камер на сайті-агрегаторі** (`estimateCameraLinksCount`) — груба
  оцінка за регуляркою на назви посилань, не точний підрахунок; призначена для сортування
  кандидатів за пріоритетом дослідження, не як точна метрика.
- Формат `web_search` tool (`/v1/responses`) і сама доступність цієї можливості на акаунті
  користувача — не перевірені реальним запитом; документація xAI станом на момент реалізації
  підтверджує існування tool'а, але не гарантує доступність на конкретному тарифі/акаунті.
- Фронтенд-зміни (нова вкладка) — перевірені балансом дужок і вручну вичитані, не прогонялись
  через `tsc`/візуально в браузері (та сама, вже неодноразово задокументована причина
  нестабільності заглушки `@types/react` у цій конкретній пісочниці).
- `prisma db push` з новою моделлю `AggregatorSiteCandidate` не прогонявся проти живої БД.
