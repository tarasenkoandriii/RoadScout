# Аудит: AI-помічник координат через Google Places API

## Контекст

Реальний скріншот `/admin/parser/review` (заявка «Пішохідний міст Києв»): Grok чесно повідомив,
що не знає, який саме міст мається на увазі серед кількох існуючих у Києві — координати `—`,
звичайний геокодинг тексту теж провалився («Не удалось геокодировать указанный адрес»). Адмін
залишався без жодного способу отримати координати, крім ручного пошуку. Запит користувача:
додати AI-помічник для отримання широти/довготи, можливо через Google Maps.

## Що зроблено

- **`GeocodingService.searchPlace(query, cityHint)`** (новий метод, `src/common/geocoding.service.ts`)
  — використовує **Google Places API (Text Search)**, не Geocoding API. Принципова відмінність:
  Geocoding API (`geocode()`, вже існуючий метод) очікує структуровану адресу і не вміє шукати
  за орієнтирами/POI; Places Text Search шукає саме по реальній базі місць Google Maps — якраз
  те, що потрібно для назв на кшталт «Пішохідний міст», «завод "Енергія"» тощо.
- Той самий `GOOGLE_GEOCODING_API_KEY` — Places API потрібно додатково включити на тому ж
  проекті Google Cloud (задокументовано в `.env.example`).
- Оскільки Places API не повертає числову впевненість (на відміну від `location_type` у
  Geocoding), впевненість — чесна евристика: **1.0**, якщо знайдено рівно один кандидат;
  **0.6**, якщо кілька (беремо перший за релевантністю Google, але позначаємо як менш певний
  результат, не видаємо за єдино правильний).
- `ScraperService.suggestAiForSourceRaw()` і `CameraSubmissionsService.suggestAiForSubmission()`
  тепер запускають **обидва джерела паралельно** (`Promise.all`): текстову здогадку Grok (з
  можливими власними координатами за памʼяттю моделі) і реальний пошук через
  `searchPlace()` — результат обʼєднується в одну відповідь з окремими полями `placesLat`/
  `placesLng`/`placesConfidence`/`placesName`/`placesFormattedAddress`.
- Фронтенд (`/admin/parser/review`, `/admin/camera-submissions`) — координати від AI і від
  Google Places показуються **окремо**, кожна зі своєю кнопкою «Использовать» — свідомо не
  один змішаний результат з автоматичним пріоритетом: адмін бачить обидва джерела (і можливу
  розбіжність між ними) і сам вирішує, якому довіряти.
- i18n: нові ключі (`cameraSubmissions_aiPlacesCoordsLabel`, `cameraSubmissions_aiUse`,
  `cameraSubmissions_aiFoundLabel`) додані в усі 10 словників, перевірено компілятором на
  повноту.

## Реально прогнані тести (ts-node, справжнє виконання)

**`GeocodingService.searchPlace()`** (10 перевірок): запит справді йде на ендпоінт
`/place/textsearch/`, не на Geocoding; єдиний знайдений кандидат → впевненість `1.0`; кілька
кандидатів → впевненість саме `0.6` (не помилково `1.0`), береться перший, `candidateCount`
відстежується коректно; нуль результатів → `null` без падіння; відсутність API-ключа → `null`,
запит навіть не робиться; мережева помилка → `null`, без виключення. Усі 10 — **пройдені**.

**Комбінована підказка `ScraperService.suggestAiForSourceRaw()`** (9 перевірок) —
**відтворює точний сценарій зі скріншота**: Grok чесно каже «не знаю» (координати `null`,
`reasoning` про кілька мостів), а Google Places (замокований, симулює реальний збіг) **знаходить
координати саме там, де память моделі не спрацювала**. Перевірено: обидва джерела викликані
рівно по одному разу; Places отримує саме `rawTitle` (реальну назву від джерела, не
перефразовану Grok-ом) з правильною підказкою міста; підсумкова відповідь коректно містить і
чесний «невідомо» від Grok, і реальні координати від Places з їхньою власною впевненістю та
назвою знайденого місця. Усі 9 — **пройдені**.

Разом 19 нових перевірок, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку — 0
помилок у змінених файлах.

## Не перевірено / відомі обмеження

- Реальний виклик Google Places API з живим ключем — мережа недоступна в цій пісочниці;
  перевірена лише логіка обробки відповіді (парсинг статусів `OK`/`ZERO_RESULTS`, підрахунок
  кандидатів, евристика впевненості), не фактична якість пошуку на реальних назвах камер.
- Чи дійсно Places API знайде правильний **конкретний** міст серед кількох існуючих у реальному
  Києві — залежить від того, чи проіндексований цей конкретний обʼєкт у базі Google Maps як
  окремий POI з відповідною назвою; не гарантія, а ймовірне покращення порівняно з відсутністю
  такого пошуку взагалі.
- Фронтенд-зміни — перевірені балансом дужок і вручну вичитані, не прогонялись через `tsc`/
  візуально в браузері (та сама, вже неодноразово задокументована причина нестабільності
  заглушки `@types/react` у цій конкретній пісочниці).
- Вартість/ліміти Google Places API окремі від Geocoding API навіть на тому самому ключі —
  не додано окремого rate-limiting саме на `searchPlace()` (викликається лише за явним запитом
  адміна, не масово, тому ризик низький, але не виміряний на практиці).
