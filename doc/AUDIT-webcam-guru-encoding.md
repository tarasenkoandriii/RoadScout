# Аудит: неправильна кодування символів (мохибейк) на реальному прогоні

## Контекст

Реальний скріншот користувача (`/admin/parser`, натиснуто Dry-run для Києва) показав назви
камер у вигляді "кракозябрів" (◆◆◆◆◆◆◆◆) замість кирилиці, і «нет адреса» для всіх рядків.

## Діагноз

**Кодування (реальна проблема, підтверджена)**: `WebcamGuruAdapter.fetchPage()` робив
`axios.get(url).then(res => res.data as string)` — за замовчуванням axios/Node декодує байти
HTTP-відповіді як **UTF-8**, незалежно від того, яку кодування реально віддав сервер. Сайт
`webcam.guru.ua` — стара сторінка (проста верстка, inline-стилі, дизайн середини 2010-х), дуже
типово для таких українських/російських сайтів того часу — реально віддається у
**windows-1251**, не UTF-8. Наївна UTF-8-інтерпретація кириличних байтів windows-1251 дає рівно
той вид "кракозябрів", що на скріншоті.

**«Нет адреса» — ймовірно НЕ окремий баг**, а очікувана поведінка "мілкого" (shallow, не
"Углублённая проверка") Dry-run: той режим свідомо показує тільки результат Фази 1 (список),
яка на цьому сайті ніколи не містить адреси (див. `doc/AUDIT-webcam-guru-real-html.md`) —
адреса з'являється лише після Фази 2 (`fetchDetails()`), яку "мілкий" dry-run навмисно не
викликає (щоб не витрачати реальні запити). Втім, оскільки Фаза 2 теж парсить сторінки того ж
самого сайту тим самим (раніше — багованим) `fetchPage()`, вона однаково постраждала б від
кодування — тобто виправлення кодування актуальне для ОБОХ симптомів одразу.

## Виправлення

- Новий `apps/api/src/scraper/common/html-encoding.util.ts` — `decodeHtmlBuffer(buffer,
  contentTypeHeader?)`: визначає реальну кодування трьома способами по черзі:
  1. Заголовок `Content-Type` відповіді (`charset=windows-1251`) — найнадійніше.
  2. `<meta charset="...">`/`<meta http-equiv="Content-Type" content="...charset=...">` у самому
     HTML (шукається в перших ~2КБ, прочитаних як ASCII/latin1 — сама декларація кодування
     завжди ASCII-сумісна, незалежно від кодування решти документа).
  3. Фолбек `windows-1251` — найпоширеніший варіант для такого типу сайтів, явний
     задокументований дефолт, а не мовчазне вгадування UTF-8, яке й спричинило баг.
- `WebcamGuruAdapter.fetchPage()` — тепер запитує сторінку як `responseType: 'arraybuffer'`
  (сирі байти, не готовий рядок) і пропускає їх через `decodeHtmlBuffer()` з реальним
  заголовком `Content-Type` відповіді.
- Додано залежність `iconv-lite` (`apps/api/package.json`) — легка, широко використовувана
  бібліотека для декодування нестандартних кодувань у Node.

## Реально прогнані тести

8 сценаріїв (ts-node, справжнє виконання) з заглушкою `iconv-lite` (чесно позначено: заглушка
не перевіряє сам байтовий алгоритм перекодування зрілої сторонньої бібліотеки, тільки
ПРАВИЛЬНІСТЬ ВИБОРУ кодування — той самий підхід, що й у попередніх аудитах цього проекту для
інших сторонніх пакетів):
1. Заголовок `charset=windows-1251` має найвищий пріоритет. **Пройдено.**
2. Синонім `CP1251` нормалізується до `windows-1251`. **Пройдено.**
3. За відсутності заголовка — знаходиться `<meta charset="koi8-u">` у самому HTML. **Пройдено.**
4. За відсутності і заголовка, і мета-тега — фолбек саме на `windows-1251` (задокументований
   дефолт). **Пройдено.**
5. Явний `charset=utf-8` — використовується рідний `Buffer.toString('utf-8')`, **не**
   викликається `iconv-lite` взагалі (швидший шлях для найпоширенішого випадку). **Пройдено.**
6. UTF-8-декодування коректно зберігає реальний кириличний текст (не ламає те, що й так було
   правильним). **Пройдено.**
7. Невідома `iconv-lite` кодування (одруківка в заголовку) — безпечний UTF-8-фолбек, не кидає
   виключення. **Пройдено.**
8. Заголовок має пріоритет над мета-тегом, коли присутні обидва (може статись розбіжність —
   заголовок надійніший, бо йде від сервера напряму). **Пройдено.**

Плюс `tsc --noEmit` по зміненому адаптеру + новій утиліті — 0 помилок.

## Не перевірено / відомі обмеження

- **Сам факт, що `webcam.guru.ua` реально віддає `windows-1251`** — не підтверджено напряму
  (немає мережі в цьому середовищі, щоб перевірити реальний заголовок `Content-Type` чи
  `<meta charset>` сайту) — це обґрунтована, але не 100%-перевірена гіпотеза, побудована на
  вигляді "кракозябрів" зі скріншота (класичний симптом саме цієї помилки) і типовості такого
  вибору для сайтів цього віку/стилю. Якщо кодування сайту виявиться іншим (наприклад koi8-u) —
  заголовок `Content-Type` або мета-тег мають бути виявлені автоматично (пункти 1-2 вище) без
  необхідності знову редагувати код; тільки якщо ОБИДВА способи виявлення нічого не знайдуть,
  спрацює фолбек на `windows-1251`, який тоді буде неправильним для такого гіпотетичного випадку.
- **Сама бібліотека `iconv-lite`** (реальне побайтове декодування) не перевірена виконанням у
  цьому середовищі — покладаємось на її зрілість і широке використання, як і в попередніх
  аудитах для інших сторонніх пакетів цього проекту.
- Реальний повторний прогін на живому сервері — найкраще підтвердження. Якщо кракозябри все ще
  з'являються після цього фіксу — це означатиме, що реальна кодування сайту не виявляється ні
  заголовком, ні мета-тегом (malformed HTML) і не дорівнює `windows-1251` — знадобиться реальний
  HTTP-заголовок `Content-Type` з відповіді сайту (наприклад, через `curl -I` чи вкладку Network
  у DevTools) для точного діагнозу.
