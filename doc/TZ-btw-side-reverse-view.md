# ТЗ: резервный показ side/reverse-ракурсов (SIDE/OPPOSING) в Beyond the Wall

**Статус:** предложение к реализации
**Контекст:** дополнение к doc/BTW-tz.md, основано на уже реализованной геометрии
(`classifyOrientationFit()`, `computeScore()` — см. doc/AUDIT-btw.md)

---

## 1. Проблема

Геометрический каскад `BtwService.scan()` уже находит и ранжирует **все** камеры, чей сектор
обзора пересекает целевую зону — независимо от того, куда именно они смотрят относительно
пользователя. Классификация ракурса (`classifyOrientationFit()`) уже различает три случая:

| Δ азимутов (камера vs пользователь) | Метка | Что реально видно на кадре |
|---|---|---|
| 0–45° | `ALIGNED` | Камера смотрит навстречу пользователю — «взгляд насквозь», та же сцена |
| 45–135° | `SIDE` | Камера смотрит сбоку — смежная, но не совпадающая сцена |
| 135–180° | `OPPOSING` | Камера смотрит В СТОРОНУ пользователя — на кадре может быть виден сам пользователь |

Сейчас все три типа попадают в **единый** ранжированный список (топ-5 по общему score, где
orientation_fit — лишь один из шести компонентов формулы, вес 0.20). Это создаёт две
проблемы:

1. **Размывание core value proposition.** Идея продукта (§1.2 BTW-tz.md) — «мгновенный ответ
   на вопрос, что там, куда я смотрю». SIDE/OPPOSING кадр отвечает на другой вопрос («что
   рядом» / «кто смотрит в мою сторону»), но подмешивается в тот же список без явного
   объяснения контекста — особенно при первом использовании это способно смутить
   («я смотрю туда, а камера показывает что-то другое / саму меня»).
2. **Приватность и доверие.** OPPOSING в буквальном смысле означает «эта камера смотрит на
   тебя». Продукт и так балансирует на грани восприятия «инструмент слежки» (§11 BTW-tz.md,
   §15 «Репутационный удар»). Молчаливое появление такого кадра в общем радаре — риск,
   которого можно избежать простым UX-решением, не трогая саму геометрию/скоринг.

## 2. Предлагаемое решение

Разделить выдачу на два явных уровня вместо одного смешанного списка:

- **Прямой уровень (direct)** — только `ALIGNED`-кандидаты, показываются как сейчас,
  автоматически, без дополнительных действий пользователя.
- **Резервный уровень (fallback)** — `SIDE` и `OPPOSING`-кандидаты, скрыты по умолчанию.
  Появляются **только** при выполнении обоих условий:
  1. `direct` пуст (нет ни одного ALIGNED-кандидата в этом скане);
  2. пользователь **явно** запросил их тапом на отдельный элемент UI.

Никаких изменений в самой геометрии, каскаде фильтров (Ф1→Ф2→Ф3) или формуле скоринга —
только в том, **как** уже посчитанный результат группируется и предъявляется.

## 3. Изменение контракта `/btw/scan`

Текущий ответ:
```ts
{ candidates: RankedCandidate[], debug: {...} }
```

Новый ответ:
```ts
{
  direct: RankedCandidate[],    // только ALIGNED, топ-3
  fallback: RankedCandidate[],  // SIDE + OPPOSING вместе, топ-3, тот же score
  debug: {...}                  // без изменений
}
```

Реализация на сервере — тривиальное разделение уже посчитанного массива `candidates` по
`orientationFit` перед финальной сортировкой/обрезкой, без дополнительных запросов к БД или
Overpass.

## 4. UX-поток на клиенте

1. Пользователь сканирует как обычно. Если `direct.length > 0` — список работает ровно так
   же, как сейчас, кнопка fallback не отображается вообще (нечего предлагать сверх того, что
   уже показано).
2. Если `direct.length === 0 && fallback.length > 0` — под основным списком (пустым)
   появляется явный элемент: «Прямых кандидатов рядом нет — показать боковые/встречные
   ракурсы?» (не автораскрытие, требуется тап).
3. По тапу раскрывается `fallback`-список, где каждая карточка несёт явную метку:
   - `SIDE` → «сбоку — не совпадает с тем, куда вы смотрите»;
   - `OPPOSING` → «встречный ракурс — на этом кадре может быть видны вы сами» (явное
     предупреждение о приватности, не просто нейтральная метка — это единственный случай в
     продукте, где камера потенциально показывает самого пользователя, и это должно быть
     сказано прямо, а не подразумеваться).
4. Если пользователь, уже раскрыв fallback, продолжает вращаться и в кадр каскада попадает
   ALIGNED-кандидат — интерфейс автоматически возвращается к прямому режиму (fallback
   скрывается) с коротким уведомлением «Найден прямой ракурс». Обратного перехода
   (fallback → скрыт → снова показан) без нового тапа не происходит — направление «более
   узкая, точная выдача важнее самого широкого охвата» соответствует духу §1.2 ТЗ.

## 5. Почему именно «только по тапу» и «только при отсутствии direct» — обоснование решения

- **Согласованность с продуктовой философией.** Взгляд = запрос (§1.2 BTW-tz.md). SIDE/
  OPPOSING отвечают на другой вопрос, поэтому не должны быть частью автоматического ответа на
  основной запрос — только явно запрошенным расширением.
- **Снижение риска недоверия.** Explicit opt-in снимает эффект неожиданности («это что, кто-то
  смотрит на меня?») там, где продукт и так уязвим к репутационному риску «инструмент слежки».
  Пользователь сам решает увидеть более слабое соответствие, а не получает его незапрошенным.
- **Экономия внимания, когда есть лучший вариант.** Нет смысла предлагать более слабый (по
  геометрии обзора) ракурс, если прямой уже устраивает пользователя — условие «только при
  отсутствии direct» не даёт интерфейсу разрастись лишними элементами в основном, самом частом
  случае.
- **Нулевая дополнительная стоимость.** Разделение уже посчитанного списка на direct/fallback
  не требует новых запросов к Overpass/AI/БД — реализуется как перегруппировка результата
  внутри `BtwService.scan()`, стоимость реализации минимальна относительно продуктовой пользы.
- **Не меняет уже провалидированную формулу скоринга.** Веса ALIGNED/SIDE/OPPOSING в
  `computeScore()` остаются как есть — меняется только способ ПРЕДЪЯВЛЕНИЯ, не сама оценка
  релевантности кандидата.

## 6. Граничные случаи

| Ситуация | Поведение |
|---|---|
| Нет ни direct, ни fallback кандидатов вообще | Текущее сообщение «Кандидатов не найдено рядом с вами», кнопка fallback не показывается — предлагать нечего |
| Пользователь раскрыл fallback, затем реально повернулся и появился direct | Автоматическое переключение на direct-режим с уведомлением, fallback скрывается |
| В fallback только OPPOSING (ни одного SIDE) | Показывается как есть, с тем же явным предупреждением о приватности на каждой OPPOSING-карточке |
| Повторный скан в той же сессии, снова direct пуст | Кнопка fallback появляется заново (это НЕ разовое состояние на сессию, а per-scan — если ситуация повторилась, предложение должно повториться) |

## 7. Метрики для последующей оценки (дополнение к §13 BTW-tz.md)

- Доля сканов, где `direct` пуст, но `fallback` непуст (насколько часто ситуация вообще
  актуальна — если редко, весь механизм малополезен и это стоит знать заранее).
- Conversion rate: доля таких сканов, где пользователь реально тапнул «показать fallback».
- Влияние на удержание: сравнение lock rate/повторных запусков между пользователями, которые
  видели и не видели fallback-предложение при отсутствии direct-кандидатов — помогает ли это
  удерживать интерес там, где прямого ответа нет, или люди просто закрывают приложение
  независимо от предложения.

## 8. Этапы реализации

| Этап | Содержание |
|---|---|
| **M1** | Серверное разделение `candidates` → `{direct, fallback}` в `BtwService.scan()`, обновление типа `ScanResult` — без изменений в каскаде фильтров/скоринге |
| **M2** | Клиент: кнопка раскрытия, fallback-список с явными метками, обязательное предупреждение о приватности для OPPOSING |
| **M3** | Телеметрия (conversion rate, доля актуальных ситуаций — см. §7) + автопереключение на direct при появлении прямого кандидата |
| **M4 (опционально, по результатам M3)** | Если метрики покажут высокую востребованность — рассмотреть более широкий угол допуска специально для fallback-режима (раз пользователь уже согласился на менее точное соответствие) |
