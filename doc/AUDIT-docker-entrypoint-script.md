# Аудит: автоматический прогон сидов/миграций вынесен в `docker-entrypoint.sh`

## Контекст

По прямому запросу пользователя — сделать так, чтобы под Docker сиды/миграции накатывались
автоматически. Формально это уже было так (см. `doc/AUDIT-parser-no-providers-incident.md`) —
`docker-compose.yml` и раньше запускал всю цепочку на каждый старт контейнера, просто в виде
одной длинной строки `command: sh -c "... && ... && ..."`, куда неудобно добавлять новые шаги
(именно в такую строку и не попал вовремя `camera-providers-seed.sql`, что и привело к
предыдущему инциденту). Этот шаг — не смена поведения, а смена **формы**: тот же набор
действий, но в виде читаемого, расширяемого скрипта с явной обработкой ошибок.

## Что сделано

- **`apps/api/scripts/docker-entrypoint.sh`** (новый файл) — пошаговый POSIX-shell скрипт:
  `prisma generate` → `prisma db push --skip-generate` → все SQL-файлы через функцию
  `run_sql <файл> [optional]`. Обязательные файлы (нет файла → `exit 1`, контейнер не
  стартует) и опциональные (нет файла → пропуск с пометкой в логе, не падает) — явно разделены
  вызовом с флагом, а не молчаливым угадыванием.
- **`apps/api/Dockerfile.dev`** — `ENTRYPOINT ["sh", "scripts/docker-entrypoint.sh"]` +
  `CMD ["npm", "run", "start:dev"]` (сохранена возможность override через `docker-compose.yml`
  `command:`, если понадобится в будущем — сейчас не используется). Скрипт вызывается через
  `sh scripts/...` явно, а не полагается на собственный исполняемый бит файла — тот легко
  теряется при архивировании репозитория в zip и распаковке на другой ОС (особенно Windows),
  либо перекрывается bind-mount'ом `./apps/api:/app` в `docker-compose.yml` (права хоста
  побеждают то, что было проставлено `chmod +x` на этапе сборки образа).
- **`docker-compose.yml`** — гигантская строка `command: sh -c "..."` для сервиса `api` убрана
  целиком; используется `CMD` из `Dockerfile.dev` как есть.
- **`doc/README.md`** — новый подраздел с описанием архитектуры скрипта (обязательные/
  опциональные файлы, как добавить новый сид), обновлена таблица сервисов и ссылка в
  разделе про инцидент с `camera-providers-seed.sql`.

## Реально прогнанные тесты

- **Синтаксис**: `sh -n` и `bash -n` по самому скрипту — 0 ошибок (оба шелла согласны, что
  скрипт синтаксически корректен, скрипт написан на переносимом POSIX `sh`, не bash-специфике).
- **Логика, 3 сценария** (реальное выполнение, с подменённым `npx` — фейковый исполняемый файл
  в `PATH`, который логирует, какие файлы реально были переданы в `--file`, вместо настоящего
  обращения к БД):
  1. Все 6 SQL-файлов присутствуют → все выполнены **в правильном порядке**
     (`geo-migration` → `route-migration` → `cities-seed` → `camera-providers-seed` →
     `cities-seed-neighboring` → `border-crossings-seed`), финальная команда (заглушка
     запуска приложения) выполняется, код возврата `0`. **Пройден.**
  2. Отсутствует опциональный файл (`cities-seed-neighboring.sql`) → пропущен с явным
     сообщением в логе, **все остальные обязательные файлы всё равно выполнены**, приложение
     всё равно запускается, код возврата `0`. **Пройден.**
  3. Отсутствует обязательный файл (`camera-providers-seed.sql`) → скрипт останавливается
     **сразу** с понятной ошибкой, код возврата `1`, **финальная команда (запуск приложения)
     не выполняется вообще** (проверено — маркерная строка "APP STARTED" не появляется в
     выводе). **Пройден.**
- Проверено, что все 6 реальных SQL-файлов действительно присутствуют в
  `apps/api/sql/` — сценарий 1 не гипотетический, соответствует фактическому состоянию репозитория.
- Исполняемый бит на самом файле `docker-entrypoint.sh` в этой песочнице был `rw-r--r--`
  (не исполняемый) сразу после создания — типичное поведение при создании файла инструментом,
  не специфичное для Docker — что и стало прямым практическим подтверждением, почему вызов
  через `sh scripts/...` (не полагаясь на "x"-бит) — правильный выбор, а не излишняя
  перестраховка.

## Не проверено

- Реальный `docker compose up --build` целиком (нет Docker в этой песочнице) — логика
  запускалась изолированно через `sh` с подменённым `npx`, не через настоящий контейнер.
- Поведение bind-mount'а `./apps/api:/app` в реальном Docker (описанное как причина
  использовать `sh scripts/...` вместо прямого исполнения файла) — обоснование основано на
  общеизвестном поведении Docker bind-mounts, не проверено вживую в этой среде.
