# RoadScout — реестр веб-камер городов Украины (и не только, см. "Світова карта")

_Проєкт послідовно перейменовували: LiveAhead → FF → Formula 1 (відхилено через товарний
знак) → **RoadScout** (поточна назва). Історичні документи в `doc/AUDIT-*`/`doc/TZ-*`
можуть містити попередні назви — див. `doc/AUDIT-project-rename-formula1-to-roadscout.md`._

Монорепо: `apps/api` (NestJS + Prisma + PostGIS) и `apps/admin` (Next.js 14 — публичная страница поиска + вся админка).

## Что реализовано (полный объём ТЗ)

- **Парсер** (`src/scraper`) — discovery → geocode → эвристика azimuth → авто-импорт / очередь ревью, лог каждого прохода (`ParserRunLog`). Опциональный прокси ("VPN", `src/scraper/proxy`) для обхода внешних реестров камер — см. раздел ниже.
- **Sector-геометрия** (`src/common/geometry.util.ts`) — haversine/bearing/sector-test, построение fan-полигона, синхронизация с PostGIS-колонкой `fov_polygon`; плюс геометрия маршрута (`routeLength`, `pointAtDistanceAlongRoute`, `nearestPointOnRoute`) для FIXED_ROUTE.
- **Cameras-модуль** — CRUD (`/admin/cameras`), калибровка (`/admin/cameras/:id/calibrate`, переводит камеру в `VERIFIED`), публичный поиск по адресу (`/search?address=...`) и по точке (`/cameras/at-point?lat=&lng=`) с PostGIS-фильтром и JS-фолбэком.
- **FIXED_ROUTE + Look-ahead (главы 16–18)** — камеры на транспорте с известным маршрутом полноправно участвуют в `/search` и `/cameras/at-point`: `src/route-position` (LOOP/TIMETABLE/LIVE_GPS провайдеры позиции + кэш `FixedRoutePositionService` + `DynamicFovBuilder`) и `src/lookahead` (`LookAheadService` — прогноз встречи камеры с точкой/маршрутом пользователя, `POST /lookahead`). Подробности и известные упрощения — ниже.
- **Occlusion (stage 2)** (`src/occlusion`) — best-effort проверка перекрытия зданиями через OSM Overpass + turf.js, включается флагом `?checkOcclusion=true`.
- **Мониторинг** (`src/monitoring`) — HTTP/hash-эвристика статуса (ONLINE/DELAYED/OFFLINE), cron-эндпоинт + дашборд в админке.
- **Providers** — минимальный CRUD источников камер, нужен для формы добавления камеры.
- **Ситуационная осведомленность** (`src/situational`) — карта-вкладка в админке (`/admin/situational`): сводка погоды (дождь/туман/гололёд) по городу и области + ручной учёт ДТП/внештатных ситуаций на дорогах. Подробности — ниже.
- **«Мой дом»** (`src/home-verification`) — авто-верификация адреса проживания по квитанции об оплате жилья с рукописной датой (AI vision + ручной фоллбэк админом), открывает доступ к сектору камер вокруг подтверждённого адреса. Подробности — ниже.
- **Города Украины** (`src/cities`) — справочник `City` (21 областной центр + Київ), поиск/парсер/погода работают по любому из них, не только по Києву. Подробности — ниже.
- **Соседние страны** — приграничные регионы Польщі/Словаччини/Угорщини/Румунії/Молдови (13 городів, `sql/cities-seed-neighboring.sql`) — те же `City`, гео-подсказка геокодингу и погода, без источника камер (пока). Подробности — ниже.
- **Мультиязычность** (`apps/admin/lib/i18n`) — 10 языков (Україна + 5 соседних стран + 4 крупнейших языка ЄС), детект по заголовку `Accept-Language` браузера + ручной выбор (флаги, `<select>`), аналогично atm-travel.org/ОРБІТА. Подробности — ниже.
- **Growth-фичи** — час очікування на кордоні (краудсорс, `src/border-crossings`, `/border`), підписки-алерти в Telegram (`src/alerts`, `/my-alerts`), «Поділитися локацією» (`src/share`, кнопка на `/`), ембед-віджет для сайтів/блогерів (`GET /cameras/:id/embed-info`, `/embed/[id]`), краудсорс «Додати камеру» (`src/camera-submissions`, `/add-camera` + окрема вкладка модерації `/admin/camera-submissions`). Подробности — ниже.
- **Виджет погоды Windy** (`components/WindyWidget.tsx`) — тот же embed-подход, что на atm-travel.org (ОРБИТА), на главной странице и на `/admin/situational`. Подробности — ниже.
- **Фронт:** `/` — публичный поиск с картой; `/admin/cameras` — список/добавление/удаление; `/admin/cameras/:id/calibrate` — калибровочный инструмент (drag-маркер + слайдеры azimuth/FOV/range с live-превью сектора); `/admin/parser` — статистика и лог парсера; `/admin/monitoring` — дашборд статусов.

## Главы 16–18: FIXED_ROUTE и Look-ahead

Камеры с `mobilityType: FIXED_ROUTE` (трамваи, фуникулёр, туристические автобусы и т.п.) участвуют в `/search` и `/cameras/at-point` наравне со `STATIONARY`: их текущая позиция вычисляется на каждый запрос (`RoutePositionProvider` → `LoopProvider` | `TimetableProvider` | `LiveGpsProvider` → `FixedRoutePositionService` с кэшем 5с/3с/1с → `DynamicFovBuilder` → тот же `cameraSeesPoint()`). Если камера не видит точку прямо сейчас, но должна проехать мимо в ближайшие ~20 минут — `LookAheadService` предсказывает встречу (ETA/расстояние/confidence), и такой результат тоже попадает в ответ поиска. Полный ответ отсортирован по ETA → расстояние → confidence (для `STATIONARY` ETA всегда 0, так что сортировка сводится к прежней «по расстоянию»).

Создание FIXED_ROUTE камеры (`POST /admin/cameras`): `mobilityType: "FIXED_ROUTE"`, `routeGeometry: [{lat,lng}, ...]` (мин. 2 точки), `routeMode: "LOOP" | "TIMETABLE" | "LIVE_GPS"`, `averageSpeed` (м/с, для LOOP/TIMETABLE), для `TIMETABLE` — `routeSchedule: { "departures": ["06:20", "06:50", ...] }`. Для `LIVE_GPS` карьер публикует координаты через `POST /internal/fixed-route/:cameraId/live-position` (заголовок `x-live-gps-secret: $LIVE_GPS_SECRET`).

Отдельный `POST /lookahead` (auth: любой Telegram-логин) принимает произвольный маршрут пользователя (`points: [{lat,lng,timestampOffsetSeconds}]`, опционально `cameraIds`) и возвращает предсказанные встречи со всеми FIXED_ROUTE камерами (или только с указанными) — это более общий случай главы 17, отдельно от точечного шортката внутри `/search`.

### Известные упрощения (главы 16–18)

- **Кэш позиций — in-process `Map`, не Redis.** На Vercel serverless это означает отдельный кэш на каждый холодный инстанс (по-прежнему корректно, просто не разделяется между «тёплыми» инстансами). Для роста нагрузки/парка камер — вынести в Redis/Supabase.
- **TIMETABLE не учитывает дни недели/календарные исключения** — `routeSchedule.departures` считается ежедневным расписанием без выходных/праздников.
- **TIMETABLE-расписание читается в локальном времени сервера** (`Date.setHours` использует таймзону процесса Node). На Docker/выделенном сервере это можно зафиксировать через `TZ=Europe/Kyiv`; на Vercel serverless процесс по умолчанию работает в UTC — «06:20» в `departures` будет означать 06:20 UTC, а не Киева, если `TZ` не выставлен явно.
- **LIVE_GPS без реального карьерского фида** — реализован только ingestion-эндпоинт (`POST /internal/fixed-route/:id/live-position`); подключение конкретного стороннего API карьера (опрос или webhook) не входило в объём этого ТЗ.
- **LIVE_GPS деградирует в LOOP-оценку**, если фикс старше 30с или отсутствует — не «зависает» на последней точке, что было бы хуже для предсказания встречи.
- **Confidence — эвристика, не статистическая модель**: `LIVE_GPS` 0.95, `LOOP` 0.85, `TIMETABLE` 0.6, дополнительно понижается при деградации до best-effort оценки.
- **`/lookahead` (маршрут пользователя) прогоняет всех FIXED_ROUTE кандидатов в JS** (сверка `turf`/PostGIS-префильтра по буферу маршрута пользователя не сделана) — приемлемо при текущем масштабе (десятки камер), но потребует push-down в PostGIS при росте парка.
- **`nearestPointOnRoute`** (для азимута/offset по сырому GPS-фиксу) — приближённая проекция на сегмент через отношение расстояний, а не точная перпендикулярная проекция; для городского масштаба (короткие сегменты) отклонение пренебрежимо мало.
- **Admin-панель (Next.js) не получила формы для редактирования `routeGeometry`/`routeSchedule`** — ТЗ описывало только бэкенд/API (главы 16–18 не упоминают UI), поля можно передать через `PATCH /admin/cameras/:id` напрямую (JSON body).
- Отдельная PostGIS-миграция `sql/route-migration.sql` (аналог `geo-migration.sql`) должна быть накачена один раз перед использованием FIXED_ROUTE в проде — как и `fov_polygon`, `route_buffer_polygon`/`route_line` не управляются Prisma-миграциями.

## ⚠️ Важно перед продакшен-деплоем

Авторизация через Telegram теперь есть (см. раздел выше) — но перед реальным запуском обязательно:
- задать `JWT_SECRET` (без него используется небезопасный дефолт с warning в логах при старте);
- выполнить `/setdomain` в `@BotFather` под реальный домен, иначе виджет входа не отрендерится/не будет доверять домену;
- убедиться, что `ADMIN_ORIGIN` в API — конкретный домен фронтенда, а не `*` (браузеры не разрешают `credentials: true` с wildcard origin).

## Авторизация через Telegram

Все данные (публичный поиск и админка) закрыты Telegram Login Widget:

1. Создать бота через `@BotFather`, получить `TELEGRAM_BOT_TOKEN`.
2. Обязательно выполнить `/setdomain` в `@BotFather` и указать реальный домен фронтенда (`localhost` для локальной разработки виджет не примет — тестировать логин локально можно только через туннель типа ngrok с настоящим доменом, либо временно замокать `/api/auth/me`).
3. Узнать свой numeric Telegram ID через `@userinfobot`, добавить его в `ADMIN_TELEGRAM_IDS` (через запятую, если админов несколько).
4. Задать `JWT_SECRET` (`openssl rand -hex 32`).
5. `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` (без `@`) — фронтенду нужен только username бота, токен остаётся исключительно на бэкенде.

Публичная страница (`/`) требует любого валидного входа через Telegram. Админка (`/admin/*`) дополнительно проверяет, что `telegramId` входит в `ADMIN_TELEGRAM_IDS` — список читается из env при каждом запросе, отзыв доступа не требует переизобретения токенов, достаточно поправить переменную и перезапустить API.

Сессия — JWT в httpOnly cookie (`session`), 30 дней. Реальная граница безопасности — на бэкенде (`TelegramAuthGuard`/`AdminGuard`/`BloggerGuard` на каждом эндпоинте); экран логина на фронте — это только UX, а не защита сама по себе.

### Рабочие места и роли

Три "рабочих места" на одном Next.js-фронтенде (`apps/admin`), различаются только гейтом `AuthGate` на бэкенде и уровнем прав:

| Рабочее место     | Роут       | Гейт           | Кто попадает                                             |
|-------------------|------------|----------------|-----------------------------------------------------------|
| Клиентский сайт   | `/`        | `TelegramAuthGuard` | любой залогиненный через Telegram                    |
| Кабинет блогера   | `/blogger` | `BloggerGuard`      | `BLOGGER_TELEGRAM_IDS` (админы тоже пускаются)        |
| Админка           | `/admin/*` | `AdminGuard`        | `ADMIN_TELEGRAM_IDS`                                   |

`/blogger` пока заглушка (см. `apps/admin/app/blogger/page.tsx`) — сама роль/гейт/авто-вход уже работают, инструменты конкретно для блогеров не спроектированы.

### Локальная отладка: авто-вход без Telegram

Реальный Telegram Login Widget не принимает `localhost` (см. пункт 2 выше) — обычно для локального теста логина нужен туннель (ngrok и т.п.) с доменом, привязанным через `@BotFather`. Чтобы не тратить на это время при каждой отладке, есть встроенный обход:

- **`DEV_AUTO_LOGIN=true`** — включает эндпоинты `GET /auth/dev-accounts` / `POST /auth/dev-login` на бэкенде. **Уже включено по умолчанию в `docker-compose.yml`** (переопределить/выключить — `DEV_AUTO_LOGIN=false` в `.env`). Никогда не задавайте `true` в проде (в Vercel эта переменная просто не определена — `vercel.json`/деплой её не выставляют).
- **`DEV_MOCK_ACCOUNTS`** — по одному мок-аккаунту на каждое рабочее место, строка вида `role:telegramId:firstName:lastName:username:photoUrl`, записи разделены `;` (см. дефолт в `docker-compose.yml` и комментарии в `apps/api/src/auth/dev-accounts.util.ts`). Указанный там `telegramId` для роли `admin`/`blogger` автоматически считается допущенным (не нужно отдельно дублировать его в `ADMIN_TELEGRAM_IDS`/`BLOGGER_TELEGRAM_IDS`).

Когда включено, на **любой странице** фронтенда (клиент/блогер/админка) в правом нижнем углу появляется плашка «🛠 Dev: авто-вход» с кнопкой на каждую роль — клик логинит (реальный upsert `TelegramUser` + настоящая session-cookie, как при обычном входе) и перезагружает страницу. Полностью скрыта, если `DEV_AUTO_LOGIN` не включён.

## Надёжность парсера: эвристика азимута, охват всех городов, health-сигнал

См. `doc/TZ-parser-import-improvements.md`, П2.

- **Эвристика азимута** (`AzimuthHeuristicService`) — кэш по сетке ~100м (`AZIMUTH_HEURISTIC_CACHE_TTL_HOURS`, по умолчанию 24ч — соседние камеры на одной улице переиспользуют один результат вместо отдельного запроса к Overpass на каждую), явный клиентский таймаут (`AZIMUTH_HEURISTIC_TIMEOUT_MS`, по умолчанию 8с — раньше `fetch()` не имел ограничения по времени вообще). Источник значения (`azimuthSource: 'heuristic' | 'fallback' | 'manual'`) теперь явно возвращается сервисом и хранится прямо в `Camera.azimuthSource` — видно и в детальном логе, и в самой камере, и агрегированно в статистике `/admin/parser`.
- **Охват всех городов** — `POST /internal/parser/run-all` (и кнопка «Запустить все источники» в админке) обходит **все** `CameraProvider`, не один захардкоженный id; `sql/pg_cron-schedule.sql` обновлён под это. Задержка между источниками — `PARSER_RUN_ALL_DELAY_MS` (по умолчанию 2с), чтобы не долбить внешний сайт параллельно по всем городам разом.
- **Health-сигнал** (`ParserRunLog.anomalyFlag`) — `discoveredCount` прохода сравнивается со скользящим средним последних успешных проходов того же источника (`PARSER_ANOMALY_HISTORY_SIZE`/`PARSER_ANOMALY_MIN_HISTORY`/`PARSER_ANOMALY_THRESHOLD`); резкое отклонение в любую сторону помечается ⚠️ в таблице проходов — обычно значит, что у источника изменилась вёрстка (см. П0.1) или в парсере баг дублирования.

## Dry-run, бюджет времени, история изменений (парсер)

См. `doc/TZ-parser-import-improvements.md`, П3.

- **Dry-run** — кнопка «Dry-run» на `/admin/parser` прогоняет `discover()` источника **без единой
  записи в БД** (ни `CameraSourceRaw`, ни `Camera`, ни `ParserRunLog`, ни `ImportLogEntry`) —
  безопасный способ проверить починку селекторов (см. П0.1), не трогая боевые данные. По
  умолчанию — только список найденного; «Углублённая проверка» дополнительно прогоняет реальный
  геокодинг и показывает, что стало бы `IMPORTED` vs `NEEDS_REVIEW` и почему (стоит реальных
  запросов к геокодингу, поэтому не включена по умолчанию).
- **Бюджет времени на проход** (`PARSER_RUN_TIME_BUDGET_MS`, по умолчанию 25с) — защита от
  таймаута serverless-функции при большом каталоге: если обработка не укладывается в бюджет,
  проход аккуратно останавливается (не обрывается посередине без объяснения), сохраняет то, что
  успел обработать, помечается статусом `PARTIAL` и явно логирует, сколько камер осталось
  необработанными — они будут подхвачены на следующем проходе.
- **История изменений** `CameraSourceRaw` — не отдельная таблица (ТЗ разрешало обойтись без неё,
  раз уже есть детальный лог после П1.2): если у уже известной камеры при повторном проходе
  изменилась ссылка на поток или название, в `ImportLogEntry` пишется `WARN`-запись со старым и
  новым значением в `metadata` — видно на `/admin/parser/log`.

## Очередь ревью парсера

`/admin/parser/review` (см. `doc/TZ-parser-import-improvements.md`, П1.1) — записи
`CameraSourceRaw` со статусом `NEEDS_REVIEW` (нет текста адреса у источника, либо уверенность
геокодинга ниже порога 0.6) теперь не тупик: список + карточка с ручным вводом адреса
(геокодируется так же, как при авто-импорте, с подсказкой города источника) либо координат
напрямую, тип потока, при необходимости — азимут/FOV/дальность. «Создать камеру» проводит
запись тем же путём, что и авто-импорт (`confidence: ESTIMATED`, точная геометрия сектора
доводится потом обычным инструментом калибровки), «Отклонить» — с необязательной причиной.
Ссылка «На ревью: N» в статистике `/admin/parser` теперь ведёт прямо в очередь, отфильтрованную
по этому источнику.

## Детальный журнал импорта

`/admin/parser/log` (отдельная вкладка от агрегированной статистики `/admin/parser`) — см.
`doc/TZ-parser-import-improvements.md`, П1.2. Пошаговый журнал (`ImportLogEntry`): что случилось
с конкретной камерой на конкретном шаге пайплайна (`FETCH_PAGE`/`PARSE_ITEM`/`GEOCODE`/
`AZIMUTH_HEURISTIC`/`CAMERA_CREATED`/`NEEDS_REVIEW`/`SKIPPED_ALREADY_RESOLVED`/`ERROR`), с
уровнем (`INFO`/`WARN`/`ERROR`) и структурированными деталями. В отличие от `ParserRunLog`
(агрегированные числа по проходу целиком), здесь видно причину каждого отдельного решения —
например, почему конкретная камера ушла на ревью, а не была импортирована автоматически.

Ключевой практический эффект: `WebcamGuruAdapter` **явно** пишет `WARN`, если источник не
нашёл ни одной камеры — вместо того чтобы молча вернуть пустой список, неотличимый от "у
источника реально нет камер в этом городе". Именно так и была впервые замечена (и затем
исправлена на основе реальной разметки сайта, см. `doc/AUDIT-webcam-guru-real-html.md`) сама
проблема с селекторами — самая критичная находка аудита парсера (см.
`doc/TZ-parser-import-improvements.md`).

Ретенция — `IMPORT_LOG_RETENTION_DAYS` (по умолчанию 30 дней), автоочистка при каждом новом
проходе (без отдельного cron-задания).

## Прокси ("VPN") для сканирования внешних реестров камер

Портировано из cargo-tracker (`config.ts`/`webshareProxyUrl`, ProxyAgent-обёртка над запросами). Зачем: сайты-каталоги камер (webcam.guru.ua и т.п.) могут ограничивать/банить datacenter-IP хостинга (Vercel/Docker-хоста), особенно при регулярных обходах реестра — прокси с ротацией внешнего IP снижает этот риск.

- **Опционально и обратно совместимо** — если ничего не задано, парсер (`ScraperService`/адаптеры вроде `WebcamGuruAdapter`) сканирует напрямую, как и раньше.
- **Настройка** (`REGISTRY_SCAN_PROXY_URL`, либо `WEBSHARE_PROXY_*`, либо обычный `HTTPS_PROXY`/`HTTP_PROXY`) — см. `.env.example` / `apps/api/.env.example` и `src/scraper/proxy/registry-proxy.util.ts`.
- **Если прокси настроен, но недоступен** ("VPN не подключён") — `RegistryProxyService.request()` автоматически повторяет тот же запрос напрямую вместо падения всего прохода парсера; событие фоллбэка логируется (`this.logger.warn`, видно в логах API / `docker compose logs api`). Ошибки самого целевого сайта (4xx/5xx — значит прокси отработал) фоллбэк не триггерят — это осмысленно, повтор напрямую тут не поможет и теряет смысл использования прокси.
- **Статус для админки** — `GET /admin/parser/proxy-status` (только конфигурация: `configured`/`proxyHost`, без логина/пароля; живой health-check не делается отдельно — реальная доступность видна по факту фоллбэков в логах конкретных прогонов).
- **Известное упрощение**: агент строится один раз лениво на процесс (не переоценивает конфиг на лету) — смена env-переменных требует перезапуска API, как и большинство других настроек этого проекта.

## Ситуационная осведомленность (погода + ДТП)

Карта-вкладка `/admin/situational` в админке (`AdminGuard`, `src/situational`):

- **Погода** (`WeatherService`) — сводка по всем городам из справочника `City` (21 областной центр + Київ, см. раздел «Города Украины» ниже — раньше было захардкожено на Київ+7 райцентрів області, теперь список берётся из БД динамически) через [Open-Meteo](https://open-meteo.com/) (бесплатно, без API-ключа). Точки с "опасными" условиями (туман, гололёд, сильный дождь/снег, гроза) подсвечиваются на карте красным и выводятся отдельным предупреждением наверху страницы. Кэш 10 минут (in-process, как и в `FixedRoutePositionService` — на serverless не общий между холодными инстансами, но каждый инстанс работает корректно). Если справочник `City` пуст (свежая БД до прогона `sql/cities-seed.sql`) — фоллбэк на одну точку (Київ), а не пустой ответ.
- **ДТП/инциденты** (`RoadIncidentsService`, модель `RoadIncident`) — пока только ручной ввод админом: клик по карте (или ручные координаты) → тип (ДТП/перекрытие/подтопление/гололёд/туман локально/ремонт/другое) → серьёзность → заголовок/описание → опционально "актуально до". `GET /admin/situational/overview` отдаёт погоду+активные инциденты одним запросом. Инцидент считается "неактуальным" и пропадает из активного списка либо по кнопке "Решено" (`resolvedAt` проставляется), либо по истечении `expiresAt`, либо через 24 часа без резолва (не удаляется — только не попадает в `listActive()`).
- **Известное упрощение**: нет интеграции с внешним фидом ДТП/дорожной обстановки (Google/HERE/TomTom Traffic Incidents и т.п. — платные API) — это оставлено на будущее; сейчас это внутренний инструмент диспетчера/админа для ручной фиксации, не автоматический скан.

## «Мой дом»: авто-верификация адреса по квитанции

`/my-home` (клиентский сайт) + `/admin/home-verifications` (админка). Идея: обычный поиск (`/search`) открыт всем, но просмотр **сектора камер конкретно вокруг своего адреса** как отдельная функция требует подтверждения, что человек там действительно живёт — иначе это был бы просто ещё один способ следить за чужим домом под видом «это мой адрес».

**Флоу:**
1. Пользователь на `/my-home` вводит адрес и загружает фото квитанции об оплате жилья (коммунальные/аренда), **обязательно с рукописной датой** — от руки, прямо на квитанции или на листе рядом в кадре. Это защита от повторного использования старого скриншота/фото: печатная дата на самой квитанции не считается.
2. `ReceiptVerificationService` отправляет фото в AI vision-модель (xAI/Grok — та же связка, что в cargo-tracker: `XAI_API_KEY`/`XAI_BASE_URL`/`GROK_VISION_MODEL`) с промптом на структурированный JSON: совпадает ли напечатанный на квитанции адрес с заявленным, есть ли **именно рукописная** и **свежая** (по умолчанию ≤3 дней, `HOME_VERIFICATION_STRICT_DATE=false` → ≤14 дней) дата, похожа ли квитанция на подлинник.
3. Авто-одобрение — только если **все** проверки прошли (адрес совпадает с уверенностью ≥70%, рукописная дата свежая, квитанция не выглядит подделкой). Если AI-провайдер не настроен, запрос упал, ответ не распарсился, или хоть одна проверка не прошла — заявка уходит на `NEEDS_REVIEW` для ручного решения администратором в `/admin/home-verifications` (там же видно само фото квитанции — единственное место, где оно вообще отдаётся по API). **Авто-отклонения не существует** — только авто-одобрение или ручное решение, чтобы алгоритмическая ошибка никогда не блокировала человека без возможности разобраться.
4. После `APPROVED` — `GET /home/sector` отдаёт тот же формат результата, что и обычный поиск (`CamerasService.findAtPoint`), но по координатам подтверждённого адреса.

**Для администраторов квитанция не требуется** — Telegram-аккаунт уже в `ADMIN_TELEGRAM_IDS`/`DEV_MOCK_ACCOUNTS` (см. `getAdminTelegramIds()`), это само по себе достаточное подтверждение личности. На `/my-home` для админа поле файла становится необязательным; если файл не приложен, `HomeVerificationService.submit()` создаёт заявку сразу со статусом `APPROVED` и `adminExempt: true`, **не вызывая ни object storage, ни AI-провайдера вообще** (`receiptImageUrl: null`). Если админ всё же приложил фото (например, чтобы вручную проверить сам AI-пайплайн) — заявка идёт по обычному пути наравне с любым пользователем, `adminExempt` остаётся `false`. В `/admin/home-verifications` такие заявки помечены бейджем «Админ», а карточка заявки показывает пояснение вместо фото.

**Известные упрощения:**
- Лимит файла — 4 МБ (с запасом под потолок тела запроса на Vercel Hobby, ~4.5 МБ) — на медленной сети/большом фото может понадобиться сжатие на стороне клиента, которого сейчас нет.
- Один незавершённый (`PENDING`/`NEEDS_REVIEW`) запрос на пользователя одновременно — новая заявка блокируется до решения по предыдущей; после `REJECTED`/`APPROVED` переотправка разрешена в любой момент (например, при переезде).
- Точное имя vision-модели (`GROK_VISION_MODEL`, по умолчанию `grok-4`) стоит сверить с актуальной документацией xAI перед продакшеном.
- Квитанции обычно содержат чувствительные данные (ФИО, адрес, иногда лицевой счёт) — фото не логируется целиком, отдаётся только под `AdminGuard`, и админ-список (`GET /admin/home-verifications`) не подгружает изображения массово (они запрашиваются по одной штуке при открытии конкретной заявки).

**Object storage (Vercel Blob):** фото квитанций загружаются в Vercel Blob с публичным доступом по прямой ссылке (`BLOB_READ_WRITE_TOKEN`, `receipt-storage.service.ts`) — "публичный" здесь значит "без авторизации по ссылке со случайным суффиксом", а не "проиндексировано где-либо"; ссылка нигде не публикуется, кроме ответов `AdminGuard`-эндпоинтов. Без токена (например, локально без привязки к Vercel-проекту) сервис прозрачно откатывается на прежнее поведение — `data:`-URL прямо в БД; при сбое самой загрузки (сеть/квота/неверный токен) — тот же откат, с логом. Известное упрощение: публичный Blob — не то же самое, что приватный бакет с временными подписанными URL; для более строгой защиты потенциально чувствительных документов это следующий шаг.

**Калибровка порога уверенности:** `HOME_VERIFICATION_MIN_CONFIDENCE` (по умолчанию `0.7`) вынесен в env, чтобы подстраивать без редеплоя. `GET /admin/home-verifications/stats` (виден на странице `/admin/home-verifications`) показывает распределение `addressMatchConfidence` по итоговому статусу (одобрено/отклонено/на ревью) по бакетам — если ниже порога много ручных одобрений, порог, вероятно, завышен; если выше порога много отклонений — занижен.

**Rate-limiting по IP:** не более `HOME_VERIFICATION_RATE_LIMIT_MAX` (по умолчанию 3) заявок за `HOME_VERIFICATION_RATE_LIMIT_WINDOW_HOURS` (по умолчанию 24) часов с одного IP — проверяется в БД (переживает холодные старты serverless, в отличие от in-process кэша), до дорогих шагов (загрузка в Blob, вызов AI), чтобы спам не жёг ни хранилище, ни платный AI-запрос. IP берётся из `x-forwarded-for` (реальный клиент за прокси Vercel/большинства хостингов) с фоллбэком на `req.socket.remoteAddress`. Известное упрощение: заявки без определённого IP (`null`, например локальная разработка без прокси перед Nest) не лимитируются вовсе — не боевой сценарий.

## Города Украины

Изначально проект был жёстко привязан к Києву (гео-подсказка «, Киев, Украина» на каждый запрос геокодинга, один парсер на `webcam.guru.ua/kiev`, погода только по Києву и области). Теперь всё это — данные, а не хардкод:

- **`City`** (`prisma/schema.prisma`) — справочник городов: `name`/`slug`/`lat`/`lng`/`region`/`countryCode`/`countryName` + опционально `webcamGuruSlug` (сегмент пути на webcam.guru.ua, например `lvov` для Львова, только для `countryCode: "UA"`). Засеян через `sql/cities-seed.sql` (21 областной центр + Київ — идемпотентно, `ON CONFLICT DO NOTHING`, можно гонять повторно; заодно проставляет `cityId = 'city_kyiv'` всем старым камерам без города). `countryCode` по умолчанию `"UA"` — обратная совместимость со всеми городами, заведёнными до появления соседних стран (см. ниже).
- **Геокодинг** (`GeocodingService.geocode(text, cityHint?)`) — без подсказки уходит как `"<адрес>, Україна"` (хуже disambiguation для частых названий улиц вроде «вулиця Шевченка», но по-прежнему работает); с `cityHint` — добавляет имя города **и страну** (`cityHint.countryName`, с фоллбэком на встроенную таблицу `COUNTRY_NAME_BY_CODE` по `countryCode`, если `countryName` не задан/`null`) в строку запроса, плюс `location`+`radius`/`region` bias для Google Geocoding API (не жёсткое ограничение, только смещение ранжирования кандидатов).
- **Парсер** (`WebcamGuruAdapter`) — один экземпляр адаптера обслуживает один город: `citySlug` передаётся в конструктор, URL каталога — `webcam.guru.ua/city/{citySlug}/`. Одна строка `CameraProvider` = один город (`CameraProvider.cityId` → `City.webcamGuruSlug`); `ScraperService.resolveAdapter()` матчит по префиксу `adapterKey` (`webcam-guru*`) и явно падает с понятной ошибкой, если у провайдера нет привязанного города или у города не задан `webcamGuruSlug`. Реальная структура сайта (подтверждена реальным HTML, см. `doc/AUDIT-webcam-guru-real-html.md`) — двухфазная: `discover()` отдаёт только список `{название, ссылка на камеру}` (быстро, один запрос), `streamUrl` дозапрашивается отдельно по одной камере за раз через `ProviderAdapter.fetchDetails()` — **внутри цикла обработки элементов** (`PARSER_DETAIL_FETCH_DELAY_MS` — пауза между этими дозапросами), а не одним блоком до возврата результата из `discover()` (так было в первой версии фикса — см. тот же аудит-файл о том, к чему это привело на реальном прогоне: 50 камер найдено, 0 обработано, весь бюджет времени ушёл внутрь `discover()`). Страницы сайта запрашиваются как raw-байты и декодируются с реально определённой кодировкой (`decodeHtmlBuffer()`, см. `doc/AUDIT-webcam-guru-encoding.md`) — по умолчанию axios/Node трактуют ответ как UTF-8, что дало "кракозябры" на живом сайте (реально другая кодировка, скорее всего windows-1251).
- **Поиск** (`/search`, `/cameras/at-point`) — необязательный `cityId` в query сужает кандидатов до одного города (PostGIS raw-запрос — через `Prisma.sql`/`Prisma.empty` условный фрагмент `AND "cityId" = ...`; JS-фолбэк — обычный `where: { cityId }`). Без `cityId` ищет по всем городам сразу.
- **Фронт** — выпадающий список городов на `/` подтягивается с `GET /cities` (не хардкодится), по умолчанию выбран Київ, если есть в списке.

**Известные упрощения:**
- `webcamGuruSlug` сверен по факту существующего парсера только для Києва (`kiev`) и Львова (`lvov`); для остальных 19 городов в сиде — предположение по образцу URL, **обязательно проверить реальный слаг вручную** перед включением парсера для нового города (иначе `WebcamGuruAdapter` просто не найдёт карточек на несуществующей странице).
- Список из 21 города — все областные центры кроме Чернівців (Буковина) и городов, где парсер/поиск сейчас неприменимы по понятным причинам (оккупированные территории/прифронтовая зона) — не исчерпывающий, но покрывает подавляющее большинство пользователей.
- Ручное создание камеры через админку (`/admin/cameras`) пока не имеет выпадающего списка City в форме — `cityId` можно проставить через `PATCH`-запрос напрямую; камеры, импортированные парсером, город получают автоматически.

## Соседние страны

Приграничные регионы стран, ближних к Украине — Польща/Словаччина/Угорщина/Румунія/Молдова — добавлены как обычные строки `City` с `countryCode`/`countryName` (см. `sql/cities-seed-neighboring.sql`, отдельный файл от основного украинского сида — необязательное расширение, можно не прогонять, если не нужно). 13 городов:

| Страна | Города |
|---|---|
| Польща (PL) | Перемишль, Жешув, Люблін, Хелм |
| Словаччина (SK) | Кошице, Михайлівці |
| Угорщина (HU) | Ніредьгаза, Захонь |
| Румунія (RO) | Сучава, Сігету-Мармацієй |
| Молдова (MD) | Кишинів, Бєльці, Отачі |

Что это даёт: (1) геокодинг адресов в этих регионах с правильной страновой подсказкой вместо ошибочного «Україна» (см. `CityHint.countryCode`/`countryName` в `GeocodingService`), (2) погода в ситуационной осведомленности (`WeatherService` берёт список городов из `City` целиком, страна значения не имеет), (3) пункты в выпадающем списке городов на `/` (сгруппированы по стране через `<optgroup>`, Україна всегда первой).

**Известные упрощения:**
- **У этих городов нет источника камер** — `webcamGuruSlug` всегда `NULL` (webcam.guru.ua — украинский сайт, эти регионы им не покрыты). Поиск камер по такому городу корректно вернёт пустой список (не ошибку) — фронт показывает отдельное честное сообщение об этом, а не «реестр пополняется» (которое подразумевало бы, что камеры там вообще предполагаются).
- Список из 13 городов — по 2–4 на страну, ближайшие к границе с Україною (не столицы, кроме Кишинева — Молдова маленькая и Кишинев сам по себе приграничный по меркам страны). Не исчерпывающий список.
- `region` (воєводство/край/медьє/повіт/район) указан не для всех — например, у Кишинева/Бєльців осознанно `NULL` (в Молдове нет прямого аналога областного деления в этом контексте).

## Виджет погоды Windy

Тот же подход, что на atm-travel.org (ОРБИТА): публичный embed-виджет `embed.windy.com/embed2.html` — обычный `<iframe>`, без API-ключа и без бэкенд-интеграции (`components/WindyWidget.tsx`). Слои: дождь/ветер/облачность/температура/радар осадков, переключаются кнопками прямо в виджете. Используется в двух местах:
- На `/` — центрирован на результат поиска (если он есть) или на выбранный город.
- На `/admin/situational` — центрирован на всю Украину (радар осадков по умолчанию), рядом со сводкой погоды из `WeatherService`/Open-Meteo (см. раздел «Ситуационная осведомленность» выше) — это разные, дополняющие друг друга источники: Windy — визуальная карта слоёв в реальном времени, `WeatherService` — структурированные числовые данные (для авто-детекции «опасно» по опорным точкам).

**Известное упрощение:** публичный embed-виджет Windy не требует ключа, но и не даёт программного доступа к данным (это просто картинка в iframe) — для структурированных данных погоды (нужны, например, для авто-детекции опасных условий) используется отдельно `WeatherService`/Open-Meteo, а не Windy.

## Мультиязычность

Публичный сайт (`/`, `/my-home`, экран входа) — на 10 языках, аналогично atm-travel.org/ОРБІТА: детект по заголовку `Accept-Language` браузера + ручной выбор через выпадающий список с флагами. Админка (`/admin/*`) и кабинет блогера (`/blogger`) остаются на русском — это внутренние инструменты для сотрудников, не публичная часть.

- **Языки**: Українська (за замовчуванням) 🇺🇦, English 🇬🇧, Polski 🇵🇱, Slovenčina 🇸🇰, Magyar 🇭🇺, Română 🇷🇴, Deutsch 🇩🇪, Français 🇫🇷, Español 🇪🇸, Italiano 🇮🇹. Выбор именно этих 10 — Україна + 5 приграничных стран (уже поддержаны в справочнике `City`, см. «Соседние страны» выше) + 4 крупнейших языка ЄС для решта аудиторії (діаспора/туристи/новинний інтерес).
- **Словари** (`apps/admin/lib/i18n/dictionaries/*.ts`) — по одному файлу на язык, все реализуют один и тот же `Dictionary` TS-интерфейс (`dictionary.types.ts`). Это не просто соглашение — если в каком-то языке не хватает ключа (или есть лишний/опечатка в имени), `tsc`/сборка Next.js упадёт с ошибкой прямо на этом файле. Полнота словарей — гарантия компилятора, а не обещание в комментарии.
- **Детект языка** (`lib/i18n/detect.ts`) — парсинг реального HTTP-заголовка `Accept-Language` запроса на сервере (`app/layout.tsx`, через `next/headers`), а не `navigator.language` на клиенте — так первый рендер сразу на правильном языке, без "мигания" дефолтным перед гидратацией. Если ни один язык из заголовка не входит в поддерживаемые 10 — фоллбэк на Українську.
- **Ручной выбор** (`components/LanguageSelector.tsx`) — обычный `<select>` с флагами-эмодзи (не кастомный dropdown — доступность из коробки, работает с клавиатуры/скринридерами без лишнего кода). Выбор сохраняется в cookie `liveahead_lang` (365 дней) — при следующем визите сервер увидит cookie и отрендерит сразу на выбранном языке, даже если он отличается от Accept-Language браузера.
- **`useI18n()`** (`components/I18nProvider.tsx`) — React-контекст с `t(key, params?)`; `params` подставляются в строки вида `{distance}`/`{direction}` через простую замену `{key}` → значение (без ICU-плюрализации — она не нужна: единственные варьируемые числа в словарях — расстояния/минуты, у них везде одна форма во всех 10 языках).

**Известные упрощения:**
- Переведён только публичный контур (`/`, `/my-home`, экран входа/AuthGate, кнопка выхода) — админка, блогерский кабинет, ситуационная осведомленность остаются на русском (внутренние инструменты, не часть многоязычного публичного сайта).
- Нет ICU-плюрализации (`1 камера` / `2 камеры` / `5 камер`) — везде используется одна нейтральная форма ("камер: 5"), это заметно на восточнославянских языках (только Українська из 10 здесь) сильнее, чем на остальных 9.
- Переключение языка через `<select>` не требует подтверждения/перезагрузки страницы — реактивно обновляет весь текст сразу через контекст, но НЕ меняет URL (нет `/en/...`-префиксов маршрутов) — сознательный выбор ради минимального риска для остальной части сессии (не пришлось переносить все существующие роуты под `app/[locale]/...`).

## Growth-фичи

П'ять функцій, орієнтованих на органічне зростання аудиторії (не тільки поліпшення того, що вже є) — див. попереднє обговорення в чаті/пораду щодо "breaking features".

### Час очікування на кордоні

`/border` — краудсорс: будь-хто, хто щойно проїхав перехід, вказує напрямок (з України / в Україну) і скільки хвилин простояв. Оцінка (`GET /border-crossings`) — просте усереднення звітів за останні `BORDER_WAIT_ESTIMATE_WINDOW_HOURS` годин (за замовчуванням 3), окремо по кожному напрямку — **не офіційні дані митниці/прикордонслужби** (відкритого API з такими даними немає). Засіяно 7 реальних переходів (UA-PL/SK/HU/RO/MD, `sql/border-crossings-seed.sql`), прив'язки до `City` немає навмисно (перехід лежить "між" двома містами різних країн). Rate-limit по IP (`BORDER_REPORT_RATE_LIMIT_MAX`/`_WINDOW_HOURS`) — той самий патерн, що й у «Мій дім».

### Підписки-алерти

`/my-alerts` — підписка на (1) зміну статусу конкретної камери (кнопка «🔔 Стежити» прямо в результатах пошуку) або (2) нові активні інциденти в радіусі точки (форма на `/my-alerts`, з опцією "використати моє місцезнаходження"). Доставка — через Telegram Bot API `sendMessage` (`TelegramNotifierService`, той самий `TELEGRAM_BOT_TOKEN`, що й для логіна — окремого не треба). **Важливе обмеження Telegram API**: бот може писати користувачу, тільки якщо той хоч раз натиснув `/start` цьому боту — інакше `sendMessage` поверне 403, і сповіщення просто не дійде (без явної помилки для користувача в цій версії).

Перевірка умов — не live-тригер у момент події, а окремий тик `POST /internal/alerts/check` (той самий `CronSecretGuard`, що й у парсера/моніторингу), запланований у `sql/pg_cron-schedule.sql` кожні 5 хвилин. Тобто затримка сповіщення — до 5 хвилин, не миттєво.

### Поділитися локацією

Кнопка «🔗 Поділитися» на сторінці пошуку — створює короткий слаг (8 символів, алфавіт без 0/O/1/I/l, щоб було легше продиктувати) через `POST /share`, посилання виду `/s/AbC12xYz` копіюється в буфер автоматично. Перехід за посиланням (`GET /share/:slug`, без авторизації — сама точка не чутливіша за звичайний пошук) резолвить координати і редиректить на `/` з готовою точкою (без повторного геокодингу тексту адреси — напряму через `/cameras/at-point`). Лічильник переглядів (`viewCount`) — метрика, не контроль доступу; посилання не одноразове і без TTL у цій версії.

### Ембед-віджет

`GET /cameras/:id/embed-info` — публічний (без авторизації, як і має бути для вбудовування на чужому сайті) ендпоінт, що віддає тільки те, що й так видно на самій трансляції (назва/посилання/тип потоку/статус). Кнопка «`</> Embed`» у результатах пошуку показує готовий `<iframe>`-код на `/embed/[id]`. **Відоме обмеження**: реально відтворити в `<iframe>` можна тільки джерела типу `IFRAME`/`YOUTUBE_LIVE` (вони й так призначені для показу в чужому фреймі); для `HLS`/`MJPEG_SNAPSHOT` потрібен окремий плеєр (наприклад hls.js), якого в цій версії немає — замість відео показується назва камери й пряме посилання.

### Краудсорс «Додати камеру»

`/add-camera` — будь-який залогінений користувач (клієнт чи блогер, окремої ролі не потрібно) кидає посилання на публічну вебкамеру; заявка йде в чергу модерації (`/admin/camera-submissions`, окрема вкладка в адмінці), а не одразу в реєстр. `approve()` створює справжню `Camera` одразу зі стандартною геометрією (azimuth=0/fovAngle=90/rangeMeters=300, confidence: ESTIMATED) — точний сектор огляду адмін доводить потім уже існуючим інструментом калібрування (`/admin/cameras/:id/calibrate`), не в цій формі. Провайдер-заглушка «Краудсорс» для таких камер створюється лениво при першому approve() (не потребує окремого sql-сида).

**Спільне для всіх п'яти**: rate-limiting по IP скрізь, де є ризик спаму (звіти про чергу, заявки камер), той самий `getClientIp()`/`assertIpRateLimit()` з `common/` (винесено з `home-verification` для перевикористання). Усі п'ять фіч, включно зі сторінками-призначеннями (`/border`, `/my-alerts`, `/add-camera`), а також вкладка модерації `/admin/camera-submissions` — тепер повністю перекладені на всі 10 мов (перевірено компілятором на повноту словників, див. `doc/AUDIT-i18n-destination-pages.md`). `/embed/[id]` і `/s/[slug]` залишаються без перекладу навмисно — це технічні сторінки (публічний ембед і редирект шер-лінка), не частина мультимовного UX сторінки пошуку.

## Известные упрощения (документированы в коде)

- Occlusion не кэшируется (ТЗ предполагал кэш по паре camera+geohash) — каждый вызов с `checkOcclusion=true` бьёт в Overpass заново.
- Мониторинг IFRAME/HLS/YOUTUBE_LIVE — только проверка доступности источника (HEAD-запрос), не проверяет, что поток реально играет.
- Азимут-эвристика парсера и occlusion используют публичный Overpass API — под нагрузкой может рейт-лимитить, для прод-объёмов стоит поднять свой инстанс Overpass или закэшировать OSM-данные локально.

## Камери всередині приміщень

Перший реальний приклад — камера Введенського храму (Київ): показує інтер'єр, не вулицю.
`Camera.locationType: OUTDOOR | INDOOR` (дефолт `OUTDOOR` для сумісності зі старими записами).
Для `INDOOR`-камер `fovAngle`/`azimuth`/`rangeMeters` не мають фізичного сенсу (немає
«напрямку огляду вулиці», який можна перетнути з адресою) — сектор (`fov_polygon`) свідомо не
будується. `CamerasService.findCandidatesNearPoint()` виключає такі камери з пошуку за адресою
(і в PostGIS-запиті, і в JS-фолбеку) через явний фільтр `locationType = 'OUTDOOR'`. Замість
цього — `findIndoorNearby(point, radius, cityId)`: проста перевірка за прямою відстанню
(`INDOOR_CAMERA_NEARBY_RADIUS_METERS`, за замовчуванням 500м), результат — окреме поле
`indoorNearby` у відповіді `/search`/`/cameras/at-point` («також поруч»). Тип камери можна
задати/змінити в трьох місцях: інструмент калібрування (`/admin/cameras/:id/calibrate`),
черга ревʼю парсера (`/admin/parser/review`), черга краудсорс-заявок (`/admin/camera-submissions`).

## AI-автоматизація додавання камер (Grok)

`GrokCameraAssistService` (`src/common/`) — той самий провайдер (xAI/Grok), що й для «Мій дім»
(`XAI_API_KEY`/`GROK_API_KEY`, окрема модель `GROK_TEXT_MODEL` для текстових, не vision-запитів).
`suggestAddressAndType(title, rawLocationText, cityName)` пропонує адресу за назвою камери,
**координати напряму зі своїх знань** (`suggestedLat`/`suggestedLng`/`coordinatesConfidence` —
окремо від геокодингу тексту, корисно саме коли геокодер не може розпізнати навіть хороший
текстовий адрес — реальний приклад: «завод "Енергія", Київ»), і класифікує «всередині
приміщення чи ні». Безпечний фолбек при недоступності AI (ніколи не кидає виключення).

**Важливо: AI викликається ВИКЛЮЧНО за запитом адміна на етапі ручного ревʼю** — кнопка
«🤖 Спросить AI» на `/admin/parser/review` і `/admin/camera-submissions`
(`POST .../ai-suggest`). **AI НЕ викликається автоматично** ні в парсері
(`ScraperService.processItem()`), ні при подачі краудсорс-заявки — раніше було навпаки
(автовиклик на кожну камеру без адреси), але на практиці більшість все одно йшло на ревью (див.
`doc/AUDIT-ai-assist-manual-review-only.md`), витрачаючи виклики API без реальної користі й
сповільнюючи автоматичний прогін. Підказка показується адміну, який сам вирішує, застосувати її
до форми (адресу, координати, тип камери) чи ні — `resolveSourceRaw()`/
`CameraSubmissionsService.approve()` приймають `lat`/`lng` напряму, тож AI-координати можна
використати навіть якщо звичайний геокодинг тексту не спрацював.

**Два незалежні джерела координат** (див. запит користувача: «AI helper для получения широты/
долготы, возможно через google maps») — «Спросить AI» тепер одночасно (`Promise.all`) запитує:
1. `GrokCameraAssistService` — здогадка за назвою камери зі знань LLM (може чесно не знати
   конкретний орієнтир серед кількох схожих — реальний приклад: «Пішохідний міст» без уточнення,
   якого саме моста серед декількох існуючих).
2. `GeocodingService.searchPlace()` — **реальний пошук через Google Places API (Text Search)**,
   той самий ключ `GOOGLE_GEOCODING_API_KEY` (потрібно додатково включити Places API на тому ж
   проекті Google Cloud). На відміну від звичайного `geocode()` (Geocoding API, очікує
   структуровану адресу), Places шукає по реальній базі орієнтирів/POI Google Maps — саме там,
   де LLM може помилятися чи чесно не знати, Places найчастіше знаходить точний збіг.

Обидва результати показані окремо в адмінці з власними кнопками «Использовать» — адмін бачить
розбіжність (якщо є) і сам обирає, якому джерелу довіряти, а не отримує один змішаний результат.

## Nominatim (OpenStreetMap) — безкоштовне джерело координат без ключа

`GeocodingService.searchPlaceOSM()` — третє джерело координат, **без жодного API-ключа
взагалі** (працює навіть якщо `GOOGLE_GEOCODING_API_KEY` порожній). На відміну від Grok і
Google Places (обидва — тільки за кнопкою «Спросить AI», коштують запитів/квоти), Nominatim
запитується **автоматично при відкритті картки** в чергах ревʼю (`/admin/parser/review`,
`/admin/camera-submissions`) — показується першим, ще до того, як адмін встиг би натиснути
будь-яку кнопку.

Публічний інстанс `nominatim.openstreetmap.org` має жорстку політику використання: максимум 1
запит/сек і обов'язковий описовий `User-Agent`. Оскільки виклик відбувається лише коли
конкретний адмін відкриває конкретний елемент вручну (не масово), `GeocodingService` додатково
підстраховує це явним троттлінгом на рівні інстанса сервіса (мінімум 1000мс між послідовними
запитами, незалежно від того, як швидко адмін гортає чергу).

## Видалення камери + автоматична перевірка доступності контенту (окремо від парсера)

За прямим запитом користувача (реальний привід — саме те недоступне YouTube-відео з попередніх
розділів): (1) кнопка «Удалить камеру» на екрані калібрування; (2) по можливості автоматично
дизейблити такі камери, контрольовано через ІІ, **свідомо окремо від парсера/автоімпорту**
(«не хватит времени у парсера»).

- **Видалення** — просто підключена вже існуюча `DELETE /admin/cameras/:id` (уже була в
  контролері) до кнопки на екрані калібрування, з підтвердженням через `confirm()`.
- **`GrokCameraAssistService.checkStreamAvailability()`** — двошарова перевірка для
  YouTube-камер: (1) **YouTube oEmbed** (`youtube.com/oembed`) — безкоштовний, детермінований,
  без ключа; 401/404 означає «відео видалено/приватне/недоступне» (саме той реальний сценарій);
  (2) **Grok vision-резерв** на мініатюрі відео, коли oEmbed недоступний з мережевої причини —
  не замінює oEmbed, а доповнює.
- **Автоматичний фоновий прохід** — `MonitoringService.checkContentAvailability()`, **новий,
  окремий метод у вже існуючому сервісі моніторингу** (не в `ScraperService`!), з власним,
  набагато рідшим cron-розкладом (`camera-content-availability-daily`, раз на добу — не 5-15хв,
  як швидкий `checkAll()`). Той самий принцип бюджету часу й акуратної зупинки, що вже є в
  парсері (П3.2) — якщо камер багато, прохід зупиняється й логує, скільки лишилось, замість
  необ'яснюваного обриву. Автоматично переводить `Camera.status` в `OFFLINE`, якщо контент
  підтверджено недоступний — `DISABLED_SECURITY` (ручний оверрайд власника) ніколи не чіпається.
- **Кнопка на екрані калібрування** («🤖 Проверить доступность видео (ИИ)») — той самий
  механізм за запитом, для перевірки конкретної камери негайно, не чекаючи наступного проходу.

## Soft delete камер по всьому проєкту + масове «Удалить нерабочие»

За прямим запитом користувача: **видалення камер по всьому проєкту тепер м'яке (soft
delete)** — `CamerasService.remove()` не видаляє запис фізично, а проставляє
`Camera.deletedAt`. Причини: (1) `CameraSourceRaw.cameraId`/`CameraSubmission.createdCameraId`
досі посилаються на цю камеру — фізичне видалення або впало б на FK-обмеженні, або залишило б
биті посилання; (2) можливість «відновити» видалену камеру в майбутньому.

**Систематично перевірено й оновлено 16 місць запитів камер у 7 файлах бекенда** (детальний
список — `doc/AUDIT-camera-soft-delete.md`): списки (`findAll`), пошук за сектором (і
PostGIS-запит, і JS-фолбек), індор-пошук поблизу, обидва цикли моніторингу, look-ahead-
прогнози, лічильники статистики парсера — усі тепер фільтрують `deletedAt: null`. Публічний
`/cameras/:id/embed-info` явно віддає 404 для видаленої камери. Підписки на алерти (`alerts`)
трактують м'яко видалену камеру так само, як фізично відсутню — не падають, просто перестають
спрацьовувати.

`findOne()` (пряме звернення за id — калібрування, AI-підказки, перевірка доступності)
навмисно НЕ фільтрує по `deletedAt` — адмінські дії за прямим посиланням мають працювати навіть
для вже видаленої камери (наприклад, для майбутньої функції «відновити»).

**Кнопка «Удалить нерабочие (N)»** над списком камер (`/admin/cameras`) — масовий soft delete
усіх активних камер зі статусом `OFFLINE` одразу (`POST /admin/cameras/delete-offline`, новий
метод `CamerasService.removeAllOffline()`) — той самий статус, який автоматично проставляє
перевірка доступності контенту вище. `DISABLED_SECURITY` (ручний оверрайд власника) і вже
видалені камери цією кнопкою не чіпаються.

## Batch API xAI для фонових Grok-викликів (`AggregatorDiscoveryService`)

⚠️ **Оновлення за прямим запитом користувача**: розширено й на групову калібровку камер
(`CamerasService.submitCalibrationBatch()`/`processPendingCalibrationBatches()`) — свідомий,
додатковий шлях поруч із синхронною `autoCalibrateBatch()` (та лишається без змін). При
відкритті `/admin/cameras` і `/admin/aggregator-sites` сторінка автоматично перевіряє стан
УСІХ ще не оброблених пакетів і оновлює таблицю, тільки якщо щось реально завершилось. Див.
`doc/AUDIT-grok-batch-api.md`, розділ "Оновлення" — там же найчесніше застереження: точний
формат мультимодального (текст+зображення) запиту всередині Batch API не підтверджений
офіційним прикладом документації, лише обґрунтованим припущенням за аналогією зі звичайним
vision-викликом.


За прямим запитом користувача — асинхронний шлях для економії бюджету (знижка 20-50% за
документацією xAI), застосований **тільки** до пошуку сайтів-агрегаторів
(`AggregatorDiscoveryService`), який і так уже виконується вночі за розкладом, без залежності
від негайного результату. **Свідомо НЕ застосовано** до авто-калібрування камер (там результат
потрібен за секунди, а Batch API — типово до 24 годин, best-effort — фундаментально
несумісно з інтерактивністю) і до пошуку окремих камер/релевантності (там результат потрібен
одразу всередині синхронного циклу `ScraperService.processItem()`).

Новий `GrokBatchJob` (модель БД) відстежує подані пакети; `submitBatchDiscovery()` подає всі
міста одним пакетом і повертається одразу; окремий cron (щогодини) —
`processPendingBatches()` — перевіряє готовність і створює `AggregatorSiteCandidate`, коли
результати з'являються (дедуплікація за URL діє і МІЖ синхронним, і batch-шляхами). Кнопка
«🕐 Пакетный запрос (дешевле)» на `/admin/aggregator-sites` поруч із існуючим синхронним
пошуком. Див. `doc/AUDIT-grok-batch-api.md` — там же чесно зазначено, що структура ендпоінтів
звірена лише з документацією, без реального виклику (немає мережі в пісочниці).

## Автокалібрування пачками по 10 (`/admin/cameras`)

За прямим запитом користувача — кнопка «🤖 Автокалибровка (10 камер)». Обирає до 10 камер зі
статусом `ESTIMATED` (ніколи не чіпає вже `VERIFIED`), пробує AI-калібрування кожної
(`GrokCameraAssistService.suggestAzimuthFov()`, той самий метод, що вже є на екрані
калібрування, зі звіркою поточного сектора). **При впевненості 100% і наявності всіх трьох
значень (азимут/FOV/дальність) одразу — координати сектора записуються в базу.** Новий
`Camera.lastAutoCalibrationAttemptAt` — гарантує, що повторні запуски рухаються по всьому
реєстру (спершу ніколи не пробувані камери), а не застрягають нескінченно на тих самих
кількох, де AI щоразу невпевнений.

⚠️ **Свідоме архітектурне рішення**: навіть при 100% впевненості AI камера лишається
`ESTIMATED`, НЕ автоматично промотується у `VERIFIED` — цей статус у всьому проєкті означає
саме людську перевірку вручну, а власна впевненість AI — не те саме. Записуються лише
координати сектора. Див. `doc/AUDIT-auto-calibrate-batch.md`.

## Батчування Overpass-запитів (до 20 точок за один запит)

За прямим запитом користувача — глибша переробка, реалізована ПІСЛЯ явного попередження про
ризик і збереження точки відновлення (`/home/claude/restore-points/`, включно з повним
знімком проєкту `roadscout-before-overpass-batching.zip`). Новий
`AzimuthHeuristicService.guessForPoints()` **прогріває той самий кеш по сітці координат**, яким
`guessForPoint()` уже користується — виклик усередині `ScraperService.processItem()` лишився
без жодної зміни, просто частіше отримує кеш-хіт. До 20 координат об'єднуються в ОДИН
Overpass-запит (`OVERPASS_BATCH_SIZE`, за замовчуванням 20); результат (спільний,
недедуплікований список доріг) кореляційно розподіляється по точках за реальною відстанню (у
межах 60м) — надійніше за попередню логіку одноточкового запиту (яка просто брала перший
елемент масиву). Реально виміряно: 25 координат → 2 запити замість 25. Стосується лише
адаптерів без `fetchDetails()` (NYC TMC, Windy, YouTube). Див.
`doc/AUDIT-overpass-batching.md` — там же чесно зазначено, що реальна поведінка живого
Overpass API з груповими запитами по 20 точок не перевірялась (немає мережі в пісочниці).

## Продуктивність парсера — конкурентна обробка для адаптерів без fetchDetails()

За прямим запитом користувача (реальний привід — NYC TMC працював дуже повільно, ~40-100+
днів на повний імпорт ~900+ камер). Причина — `AzimuthHeuristicService.guessForPoint()`
робить живий запит до Overpass API на КОЖНУ камеру, а обробка йшла строго послідовно.
Виправлення: цикл у `ScraperService.runForProvider()` обробляє елементи пачками через
`Promise.all()` — **конкурентність = 1 (без змін) для адаптерів із `fetchDetails()`**
(webcam-guru й подібні — ввічливість до сайту-джерела зберігається), **конкурентність =
`PARSER_ITEM_CONCURRENCY` (за замовчуванням 8) для адаптерів без цієї фази** (NYC TMC, Windy,
YouTube-пошук — єдиний per-item мережевий виклик тут — сторонній Overpass, не сайт-джерело).
Реально виміряний виграш у тестах — ~6.5x. Див. `doc/AUDIT-nyctmc-performance.md`.

## Фільтр камер по країні + дабл-клік пошук сайтів-агрегаторів по країні

За прямим запитом користувача:

- **`/admin/aggregator-sites`** — дабл-клік по комірці «Страна» запускає пошук сайтів-

## Windy Webcams API + клас камер «природа/пляж/море» (NATURE)

За прямим запитом користувача: реальна, структурована база камер через Windy Webcams API
(`WindyWebcamsAdapter`) — доповнення до текстового пошуку (YouTube/Google), заміна
webcam.guru.ua для не-українських міст. **Категорії Windy дають ДЕТЕРМІНОВАНУ (не AI-угадану)
класифікацію** — камера з категорією `beach`/`sea`/`nature` тощо одразу створюється як новий
клас `CameraLocationType.NATURE`, без потреби у виклику AI. Новий
`RawCameraItem.suggestedLocationType` — загальний механізм, яким будь-який майбутній адаптер
зі структурованими даними може передати тип напряму, обходячи AI-класифікацію.

NATURE-камери, за тим самим принципом, що INDOOR: **автоматично виключені з пошуку за
сектором** (жодних змін логіки пошуку не знадобилось — вже існуючий фільтр `locationType =
'OUTDOOR'` — allowlist, не denylist, тому новий клас відсікається сам собою), але лишаються
видимими «поруч» через нову `findNatureNearby()`. AI-класифікація (Grok, для інших джерел)
розширена новим полем `isLikelyNature`. Окремий cron-розклад/ендпоінти — той самий принцип
взаємного виключення, розширений на четверте сімейство адаптерів.

⚠️ Точні назви полів відповіді Windy API звірені лише з публічною документацією
(`https://api.windy.com/webcams/docs`), без реального тестового виклику (немає мережі в
пісочниці) — перед продакшеном варто звірити один живий виклик. Див.
`doc/AUDIT-windy-webcams-and-nature-cameras.md`.

## NYC DOT Traffic Cameras (NycTmcAdapter) — перший у списку парсерів

Реальний, безкоштовний публічний API без ключа (`webcams.nyctmc.org/api/cameras`), знайдений
і підтверджений користувачем напряму. Єдиний глобальний провайдер (`adapterKey: nyctmc`, не
по місту) — один виклик повертає ВСІ камери Нью-Йорка (сотні записів) з готовими
координатами. **Обходить геокодинг тексту повністю** — нове поле
`RawCameraItem.suggestedLat/suggestedLng` дозволяє будь-якому адаптеру зі структурованими
даними передати точні координати напряму, `ScraperService.processItem()` використовує їх
замість виклику `GeocodingService.geocode()`. `streamType: MJPEG_SNAPSHOT` (прямий JPEG-
знімок, оновлюється що ~2с) — перший реальний адаптер, що використовує це значення enum.

Без ключа/квоти — **не виключений** із загального `run-all()` (на відміну від YouTube/Google/
Windy), працює на тому самому частому розкладі, що webcam.guru.ua.

**«Перший у списку парсерів»** — забезпечено двома шляхами: (1) сід
(`sql/nyctmc-provider-seed.sql`) підключений першим у `docker-entrypoint.sh`; (2) новий
`CameraProvider.createdAt` (явно встановлений на штучно ранню дату `2000-01-01` саме для цього
сіда — це гарантує порядок надійніше, ніж покладатися на порядок вставки рядків) +
`orderBy: { createdAt: 'asc' }` у запиті, що живить список на `/admin/parser`.

⚠️ Структура ендпоінтів звірена з незалежними технічними джерелами (блог-пост про скрапінг
цього самого API + відкритий репозиторій з реальним прикладом відповіді), не з офіційною
документацією NYC DOT (публічно її не веде) — перед продакшеном варто перевірити один живий
виклик. Див. `doc/AUDIT-nyctmc-adapter.md`.

## Пошук через Google (окремо камер, окремо сайтів-агрегаторів)

За прямим запитом користувача — два нові, окремі джерела камер, з VPN там, де це технічно
застосовно. **Важливо**: офіційний Google Custom Search JSON API **закритий для нових
клієнтів з 2025 року** — замінено вбудованим `web_search` tool xAI/Grok (`/v1/responses`,
той самий ключ, що вже є в проєкті). Сам пошук виконується на серверах xAI, тому VPN
(`RegistryProxyService`) до цього кроку не застосовний — VPN використовується окремо, там, де
наш сервер сам відвідує знайдені сторінки. Див. `doc/AUDIT-google-web-search-cameras.md`.

- **`GoogleWebCameraSearchAdapter`** — окремі камери, той самий двофазний принцип, що
  webcam.guru.ua: `discover()` знаходить сторінки через Grok web_search, `fetchDetails()`
  (наш сервер, VPN застосовний) відвідує сторінку й витягує реальний iframe/YouTube/HLS URL
  з HTML.
- **`AggregatorDiscoveryService`** — сайти-каталоги (не окремі камери) — окрема, ще рідша
  автоматика (раз на 3 дні), результати в новій вкладці адмінки `/admin/aggregator-sites`
  (таблиця URL/місто/орієнтовна кількість камер). Оцінка кількості — зі сніпета пошуку або
  реальним відвідуванням сайту через VPN (кнопка «Уточнить»).
- Взаємне виключення cron-розкладів розширено на три сімейства адаптерів одразу
  (`webcam-guru-*`/`youtube-search-*`/`web-search-*`) — жоден провайдер не тригериться
  більше ніж одним job'ом.

## Реальний найденний інцидент: битая ссылка на поток ломала embed-виджет

Реальный случай (см. `doc/AUDIT-embed-bare-url-fix.md`): камера "Шулявка реконструкція" получила
`streamUrl: "https://www.youtube.com/"` (голая главная страница YouTube, не ссылка на
конкретное видео) — попала в базу через ручное резолвление в очереди ревью, где форма всегда
открывалась с жёстко закодированным `streamType: 'IFRAME'` по умолчанию, независимо от реальной
ссылки. Итог: `/embed/[id]` пытался вставить главную страницу YouTube в `<iframe>` — та
отвечает `X-Frame-Options: sameorigin` (в отличие от настоящих embed/watch-ссылок) и
блокирует показ, пользователь виджета видел пустой прямоугольник без объяснения.

Виправлено в двох місцях:
- **`/embed/[id]`** — новая проверка `looksEmbeddable()`: голый корень домена (путь `/` или
  пусто, без query/hash) считается НЕ встраиваемым независимо от `streamType` — вместо попытки
  показать битый iframe, пользователь видит понятное сообщение и прямую ссылку.
- **Формы `/admin/parser/review` и `/admin/camera-submissions`** — `streamType` теперь
  угадывается по самой ссылке при открытии карточки (`youtube.com`/`youtu.be` → `YOUTUBE_LIVE`,
  иначе `IFRAME`), а не жёстко `'IFRAME'` — резко снижает шанс повторения той же ошибки.
- **Инструмент калибровки** (`/admin/cameras/:id/calibrate`) — `streamUrl`/`streamType` теперь
  редактируемы прямо там (раньше это можно было исправить только напрямую в БД) — уже
  существующие камеры с такой же проблемой можно поправить без доступа к базе.
- **Превью на экране калибровки** (реальный найденный follow-up инцидент — см.
  `doc/AUDIT-embed-bare-url-fix.md`, раздел "Оновлення") — раньше превью грузилось через
  `<iframe src="/embed/{id}">`, отдельный запрос к серверу за СОХРАНЁННЫМ состоянием камеры, а
  не тем, что админ только что ввёл в поле выше. Правишь `streamUrl` в форме — превью
  продолжает показывать старую ссылку и ту же ошибку, пока не нажмёшь "Сохранить", что вводит в
  заблуждение, будто фикс не сработал. Теперь превью рендерится напрямую из ТЕКУЩЕГО
  (несохранённого) состояния формы — общая логика `canEmbedStream()`/`looksEmbeddable()`
  вынесена в `apps/admin/lib/embeddable.ts`, используется и здесь, и в `/embed/[id]`, чтобы не
  разойтись при будущих правках.

## Автокалибровка (ИИ) азимута/FOV + превью трансляции на экране калибровки

`/admin/cameras/:id/calibrate` — два дополнения по прямому запросу пользователя:

- **Небольшой iframe-превью трансляции** прямо на экране калибровки (переиспользует уже
  существующий публичный ембед-виджет `/embed/[id]`, не дублирует логику определения типа
  потока) — видно кадр и сектор на карте одновременно, без открытия трансляции в отдельной
  вкладке.
- **Кнопка «🤖 Автокалибровка (ИИ)»** — `GrokCameraAssistService.suggestAzimuthFov()`
  анализирует реальный кадр трансляции (vision-модель, тот же `GROK_VISION_MODEL`, что уже
  используется в «Мой дом») и предлагает азимут/FOV. **Честное ограничение**: получить кадр
  автоматически можно только для `YOUTUBE_LIVE` со ссылкой на конкретное видео/эфир (публичная
  превью-картинка `img.youtube.com`, без ключа) — для ссылки на канал целиком (реальный случай,
  см. `doc/AUDIT-webcam-guru-real-html.md`) или других типов потока (`IFRAME`/`HLS`/
  `MJPEG_SNAPSHOT`) кадр не захватывается (нужен headless-браузер, которого в проекте нет) —
  сервис честно отвечает «недоступно», не гадает. Даже когда кадр доступен, определение
  компасного азимута по одному изображению — принципиально приблизительная задача для
  vision-модели (нет GPS/компас-оверлея), результат — только подсказка для сверки с картой и
  реальной трансляцией, не готовое значение для слепого применения.

## Beyond the Wall (BTW) — новый Telegram Mini App на общем реестре камер

Отдельный мини-апп `apps/btw/` (порт 3002) — за прямым запросом пользователя, полное ТЗ в
`doc/BTW-tz.md`. Идея: пользователь наводит телефон вокруг себя, приложение показывает, в
каких направлениях есть публичная камера, чей обзор покрывает то, что скрыто препятствием на
линии взгляда. Использует **ту же таблицу `Camera`**, что и RoadScout (не отдельный реестр) —
`WHERE confidence = 'VERIFIED'`.

Реализовано ядро: геометрический движок (целевая зона, угловой допуск, конус без окклюзии,
скоринг — все с реальными юнит-тестами), серверный API (`/btw/scan`, `/btw/thumb`, `/btw/lock`
со всеми проверками — зона запрета, антисталкинг, радиус камеры), MVP-клиент со сканированием.
**Честно НЕ реализовано** (см. `doc/AUDIT-btw.md` для полного списка и обоснования): PMTiles-
пайплайн и клиентский Web Worker (сканирование идёт через серверный фолбек), фильтры компаса
У2-У5, размытие лиц/номеров (критично для публичного релиза — см. аудит), монетизация,
модерация. Оценка полного ТЗ — 11-12 недель одним разработчиком (§14 ТЗ); за один шаг сделано
функциональное ядро, не вся система.

## Локальная разработка (Docker Compose)

```bash
cp .env.example .env   # при желании подставить реальный GOOGLE_GEOCODING_API_KEY
docker compose up --build
```

Поднимаются:

| Сервис    | URL                          | Назначение                              |
|-----------|------------------------------|------------------------------------------|
| `postgres`| localhost:5432               | БД (liveahead/liveahead/liveahead)             |
| `adminer` | http://localhost:8081        | Просмотр БД в браузере                   |
| `api`     | http://localhost:3000         | NestJS API (схема + все SQL-сиды/миграции применяются автоматически при старте — см. `apps/api/scripts/docker-entrypoint.sh`) |

По умолчанию в этом Docker-окружении включён `DEV_AUTO_LOGIN` (см. «Локальная отладка: авто-вход без Telegram» выше) — можно сразу открыть http://localhost:3001/, http://localhost:3001/blogger или http://localhost:3001/admin/cameras и войти одной кнопкой в правом нижнем углу, без настоящего Telegram-бота.

### Автоматический прогон схемы и сидов (`apps/api/scripts/docker-entrypoint.sh`)

На каждый старт контейнера `api` (не только первый) автоматически прогоняется, по порядку: `prisma generate` → `prisma db push` → все SQL-файлы из `apps/api/sql/` (миграции PostGIS, затем сиды данных — города, провайдеры камер, приграничные страны, переходы). Раньше это была одна длинная строка `command: sh -c "... && ... && ..."` прямо в `docker-compose.yml` — переехало в отдельный читаемый скрипт (см. `doc/AUDIT-parser-no-providers-incident.md` о том, к чему приводило неудобство добавления нового сида в такую строку).

Два важных свойства скрипта:
- **Обязательные файлы** (`geo-migration.sql`, `route-migration.sql`, `cities-seed.sql`, `camera-providers-seed.sql`, `border-crossings-seed.sql`) — если такого файла нет, контейнер **не запустится** (явная ошибка вместо тихого недосчёта данных, как в инциденте с отсутствовавшим `camera-providers-seed.sql`).
- **Опциональные файлы** (сейчас только `cities-seed-neighboring.sql`) — если файла нет, пропускается молча, без падения.

Добавить новый сид — одна строка `run_sql sql/новый-файл.sql` в скрипте (опционально — с `true` вторым аргументом, если он необязателен), без правки `docker-compose.yml`.

### Известная проблема: "Could not parse schema engine response" / OpenSSL

Если в логах `api` видно `prisma:warn Prisma failed to detect the libssl/openssl version...` и следом `Error: Could not parse schema engine response: SyntaxError: Unexpected token 'E', "Error load"... is not valid JSON` — это классическая несовместимость Prisma с Alpine/musl (движок schema-engine падает при старте из-за отсутствующей/неверной версии libssl, а его сообщение об ошибке само не является JSON, из-за чего Prisma спотыкается на парсинге). Уже исправлено (см. `apps/api/Dockerfile.dev` — теперь `node:20-slim`/Debian вместо `node:20-alpine`, плюс явные `binaryTargets` в `schema.prisma`), но если ловите эту ошибку после обновления:

```bash
docker compose down -v   # ОБЯЗАТЕЛЬНО с -v — без этого old api_node_modules volume переживёт пересборку
docker compose up --build
```

Без `-v` именованный volume `api_node_modules` (переживает `--build`) может по-прежнему содержать старый Prisma-клиент, сгенерированный под Alpine/musl ещё до этого исправления — пересборка образа сама по себе это не починит.

### Известная проблема: `TypeError: (0, cookie_parser_1.default) is not a function`

Падение на первой строке `bootstrap()` в `main.ts`, при этом TS-компиляция перед этим отчитывается `Found 0 errors` — реальный (уже исправленный) баг конфигурации: `apps/api/tsconfig.json` не имел `esModuleInterop: true` (только `allowSyntheticDefaultImports`, который влияет лишь на тайп-чекинг, не на генерацию JS), из-за чего ES-style `import cookieParser from 'cookie-parser'` компилировался в код, обращающийся к несуществующему `.default` на CommonJS-экспорте. Исправлено — `esModuleInterop: true` в `tsconfig.json` + сам импорт в `main.ts` переписан на `import cookieParser = require('cookie-parser')` (TS-нативный синтаксис для `export =`-модулей, не зависит от interop-угадывания вообще). Подробности и как это было подтверждено — `doc/AUDIT-cookie-parser-fix.md`. Если ловите эту ошибку на версии кода, где это уже исправлено — то же самое: `docker compose down -v && docker compose up --build` (старый скомпилированный dist/закэшированный volume может маскировать исправление).

### Известная проблема: «Импорт не находит камер вообще» / `/admin/parser` и `run-all` полностью пустые

Если статистика и лог запусков на `/admin/parser` полностью пустые (не «0 найдено» по каждому источнику, а вообще без единой строки), а `POST /admin/parser/run-all` возвращает `[]` — это не баг парсера/селекторов (см. `doc/TZ-parser-import-improvements.md`, П0.1), а **отсутствие самих `CameraProvider` в базе**: `sql/cities-seed.sql` заполняет `City.webcamGuruSlug`, но до этого исправления **ни один SQL-скрипт в проекте не создавал строки `CameraProvider`** — парсеру физически нечего было обходить. Исправлено — `sql/camera-providers-seed.sql` (создаёт по одному `CameraProvider` на каждый `City` с непустым `webcamGuruSlug` — сейчас это Київ/Львів/Харків/Одеса/Дніпро), прогоняется автоматически при каждом старте контейнера через `apps/api/scripts/docker-entrypoint.sh` (см. раздел выше) как обязательный файл. Подробности — `doc/AUDIT-parser-no-providers-incident.md`. Если ловите эту проблему на версии кода, где сид уже добавлен — прогоните его вручную (см. «Полезные команды» ниже) или пересоздайте volume: `docker compose down -v && docker compose up --build`.

### Известная проблема: `api` уходит в бесконечный цикл рестарта на `prisma db push` («Error: Use the --accept-data-loss flag»)

Реальный инцидент — см. `doc/AUDIT-postgis-unsupported-fields.md`. Если в логах `docker compose logs api` виден повторяющийся цикл «Применение схемы к базе (prisma db push)... → Error: Use the --accept-data-loss flag... → Генерация Prisma Client... → снова db push...» — это означало, что `Camera.fov_polygon`/`route_buffer_polygon`/`route_line` (сырые PostGIS-колонки, управляются только через `sql/geo-migration.sql`/`sql/route-migration.sql`) не были объявлены в `schema.prisma` вообще, из-за чего `db push` на каждый запуск пытался их удалить — молча, пока данных не было, и с явной остановкой, как только в `fov_polygon` накопились реальные значения. Исправлено — эти три колонки объявлены через `Unsupported("geometry(...)")` в модели `Camera`, что говорит Prisma «эта колонка существует навмеренно, не трогай её при `db push`». **Не** используйте `--accept-data-loss` как обходной путь — это тихо снесло бы сектора обзора у всех уже импортированных камер. Если ловите эту проблему на версии кода, где фикс уже есть — просто `docker compose restart api` (volume с БД трогать не нужно, все существующие камеры останутся нетронутыми).

### Полезные команды внутри контейнеров

```bash
# Прогнать парсер вручную для конкретного провайдера (CameraProvider уже создаются автоматически
# через sql/camera-providers-seed.sql — см. /admin/parser за списком id провайдеров)
docker compose exec api npx prisma studio          # GUI для Prisma-моделей
docker compose exec postgres psql -U liveahead        # psql-консоль

# Создать провайдера вручную (пока нет отдельного CRUD-эндпоинта)
docker compose exec postgres psql -U liveahead -c \
  "insert into \"CameraProvider\" (id, name, \"baseUrl\", \"adapterKey\") \
   values ('webcam-guru-1', 'webcam.guru.ua', 'https://webcam.guru.ua', 'webcam-guru');"

# Запустить парсер руками через admin API
curl -X POST http://localhost:3000/admin/parser/run/webcam-guru-1
```

## Продакшен

- **API + admin** деплоятся на Vercel (см. `AUDIT-vercel-hobby.md` — важные оговорки перед первым деплоем).
- **БД** — Supabase Postgres, `DATABASE_URL` через PgBouncer-пулер (порт 6543), `DIRECT_URL` — прямое подключение (порт 5432) для миграций. Перед первым деплоем один раз накатить схему (`npx prisma db push` локально с `DIRECT_URL`, указывающим на Supabase) и выполнить `apps/api/sql/geo-migration.sql` в SQL Editor Supabase (включает PostGIS и добавляет `fov_polygon`), а если используются FIXED_ROUTE камеры — ещё и `apps/api/sql/route-migration.sql` (`route_line`/`route_buffer_polygon`), и `apps/api/sql/cities-seed.sql` (справочник городов Украины — без него поиск/погода будут работать только по адресам без городской подсказки и с фоллбэком на один Київ в ситуационной осведомленности), **и `apps/api/sql/camera-providers-seed.sql` (ОБЯЗАТЕЛЬНО, не опционально — без него парсер физически не имеет ни одного источника для обхода, `/admin/parser` и `run-all` будут молча работать с пустым списком провайдеров, см. `doc/AUDIT-parser-no-providers-incident.md`)**, и опционально `apps/api/sql/cities-seed-neighboring.sql` (приграничные регионы соседних стран, см. раздел «Соседние страны» — можно пропустить, если не нужно).
- **Планировщик** — Supabase `pg_cron` + `pg_net`, дергает `POST /internal/parser/run/:providerId` по расписанию (см. `sql/pg_cron-schedule.sql`). Встроенный Vercel Cron не используется — на Hobby-плане он ограничен одним запуском в сутки и предназначен для другого сценария.
