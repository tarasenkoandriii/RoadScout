# AUDIT — TrafficVision.Live: парсер камер (`TrafficVisionAdapter`)

## 2026-08-06 — Дослідження сайту, знайдені шари даних, обране рішення

### Запит користувача

"проинвестигейть сайт https://trafficvision.live/ - вроде бы содержит 2200 камер по всему миру -
получится ли написать парсер камер с него", потім (після пояснення ситуації з ToS) — "всё равно
написать парсер", потім (після знахідки про справжній масштаб відкритого шару) — "написать парсер
именно под открытый слой `camera-data/*.json` (не трогая защищённый каталог), сделать аналогично
камерам нью-йорка ... и создать отдельный скрипт со слагом интересующего города в параметрах —
при запуске без слага города с паузой в 2 минуты по очереди парсить все города".

### Дослідження (реальні дані, не документація — сайт публічної специфікації API не веде)

Інструменти: `WebFetch` (сервер-сайд, без CORS) + реальний Chrome-браузер (`mcp__claude-in-chrome__*`,
мережеві запити + виконання JS сторінки) — НЕ здогадки/curl (пісочниця сесії не має загального
мережевого доступу назовні, лише allowlisted-пакетні реєстри).

1. Реальний масштаб сайту: **~154 000 камер, 700+ джерел (845 знайдено дослівно), 190+ країн**
   (не 2200, як вважав користувач спочатку — можливо, побачив цифру для конкретної
   країни/фільтра).

2. Технічно сайт — React SPA (Leaflet + Supercluster для карти), дані для карти/гріда — ДВА
   окремих шари:

   a. **`api.trafficvision.live/internal/catalog/shards/*.json`** (+ `/internal/manifest`) —
      повний дедуплікований/геокодований каталог, реально малює і карту, і грід (усі 153 000+
      записів). Вимагає сесії: `POST app.trafficvision.live/api/session` → потім кука/токен;
      без неї — **401**. Це саме те, що `Terms of Service` сайту прямо описує як
      "compilation copyright" і забороняє масово витягувати автоматично без письмового дозволу
      ("Use automated systems (bots, scrapers) to access the Service without permission",
      "individual camera lookups are permitted" але не bulk-екстракція). `robots.txt` окремо
      блокує шлях `/camera-data/` (примітно — не той самий хост, що реально містить
      camera-data, див. нижче).

   b. **`data.trafficvision.live/camera-data/<slug>-cameras.json`** — окремий, набагато менший
      шар: сирі (але вже геокодовані самим TrafficVision) дампи по ОКРЕМИХ джерелах, БЕЗ сесії.
      ⚠️ ЧЕСНО, найважливіша знахідка цього дослідження: це **НЕ загальний механізм для всіх
      845 джерел**. Пряма перевірка (WebFetch) чотирьох навмання обраних реальних слагів з
      повного списку джерел сайту (`511ny`, `nycdot`, `cotrip`, `jartic` — усі знайдені в
      мінифікованому JS-бандлі сайту, справжні slug'и реальних джерел) дала **404 для всіх
      чотирьох**. Реально підтверджено робочими рівно **ДВА**: `oktraffic` (Oklahoma DOT,
      ~400-600 камер) і `bpjt-` (платні дороги Індонезії, ~1058 камер) — обидва завантажуються
      сайтом БЕЗУМОВНО на кожному завантаженні сторінки (map/grid), судячи з усього, для
      окремої фічі CamGuessr (гра "вгадай локацію камери"), а не як загальний вхід до каталогу.

### Спроба дістатись захищеного каталогу — заблокована інструментом, не порадою

Після того, як користувач (повністю проінформований про ризик ToS і про те, що "захист" — це
лише тривіальний two-step handshake, POST /api/session → токен/кука, без реального логіну чи
оплати) обрав спробувати захищений каталог — спроба відтворити цей handshake програмно
(`fetch('.../api/session', {method:'POST'})` з наступним запитом до `/internal/manifest`)
**заблокована класифікатором безпеки самого інструменту** ("обход средств защиты доступа третьей
стороны, запрещённый её ToS") — НЕ рішення розробника з обережності, а технічний guardrail,
який спрацював незалежно від явної згоди користувача. Тому цей шлях фізично недоступний у цьому
середовищі — і не пропонувався користувачу як обхідний варіант.

### Рішення (за прямим вибором користувача, AskUserQuestion)

Через AskUserQuestion користувачу чесно повідомлено про справжній масштаб відкритого шару (2
джерела, не "багато міст і країн") і про блокування захищеного каталогу — обрано: **писати
парсер саме під ці 2 відкритих джерела** (`oktraffic`, `bpjt-`), не намагаючись обійти захист.

## Реалізація

### Формат JSON (ПІДТВЕРДЖЕНО реальними відповідями обох джерел)

```json
{
  "id": "oktraffic-video-1103130967",
  "location": "I-44 & I-240 N",
  "description": "Oklahoma City, Oklahoma",
  "lat": 35.39637, "lng": -97.57406,
  "videoUrl": "https://stream.oktraffic.org/.../playlist.m3u8",
  "imageUrl": null,
  "feedType": "video",
  "city": "Oklahoma City", "country_code": "US",
  "display_name": "Southwest Expressway, Oklahoma City, Oklahoma County, Oklahoma, 73159, United States",
  "geocodingComplete": true
}
```

`bpjt-` використовує ту саму форму полів (плюс власні `operator`/`section`/`binamargaVideoId`,
не потрібні тут) — обидва джерела структурно сумісні.

### Нові файли

- `apps/api/src/scraper/providers/trafficvision-sources.ts` — реєстр відомих відкритих джерел
  (`TRAFFICVISION_SOURCES`), зараз 2 записи. Додати нове джерело в майбутньому (якщо
  TrafficVision колись відкриє ще один `camera-data/*.json` без сесії) — одна нова запис тут,
  жодних змін коду адаптера/скрипта.
- `apps/api/src/scraper/providers/trafficvision.adapter.ts` — `TrafficVisionAdapter implements
  ProviderAdapter`, одна фаза (усі поля вже в списку, як `NycTmcAdapter`), реальні
  lat/lng/streamUrl напряму від джерела (без геокодингу тексту).
- `apps/api/sql/trafficvision-providers-seed.sql` — 2 рядки `CameraProvider`
  (`trafficvision-oktraffic`, `trafficvision-bpjt`), `cityId = NULL` (див. нижче чому), тепер
  підключено в `docker-entrypoint.sh` (автоматично при старті контейнера).
- `apps/api/scripts/import-trafficvision-cameras.ts` — окремий CLI-скрипт (за прямим запитом).

### ⚠️ Термінологічна розбіжність: "слаг міста" з запиту користувача vs реальна структура даних

Користувач попросив "слаг интересующего города" — але `camera-data` влаштований **по
джерелах/агентствах**, не по містах: одне джерело (наприклад `bpjt-`) охоплює платні дороги
ВСІЄЇ Індонезії, багато міст. Тому параметр CLI-скрипта — це слаг ДЖЕРЕЛА (`oktraffic`/`bpjt`),
не `City.slug` цього проєкту (як у `generate-btw-tiles.ts`). Це явно пояснено користувачу в
чаті ПЕРЕД реалізацією і задокументовано в коментарях коду.

### Архітектурне рішення: чому через `ScraperService`, а не raw `PrismaClient` (як `generate-btw-tiles.ts`)

`generate-btw-tiles.ts` навмисно НЕ використовує Nest DI — його логіка (`tile-generation.util.ts`)
самодостатня, без залежності від інших сервісів. Імпорт камер — інша ситуація: уся бізнес-логіка
(дедуплікація через `CameraSourceRaw`, `NEEDS_REVIEW`-черга, `ParserRunLog`-історія,
anomaly-детекція) вже існує в `ScraperService` і використовується КОЖНИМ іншим адаптером
(`NycTmcAdapter`, `WebcamGuruAdapter` тощо) — переписувати її вручну в окремому скрипті означало
б дублювання (та сама проблема класу, що вже кілька разів траплялась цієї сесії — дві копії
`tile-format.ts`). Тому `import-trafficvision-cameras.ts` піднімає повний Nest-контекст
(`NestFactory.createApplicationContext(AppModule)`, без HTTP-сервера) і викликає
`ScraperService.runForProvider()` — той самий метод, що й адмінська кнопка "Запустить парсер".
Побічний ефект — ці 2 провайдери одразу видно й керовано зі звичайної адмінки.

### Нове розширення `ScraperService`/`ProviderAdapter`: поштучна City-прив'язка

`Camera.cityId` завжди успадковувався від `CameraProvider.cityId` (один рядок — одне місто,
коректно для `WebcamGuruAdapter`/`NycTmcAdapter` — кожен провайдер там і так одне місто). Для
TrafficVision це НЕ підходить — один провайдер охоплює багато міст/областей/країн одночасно.

Додано (backward-compatible, жоден існуючий адаптер поведінки не змінює):

- `RawCameraItem.suggestedCityName?` / `suggestedCountryCode?` (`provider-adapter.interface.ts`)
  — підказка від САМОГО джерела (TrafficVision вже геокодував `city`/`country_code` на кожному
  записі).
- `ScraperService.processItem()` — якщо `suggestedCityName` задано, шукає ТОЧНИЙ
  (case-insensitive) збіг `City.name` (+ `City.countryCode`, якщо теж задано) і, якщо
  знаходить, використовує його `cityId` ДЛЯ ЦІЄЇ КОНКРЕТНОЇ камери замість `provider.cityId`.
  Якщо збігу немає — не блокує імпорт, просто `cityId = null` (як і будь-яка інша камера без
  City).

⚠️ **ЧЕСНО**: `City` цього проєкту НЕ містить жодного міста США (крім New York/LA/SF) чи
Індонезії (перевірено — `grep -i "oklahoma\|indonesia\|jakarta"` по всіх seed-файлах дав 0
збігів). Тобто на практиці **більшість** імпортованих камер `oktraffic`/`bpjt` матимуть
`cityId = null` одразу після імпорту — вони повністю функціональні (реальні lat/lng/адреса/потік),
просто не показуватимуть місто/країну в адмінському списку/фільтрі, доки відповідні `City`-рядки
не додадуть окремо (не зроблено в цьому кроці навмисно — автоматичне створення нових `City`-рядків
для десятків невідомих міст це окреме, більш ризиковане рішення, не запитане тут).

### Verification

- `tsc --noEmit --skipLibCheck` (та сама scratch-перевірка, що й увесь цей сеанс) на всі нові/
  змінені файли — 0 нових помилок TS1xxx/TS17xx; єдина TS7006-помилка з ізольованої компіляції —
  на рядку 519 `scraper.service.ts` (`detectAnomaly()`), НЕ зачепленому цим кроком (pre-existing
  шум ізольованої компіляції без повного графа типів Prisma, той самий клас шуму, що й раніше
  цієї сесії).
- ⚠️ ЧЕСНО: жоден реальний виклик `ScraperService.runForProvider()` для цих 2 джерел НЕ
  виконувався в цьому середовищі (немає `DATABASE_URL`/мережевого доступу до продакшн-БД) —
  сам JSON обох джерел РЕАЛЬНО завантажено (WebFetch, дивись зразки полів вище), але повний шлях
  discover() → processItem() → Camera.create() не прогонявся живим викликом. Перед продакшн-
  використанням варто перевірити один реальний запуск (`--` той самий принцип, що вже
  застосовувався для `WebcamGuruAdapter`/`NycTmcAdapter`).

## 2026-08-06 — Автостворення City при імпорті (за прямим запитом користувача)

### Запит користувача

"добавить при импорте проверку есть ли в базе город провайдер и добавлять если отсутствуют" —
пряме продовження чесно задокументованого вище обмеження ("City цього проєкту не містить
жодного міста США/Індонезії — більшість камер отримають cityId=null").

### Реалізація

`ScraperService.resolveOrCreateCityId()` (новий приватний метод) замінив попередню логіку
"знайти City або лишити cityId=null":

1. Точний (case-insensitive) пошук `City` за `name` (+ `countryCode`, якщо адаптер його дав) —
   без змін порівняно з попередньою версією.
2. Якщо не знайдено — **створює новий `City`-рядок** через `prisma.city.upsert({where:{slug},
   update:{}, create:{...}})`:
   - `name`/`countryCode`/`countryName`/`region` — напряму з нових полів `RawCameraItem`
     (`suggestedCityName`/`suggestedCountryCode`/`suggestedCountryName`/`suggestedRegion` —
     останні два додано цим кроком, `TrafficVisionAdapter` заповнює їх з полів `country`/
     `state` відповіді джерела).
   - `slug` — власна легка `slugify()` (без зовнішньої бібліотеки — назви вже латиницею) +
     дедуплікація числовим суфіксом (`uniqueCitySlug()`) на випадок двох різних міст з
     однаковим базовим slug.
   - `lat`/`lng` — координати ЦІЄЇ КОНКРЕТНОЇ камери (наближення центру міста — джерело не дає
     справжнього центру міста, а окремий геокодинг-запит "де центр міста X" заради цього не
     виправданий; для потреб проєкту достатньо точно).
3. **upsert, не findFirst+create окремо** — навмисно, через паралельну обробку елементів
   (`Promise.all` у `runForProvider()`, декілька камер ОДНОГО нового міста можуть одночасно не
   знайти City в кроці 1 і одночасно спробувати створити його): `upsert` за унікальним `slug`
   атомарний на рівні БД, тому паралельна гонка не породжує ні дублікат City, ні помилку
   унікальності — обидві камери отримають той самий `cityId`.

### Наслідки для вже описаного обмеження вище

Розділ "⚠️ ЧЕСНО: City цього проєкту НЕ містить жодного міста США чи Індонезії..." вище тепер
описує СТАРУ поведінку (до цього кроку) — з цим виправленням нові міста створюються
автоматично при першому імпорті. Залишковий, свідомо прийнятий компроміс: `City.lat/lng` для
автостворених міст — координати першої обробленої камери в цьому місті, не справжній
географічний центр (не блокує функціональність — City тут потрібне переважно для
відображення назви/країни й геокодинг-підказки, не для точної навігації по самому City).

### Verification

Той самий scratch `tsc --noEmit --skipLibCheck` — 0 нових помилок TS1xxx/TS17xx/TS7006 (окрім
того самого pre-existing шуму в `detectAnomaly()`, не зачепленого цим кроком). Живий виклик
(`prisma.city.upsert`) НЕ виконувався в цьому середовищі (немає доступу до БД) — та сама
причина, що й для решти цього документа.

## 2026-08-06 — Живий інцидент: статус 200, discoveredCount=0 (реальна обгортка `{cameras: [...]}`)

### Що сталось

Перший живий прогін користувача (`npx ts-node scripts/import-trafficvision-cameras.ts
oktraffic`): `статус=SUCCESS, найдено=0`. Скрипт спершу не друкував ПРИЧИНУ (вона писалась
лише в `ImportLogEntry`, у БД) — додано (`import-trafficvision-cameras.ts`) автоматичний друк
цього запису в консоль одразу, коли `discoveredCount === 0`, щоб не змушувати гортати адмінку.

Реальна причина (побачена саме завдяки цьому фіксу): **`TrafficVisionAdapter` очікував, що
`res.data` — ГОЛИЙ масив камер. Насправді відповідь — `{ "_metadata": {...}, "cameras":
[...] }`** — обгортка, не масив. `Array.isArray(res.data)` був `false`, тому парсер трактував
це як "структура відповіді змінилась/зламана" і повертав 0 елементів.

⚠️ ЧЕСНО: раніше в цьому сеансі (при первинному дослідженні) я показував користувачу "перші
записи як масив" — фактично WebFetch (AI-резюмування вмісту сторінки) розпаковував обгортку й
показував лише `cameras`, не повідомляючи, що насправді є зовнішній об'єкт з ключем `_metadata`
поруч. Це і був корінь помилки в першій версії адаптера — не зміна відповіді сайту з часом, а
неповна картина від інструменту дослідження вже на самому початку.

### Виправлення

`TrafficVisionAdapter.discover()` тепер приймає ОБИДВА варіанти форми відповіді: якщо
`res.data` — масив, використовує його як є (захисний фолбек, раптом колись повернеться "гола"
форма); якщо `res.data.cameras` — масив, використовує його. Якщо жоден варіант не спрацював —
явна діагностика з переліком реальних top-level ключів відповіді (`responseTopLevelKeys`), щоб
наступного разу відразу було видно нову форму, а не гадати.

### ⚠️ Нова, важливіша знахідка: `_metadata` явно забороняє bulk-завантаження

Сам `_metadata`-об'єкт відповіді містить (дослівно, з живого запиту, обидва джерела ідентично):

```json
"license": "Public government data with TrafficVision compilation copyright. Attribution requested for reuse.",
"usage": {
  "permitted": ["Individual camera lookups", "Integration with attribution", "Educational and research use"],
  "prohibited": ["Bulk downloading without permission", "Republishing without attribution", "Removing source metadata"],
  "contact": "For bulk access or API licensing, contact: legal@trafficvision.live"
}
```

Це СИЛЬНІШЕ й конкретніше за загальний `Terms of Service` сайту (знайдений і задокументований
раніше вище в цьому файлі) — застереження прямо в самому файлі, який автоматично завантажує
скрипт, адресоване буквально будь-якому автоматичному споживачу цього JSON. За прямим, ВЖЕ
ВТРЕТЄ повторно підтвердженим рішенням користувача (через AskUserQuestion — "Оба — починить
сейчас, но параллельно исследовать oktraffic.org") парсер лишається робочим для цих 2 джерел,
АЛЕ паралельно досліджено прямий першоджерельний шлях (нижче) як довгостроковий, юридично
чистіший варіант.

### Дослідження прямого першоджерела (`oktraffic.org`) — за вибором користувача, паралельно

`_metadata` сам розкриває реальні API-адреси Oklahoma DOT:
- `https://oktraffic.org/api/CameraPoles` — 241 запис, але **ЛИШЕ** `{id, name, dateInserted,
  dateUpdated}` — жодних координат, жодних stream URL. Це просто список "стовпів"/локацій
  (наприклад "I-44 & I-240"), не самих камер.
- `https://oktraffic.org/api/SpeedRadars/getLatesRadarData` — РЕАЛЬНО дає `latitude`/
  `longitude` і посилання на JPEG-знімки (`pictures[].path`, наприклад
  `http://oktrafficradar.org/hrserver/2/snap-....jpg`) — це покриває "221 image cameras" з
  `_metadata.notes` TrafficVision.

⚠️ ЧЕСНО: **цих двох ендпоінтів НЕДОСТАТНЬО** для повної заміни TrafficVision-джерела.
`CameraPoles` не дає ні координат, ні URL відеопотоку — а саме 395 ВІДЕО-камер (HLS-потоки на
`stream.oktraffic.org`, дивись формат JSON вище) якраз і складають більшу частину джерела.
TrafficVision десь бере відповідність pole→камера→координати→streamUrl — або через
недокументований третій ендпоінт oktraffic.org (не серед тих двох, що вони самі розкрили в
`_metadata.apiEndpoints`), або через власний скрапінг фронтенду oktraffic.org (аналогічно до
того, як довелось реверс-інжинірити сам trafficvision.live в першому розділі цього документа).
Це означає, що "просто піти напряму в oktraffic.org" — НЕ швидка заміна одним файлом, а
окреме, порівнянне за обсягом дослідження (потрібен реальний браузер, мережеві запити,
можливо аналіз JS фронтенду oktraffic.org) — TrafficVision тут справді виконав реальну
"компіляційну" роботу (кросреференс кількох джерел + геокодинг), не просто ретранслює один
чужий API.

**Висновок**: пряма заміна на `oktraffic.org` — окрема, більша задача, не зроблена в цьому
кроці. Поточний парсер (проти `data.trafficvision.live/camera-data/*.json`, тепер із
виправленим розпакуванням `{cameras: [...]}`) лишається робочим рішенням, з чесно
задокументованим застереженням про bulk-download вище.

## 2026-08-06 (продовження) — Реверс-інжиніринг `oktraffic.org`: результат — тупик (не через відмову, а фактично)

### Запит користувача

"заняться реверс-инжинирингом oktraffic.org и написать аналогичный парсер под него". Далі
користувач додав "использовать впн америки" разом із проксі-креденшлами (`REGISTRY_SCAN_PROXY_URL`)
для обходу Cloudflare-блокування — **ця конкретна дія відхилена** (обхід bot-detection —
категорія дій, які я не виконую НАВІТЬ за прямою згодою користувача, на відміну від категорії
"потрібен явний дозвіл"). Користувач не заперечив і погодився продовжити дослідження ЛИШЕ через
`WebFetch` (без браузера, без проксі) — саме це й зроблено нижче.

### Спроба через реальний браузер (`mcp__claude-in-chrome__*`)

І `https://oktraffic.org`, і `https://oktraffic.org/api/CameraPoles` — Cloudflare
"Sorry, you have been blocked" (скріншоти зроблено, підтверджено). Браузерний шлях закрито
остаточно — жодних спроб обходу (проксі/VPN/інше) не робилося.

### Спроба через `WebFetch` (дозволений шлях — інша інфраструктура запиту, Cloudflare поки не
блокує WebFetch на цих конкретних шляхах)

### ⚠️ ЧЕСНИЙ висновок

`_metadata.apiEndpoints` самого TrafficVision розкриває РІВНО два ендпоінти oktraffic.org
(`CameraPoles`, `SpeedRadars/getLatesRadarData`) — і це, судячи з усього, дійсно ВСІ публічно
задокументовані (навіть непрямо) шляхи. Перевірено ще ~10 правдоподібних варіантів назв
(`Cameras`, `Videos`, `VideoCameras`, `Feeds`, дії за зразком `getLates*Data`) — жоден не існує.
Пряме підтвердження від самого TrafficVision (`_metadata.notes`): їхні 649 камер oktraffic —
це **428 відео-камер (HLS) + 221 камера-радар (знімки)**. Другу групу (221) `SpeedRadars`
дійсно покриває. Але для першої, більшої групи (428 HLS-камер, `stream.oktraffic.org/.../
playlist.m3u8`) **жодного публічного oktraffic.org API з координатами/stream URL знайти не
вдалося** — ні через дозволені запити, ні через задокументовані `_metadata.apiEndpoints`.

Це означає: TrafficVision.Live сам десь бере зв'язок "стовп→камера→координати→streamUrl" для
428 відео-камер — або через недокументований і поки що не знайдений ендпоінт, або через власний
скрапінг/парсинг фронтенду oktraffic.org (JS-бандл SPA, до якого WebFetch не показав прямого
шляху, а браузер — заблокований Cloudflare). Подальше вгадування назв ендпоінтів навмання дає
дедалі менше шансів і починає виглядати як перебір/сканування API без документації — свідомо
зупинився тут, а не продовжив наосліп.

**Практичний висновок**: пряма заміна `oktraffic.org` замість TrafficVision-джерела для
відео-камер (найбільша частина датасету) **наразі неможлива** без або (а) браузерного доступу
(заблоковано Cloudflare, обхід — навмисно відхилено), або (б) офіційного звернення до
oktraffic.org/ODOT за API-доступом. `SpeedRadars` (221 камера-радар) технічно можна б забрати
напряму вже зараз (координати + JPEG є) — але це лише третина джерела, і поточний
TrafficVision-парсер вже покриває всі 649 камер (обидві групи) одним запитом. Рішення, чи
продовжувати (наприклад, писати окремий частковий парсер лише під `SpeedRadars`, чи звернутися
до legal@trafficvision.live/ODOT за офіційним bulk-доступом, чи прийняти поточний парсер як
достатній) — за користувачем.

За вибором користувача (AskUserQuestion: "Принять текущий парсер как решение") —
`oktraffic.org`-реверс-інжиніринг закрито, `TrafficVisionAdapter` лишається робочим рішенням для
обох джерел (`oktraffic`, `bpjt-`) без подальших змін коду.

## 2026-08-06 (продовження 2) — Батчове дотягування азимуту для fallback-камер (реальний інцидент з мережею)

### Запит користувача

Живий прогін `npx ts-node scripts/import-trafficvision-cameras.ts oktraffic` показав повторювані
попередження `[AzimuthHeuristicService] Batched azimuth heuristic failed for 20 points: Overpass:
все 4 параллельных попытки провалились — ... connect ECONNREFUSED ...` (усі 4 дзеркала
одночасно — мережа середовища користувача на момент прогону не мала виходу до жодного з
overpass-хостів; НЕ проблема коду парсера чи самого джерела камер). Користувач перервав прогін
(`^C`) і запитав: "то есть текущий парсер импортирует все 649 камер oktraffic в базу ?" і
"возможно ли потом в админке батчами дотянуть оверпасс ?".

### ⚠️ ЧЕСНО: збій Overpass НЕ втрачає камери

`ScraperService.processItem()` і так завжди створює камеру, навіть якщо
`AzimuthHeuristicService.guessForPoint()`/`guessForPoints()` впав чи не знайшов дорогу поруч —
просто з `azimuthSource:'fallback'` (`azimuth:0`, `rangeHint:'yard'`, тобто порожня заглушка
замість реального напрямку вздовж дороги). Тобто камери з упалого прогону все одно потрапляють у
базу — лише з гіршою якістю автокалібрування азимуту/сектора огляду.

### Реалізовано: `ScraperService.recalibrateFallbackAzimuths(providerId?)`

Новий метод — НЕ перезапускає весь імпорт (не потрібно: dedup по `[providerId, externalId]` і
так відсіяв би вже імпортовані елементи, це був би зайвий прохід по всьому джерелу заради
невеликої частки, що впала). Натомість точково перебирає ТІЛЬКИ вже існуючі камери з
`azimuthSource==='fallback'` (опційно — лише одного провайдера), групує їх по `citySlug` (камери
TrafficVision-джерел прив'язані до РІЗНИХ міст поштучно, § `resolveOrCreateCityId()` вище — не
можна змішати в один виклик `guessForPoints()`, який приймає ОДИН `citySlug` на весь пакет), і
заново пробує Overpass пачками по 20 точок (той самий тайл-кеш-спершу шлях, що й при звичайному
імпорті). Для кожної камери, де новий результат — уже не `'fallback'`, оновлює `azimuth`,
`azimuthSource`, `rangeMeters` (за тією ж таблицею `DEFAULT_RANGE_BY_HINT`, що й при створенні) і
перебудовує `fov_polygon` (`syncCameraPolygon`) для OUTDOOR-камер — той самий набір дій, що й при
первинному імпорті, лише за вже наявними в БД координатами.

Новий ендпоінт: `POST admin/parser/recalibrate-azimuth-fallback` (`?providerId=` — опційно,
`AdminGuard`). Повертає `{ totalFallback, updated, stillFallback }`.

### Адмінка (`apps/admin/app/admin/parser/page.tsx`)

- Глобальна кнопка "📐 Досчитать азимуты (fallback)" біля "Запустить все источники" — по всій
  базі одразу.
- Кнопка "Досчитать азимут (N)" у кожному рядку таблиці статистики (поруч із "Dry-run") —
  показується лише коли `azimuthFallbackCount > 0` для цього джерела.
- Результат (`було/оновлено/лишилось fallback`) — банер над таблицею, той самий стиль, що вже
  використовується для результатів імпорту/YouTube/Google-пошуку.

### Обмеження (чесно)

Якщо Overpass і зараз недоступний (та сама мережева проблема середовища, не сам код) — кнопка
просто нічого не змінить (`updated: 0`, `stillFallback` = як було), можна натиснути повторно
пізніше без жодного ризику дублювання чи побічних ефектів (кожен виклик — чистий перерахунок за
вже наявними координатами, не створює нових записів).
