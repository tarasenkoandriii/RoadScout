# Аудит: AI-автокалібрування азимута/FOV + iframe-прев'ю на екрані калібрування

## Контекст

За прямим запитом користувача: (1) автоматизувати автокалібрування — щоб ІІ визначав азимут і
FOV камери; (2) додати невеликий iframe-прев'ю трансляції прямо на екрані калібрування.

## Що зроблено

### iframe-прев'ю

`/admin/cameras/:id/calibrate` — невеликий `<iframe src={/embed/${camera.id}}>` під картою
сектора. Свідомо **перевикористовує вже існуючий публічний ембед-віджет** (`/embed/[id]`), а не
дублює логіку визначення IFRAME/YOUTUBE_LIVE/HLS/MJPEG_SNAPSHOT — той самий підхід, що вже
обробляє нездатність вбудувати HLS/MJPEG напряму (показує назву + пряме посилання замість
спроби відтворити).

### AI-автокалібрування (азимут/FOV)

- **`extractYoutubeThumbnailUrl(streamUrl)`** (`src/common/grok-camera-assist.service.ts`) —
  дістає id відео з URL (`watch?v=`/`youtu.be/`/`embed/`/`live/`) і повертає публічну прев'ю-
  картинку `img.youtube.com` — **без жодного ключа**. **Чесно повертає `null` для посилання на
  канал цілком** (реальний випадок зі скрапленого сайту, див.
  `doc/AUDIT-webcam-guru-real-html.md`) — отримати id поточного ефіру каналу без YouTube Data
  API неможливо, і сервіс не намагається вгадати.
- **`GrokCameraAssistService.suggestAzimuthFov()`** — той самий vision-виклик (xAI/Grok,
  `GROK_VISION_MODEL`), що вже є в `ReceiptVerificationService`. Промпт явно просить модель
  чесно повертати `null`, якщо по кадру неможливо впевнено визначити напрямок (немає впізнаваних
  орієнтирів/тіней/перспективи вулиці) — **не вигадувати навмання**.
- `CamerasService.suggestAzimuthFovForCamera(id)` + ендпоінт
  `POST /admin/cameras/:id/ai-calibrate-suggest` (під `AdminGuard`) — резолвить камеру, викликає
  vision-сервіс, нічого не зберігає — тільки пропозиція.
- Фронтенд: кнопка «🤖 Автокалибровка (ИИ)» на екрані калібрування, показує запропонований
  азимут/FOV з упевненістю та поясненням моделі, кнопка «Применить» заповнює повзунки — **явне
  попередження в UI**, що це приблизна оцінка по одному кадру, яку треба звірити з сектором на
  карті й реальною трансляцією.

## Реально прогнані тести (ts-node, справжнє виконання)

**`extractYoutubeThumbnailUrl()`** (6 перевірок): усі 4 формати YouTube-посилань
(`watch?v=`/`youtu.be/`/`embed/`/`live/`) коректно дають правильний URL мініатюри; **посилання
на канал цілком (точний реальний випадок) → `null`**; не-YouTube посилання → `null`. Усі 6 —
**пройдені**.

**`GrokCameraAssistService.suggestAzimuthFov()`** (14 перевірок): посилання на канал →
`imageAvailable: false` з зрозумілою причиною, азимут/FOV `null` (не вгадується); не-YouTube тип
потоку (`HLS`) → теж `imageAvailable: false`; валідне відео без API-ключа →
`imageAvailable: true`, `configured: false`; успішна відповідь моделі → азимут/FOV/впевненість
коректно розпарсені; **модель чесно каже «не впевнена» (обидва `null`) → підсумкова впевненість
примусово `0`, навіть якщо модель помилково прислала ненульове значення поруч з `null`**;
азимут поза діапазоном (400°) → відхилений, при цьому валідний FOV з тієї ж відповіді
зберігається; мережева помилка → безпечний фолбек, без падіння. Усі 14 — **пройдені**.

**`CamerasService.suggestAzimuthFovForCamera()`** (6 перевірок): викликає vision-сервіс саме з
реальними назвою/streamUrl/streamType/координатами камери; коректно повертає пропозицію;
невідомий id камери → 404 (через уже існуючий `findOne()`). Усі 6 — **пройдені**.

Разом 26 нових перевірок, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку — 0
помилок у змінених файлах.

## Не перевірено / відомі обмеження

- **Реальний виклик vision-моделі з живим ключем і реальним кадром** — мережа недоступна в цій
  пісочниці; перевірена лише логіка обробки відповіді (парсинг, валідація діапазонів,
  безпечні фолбеки), не фактична якість візуального визначення азимута на реальних кадрах
  українських камер.
- **Принципове обмеження самої задачі** (задокументовано і в коді, і в UI): визначення
  компасного азимута по одному зображенню без GPS/компас-оверлею — суттєво менш надійна задача
  для vision-моделі, ніж читання тексту (як у `ReceiptVerificationService`). Результат
  призначений як підказка для звірки, не як значення для автоматичного застосування без
  перевірки людиною.
- Отримання кадру реалізовано **тільки** для `YOUTUBE_LIVE` з посиланням на конкретне відео —
  для `IFRAME`/`HLS`/`MJPEG_SNAPSHOT` і посилань на YouTube-канал цілком автокалібрування
  недоступне; повноцінне рішення (headless-браузер для знімку кадру з довільного iframe) — поза
  обсягом цього кроку.
- Фронтенд-зміни — перевірені балансом дужок і вручну вичитані, не прогонялись через `tsc`/
  візуально в браузері (та сама, вже неодноразово задокументована причина нестабільності
  заглушки `@types/react` у цій конкретній пісочниці).
