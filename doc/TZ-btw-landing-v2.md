# ТЗ: лендинг v2 для Beyond the Wall (BTW) — планирование маршрута + живая персонализация по IP

**Статус:** ✅ реализовано как отдельный проект `apps/interactive` (см. § 11 внизу документа —
за прямым запросом пользователя предположение из § 0 ниже было прямо отменено: «создай
интерактивный лендинг apps/interactive по тз - отдельный прект деплой / старый лендинг для
пешеходов / интерактивный для велосипедистов - авто»). Раздел 0 ниже оставлен как есть —
это честная запись первоначального (неверного, как выяснилось) предположения и его
обоснования, а не переписана задним числом; актуальное решение — в § 11.
**Контекст:** `doc/TZ-btw-landing.md` (Этап 1) описывал лендинг для мини-аппа, каким он был
ДО функции планирования маршрута — только сканирование камер вокруг себя. С тех пор в
`apps/btw` появилась вся ветка планирования поездок (`doc/TZ-btw-route-planning.md`):
выбор точек А/Б, построение маршрута, прогноз камер/погоды/инцидентов/трафика вдоль пути,
и полноценный «режим сопровождения» — живой GPS-трекинг, индикатор отклонения от маршрута,
авто-перестроение, список «что впереди» с быстрым переходом в скан. Секция «Как это
работает» в исходном ТЗ лендинга полностью описывает только старый сценарий и не упоминает
ничего из этого.

**За прямым запитом пользователя** — этот документ (а) актуализирует контент лендинга под
реальные возможности мини-аппа, и (б) добавляет новую, отдельную от мини-аппа функцию:
интерактивность самого лендинга по IP посетителя — определение города, живая погода и
инциденты по этому городу, возможно дорожная ситуация по TomTom.

## 0. Как это соотносится с существующим `TZ-btw-landing.md`

**⚠️ ЧЕСНО, принятое решение (не запрошено явно пользователем — предположение с явным
обоснованием, а не блокирующий вопрос):** этот документ трактуется как **ревизия/замена**
секций 2.2–2.6 исходного ТЗ, а не как отдельный второй сайт. Причины:
- Пользователь написал «расширенное тз на второй лендинг» — формулировка допускает и
  «второй, отдельный от первого» (например, для другой аудитории/кампании), и «следующая,
  расширенная версия того же лендинга» (v2, замена контента). Явных сигналов «это должна
  быть отдельная страница, сосуществующая с первой» (другая аудитория, другой домен, A/B-тест)
  в запросе нет — только «с учётом последних изменений в мини апп», что по смыслу — актуализация,
  а не параллельный сайт.
- Технически поддерживать ДВА лендинга с разным описанием одного и того же продукта
  (один — только про сканирование, другой — про сканирование + маршруты) создавало бы
  постоянный риск рассинхронизации и путаницы у пользователя, если он попадёт не на ту версию.
- Раздел 3 ниже (IP-персонализация) добавляется к тому же `apps/landing`, а не создаёт новый
  проект — по той же причине: нет технической необходимости в отдельном деплое, а разделение
  усложнило бы поддержку (два `next.config.js`, два набора i18n-словарей и т.д.).

**Если это предположение неверно** (то есть на самом деле нужен именно второй, отдельный от
`apps/landing` сайт) — раздел 3 (техническое решение) всё равно применим почти без изменений,
меняется только то, что секции 1–2 ниже описывают контент НОВОГО файла/маршрута, а не правку
существующих файлов `apps/landing`.

Итог: этот документ **не отменяет** `TZ-btw-landing.md` целиком — раздел 1 (цель страницы),
2.1 (Hero, с уточнением ниже), 2.4 (приватность, дополняется), 2.7 (финальный CTA) и раздел 3
исходного документа (технические требования по deep-ссылке и мобильной адаптации) остаются в
силе. Переписываются: 2.2 (проблема/мотивация — шире), 2.3 («как это работает» — два сценария
вместо одного), 2.5 (скриншоты — новый набор), 2.6 (FAQ — новые вопросы). Добавляется целиком
новая секция «живой блок по городу» и новое техническое требование (раздел 3 этого документа),
явно противоречащее исходному «без бэкенда» — это прямо обсуждается ниже.

## 1. Что изменилось в мини-аппе (контекст для контента лендинга)

Кратко, для связи с текстом секций ниже — на момент этого ТЗ `apps/btw` умеет:

1. **Быстрый скан** (сценарий из v1 лендинга, без изменений) — наведи телефон, приложение
   подсвечивает камеры поблизости и их сектор обзора.
2. **Построение маршрута** — точка А/Б (текущее место / сохранённое / вручную), профиль
   (пешком/на авто/на велосипеде), маршрут строится через OpenRouteService.
3. **Прогноз вдоль маршрута, ДО поездки** — по построенному маршруту показывается: какие
   камеры встретятся, погода в средней точке пути, известные инциденты (511NY в штате
   Нью-Йорк + TomTom как fallback вне штата), трафик, и отдельно — встречи с FIXED_ROUTE-
   камерами (например, трамвайными) на пути.
4. **Режим сопровождения в поездке** — после старта: живое отслеживание позиции
   (`navigator.geolocation.watchPosition`), индикатор «сошёл с маршрута» (порог 200м),
   автоматическое перестроение маршрута при устойчивом отклонении (с кулдауном между
   перестроениями), список «что впереди» (камеры/инциденты в ближайших ~800м по ходу
   движения) с кнопкой быстрого перехода в скан конкретной точки, и ручная кнопка
   «пересчитать маршрут».
5. **Сохранённые места** — «дом», «работа» и т.п., хранятся на сервере (не только локально).

Это — источник правды для новой секции 2.3 ниже; изображения/копирайтинг должны показывать
именно эти реальные экраны, не абстрактные заглушки (тот же принцип «честного ожидания», что
уже зафиксирован в исходном ТЗ, § 2.5).

### 2.1 Hero — уточнение

Заголовок и подзаголовок исходного ТЗ («Наведи телефон — узнай, кто может это видеть») по-
прежнему точно описывают быстрый скан, но больше не описывают продукт целиком — теперь это
«сканер камер» **плюс** «планировщик поездки, который знает, что тебя ждёт по дороге».
**Принятое решение:** не переписывать заголовок на нейтральный/размытый под оба сценария —
конкретный, эмоционально понятный заголовок про «кто меня видит» сильнее как крючок первых 3
секунд, чем попытка вместить туда и маршруты. Вместо этого подзаголовок расширяется до двух
предложений: первое — прежнее (про сканирование), второе — новое, про то, что приложение
также умеет строить маршрут и предупреждать заранее. Пример направления (не финальный текст):
«Наведи телефон — узнай, кто может это видеть. А если собираешься в путь — построй маршрут,
и приложение заранее покажет камеры, погоду и обстановку на дороге».

### 2.2 Проблема/мотивация — расширение

К существующему тексту (публичные камеры вокруг, нет способа понять, что реально видно)
добавляется вторая мысль, короче первой: помимо «что видно прямо сейчас», людям, которые
куда-то едут, часто неизвестно, что их ждёт по пути — не просто камеры, а погода, известные
инциденты/ДТП, качество трафика. BTW отвечает на оба вопроса одним и тем же простым
инструментом.

### 2.3 «Как это работает» — переписывается на два сценария

Вместо одной последовательности 3–4 шагов — два блока-вкладки/переключателя (или один под
другим на мобильном, без вкладок — решение оставлено на дизайн-реализацию, не блокирует ТЗ):

**Сценарий А — «Быстрый скан»** (те же 4 шага, что в v1 лендинга, без изменений):
1. Открой приложение в Telegram — без регистрации, без установки.
2. Наведи телефон вокруг себя.
3. Приложение подсвечивает камеры поблизости и их сектор обзора.
4. Если прямого совпадения нет — можно посмотреть боковые/встречные ракурсы.

**Сценарий Б — «Построй маршрут»** (новый, 4 шага):
1. Укажи точку А и точку Б — текущее место, сохранённое избранное или координаты вручную.
2. Приложение строит маршрут и сразу показывает, что встретится по пути — камеры, погода,
   известные инциденты, трафик.
3. В дороге — живой трекинг: приложение подскажет, если ты сошёл с маршрута, и само
   перестроит путь.
4. Список «что впереди» — по мере движения приложение показывает следующие несколько сотен
   метров: камера или инцидент рядом — один тап, чтобы посмотреть детали через скан.

**⚠️ ЧЕСНО:** шаг 3 сценария Б зависит от того, что вкладка/страница мини-аппа остаётся
открытой и `watchPosition` продолжает получать обновления — то же честное ограничение, что
уже зафиксировано в `TZ-btw-route-planning.md` (раздел 10): фоновый трекинг при полностью
свёрнутом Telegram не гарантирован платформой. Текст лендинга не должен обещать «работает в
фоне» — только «пока приложение открыто».

### 2.4 Приватность/доверие — дополнение

К существующим четырём пунктам (координаты не передаются идентифицированно, только публичные
камеры, история не хранится трекуемым образом, ссылка на политику) добавляется пятый — про
режим сопровождения:
- Во время поездки координаты используются только локально в браузере для расчёта «сошёл ли
  ты с маршрута» и что показать в списке «впереди» — тот же принцип, что и в режиме карты:
  сервер не получает поток идентифицированных координат пользователя.

И отдельно, если раздел 3 (IP-персонализация) реализуется — шестой пункт специально про него
(см. § 3.5 ниже, вынесено туда, чтобы не дублировать текст).

### 2.5 Скриншоты/демо — обновление набора

К 2–3 скриншотам быстрого скана (без изменений) добавляются 2 новых: (а) экран построения
маршрута с карточками «камеры/погода/инциденты вдоль пути» до старта поездки, (б) экран
режима сопровождения — индикатор отклонения + список «что впереди». Реальные снимки
интерфейса, не иллюстрации — тот же принцип, что в v1.

### 2.6 FAQ — новые вопросы

К существующим пяти вопросам добавляются:
- Приложение видит, где я нахожусь во время поездки?
- Что если я отклонюсь от маршрута — надо строить заново вручную?
- Работает прогноз погоды/инцидентов в любом городе?  (честный ответ — зависит от покрытия:
  511NY привязан к штату Нью-Йорк, TomTom — фолбэк там, где есть ключ и покрытие, погода — по

- (если раздел 3 реализован) Откуда лендинг знает мой город? Он использует мою точную
  геопозицию?

## 3. Новая секция: «живой блок по городу» на самом лендинге

**За прямым запитом пользователя:** «возможно добавить интерактивность по айпи посетителя -
погода и инциденты по городу - возможно дорожную ситуацию по tom-tom».

### 3.1 Именно та проблема, которую нужно явно назвать

`TZ-btw-landing.md` § 3 прямо требует: «Без бэкенда — статическая/чисто клиентская страница,
никаких обращений к API BTW не требуется». Живая погода/инциденты по городу посетителя — это
по определению серверная функция (сторонние API-ключи открытой стороне не раздаются, к тому
же WeatherService/511NY/TomTom уже реализованы как раз на бэкенде `apps/api`). Эти два
требования прямо противоречат друг другу для НОВОЙ секции — старая часть лендинга (deep-
ссылка в Telegram) как была статической, так и остаётся.

**Принятое решение:** ограниченный, явно выделенный отход от «без бэкенда» — только для
этой одной секции, через один новый маленький публичный (анонимный, без авторизации)
эндпоинт в `apps/api`, переиспользующий уже существующие сервисы. Это тот же принцип, что уже
применён для `/btw/coverage` и `/btw/manifest` — публичные, не привязанные к пользователю,
без `TelegramAuthGuard`/`AdminGuard`. Остальной лендинг (Hero, шаги, FAQ, deep-ссылка) как
был статическим, так и остаётся — секция городского виджета не должна блокировать первый
рендер страницы (см. § 3.6, деградация).

### 3.2 Определение города посетителя — переиспользование уже проверенного паттерна

`apps/landing/middleware.ts` уже определяет язык по IP через заголовок Vercel
`x-vercel-ip-country` (см. `lib/i18n/detect.ts`). Vercel на каждый реальный запрос (не на
`localhost`/дев-режим — см. § 3.6) отдаёт полный набор geo-заголовков, подтверждённый
официальной документацией на момент написания этого ТЗ (`vercel.com/docs/headers/request-headers`):

| Заголовок | Значение |
|---|---|
| `x-vercel-ip-country` | код страны (уже используется для языка) |
| `x-vercel-ip-country-region` | регион первого уровня (для NY — здесь будет `NY`, что важно для § 3.4) |
| `x-vercel-ip-city` | название города — **закодировано по RFC3986, нужно `decodeURIComponent()`** |
| `x-vercel-ip-latitude` / `x-vercel-ip-longitude` | координаты (строка, например `50.4501`) |
| `x-vercel-ip-timezone` | таймзона IANA (не используется в этом ТЗ, но доступна бесплатно) |

**Принятое решение:** для сопоставления «город → что показывать» используется НЕ текстовое
имя города (ненадёжно — разное написание, разные языки), а `x-vercel-ip-latitude`/
`x-vercel-ip-longitude` — те же координаты, которыми уже оперируют
`WeatherService.getReferencePoints()` (список городов с lat/lng из таблицы `City`) и
`centerRadiusToBoundingBox()` (уже существует в `tomtom.service.ts` для похожей задачи —
превращения «центр + радиус» в bbox). Имя города из `x-vercel-ip-city` используется только
для отображения текста «Сейчас в Киеве…» и т.п. — косметика, не логика сопоставления.

### 3.3 Новый эндпоинт — предложение

`GET /btw/landing-snapshot` (имя условное, финальное — на усмотрение реализации), без guard,
принимает `lat`/`lng`/`cityLabel` query-параметрами (лендинг сам читает Vercel-заголовки на
своей стороне через Next.js middleware/route handler и передаёт координаты явно — так и
`apps/api`, и `apps/landing` остаются раздельными деплоями без прямой зависимости от
внутренних деталей заголовков друг друга).

Что эндпоинт агрегирует, переиспользуя существующие сервисы `apps/api/src/situational`
(параллельно, каждый источник — с собственной деградацией по примеру уже реализованного
`BtwRouteForecastService.safeForecast()`, чтобы падение одного источника не гасило остальные):

- **Погода** — `WeatherService`: сейчас работает по фиксированному списку городов из
  справочника `City` (в основном украинские города, см. `apps/api/src/situational/weather.service.ts`
  комментарий про `City.list()`), не по произвольным координатам. **⚠️ ЧЕСНО:** для города вне
  этого справочника (типичный случай для лендинга — посетитель может быть откуда угодно)
  понадобится либо (а) добавить в `WeatherService` метод «погода по произвольным lat/lng»
  (сам провайдер погоды это скорее всего поддерживает — сейчас просто не вызывается так), либо
  (б) на этом этапе показывать погодный виджет только для городов, уже входящих в справочник
  `City`, и честно скрывать блок погоды для остальных. Второе — дешевле для MVP, но сильно
  сужает охват для не-украинской аудитории. Решение по (а)/(б) — открытый вопрос реализации,
  см. § 3.7.
- **Инциденты в штате Нью-Йорк** — `FiveElevenNyService.getEvents()`: единый живой фид на
  весь штат целиком (не принимает координаты) — на эндпоинте достаточно проверить
  `x-vercel-ip-country-region === 'NY'` (US) и, если да, отдать события из уже вызванного
  (и, вероятно, закешированного на уровне сервиса) фида без географической фильтрации по
  близости — сам фид уже покрывает весь штат.
- **Трафик/инциденты вне штата Нью-Йорк** — `TomTomTrafficService.getIncidents(bbox)` +
  уже существующая `centerRadiusToBoundingBox()`: работает по любым координатам, при условии
  настроенного `TOMTOM_API_KEY`.
- **Инциденты, добавленные вручную админом** (`RoadIncidentsService`) — **сознательно НЕ
  включаются** в эту секцию: это внутренний рабочий инструмент админки для конкретных
  зафиксированных случаев, не предназначенный как публичный живой фид «что происходит в
  твоём городе» — включение потребовало бы отдельного решения о том, какие из них вообще
  безопасно/уместно показывать анонимным посетителям сайта.

Форма ответа (черновая, для ориентира):
```json
{
  "cityLabel": "Kyiv",
  "weather": { "available": true, "tempC": 18, "condition": "cloudy" },
  "incidents": { "source": "tomtom", "configured": true, "count": 2, "items": [...] },
  "coverageNote": "outside-ny-and-city-catalog"
}
```
Поле `coverageNote`/аналог — обязательное, не опциональное: фронт лендинга должен уметь
честно показать «для вашего города пока нет данных» вместо пустого/сломанного виджета —
тот же принцип прозрачной деградации, что уже применяется в `configured: false` для 511NY
на админ-панели.

### 3.4 Честные границы покрытия (переносится из уже задокументированных ограничений мини-аппа)

Те же ограничения, что уже прямо зафиксированы в `TZ-btw-route-planning.md` § 7.2/10,
применимы и здесь — не новые допущения, а прямое наследование:
- 511NY = только штат Нью-Йорк, США. Для подавляющего большинства посетителей (Украина и
  вообще не-NY) этот источник не сработает — TomTom берёт на себя эту роль, если ключ
  настроен и покрытие есть в конкретной локации.
- Погода — только по городам из справочника `City` в текущей реализации (см. § 3.3, открытый
  вопрос).
- Если ни `TOMTOM_API_KEY`, ни город в справочнике — секция должна деградировать в текст
  вида «этот блок пока не покрывает ваш регион», а НЕ молча исчезать или показывать
  устаревшие/неверные данные.

### 3.5 Приватность — доп. пункт к § 2.4

- Определение города — по IP, на уровне города (не точного адреса), тем же способом, что
  уже определяет язык интерфейса (`x-vercel-ip-country`) — без запроса разрешения на реальную
  геолокацию браузера (`navigator.geolocation`) для этой секции лендинга.
- Координаты/IP посетителя не сохраняются на сервере — новый эндпоинт stateless
  (`request in → response out`, без записи в БД), тот же принцип, что `/btw/coverage`.
- Пользователь может свободно отказаться от полезности этого блока — это дополнительная
  витрина, а не обязательный шаг к CTA «Открыть в Telegram».

### 3.6 Деградация/производительность

- Секция городского виджета — НЕ должна блокировать первую отрисовку остального лендинга
  (Hero и CTA должны быть видимы и кликабельны мгновенно, требование § 3 исходного ТЗ
  остаётся в силе для всего, что не является этим новым блоком) — реализуется как отдельный
  клиентский запрос после гидратации страницы (skeleton/лоадер на месте блока), а не как
  часть серверного рендера самой страницы.
- В локальной разработке (`next dev`) Vercel geo-заголовки отсутствуют — тот же нюанс, что
  уже, вероятно, встречался при разработке i18n-детекции по стране; нужен dev-фолбэк
  (например, фиксированные тестовые координаты за флагом окружения), чтобы блок был
  тестируем локально.
- Таймаут/ошибка нового эндпоинта → секция скрывается целиком (не показывает частично
  загруженные/нулевые значения как настоящие) — консистентно с тем, как уже задокументирован
  принцип "не показывать неправду" в `BtwRouteForecastService`.

### 3.7 Что по-прежнему остаётся уточнить при реализации (не блокирует старт)

- Погода по произвольным (не из справочника `City`) координатам — расширять
  `WeatherService` или сознательно ограничивать охват виджета на MVP (§ 3.3).
- Финальное имя/путь нового эндпоинта и точная форма ответа (набросок в § 3.3 — не
  контракт).
- Кешировать ли ответ на уровне `apps/landing` (например, по городу, на несколько минут),
  чтобы не дёргать `apps/api` на каждый визит лендинга — вероятно да, но конкретный TTL не
  определён в этом ТЗ.
- Нужен ли на самой странице явный текст-объяснение «как мы узнали ваш город» рядом с
  виджетом (прозрачность) или это достаточно закрыть общей политикой приватности — вопрос
  UX-формулировки, не архитектуры.

## 4. Технические требования (дополнение к § 3 `TZ-btw-landing.md`)

- Реализация в существующем `apps/landing` (Next.js 14.2.15, см. § 0 выше) — без нового
  Vercel-проекта.
- Новый публичный эндпоинт — в `apps/api/src/btw` (переиспользует существующие
  `WeatherService`/`FiveElevenNyService`/`TomTomTrafficService` из `apps/api/src/situational`,
  инжектируемые в `BtwModule`, тот же паттерн, что уже применён в `BtwRouteForecastService`),
  не требует новой авторизации/гварда.
- Городской виджет — клиентский запрос из `apps/landing` к `apps/api` (CORS должен быть уже
  открыт для публичных BTW-эндпоинтов — проверить на реализации, не предполагать).
- Остальные технические требования исходного ТЗ (мобильная адаптация в приоритете, минимум
  зависимостей для первого экрана, deep-ссылка `t.me/<bot_username>/<app_short_name>`) —
  без изменений.

## 5. Этапы

1. **Контент** — переписать секции 2.2/2.3/2.5/2.6 под текущие возможности мини-аппа (не
   требует нового бэкенда, можно делать независимо и раньше городского виджета).
2. **Городской виджет, базовая версия** — новый эндпоинт (§ 3.3) с ограниченным покрытием
   (511NY + TomTom + погода только для городов из справочника `City`, честная деградация для
   остальных), новая секция на лендинге, dev-фолбэк для локальной разработки.
3. **(Не MVP, отдельное решение позже)** — расширение погоды на произвольные координаты, если
   после запуска Этапа 2 окажется, что доля посетителей вне справочника `City` достаточно
   велика, чтобы это того стоило.

## 6. Известные упрощения (⚠️ ЧЕСНО, по конвенции проекта)

- Городской виджет — по IP, не по факту нахождения человека физически в этом городе (обычная
  для geo-IP погрешность — мобильные операторы, VPN, корпоративные прокси могут показать не
  тот город); текст рядом с виджетом не должен звучать как гарантия точности.
- Инциденты в этой секции — не все инциденты, известные системе (см. § 3.3, admin-инциденты
  сознательно исключены), только то, что дают 511NY/TomTom.
- Раздел 3 целиком — это добавление серверной зависимости к странице, которая изначально была
  спроектирована как полностью статическая; это осознанный компромисс ради запрошенной
  функции, а не незамеченное нарушение исходной архитектуры.

## 11. Реализация (за прямым запросом пользователя — отдельный проект, аудитория «велосипед/авто»)

**Прямой запрос:** «создай интерактивный лендинг apps/interactive по тз - отдельный прект
деплой / старый лендинг для пешеходов / интерактивный для велосипедистов - авто». Это прямо
отменяет предположение § 0 (там была ставка на «ревизия существующего лендинга») — реализовано
как **новый, полностью отдельный** Next.js-проект `apps/interactive` (свой `package.json`,
свой деплой, порт 3004 для dev), не правка `apps/landing`. Разделение аудитории: `apps/landing`
остаётся про пеший сценарий (сканирование камер, без изменений в этом раунде), `apps/interactive`
— целиком про сценарий «Построй маршрут» (§ 2.3 «Сценарий Б» этого документа) для велосипедиста
и водителя; пеший сценарий сознательно НЕ продублирован в `apps/interactive`.

### 11.1 Что сделано

- **Backend (`apps/api`):**
  - `WeatherService.getPointWeather()` (`apps/api/src/situational/weather.service.ts`) —
    новый публичный метод, переиспользует существующий приватный `fetchOne()` для ЛЮБЫХ
    координат (не только городов из справочника `City`) — решён открытый вопрос § 3.7 этого
    документа в пользу варианта (а). Отдельный in-memory кеш по округлённым lat/lng (10 мин
    TTL), независимый от кеша `getSnapshot()`.
  - `BtwLandingSnapshotService` (новый файл `apps/api/src/btw/btw-landing-snapshot.service.ts`)
    — агрегирует погоду + 511NY (в границах `NY_STATE_BBOX`, той же грубой оценки, что уже
    используется в `btw-route-forecast.service.ts`) или TomTom (`centerRadiusToBoundingBox`)
    вне штата Нью-Йорк, каждый источник — с собственной деградацией (`safeCall()`, тот же
    паттерн, что `BtwRouteForecastService.safeForecast()`).
  - `GET /btw/landing-snapshot` (`btw.controller.ts`) — новый анонимный эндпоинт (без guard,
    тот же уровень публичности, что `/btw/coverage`), валидация lat/lng через
    `BadRequestException`.
  - CORS (`apps/api/src/main.ts`) — расширен с одного `ADMIN_ORIGIN` до списка
    `CORS_ALLOWED_ORIGINS` (через запятую, с фолбеком на `ADMIN_ORIGIN` для обратной
    совместимости) — иначе браузер блокировал бы запросы с origin `apps/interactive`.
- **Frontend (`apps/interactive`, новый проект):**
  - Полная копия архитектуры `apps/landing` (Next.js 14.2.15, тот же паттерн `/[lang]/`
    роутинга, `middleware.ts` с детекцией языка по `x-vercel-ip-country`, те же 10 языков) —
    НЕ shared-пакет, отдельные файлы, тот же принцип независимости проектов, что уже принят
    для `apps/admin`/`apps/btw`/`apps/landing` в этом монорепо.
  - Новый контент под аудиторию «велосипед/авто» — Hero, «как это работает» (4 шага сценария
    построения маршрута), блок «для кого» (велосипед/авто отдельными карточками), приватность,
    FAQ — переведено на все 10 языков (`lib/i18n/dictionaries/*.ts`).
  - `CityWidget.tsx` — двухэтапный клиентский виджет: сперва свой же `GET /api/geo` (новый
    Route Handler, читает заголовки `x-vercel-ip-latitude/-longitude/-city`, недоступные
    клиентскому JS напрямую), затем внешний `GET {NEXT_PUBLIC_API_URL}/btw/landing-snapshot`
    с явными координатами. Не блокирует первый рендер страницы (собственный `useEffect`),
    честно показывает `loading`/`error`/`unavailable`/`ready`.
  - Иконки — НЕ фотореалистичные иллюстрации (тех, что уже в `design-source`, сделаны под
    камера-сканирование, не под маршруты; новые фотореальные сцены здесь не заказывались и не
    изготавливались) — вместо этого лёгкий SVG/mask-image подход (тот же техприём, что был в
    первой, дофотореалистичной версии `apps/landing`), иконки скопированы из уже существующего
    `design-source/btw-illustrations/05-Icons/{navigation,detection,privacy}`.

### 11.2 Проверка

**⚠️ ЧЕСНО — важное ограничение проверки этого раунда:** песочница этой сессии не имеет
доступа к npm-реестру (`npm install` для и `apps/api`, и `apps/interactive` завершается
`403 Forbidden` от `registry.npmjs.org`) — поэтому **ни разу не запускались** ни настоящий
`nest build`, ни настоящий `next build`/`next dev`. Верификация выполнена тем же методом
изолированной проверки `tsc --strict`, что уже задокументирован и принят ранее в этой сессии
(`doc/AUDIT-btw-route-planning.md`, «продовження 8»):
- Backend: синтаксическая проверка (`ts.transpileModule`) всех 5 изменённых/новых файлов —
  чисто. Отдельно — изолированный `tsc --strict` с РЕАЛЬНЫМИ копиями зависимостей
  (`weather.service.ts`, `five11ny.service.ts`, `tomtom.service.ts`, `geometry.util.ts`,
  `cities.service.ts`) и типизированными заглушками только для внешних пакетов
  (`@nestjs/common`, `axios`, `@prisma/client`) — 0 ошибок после исправления двух артефактов
  самой заглушки (не бага в коде): отсутствующий `$executeRawUnsafe` в стабе `PrismaClient` и
  неинициализированное поле в стабе `PrismaService`.
- Frontend: изолированный `tsc --strict` над ВСЕМ реальным деревом `apps/interactive`
  (`app/`, `components/`, `lib/i18n/` включая все 10 словарей) с заглушками для `react`,
  `next`, `next/navigation`, `next/font/google` — 0 ошибок после исправления одного шим-
  артефакта (`JSX.ElementChildrenAttribute` — без него голый TS без настоящих `@types/react`
  не знает, что вложенные JSX-дети должны попадать в проп `children`; та же природа, что уже
  известная в сессии `useRef`-null ложноположительная категория, не баг кода).
- Конфигурационные файлы (`next.config.js`, `tailwind.config.js`, `postcss.config.js`,
  `package.json`, `tsconfig.json`) — синтаксически валидны (`node --check` / `JSON.parse`).

**Что это ДОКАЗЫВАЕТ:** типы согласованы (все поля/сигнатуры совпадают между новым кодом и
реальными существующими сервисами, включая эту сессию добавленный `getPointWeather()`), весь
код синтаксически корректен, все 10 словарей полностью satisfy интерфейс `Dictionary` (при
малейшем расхождении — TS ошибка, её не было). **Что это НЕ доказывает:** реальную сборку
Next.js (webpack/SWC-специфичные проверки, `generateStaticParams`/`dynamicParams` поведение на
проде, реальный fetch шрифтов Google Fonts), поведение самого `/btw/landing-snapshot` при
реальном сетевом вызове к Open-Meteo/511NY/TomTom, и реальную работу geo-заголовков Vercel (они
физически не появляются вне настоящего Vercel Edge Network — см. § 3.6 этого документа,
dev-фолбэк для этого явно помечен как открытый вопрос реализации). Перед реальным деплоем
рекомендуется прогнать `npm install && npm run build` в среде с доступом к npm-реестру.
