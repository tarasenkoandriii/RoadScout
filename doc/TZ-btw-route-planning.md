**Кодовое имя:** BTW Route Planning (рабочее)
**Тип:** новый главный экран Telegram Mini App `apps/btw` (Next.js 14 App Router) + NestJS + PostgreSQL/PostGIS
**Статус:** ТЗ, реализация не начата
**Связанные документы:** `doc/BTW-tz.md` (текущий главный сценарий — «Сканирование», §3.1), `doc/README.md` (главы 16–18 — FIXED_ROUTE/Look-ahead, уже есть в `apps/api`)

> **За прямым запросом пользователя** (скриншот главного экрана + описание): «главный функционал — поиск маршрута и, соответственно, камеры вдоль него — главный экран приложения должен быть по такому типу: задание начальной/конечной точек маршрута (включая ранее сохранённые точки) → поиск оптимального маршрута → прогноз дорожной ситуации вдоль него → сопровождение в поездке». Место реализации подтверждено пользователем в отдельном уточнении: **`apps/btw`, новый главный экран** (не `apps/admin`, не новое приложение).

## 1. Идея

Пользователь собирается куда-то ехать (или идти). Вместо «включить сканер и водить телефоном», он:
1. задаёт точку А (откуда) и точку Б (куда) — вручную, из ранее сохранённых мест, или «моё текущее положение»;
2. приложение строит оптимальный маршрут;
3. показывает вдоль маршрута: камеры (реестр RoadScout/BTW), известные проблемы (ДТП, погода, заторы — из того, что уже собирает `situational`-модуль) и, где возможно, встречи с движущимися камерами (трамваи и т.п., уже считает `/lookahead`);
4. в поездке — сопровождает: где я сейчас относительно маршрута, что впереди, отклонился ли я.

Метафора смещается с «перископ вокруг себя здесь и сейчас» (BTW-tz.md §1) на «что меня ждёт по пути» — тот же реестр камер, другой режим доступа к нему.

### 1.1. Что это НЕ (по аналогии с BTW-tz.md §1.1)

- это не полноценный навигатор с голосовыми подсказками поворот-за-поворотом (turn-by-turn voice) — см. §5.3, сознательно упрощено для MVP;
- это не замена Google/Waze как основного маршрутизатора — ценность именно в слое камер+прогноза поверх маршрута, не в самой прокладке пути;
- «прогноз дорожной ситуации» на старте — это не гарантированно точные пробки в реальном времени (см. §6, честный статус источника данных).

## 3. Данные

### 3.1. `SavedPlace` (новая модель)

**✅ Реализовано (2026-08-06)** — модель добавлена в `apps/api/prisma/schema.prisma` (ровно как ниже), CRUD в `apps/api/src/btw/btw.service.ts`/`btw.controller.ts` (`saveSavedPlace`/`listSavedPlaces`/`removeSavedPlace`, эндпоинты `POST`/`GET`/`DELETE /btw/saved-places`, `TelegramAuthGuard`, тот же шаблон, что уже `BtwViewpoint`/`viewpoints` ниже). `prisma migrate`/`db push` против реальной БД в этой песочнице не прогонялся (нет `DATABASE_URL`) — тот же честный статус, что и у других моделей, добавленных в этой сессии/проекте без доступа к живому Postgres (см. `doc/AUDIT-btw-route-planning.md`).

```prisma
model SavedPlace {
  id         String   @id @default(cuid())
  telegramId String
  label      String   // "Дом", "Работа", свободный текст
  lat        Float
  lng        Float
  address    String?  // человекочитаемый адрес, если задавался через геокодинг — для отображения, не для расчётов
  createdAt  DateTime @default(now())

  @@index([telegramId])
}
```

Сознательно НЕ переиспользуем `BtwViewpoint` (§3.4 BTW-tz.md) — у той модели обязательное поле `heading` (азимут взгляда для скана), которое здесь не нужно и не имеет смысла для точки маршрута; смешение двух разных концепций в одной таблице усложнило бы обе фичи без выигрыша. Если понадобится «сохранить точку маршрута И направление скана из неё одновременно» — это отдельный будущий кейс, не в объёме этого документа.

### 3.2. Маршрут — не персистентная сущность (для MVP)

Сам построенный маршрут (геометрия + вычисленные камеры/прогноз) **не сохраняется в БД** на старте — строится по запросу и живёт в состоянии клиента на время сессии/поездки. Обоснование: как и `route-position`-кэш для FIXED_ROUTE-камер (`doc/README.md`, «Известные упрощения главы 16–18» — in-process `Map`, не Redis), персистентность маршрутов пользователя — рост объёма работы (история поездок, синхронизация между устройствами), не нужный для первой версии основного сценария. История поездок — возможное направление §8 (этапы), не MVP.

## 4. Камеры вдоль маршрута

### 4.1. Геометрический приём (переиспользует существующий паттерн)

`cameras.service.ts` уже умеет: STATIONARY-камеры имеют `fov_polygon` (PostGIS-полигон сектора обзора), FIXED_ROUTE-камеры имеют `route_buffer_polygon` (буфер вокруг ИХ маршрута) — и уже есть prefilter-паттерн `ST_Contains(fov_polygon, точка)` для поиска «какие камеры видят эту точку» (§`/cameras/at-point`).

Для «камеры вдоль маршрута пользователя» — симметричная операция: строим буфер вокруг маршрута ПОЛЬЗОВАТЕЛЯ (`ST_Buffer(ST_GeomFromEWKT(route_line_ewkt), N_метров)`, тот же приём, что уже применяется к `route_line` FIXED_ROUTE-камер при импорте, `cameras.service.ts:370`) и находим все STATIONARY-камеры, чей `fov_polygon` пересекает этот буфер (`ST_Intersects`, не `ST_Contains` — сектор камеры может частично попадать в буфер маршрута, не обязательно целиком).

```sql
SELECT id, name, lat, lng, azimuth, fov_angle, range_meters
FROM "Camera"
WHERE deleted_at IS NULL
  AND confidence = 'VERIFIED'
  AND mobility_type = 'STATIONARY'
  AND fov_polygon IS NOT NULL
  AND ST_Intersects(fov_polygon, ST_Buffer(ST_GeomFromEWKT($1), $2))
```

Радиус буфера (`N_метров`) — **решено (прямой запрос пользователя): 250–400м** (шире, чем предварительно прикинутые 150–250м, — сопоставимо с `MAX_TARGET_RADIUS_M = 120` в `btw-geometry.util.ts`, но с явным запасом на типичный `rangeMeters` камер и погрешность геометрии маршрута). Конкретное значение в этом диапазоне (250 vs 400) — по плотности камер в городе; возможна донастройка по результатам реального использования, но диапазон больше не открытый вопрос.

**✅ Реализовано (2026-08-06):** `BtwRouteForecastService.findCamerasAlongRoute()` (`apps/api/src/btw/btw-route-forecast.service.ts`) — ровно этот SQL-приём (`ST_Intersects(fov_polygon, ST_Buffer(...))`), радиус зафиксирован как **300м** (середина решённого диапазона 250–400м, конкретное значение — выбор реализации, не переспрошено у пользователя отдельно). Вызывается автоматически при каждом `POST /btw/route` — не отдельный эндпоинт.

### 4.2. Позиция вдоль маршрута (для сортировки/отображения)

Для каждой найденной камеры — расстояние вдоль маршрута до неё нужно для сортировки списка «по пути» (§2.1, шаг 5). Прямое переиспользование `nearestPointOnRoute(route, cameraPoint)` (`geometry.util.ts`, уже существует, см. §0 таблицу) — возвращает `offsetMeters` (расстояние от начала маршрута) и `distanceToRouteM` (насколько камера в стороне от линии маршрута — полезно тоже показать, «камера в 30м от дороги»).

**✅ Реализовано (2026-08-06):** ровно так, как описано выше — `nearestPointOnRoute` вызывается для каждой найденной камеры, список сортируется по `offsetMeters`, `distanceToRouteM` передаётся на клиент и показывается в списке («камера в N м от дороги»).

### 4.3. FIXED_ROUTE-камеры вдоль маршрута

Не отдельная задача — уже решена `POST /lookahead` (глава 17 ТЗ, `apps/api/src/lookahead`). Новому экрану нужно только **правильно собрать `points: [{lat,lng,timestampOffsetSeconds}]`** из геометрии построенного маршрута + расчётной скорости (см. §6) и передать в уже существующий эндпоинт.

**✅ Реализовано (2026-08-06):** `BtwRouteForecastService.findFixedRouteEncounters()` — ровно как предполагало ТЗ: сам `LookAheadService`/`predictRouteMeetings()` не изменён ни на строчку, новый код только строит `points` (даунсэмплинг декодированного polyline до 200 точек + `timestampOffsetSeconds` = накопленное расстояние / средняя скорость из ответа OpenRouteService) и вызывает уже существующий метод напрямую (без HTTP-запроса на себя же — прямая инъекция `LookAheadService` в новый сервис, тот же модуль `LookAheadModule` импортирован в `BtwModule`).

## 5. Сопровождение в поездке

### 5.1. Что показывать

Живой список «что впереди» (следующие ~500м–1км или ~2–5 минут пути) — камеры (§4) и известные проблемы (§7), отсортированные по `offsetMeters` относительно текущей позиции пользователя вдоль маршрута.

**✅ Реализовано (2026-08-06)** — `buildAheadItems()` (`app/page.tsx`) фильтрует камеры/инциденты/трафик по `offsetMeters` в окне `[текущий_offset − 50м, текущий_offset + 800м]` (800м — середина заявленного диапазона 500м–1км, конкретное число не зафиксировано ТЗ; 50м «назад» — запас на погрешность/задержку GPS-фикса, чтобы список не «мигал»), сортирует по возрастанию. FIXED_ROUTE-встречи (трамваи и т.п.) сознательно показаны ОТДЕЛЬНЫМ блоком, сортированным по ETA — у них нет стабильного `offsetMeters` вдоль маршрута (это прогноз движущейся цели, §4.3), тот же подход, что уже был в до-поездковой секции «Вдоль маршрута» (Этап 2).

### 5.2. Трекинг прогресса — переиспользует существующую геометрию

`nearestPointOnRoute(route, текущая_GPS_точка)` (уже существует, §0) на каждый GPS-фикс даёт:
- `offsetMeters` — где пользователь сейчас находится вдоль маршрута (для фильтра «что впереди», §5.1);
- `distanceToRouteM` — насколько пользователь отклонился от линии маршрута.

**⚠️ ЧЕСНО — уточнение порога.** Ранее (первая версия этого раздела ТЗ, до текущего решения) был зафиксирован порог **300м** — как порог для *индикатора* «вы отклонились от маршрута», при том что авто-ре-роутинг тогда сознательно оставался вне MVP (см. старую редакцию §5.3 ниже, зачёркнутую логику). Прямым следующим запросом пользователь задал **порог 200м уже для авто-ре-роутинга**: «авто-ре-роутинг внести в тз - при превышении порога отклонения от маршрута 200 м». Пользователь не уточнил, заменяет ли 200м прежние 300м индикатора или это два разных порога (более чувствительный — для запуска пересчёта, более грубый — просто для индикатора). **Решение этого документа (требует подтверждения пользователя при реализации): унифицировать в один порог — 200м** — и для индикатора «вы отклонились», и как триггер авто-ре-роутинга (§5.3). Обоснование унификации: два отдельных, близких по величине порога (200м/300м) для одного и того же измеряемого значения (`distanceToRouteM`) — источник путаницы в UI (индикатор загорится, а пересчёт ещё не начнётся, 100м «серой зоны») без явной пользовательской пользы; единый порог проще объяснить в UI («вы отклонились — строим новый маршрут») и проще реализовать. Если пользователь имел в виду именно два разных порога — нужно явно сказать при следующей итерации, разделить обратно легко (два отдельных константы вместо одной).

Итого — **решено: единый порог `distanceToRouteM` = 200м** (супersedes/обновляет прежние 300м) → одновременно (а) индикатор «вы отклонились от маршрута» в UI и (б) триггер авто-ре-роутинга (§5.3). `pointAtDistanceAlongRoute(route, offsetMeters + N)` (тоже уже существует) по-прежнему даёт «точку впереди» для предпросмотра/переключения в режим скана (§2.4) независимо от порога отклонения.

**✅ Подтверждено пользователем и реализовано (2026-08-06)** — при реализации Этапа 3 (за прямым запросом «полностью реализовать п 3 и п 4 по тз») пользователю прямым вопросом (`AskUserQuestion`) был задан именно этот открытый вопрос; ответ — «Да, единый порог 200м (Рекомендуется)». `DEVIATION_THRESHOLD_M = 200` (`app/page.tsx`) — единственная константа, используется и для индикатора отклонения, и как триггер `triggerReroute()` (§5.3). Двух отдельных порогов НЕ вводилось.

### 5.3. Автоматическое перестроение маршрута (обновлено — прямой запрос пользователя: авто-ре-роутинг в MVP)

**Решено (прямой запрос пользователя): «авто-ре-роутинг внести в тз - при превышении порога отклонения от маршрута 200 м»** — авто-ре-роутинг переходит из категории «будущее, вне MVP» (как было в предыдущей редакции этого раздела) в активный объём MVP, Этап 4 (§8).

**Механика:**
1. Каждый GPS-фикс во время «Сопровождения» (§5.1) считает `distanceToRouteM` через `nearestPointOnRoute` (§5.2).
2. Как только `distanceToRouteM` превышает порог 200м (§5.2) — запускается пересчёт маршрута: повторный вызов OpenRouteService (§6.1) с новой точкой А = текущая GPS-позиция пользователя, той же точкой Б (исходный пункт назначения) и, если есть, ещё не пройденными промежуточными точками.
3. Пока пересчёт не завершился — старый маршрут остаётся отображённым и активным (нет «мигания» на пустой экран); в UI — ненавязчивый индикатор «Строим новый маршрут…» (переиспользует стиль индикатора «вы отклонились», §5.2 — по сути одно и то же событие).
4. Когда ответ приходит — новый маршрут заменяет старый, список камер вдоль маршрута (§4.1) и прогноз (§7) пересчитываются для новой геометрии (тот же путь, что и при первом построении маршрута, §2.1, просто без явного действия пользователя).

**Анти-race/дебаунс — переиспользует существующий паттерн, не новый:** та же ситуация, что уже решена в BTW-сканировании (`apps/btw/lib/btwLocalScanner.ts`, класс `ScanSupersededError` + `pending`-карта в `scan()`, и парный клиентский `lastScanRef` в `page.tsx` для серверного пути `/api/scan`, см. `doc/AUDIT-btw-radar-m1-m2.md`) — если GPS продолжает поступать во время пересчёта (частый случай, движение продолжается), новый пересчёт может быть запрошен раньше, чем пришёл ответ на предыдущий. Тот же принцип «важен только последний результат» применяется здесь: (а) следующий вызов OpenRouteService отменяет/игнорирует ещё не завершённый предыдущий (через `AbortController` на fetch, аналог того, что делает `ScanSupersededError` для воркер-сообщений); (б) простой **кулдаун** между пересчётами (например, не чаще одного пересчёта в 15–20 секунд) — предотвращает шквал запросов к платному API (§6.1) при движении вдоль границы 200м-порога (частый краевой случай — путь идёт параллельно основному маршруту на расстоянии, близком к порогу).

**⚠️ ЧЕСНО — упрощения и риски этой части MVP:**
- **Стоимость/лимиты API.** Каждый авто-пересчёт — отдельный запрос к OpenRouteService (§6.1, бесплатный тир ограничен, порядка ~2000 запросов/день на момент написания — актуальные цифры проверить на сайте). Частые отклонения на длинной поездке (например, у пользователя, который систематически едет своим путём, отличным от предложенного) могут заметно увеличить расход лимита по сравнению с ручным «Построить маршрут заново» (было до этого решения) — кулдаун выше снижает, но не устраняет риск.
- **Нет учёта трафика в пересчитанном маршруте.** Как и исходный маршрут (§6/§7), пересчитанный маршрут — чисто геометрический (OpenRouteService не даёт живых пробок, §7.2) — авто-ре-роутинг решает задачу «маршрут больше не соответствует фактической позиции пользователя», а не задачу «объехать пробку впереди» (последнее зависит от исхода Этапа 1, `oktraffic.org`, §7.2, и в объём этого решения не входит).
- **Ручной путь остаётся.** Кнопка «Построить маршрут заново» (была в предыдущей редакции этого раздела) не убирается — остаётся полезной, если пользователь хочет пересчитать маршрут не дожидаясь превышения порога 200м (например, увидел затор на глаз).

**✅ Реализовано (2026-08-06)** — вся механика п.1–4 выше подключена в `app/page.tsx`: `handleTripFix()` (GPS-фикс → `nearestPointOnRoute` → проверка порога), `triggerReroute()` (вызов `fetchRoute()` с новой точкой А, `AbortController` отменяет ещё не завершённый попередній виклик — п.1 анти-race), `lastRerouteTriggerAtRef` + `REROUTE_COOLDOWN_MS = 20_000` (стартова величина з верхньої межі запропонованого діапазону 15–20с, як і сказано вище, — не відкалібрована) — п.2 анти-race. Індикатор «Строим новый маршрут…» — той самий стиль, що й індикатор відхилення (п.3, `rerouting` стан). «Ручний шлях» (останній пункт вище) — окрема кнопка «🔄 Пересчитать маршрут вручную» в UI поїздки, викликає той самий `triggerReroute()`, доступна незалежно від порогу 200м і кулдауну.

## 6. Маршрутизация — движок построения пути

В проекте сейчас нет ничего, что строит путь A→Б по дорогам (проверено — только `geocoding.service.ts` для адрес→координаты). Нужен внешний движок. Важное архитектурное решение — **разделить две разные задачи**, которые легко перепутать:

1. **Построение геометрии маршрута** (путь по дорогам, расстояние, время в пути) — чистая математика по графу дорог, не требует «живых» данных.
2. **Прогноз дорожной ситуации** (§7) — это данные RoadScout (свои камеры + `situational`-модуль +, возможно, внешний источник трафика), накладываемые НА уже построенный маршрут, а не часть самого маршрутизатора.

Смешивать их не обязательно — платный «трафик» в коммерческих Directions API (Google/Mapbox) нужен только если своего источника прогноза нет; раз у проекта уже есть/строится собственный источник (см. §7), для (1) можно взять существенно более дешёвый/бесплатный вариант.

### 6.1. Рекомендация для MVP

**OpenRouteService** (openrouteservice.org, построен поверх той же OSM-экосистемы, что уже использует парсер камер через Overpass API):
- бесплатный API-ключ, разумный бесплатный лимит для старта (~2000 запросов/день, ~40/мин на момент написания — **проверить актуальные лимиты на сайте перед принятием решения**, тарифы меняются);
- ничего не нужно хостить/поддерживать — HTTP-вызов из `apps/api`, тот же паттерн, что уже `geocoding.service.ts`/`AzimuthHeuristicService` (внешний HTTP API с таймаутом);
- отдаёт геометрию маршрута (polyline/GeoJSON), расстояние, оценку времени в пути — этого достаточно для §2.1 и построения `points` для `/lookahead` (§4.3).
- Альтернатива с похожим профилем (бесплатный тир, OSM-based, без хостинга) — GraphHopper Cloud API; выбор между ними — вопрос вкуса/лимитов на момент реализации, не принципиальная разница для этого ТЗ.

### 6.2. Путь роста (не MVP)

**OSRM self-hosted** — бесплатно НАВСЕГДА (свои данные OSM, без лимита запросов), но требует отдельный постоянно работающий сервис (Docker-контейнер с предобработанным OSM-экстрактом Украины) — НЕ вписывается в текущий serverless-деплой `apps/api` на Vercel напрямую (то же ограничение, что уже задокументировано для in-process кэша FIXED_ROUTE-позиций, `doc/README.md`), нужен отдельный хостинг (Fly.io/Railway/VPS) и процесс обновления OSM-экстракта. Разумный апгрейд, когда/если бесплатный лимит OpenRouteService станет тесен — не блокер для старта.

### 6.3. Провайдер — решено

**Решено: OpenRouteService** (§6.1). Пользователь регистрирует аккаунт и получает API-ключ на openrouteservice.org самостоятельно (действие вне этой кодовой базы) — переменная окружения `apps/api`: `OPENROUTESERVICE_API_KEY` (см. `.env.example`), тем же паттерном, что уже другие внешние API-ключи в проекте.

**✅ Реализовано (2026-08-06):** за прямым запросом пользователя «маршрутизация не вызывается — ключа OpenRouteService пока нет (§6.3) исправь» — `apps/api/src/routing/openrouteservice.service.ts` (`OpenRouteServiceClient`), реальний виклик `POST https://api.openrouteservice.org/v2/directions/{profile}` (plain-JSON, НЕ `/geojson`), декодування Google encoded polyline вручну (немає мережі для встановлення npm-пакета в цій пісочниці), локальний троттлінг ~40/хв (той самий чесний застереження, що вже TomTom — не персистентний, не гарантія на serverless з кількома інстансами). Підключено в `BtwModule` (провайдер, той самий принцип, що вже `RegistryProxyService`), новий ендпоінт `POST /btw/route` (`TelegramAuthGuard`) → `BtwService.buildRoute()` → мапить помилки в конкретні HTTP-статуси (503 — немає/невірний ключ, 429 — ліміт, 400 — маршрут не знайдено, 502 — інша помилка upstream). Клієнт (`apps/btw/app/page.tsx`) показує різні чесні повідомлення залежно від причини. ⚠️ ЧЕСНО: цей клієнт НЕ був живо протестований проти справжнього OpenRouteService API в цьому сендбоксі (немає мережевого доступу) — схема запиту/відповіді взята з офіційної документації, той самий рівень впевненості, що вже задокументований для TomTom (на відміну від 511NY, який був живо перевірений). Без ключа на сервері §4.3/§5 (авто-ре-роутинг, «Сопровождение в поездке») усе ще не можуть використовувати реальну маршрутизацію — сам цей крок (§2.1, разова побудова маршруту) вже може.

### 6.4. Профили маршрутизации — решено (прямой запрос пользователя)

**Решено: явный выбор профиля в UI** — «большинство роутеров (включая OpenRouteService) поддерживают несколько профилей «из коробки» — выбор профиля в UI можно добавить дёшево, добавить в тз». Раньше (§9/§10 предыдущих редакций) это было открытым вопросом («пеший режим vs автомобильный — не разделены явно») — теперь входит в объём MVP, не в будущее.

**Механика:**
- OpenRouteService принимает профиль как часть эндпоинта запроса (`/v2/directions/{profile}`) — это не отдельный API-ключ и не отдельная интеграция, просто параметр уже строящегося запроса (§6.1/§6.3).
- Для MVP — три профиля, по стандартным именам OpenRouteService: **`driving-car`** (авто, значение по умолчанию — самый частый сценарий приложения про камеры на дорогах), **`cycling-regular`** (велосипед), **`foot-walking`** (пешком, прямая реализация ранее заявленного, но не сделанного BTW-tz.md §3.5 «что за поворотом», см. §0 таблицу выше).
- UI: переключатель профиля на экране «Построить поездку» (§2.1, между шагом 3 «точка Б» и шагом 4 «Построить маршрут») — три иконки/таба (авто/велосипед/пешком), `driving-car` выбран по умолчанию. Смена профиля ПОСЛЕ построения маршрута — просто новый вызов OpenRouteService с тем же А/Б, но другим профилем (не отдельный флоу).
- Профиль влияет только на геометрию/время маршрутизатора (§6) — на буфер камер вдоль маршрута (§4.1, 250–400м) и порог отклонения (§5.2, 200м) профиль **не** влияет; это сознательное упрощение (см. §10) — в реальности пешеход отклоняется от маршрута на существенно меньшем расстоянии, чем водитель, но раздельная калибровка порогов по профилю — не в объёме первой версии.
- Авто-ре-роутинг (§5.3) переиспользует выбранный профиль без изменений — пересчёт маршрута идёт в том же профиле, в котором был построен исходный.

## 7. Прогноз дорожной ситуации вдоль маршрута

### 7.1. Что уже есть и переиспользуется

`situational`-модуль (`apps/api/src/situational`): `WeatherService.getSnapshot()` (погода дождь/туман/гололёд по опорным точкам городов) и `RoadIncidentsService.listActive()` (вручную заводимые ДТП/внештатные ситуации). Оба сейчас **городского уровня**, не привязаны к конкретному маршруту.

Для этого экрана нужна route-aware фильтрация: инциденты, чья точка попадает в тот же буфер маршрута, что уже строится для камер (§4.1) — `ST_Intersects`/`ST_DWithin` от точки инцидента до буфера маршрута, тот же геометрический приём. Погода — можно брать ближайшую опорную точку к каждому сегменту маршрута (или просто к городу, в котором маршрут в основном пролегает, — упрощение, приемлемое для MVP).

**✅ Реализовано (2026-08-06):** за прямым запросом пользователя «полностью реализовать п 1 и п 2 по тз» — `BtwRouteForecastService.findIncidentsAlongRoute()`/`findNearestWeather()`. Инциденты (`RoadIncident` — нет PostGIS-геометрии, только `lat`/`lng`, см. schema.prisma) фильтруются route-aware, но **в JS через `nearestPointOnRoute()`, не SQL `ST_DWithin`** — функционально эквивалентно (то же измеряемое расстояние до линии маршрута), но не отдельным геозапросом, буфер 500м. Погода — взято самое простое из двух явно допущенных ТЗ упрощений: одна ближайшая опорная точка `WeatherService` к географическому центру маршрута (не к каждому сегменту отдельно).

### 7.2. Реальный прогноз загруженности/пробок — 511NY (основной источник) + TomTom (fallback)

**✅ Реализовано (2026-08-06):** парсер `apps/api/src/situational/five11ny.service.ts` (`FiveElevenNyService`) + визуализация на `/admin/situational` (`components/NyTrafficMap.tsx`, `components/NySituationalPanel.tsx` — карта штата Нью-Йорк, вертикальный селектор слоёв «Инциденты 511NY» + 5 слоёв Windy) — по прямому запросу пользователя, в рамках Этапа 2 (§8).

**Решено: 511NY — основной источник, TomTom Traffic API — fallback.**

- **511NY** (`511ny.org`) — официальная система дорожной информации штата Нью-Йорк (NYSDOT), покрывает NYC и весь штат. Есть публичный REST API (`GetEvents`/`GetCameras`/`GetAlerts`) с реальными инцидентами (ДТП, ремонт, перекрытия, полосы, VMS-табло), геопозицией и таймстампами. **Бесплатно** — Developer's Access Agreement явно разрешает бесплатное и коммерческое использование; нужна только регистрация аккаунта разработчика и получение ключа. Лимит — 10 запросов/60 сек (для route-aware опроса вдоль буфера маршрута, §4.1, этого достаточно — опрос идёт по региону/маршруту, не поштучно на каждую камеру). Формат — JSON или XML, ключ — переменная окружения `apps/api` (например `FIVE11NY_API_KEY`), тот же паттерн, что уже `OPENROUTESERVICE_API_KEY` (§6.3). Часть полей может быть помечена «FOR OFFICIAL USE ONLY» с ограничением на распространение — проверить по факту получения ключа, какие именно поля это затрагивают.
- **TomTom Traffic API** — fallback/дополнение вне NY State. **✅ Реализовано (2026-08-06)** — `Traffic Incidents` (v5 `incidentDetails`, классический, НЕ Orbis) подключён и визуализирован (см. выше); `Traffic Flow` (скорость/загруженность по сегментам) — НЕ реализован, только Incidents, для паритета с тем, что показывает 511NY-секция (погода отдельно через Windy, не через TomTom Flow). Глобальное покрытие — полезно, если проект расширится за пределы Нью-Йорка на города, где 511NY-аналога нет. Бесплатный тир — 2500 запросов/мес на Incidents, 20000/мес на Flow (Flow пока не используется), без карты для регистрации; ключ — переменная окружения `TOMTOM_API_KEY` (уже добавлена в `.env.example`).
- **Логика выбора источника в коде:** по городу маршрута (`citySlug`/штат) — для Нью-Йорка (и в перспективе других городов NY State) запрос идёт в 511NY; для городов вне зоны покрытия 511NY — в TomTom (если он подключён) или просто пропуск трафик-слоя (деградация к §7.1: только погода/инциденты). Единый внутренний интерфейс (`TrafficProvider.getIncidents(routeBuffer)` или аналог) скрывает разницу форматов ответа обоих провайдеров от остального кода прогноза (§7.1, route-aware буфер).

**✅ Реализовано (2026-08-06):** маршрут не привязан к `City`-записи (строится по свободным координатам, не по городскому справочнику), поэтому вместо точной привязки к штату/округу — **грубое приближение границ штата Нью-Йорк прямоугольником** (`NY_STATE_BBOX` в `btw-route-forecast.service.ts`, НЕ настоящий контур штата): если маршрут касается этого прямоугольника — источник 511NY, иначе — TomTom-фолбэк (bbox строится напрямую по крайним точкам маршрута + отступ, отдельная функция `routeBoundingBox()`, не переиспользует `centerRadiusToBoundingBox()` из `tomtom.service.ts` — та рассчитана на один центр+радиус, не на протяжённую линию маршрута). Отдельного интерфейса `TrafficProvider` не заводилось — оба источника нормализуются в единую форму `TrafficEventAlongRoute` прямо внутри `findTrafficAlongRoute()`, без отдельной абстракции (не запрошено, сочтено избыточным для двух конкретных источников).

Интеграция обоих источников в прогноз вдоль маршрута (§7.1, тот же route-aware буфер, что уже для камер §4.1) — **✅ реализовано (2026-08-06)**, была частью Этапа 2 (§8) — за прямым запросом пользователя «полностью реализовать п 1 и п 2 по тз».

- **511NY/TomTom выбор источника — грубый bbox штата Нью-Йорк, не настоящая граница.** См. §7.2 обновление выше — маршрут, formально проходящий рядом с (но не строго внутри) реальной извилистой границы штата, может получить не тот источник трафика, что "правильнее" географически. Не запрошено более точное решение (геокодинг штата/округа по каждой точке маршрута).
- **`findFixedRouteEncounters()` — средняя скорость маршрута, не поточная.** `timestampOffsetSeconds` для каждой точки маршрута считается через ЕДИНУЮ среднюю скорость (`distanceMeters/durationSeconds` всего маршрута ORS) — не учитывает, что на светофорах/пробках скорость ниже, а на трассе — выше, поэтому прогноз "когда именно я буду в такой-то точке маршрута" неточен пропорционально этой неравномерности (тот же класс упрощения, что уже §5.3 честно отмечает для авто-ре-роутинга — "чисто геометрический пересчёт").
- **Погода — одна точка на весь маршрут, не по сегментам.** §7.1 явно допускало оба упрощения ("к каждому сегменту" ИЛИ "просто к городу") — реализовано самое простое: одна ближайшая опорная точка `WeatherService` к географическому центру маршрута. Длинный маршрут, пересекающий несколько городов/климатических зон, покажет погоду только этого одного центра, не всего пути.
- **Форекаст вдоль маршрута деградирует мягко, но молча по каждому источнику отдельно.** Если, например, PostGIS-миграция для камер не прогнана — `camerasAlongRoute` придёт пустым списком БЕЗ явного признака "ошибка" на клиенте (тот же паттерн деградации, что уже `findCandidatesNearPoint()` в `cameras.service.ts`) — пользователь увидит просто "камер не найдено", неотличимо от честного "камер там действительно нет". Осознанный компромисс ради того, чтобы сбой второстепенного источника не блокировал уже построенный маршрут (см. `BtwService.getForecastSafely()`), но означает, что диагностировать причину пустого списка можно только по серверным логам, не из UI.
- **Сопровождение в поездке (§2.2/§5, Этап 3) — `watchPosition`, не фоновый трекинг.** Живе стеження працює лише поки відкрита вкладка/Telegram Mini App активний (`navigator.geolocation.watchPosition`, стандартне обмеження веб-геолокації) — на відміну від нативних навігаторів, немає фонового трекінгу, коли застосунок згорнутий/екран заблокований. Не запрошено і не реалізовано (виходить за межі можливостей Telegram Mini App без нативного плагіна).
- **`AHEAD_WINDOW_M = 800` і `AHEAD_BACK_TOLERANCE_M = 50` (§5.1) — вибір реалізації, не число з ТЗ.** ТЗ задає діапазон "~500м-1км або ~2-5 хвилин" без точного числа; 800м узято як середина діапазону, 50м "назад" — довільний запас на похибку GPS-фікса. Обидва — кандидати на донастройку за результатами реального використання, той самий клас упрощення, що вже §10 відзначає для буфера камер/порогу відхилення.
- **Ручний "Пересчитать маршрут вручную" не оновлює кулдаун авто-ре-роутингу.** Кнопка ручного перерахунку (§5.3, "ручний шлях залишається") викликає той самий `triggerReroute()`, але НЕ записує час у `lastRerouteTriggerAtRef` — тобто одразу після ручного перерахунку, якщо відхилення все ще > 200м, наступний GPS-фікс може одразу ж запустити ЩЕ ОДИН (автоматичний) перерахунок, не чекаючи повного кулдауну. Малоймовірний і не шкідливий крайовий випадок (просто зайвий запит до OpenRouteService), не виправлено — ускладнило б код заради рідкісного сценарію.
- **Клієнтський `nearestPointOnRoute()` (`lib/geometry.ts`) — точна копія серверного алгоритму, окремо підтримувана копія.** Той самий свідомий компроміс дублювання клієнт/сервер, що вже й решта `lib/geometry.ts` (§0 таблиця) — у проєкті немає спільного workspace-пакета типів/утиліт; зміна алгоритму на сервері (`common/geometry.util.ts`) НЕ підхопиться автоматично клієнтом, вимагає ручної синхронізації обох копій.
