# ТЗ: пошук камер через YouTube Search API (окреме джерело, доповнення до webcam.guru.ua)

## Статус реалізації

✅ **Реалізовано повністю (П0–П5)** — див. `doc/AUDIT-youtube-camera-discovery.md` за деталями
й результатами реального тестування (30 перевірок, включно з точним прикладом шуму із
реального скріншота користувача).

## Контекст

`webcam.guru.ua` дає мало камер, і значна їх частка виявилась непрацюючою (посилання на
видалені/приватні YouTube-відео — див. `doc/AUDIT-camera-content-availability.md`,
`doc/AUDIT-embed-bare-url-fix.md`). Мета цього ТЗ — окреме джерело, яке шукає публічні
live-трансляції камер напряму через YouTube Data API v3 (`search.list`), з упором на потрібну
географію проєкту (міста України, де вже є `City`-записи з координатами).

Це **свідомо тільки публічні, самостійно опубліковані трансляції** (на відміну від
Insecam/Shodan/гугл-дорків — див. попереднє обговорення, чому ці джерела виключені з розгляду).

## Ціль

Новий, повністю окремий провайдер-адаптер (`YoutubeSearchAdapter`), що працює за тим самим
контрактом `ProviderAdapter`, що й `WebcamGuruAdapter`, і використовує вже існуючий пайплайн
(`ScraperService`, `CameraSourceRaw`, чергу ревʼю, AI-помічник на етапі ручного ревʼю) без
дублювання інфраструктури.

---

## П0. Провайдер і конфігурація

- Новий адаптер `apps/api/src/scraper/providers/youtube-search.adapter.ts`, `adapterKey`:
  `youtube-search-{citySlug}` (той самий принцип, що `webcam-guru-{citySlug}` — один екземпляр
  адаптера = одне місто).
- Новий `CameraProvider` на кожне місто з `City.lat`/`City.lng` (для геофільтра) — окремий
  SQL-сід `sql/youtube-search-providers-seed.sql`, за зразком `camera-providers-seed.sql`.
- Новий env: `YOUTUBE_DATA_API_KEY` (окремий ключ Google Cloud, `YouTube Data API v3` треба
  включити на проєкті — той самий принцип, що вже задокументований для Places API).
- **Критерій приймання**: провайдер видно в `/admin/parser`, запуск через «Запустить сейчас»
  не падає навіть без реального ключа (чіткий `ERROR` в журналі, не краш).

## П1. Discover() — пошук через `search.list`

- Запит: `type=video&eventType=live&location={City.lat},{City.lng}&locationRadius=25km&q=веб камера|webcam|онлайн трансляция&regionCode=UA&relevanceLanguage=uk&maxResults=50`.
- **VPN** (`RegistryProxyService`, той самий механізм, що вже використовує `WebcamGuruAdapter`) —
  опціональний параметр конструктора; якщо `REGISTRY_SCAN_PROXY_URL` налаштований, запити до
  `googleapis.com` йдуть через нього з автоматичним фолбеком на прямий запит, якщо сам проксі
  недоступний. Реалізовано і протестовано — див. `doc/AUDIT-youtube-camera-discovery.md`.
- **Дворівневий запит** (для повноти покриття — гео-фільтр відсікає відео без геотегу):
  1. З `location`/`locationRadius` — точні, геотеговані результати.
  2. Без `location`, тільки `q="веб камера {назва міста}"` — текстовий пошук ширший, але
     потребує ретельнішої фільтрації на етапі AI-класифікації (П3).
- Квота: `search.list` = 100 одиниць/виклик, дефолтна квота 10 000/добу → **не більше 90
  викликів на добу** (лишає запас). Один прохід `runAll()` на всі міста = 2 виклики на місто
  (гео + текстовий) — при ~15-20 містах це вже 30-40 викликів, отже **`runAll()` для цього
  провайдера має власний, окремий, значно рідший розклад** (не той самий 2-годинний цикл, що
  webcam.guru.ua) — раз на добу, окремий cron-запис.
- Дедуплікація: `externalId = videoId` (з `id.videoId` відповіді) — при повторному знаходженні
  того самого відео на наступному проході `ScraperService` вже коректно обробляє через
  `SKIPPED_ALREADY_RESOLVED`, нічого додаткового писати не треба.
- **Критерій приймання**: реальний виклик на 2-3 тестових міста повертає результати БЕЗ падіння
  при вичерпанні квоти (чітка обробка `403 quotaExceeded` — зупинка проходу з поясненням у
  журналі, не краш; наступний плановий прохід продовжує з того місця, де зупинився, той самий
  принцип бюджету часу, що вже є в П3.2 парсера).

## П2. fetchDetails() — те, що вже є в `WebcamGuruAdapter`, тут не потрібне

`search.list` з `part=snippet` уже дає `title`+`channelTitle`+`videoId` за один виклик — окремої
фази 2 (дозапиту сторінки відео) не потрібно, `discover()` одразу повертає повний
`RawCameraItem` (не плейсхолдер) зі `streamType: YOUTUBE_LIVE`, `streamUrl:
https://www.youtube.com/watch?v={videoId}`.

- `locationText` — беремо назву відео (`snippet.title`) як є, той самий підхід, що вже
  застосований для webcam.guru.ua (назва камери = орієнтир для геокодингу).
- **Критерій приймання**: створена `CameraSourceRaw` містить справжній `videoId`-based
  `streamUrl` виду `watch?v=...` (не голий канал, не корінь домену — та сама помилка, що вже
  була знайдена й задокументована в `doc/AUDIT-embed-bare-url-fix.md`, тут структурно
  неможлива, бо `videoId` завжди явний у відповіді `search.list`).

## П3. AI-фільтрація «це справді камера міста, чи шум» — ОБОВʼЯЗКОВИЙ крок перед створенням запису

Текстовий пошук (без гео-фільтра) дасть багато нерелевантного шуму (новини, стріми ігор,
музика) — на відміну від webcam.guru.ua, де кожен запис на сторінці міста вже гарантовано
камера. Тому **перед тим, як `CameraSourceRaw` взагалі створюється**, потрібна додаткова AI-
перевірка релевантності (текстова, `GrokCameraAssistService`, новий метод
`isLikelyCityCamera(title, channelTitle, description)`):

```
Промпт: "Название YouTube-видео похоже на реальную городскую веб-камеру (статичный вид улицы/
площади/перекрёстка в прямом эфире), а не на новости/игровой стрим/музыку/что-то ещё? Ответь
JSON: {"isLikelyCamera": boolean, "confidence": number, "reasoning": string}"
```

- Якщо `isLikelyCamera: false` або впевненість нижча порогу — елемент **взагалі не потрапляє
  в `CameraSourceRaw`** (не в NEEDS_REVIEW, а просто пропускається з `INFO`-записом у журналі
  «AI відфільтрував як нерелевантне») — інакше черга ревʼю захлинеться шумом.
- **Критерій приймання**: реальний тестовий прогін на кількох штучних заголовках («Прямая
  трансляция — Майдан Незалежности, Киев» vs «КОРОЛЬ И ШУТ ЛУЧШИЕ ПЕСНИ» — той самий приклад,
  що реально зустрівся в скріншоті користувача при перевірці недоступного відео) — коректно
  розрізняє.

## П4. Індор/аутдор + звʼязок з уже існуючою інфраструктурою

- Той самий `GrokCameraAssistService.suggestAddressAndType()` (уже є) викликається на етапі
  ручного ревʼю адміном — жодної нової логіки індор/аутдор писати не треба, повністю
  перевикористовується.
- Індор-камери з цього джерела так само виключаються з пошуку за сектором (`locationType:
  INDOOR` → `fov_polygon` не будується) — уже існуючий механізм, тут просто ще одне джерело
  даних для нього.

## П5. Періодична перевірка живучості (уже існуюча інфраструктура)

`MonitoringService.checkContentAvailability()` (уже реалізовано) автоматично покриє й ці
камери — жодних змін не потрібно, оскільки перевірка вже фільтрує за `streamType:
'YOUTUBE_LIVE'`, не за конкретним провайдером.

## Відкриті питання / ризики (чесно, до реалізації)

- **Квота 100 запитів/добу — це стеля**, не гарантія: якщо в проєкті вже є інші споживачі
  Google-квоти на тому ж проєкті Google Cloud (Places API теж там), варто завести YouTube Data
  API на **окремому** Google Cloud проєкті/ключі, щоб уникнути конкуренції за квоту.
- **Гео-фільтр (`location`/`locationRadius`) працює тільки для відео з геотегом** — багато
  авторів live-трансляцій геотег не проставляють; реальна частка покриття невідома, поки не
  перевірено на практиці (див. попередню відповідь — «Крок 2» валідації).
- Life-цикл id відео — на відміну від сталого посилання на канал, конкретне live-відео може
  завершитись і замінитись новим — потрібен періодичний повторний пошук (не одноразовий
  імпорт), що вже закладено через окремий щоденний cron.
