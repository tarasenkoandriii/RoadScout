## Контекст: что не так сейчас (кратко)

Текущий пайплайн — `ScraperService.runForProvider()` (`apps/api/src/scraper/scraper.service.ts`),
один проход = один `CameraProvider` (= один город), лог агрегированной статистики пишется в
`ParserRunLog`. Найдены проблемы, от блокирующих до второстепенных:

1. **Селекторы `WebcamGuruAdapter` (`apps/api/src/scraper/providers/webcam-guru.adapter.ts`)
   никогда не проверялись на реальной странице** — в коде прямым текстом «placeholders,
   inspect real page markup before first production run». Пайплайн, вероятно, сейчас находит 0
   камер при каждом запуске.
2. **Очередь `CameraSourceRaw.importStatus = NEEDS_REVIEW` — тупик без выхода**: нет ни одного
   API-эндпоинта, читающего эти записи списком (кроме `count()` для одной цифры в статистике),
   нет UI для просмотра/разрешения.
3. **Жёсткая зависимость от бесплатного Overpass API** (`AzimuthHeuristicService`) без кэша,
   без видимого признака отказа — при любой ошибке тихий фолбэк на `azimuth: 0`.
4. **`pg_cron`-расписание покрывает один захардкоженный `providerId`**, не все города.
5. **Синхронное выполнение внутри HTTP-запроса** — риск таймаута serverless-функции при росте
   каталога.
6. **Нет раннего сигнала о «сломанном» источнике** (например, `discoveredCount` внезапно упал
   до 0 — сайт поменял вёрстку).
7. **Обновление существующей `CameraSourceRaw` затирает предыдущие `rawStreamUrl`/`rawTitle`**
   без истории.
8. **Нет визуального превью** источника на этапе ревью.
9. **Существующий лог (`ParserRunLog`) — только агрегированные числа по проходу**, нет
   детального пошагового лога (что произошло с конкретным элементом на каждом шаге) — именно
   это просил добавить пользователь отдельно.

## Цель этого ТЗ

Дать конкретный, приоритизированный план работ с точными критериями приёмки для каждого пункта,
достаточный, чтобы следующий шаг (код) можно было делать без дополнительных уточнений.

## P1.2 — Новый детальный лог процесса импорта + отдельная вкладка

**Проблема:** существующий `ParserRunLog` — только агрегированные числа по проходу целиком
(`discoveredCount`, `newCount`, ...). Нет пошагового лога: что конкретно произошло с каждым
отдельным элементом на каждом шаге пайплайна (найден → геокодирован/не геокодирован → создана
камера / отправлено на ревью / ошибка).

### Новая модель `ImportLogEntry`

Одна запись = одно событие пайплайна, привязанное к конкретному проходу (`ParserRunLog`) и (где
применимо) к конкретному элементу (`CameraSourceRaw`/`externalId`).

Поля:
- `id`
- `runId` → FK на `ParserRunLog`
- `providerId` → FK на `CameraProvider` (дублирует `run.providerId` — для быстрой фильтрации без
  джойна на список записей одного источника за всё время, не только за один проход)
- `timestamp DateTime @default(now())`
- `level` — enum: `INFO | WARN | ERROR`
- `stage` — enum, соответствует реальным шагам `processItem()`/`runForProvider()`:
  `FETCH_PAGE` (запрос страницы источника — один на проход, не на элемент) `PARSE_ITEM`,
  `GEOCODE`, `AZIMUTH_HEURISTIC`, `CAMERA_CREATED`, `NEEDS_REVIEW`, `SKIPPED_ALREADY_RESOLVED`
  (см. ветку `existing.importStatus === 'IMPORTED' || 'REJECTED'` в текущем коде — сейчас это
  просто `return`, без всякого следа в логах), `ERROR`.
- `externalId String?` — id элемента у источника (когда событие относится к конкретной камере,
  а не к проходу в целом, например `FETCH_PAGE`)
- `cameraSourceRawId String?` → FK, если к этому моменту запись уже создана
- `message String` — человекочитаемое краткое описание («Геокодинг: уверенность 0.42, ниже
  порога 0.6», «Overpass API вернул таймаут, азимут по умолчанию»)
- `metadata Json?` — структурированные детали для отладки без раздувания `message`
  (например: `{ geocodeConfidence: 0.42, threshold: 0.6 }` для `GEOCODE`,
  `{ azimuthSource: 'heuristic' | 'fallback', httpStatus: number }` для `AZIMUTH_HEURISTIC`)

Индексы: `@@index([runId, timestamp])`, `@@index([providerId, timestamp])`,
`@@index([level, timestamp])` (для быстрой фильтрации «только ошибки за всё время»).

### Откуда пишутся записи

`ScraperService` — на каждом реальном шаге текущего кода добавляется соответствующий вызов
записи в `ImportLogEntry` (без изменения существующей логики принятия решений — это
исключительно наблюдаемость, не должно менять поведение пайплайна). Практическое правило:
каждое `return`/переход на следующий шаг внутри `processItem()` — точка, где стоит писать
запись лога, и каждый `catch` — тоже.

### Retention (не хранить вечно)

Детальный лог на уровне отдельных элементов может расти быстро (десятки записей на один
проход при реальном объёме камер). Нужна политика удержания — например,
`IMPORT_LOG_RETENTION_DAYS` (по аналогии с остальными `*_WINDOW_HOURS`/`*_RETENTION_*`
переменными окружения проекта), с фоновой очисткой (cron-задание или простая проверка «удалить
записи старше N дней» при каждом новом проходе). Конкретное значение и механизм очистки —
решить на этапе реализации, но требование зафиксировать здесь: неограниченный рост этой таблицы
недопустим.

### Backend API

- `GET /admin/parser/log` — фильтры: `?runId=&providerId=&level=&stage=&externalId=&take=&skip=`,
  сортировка `timestamp desc`. Под `AdminGuard`.
- Опционально: `GET /admin/parser/log/stream` или поллинг с коротким интервалом для
  «живого» просмотра лога прохода со статусом `RUNNING` — решить на этапе реализации, нужен ли
  реальный live-эффект, или обычного поллинга раз в несколько секунд достаточно (см. раздел
  «Открытые вопросы»).

### Frontend — отдельная вкладка

Новый роут `/admin/parser/log` (именно **отдельная** вкладка, как и просил пользователь, не
подраздел существующей `/admin/parser`):
- фильтры сверху: источник (`provider`), уровень (`INFO`/`WARN`/`ERROR`), этап (`stage`),
  диапазон дат, поиск по `externalId`;
- список записей с пагинацией (не подгружать всё разом — объём потенциально большой);
- переход по `runId` из существующей таблицы логов проходов на `/admin/parser` — открывает этот
  же экран с уже применённым фильтром по конкретному проходу (главный пользовательский сценарий:
  «этот проход подозрительно быстро завершился/дал 0 результатов — что произошло по шагам»);
- визуально различать `ERROR`/`WARN`/`INFO` (цвет строки/бейдж), чтобы проблемные события были
  заметны при беглом просмотре, а не только через фильтр.

**Критерий приёмки:** для конкретного прохода (`runId`) админ может открыть пошаговый журнал и
увидеть по каждой найденной камере, на каком именно шаге и почему она не стала полноценной
записью в реестре (либо убедиться, что стала) — без обращения к серверным логам/БД напрямую.

## P2.1 — Надёжность эвристики азимута (Overpass API)

**Проблема:** живой запрос на каждую новую камеру к общему бесплатному API, тихий фолбэк при
любой ошибке.

**Что нужно сделать:**
- Кэшировать результат по координатам (округление до сетки, например ~50-100м, чтобы соседние
  камеры переиспользовали один и тот же результат) — TTL, а не «навсегда» (дорожная сеть
  меняется редко, но не никогда).
- Сократить таймаут запроса к Overpass до разумного значения (сейчас не ограничен явно, кроме
  того, что заложено в самом Overpass-запросе — `timeout:10` в самом запросе, но не в `fetch`).
- Добавить признак **источника** итогового азимута — сохранять в `Camera` (новое опциональное
  поле, например `azimuthSource: 'heuristic' | 'fallback' | 'manual'`) и/или писать это в
  `ImportLogEntry.metadata` при событии `AZIMUTH_HEURISTIC` — чтобы можно было посчитать долю
  камер с azimuth=0-по-умолчанию против реально определённых.
- Рассмотреть self-hosted/платный Overpass-инстанс или альтернативный источник дорожного графа,
  если доля фолбэков окажется высокой на практике — это отдельное решение по фактическим данным
  после включения видимости (предыдущий пункт), не факт, что нужно делать заранее.

**Критерий приёмки:** в детальном логе (`ImportLogEntry`) и/или статистике видно, какая доля
новых камер получила азимут от реальной эвристики, а какая — фолбэк по умолчанию.

## P2.3 — Health-сигнал по источнику

**Что нужно сделать:** при завершении прохода сравнивать `discoveredCount` со скользящим
средним последних N успешных проходов этого же источника; при отклонении больше порога (оба

десятки камер, видно в интерфейсе без необходимости сравнивать числа вручную по логу.

## P3.1 — Dry-run режим

`POST /admin/parser/dry-run/:providerId` — прогоняет `adapter.discover()` (и, опционально,
геокодинг, без реального создания `Camera`/записи в `CameraSourceRaw`), возвращает то, что
было бы найдено/импортировано/отправлено на ревью, без побочных эффектов в БД. Основной сценарий
использования — проверка починки селекторов (P0.1) и любых будущих правок парсера без риска для
боевых данных.

## P3.2 — Асинхронный запуск для больших каталогов

Если после P0.1 окажется, что реальный каталог по городу — десятки-сотни камер, а полный проход
(с геокодингом и Overpass-запросом на каждую новую камеру) занимает больше нескольких секунд —
вынести выполнение из синхронного HTTP-обработчика в фоновую задачу (например, `ParserRunLog`
сразу создаётся и возвращается со статусом `RUNNING`, реальная обработка идёт в фоне, статус
опрашивается через уже существующий `GET /admin/parser/runs/:id`). Приоритет этого пункта
зависит от фактических объёмов после починки P0.1 — если каталог небольшой, можно отложить.

## P3.3 — История изменений `CameraSourceRaw`

Вместо перезаписи `rawStreamUrl`/`rawTitle` при повторном обнаружении — либо вести отдельную
таблицу истории (`CameraSourceRawHistory`, одна строка на каждое изменение), либо, как более
лёгкий вариант, просто логировать факт изменения в `ImportLogEntry` (`stage: PARSE_ITEM`,
`metadata: { previousStreamUrl, newStreamUrl }`) — второй вариант проще и, вероятно, достаточен,
раз детальный лог (P1.2) уже появляется в системе; отдельная историческая таблица имеет смысл,
только если понадобится длительное хранение/аналитика поверх этого, отдельно от retention-политики
самого лога.

## Открытые вопросы (решить на этапе реализации, не блокируют начало работ)

1. Headless-браузер (Playwright) вместо `axios`+`cheerio`, если окажется, что
   `webcam.guru.ua` рендерит список камер на клиенте — зависит от результата P0.1.
2. Отдельный контроллер `CameraSourceRawController` или расширение существующего
   `ScraperController` — архитектурное решение без функциональной разницы.
3. Живой (WebSocket/SSE) просмотр лога активного прохода или обычный поллинг раз в
   несколько секунд — второе значительно проще и, скорее всего, достаточно для внутреннего
   инструмента.
4. Конкретные пороговые значения (retention дней для лога, порог аномалии для health-сигнала,
   TTL кэша Overpass) — подобрать эмпирически после первых реальных проходов, не гадать заранее.
