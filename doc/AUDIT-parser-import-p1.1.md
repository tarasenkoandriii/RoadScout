# Аудит: реализация П1.1 (очередь ревью `CameraSourceRaw`) из `doc/TZ-parser-import-improvements.md`

## Что сделано

- Схема: `CameraSourceRaw` дополнена полями `reviewedByTelegramId`/`reviewedAt`/
  `rejectionReason` (тот же паттерн, что у `HomeAddressVerification`/`CameraSubmission`) +
  индекс `[importStatus, scrapedAt]` для быстрой выборки очереди.
- `ScraperService` дополнен четырьмя публичными методами:
  - `listSourceRaw(filters)` — по умолчанию только `NEEDS_REVIEW` (сама очередь), `status=all`
    снимает фильтр, есть фильтр по `providerId`.
  - `getSourceRaw(id)` — деталка, 404 если не найдена.
  - `resolveSourceRaw(id, adminTelegramId, dto)` — создаёт настоящую `Camera` тем же путём, что
    и авто-импорт (`confidence: 'ESTIMATED'`, `status: 'UNKNOWN'`, `syncCameraPolygon`), принимая
    либо `lat`/`lng` напрямую, либо `address` (геокодируется с подсказкой города источника — тот
    же `CityHint`, что и в `processItem()`). Помечает исходную запись `IMPORTED` с
    `cameraId`/`reviewedByTelegramId`/`reviewedAt`.
  - `rejectSourceRaw(id, adminTelegramId, reason?)` — помечает `REJECTED`.
- Осознанное архитектурное решение (зафиксировано в комментарии в коде): действия ревью **не**
  пишутся в `ImportLogEntry` — тот журнал привязан к конкретному `ParserRunLog` ("что случилось
  во время автоматического прохода"), а ручное ревью может происходить днями позже вне
  какого-либо прохода. История решения хранится прямо в полях `CameraSourceRaw`.
- Новые эндпоинты в `ScraperController`, все под `AdminGuard`:
  `GET /admin/parser/source-raw`, `GET /admin/parser/source-raw/:id`,
  `POST /admin/parser/source-raw/:id/resolve`, `POST /admin/parser/source-raw/:id/reject`.
- Новая вкладка `/admin/parser/review` — список + карточка (тот же UX-паттерн, что уже есть на
  `/admin/camera-submissions`), с формой ручного ввода (адрес ИЛИ координаты, тип потока,
  азимут/FOV/дальность с разумными дефолтами).
- Цифра «На ревью» в существующей таблице статистики `/admin/parser` стала кликабельной ссылкой
  на очередь, отфильтрованную по конкретному источнику.

## Реально прогнанные тесты (ts-node, настоящее выполнение логики)

8 сценариев с фейковыми `PrismaService`/`GeocodingService`:

1. `listSourceRaw()` без параметров показывает только `NEEDS_REVIEW`, не остальные статусы.
   **Пройден.**
2. `listSourceRaw({ status: 'all' })` снимает фильтр — видно записи любого статуса. **Пройден.**
3. `getSourceRaw()` на неизвестный id бросает 404. **Пройден.**
4. `resolveSourceRaw()` с явными `lat`/`lng` создаёт камеру с этими координатами и **не
   вызывает геокодинг вообще** (проверено счётчиком вызовов `geocode()`), проставляет
   стандартные дефолты (`confidence: 'ESTIMATED'`, `status: 'UNKNOWN'`), помечает исходную
   запись `IMPORTED` с `cameraId`+`reviewedByTelegramId`. **Пройден.**
5. `resolveSourceRaw()` только с `address` (без координат) → геокодинг вызывается **с
   подсказкой города источника** (проверено, что переданный `cityHint.name` совпадает с городом
   провайдера, не абстрактным «Україна»). **Пройден.**
6. `resolveSourceRaw()` без адреса и без координат → `BadRequestException`, понятное сообщение.
   **Пройден.**
7. `resolveSourceRaw()` с адресом, который геокодинг не смог разрешить (вернул `null`) →
   `BadRequestException`, **камера не создаётся** (проверено — `cameras.length === 0` после
   попытки). **Пройден.**
8. `rejectSourceRaw()` корректно проставляет `REJECTED`+причину+telegramId ревьюера.
   **Пройден.**

Плюс `tsc --noEmit` над всем модулем `src/scraper/*` вместе с `app.module.ts` — 0 ошибок,
относящихся к изменённым файлам.

## Не проверено / известные ограничения

- Фронтенд-страница `/admin/parser/review` — проверена балансом скобок и вручную вычитана, не
  прогонялась через `tsc`/визуально в браузере (та же, уже неоднократно задокументированная в
  других аудитах этого проекта причина нестабильности самодельной заглушки `@types/react` в
  этой конкретной песочнице).
- Реальный `prisma db push` с новыми полями — не прогонялся против настоящего Postgres; поля
  все опциональные, обратная совместимость по построению, но не проверено вживую.
- Решение не писать действия ревью в `ImportLogEntry` — архитектурный выбор в рамках толкования
  ТЗ (сам документ П1.1 не требовал этого явно), а не то, что было формально проверено тестами
  на «правильность» — при желании можно пересмотреть, сделав `ImportLogEntry.runId` опциональным
  полем и логируя туда и ручные действия тоже, для единого журнала по всем событиям вокруг
  `CameraSourceRaw`.
