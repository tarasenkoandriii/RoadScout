# Аудит: батчування Overpass-запитів (до 20 точок за один запит)

## Контекст

Прямий запит користувача, після пояснення попереднього кроку («глибша, ризикованіша
переробка, поза обсягом»): реалізувати саме цю переробку, підняти розмір пачки до 20 точок.
За прямою вказівкою — перед реалізацією збережено точку відновлення (детальніше нижче).

## Точка відновлення (перед ризикованою зміною)

- `/home/claude/restore-points/azimuth-heuristic.service.ts.before-batching` —
  копія файлу до зміни.
- `/home/claude/restore-points/scraper.service.ts.before-batching` — копія файлу до зміни.
- `/home/claude/restore-points/roadscout-before-overpass-batching.zip` — повний знімок
  усього проєкту (усі файли, не тільки ці два) станом ПЕРЕД цим кроком — розпакувати замість
  поточного стану, якщо переробка виявиться проблемною на живому Overpass API.

## Ключове архітектурне рішення — без зміни існуючих виклик-сайтів

Замість переписування `guessForPoint()`/`processItem()` (ризиковано — торкнулося б усіх
адаптерів одразу), реалізовано **прогрів кешу**: новий метод `guessForPoints()` заповнює той
самий кеш по сітці координат (`this.cache`), яким `guessForPoint()` вже користується. Виклик
`guessForPoint()` усередині `processItem()` лишився **буквально без жодної зміни** — просто
тепер частіше отримує кеш-хіт замість власного мережевого запиту, якщо точку вже прогріто
заздалегідь одним груповим запитом.

### Де саме відбувається прогрів

У `ScraperService.runForProvider()`, **тільки для адаптерів без `fetchDetails()`** (NYC TMC,
Windy, YouTube — там, де прямі координати `suggestedLat`/`suggestedLng` вже відомі одразу з
`discover()`, до будь-якої обробки окремого елемента) — перед основним циклом обробки всі такі
координати збираються, розбиваються на пачки по 20 (`OVERPASS_BATCH_SIZE`, за замовчуванням
20) і прогріваються одним запитом на пачку. Елементи, де координати стають відомі лише ПІСЛЯ
геокодингу тексту всередині `processItem()` (webcam-guru тощо), прогріти заздалегідь
неможливо — для них `guessForPoint()` і далі робить власний одноточковий запит, як і раніше.

### Технічна складність, яку довелось вирішити — кореляція результатів

Overpass повертає **один спільний, дедуплікований список доріг** для всіх 20 запитаних точок
одразу, без явного маркування «яка дорога — до якої точки». Вирішено клієнтською кореляцією
за відстанню: для кожної вхідної точки шукається серед УСІХ повернутих доріг та, чия геометрія
проходить у межах 60м (той самий радіус, що вже був у одноточковому запиті) — вибирається
найближча. Це навіть НАДІЙНІШЕ за попередню логіку одноточкового запиту (`elements[0]` — просто
перший елемент масиву, без перевірки відстані взагалі).

## Реально прогнані тести (ts-node, справжнє виконання)

**`guessForPoints()` — 10 перевірок**:
- **Реальне батчування підтверджено**: 3 точки → рівно 1 HTTP-запит (не 3).
- Єдиний запит справді містить усі 3 пари координат, той самий радіус `around:60`.
- **Кореляція за відстанню працює коректно** — реальний тестовий сценарій із двома різними
  дорогами в одній спільній відповіді: кожна точка коректно зіставлена саме з НАЙБЛИЖЧОЮ до
  неї дорогою, не з першою в масиві.
- **Прогрів кешу реально працює**: після групового виклику наступний одноточковий
  `guessForPoint()` для ТІЄЇ Ж точки не робить жодного нового HTTP-запиту.
- Мережевий збій → усі точки коректно отримують безпечний fallback, без падіння.
- **45 точок коректно розбиваються на 3 запити** (`ceil(45/20)`), не в один гігантський запит.

**Інтеграція зі `ScraperService` — 2 перевірки** (з РЕАЛЬНИМ `AzimuthHeuristicService`, не
заглушкою): 25 елементів (як NYC TMC) → прогрів робить рівно 2 запити
(`ceil(25/20)`), не 25 окремих; усі 25 камер успішно оброблені end-to-end.

Плюс `tsc --noEmit` по всьому графу застосунку — 0 помилок у змінених файлах (2 залишкові —
той самий, вже неодноразово підтверджений артефакт спрощеної заглушки типів).

## Не перевірено / відомі обмеження (чесно, як і попереджав користувача)

- **Реальна поведінка живого Overpass API з груповими запитами по 20 точок** — недоступна в
  цій пісочниці (немає мережі). Теоретично Overpass QL підтримує кілька `way(around:...)` в
  одному union-блоці, але:
  - Реальний ліміт часу виконання складного запиту (`timeout:25` у запиті) для 20 одночасних
    `around`-умов може виявитись довшим, ніж для однієї — не вимірювалось на живому сервері.
  - Overpass може мати власні обмеження на складність/розмір запиту (кількість union-елементів),
    які не задокументовані публічно настільки чітко, щоб бути повністю впевненим у 20 як
    безпечному числі — саме тому `OVERPASS_BATCH_SIZE` винесено в env, легко зменшити (наприклад,
    до 10) без зміни коду, якщо на практиці 20 виявиться завеликим.
- Якщо груповий запит поверне ЗАНАДТО БАГАТО доріг (у щільній забудові, де багато вулиць
  потрапляють у радіус 60м від різних із 20 точок одночасно) — клієнтська кореляція виконує
  O(точки × дороги × вершини) порівнянь, що при екстремально щільній забудові теоретично
  повільніше за 20 незалежних менших запитів; для звичайного міського контексту (кілька
  сотень вершин на відповідь) це несуттєво, але не виміряно на реальних даних.
- **Якщо на практиці ця переробка виявиться проблемною** (Overpass відхиляє груповий запит,
  неправильна кореляція на реальних даних тощо) — відкотитись до попередньої, перевіреної
  версії просто, розпакувавши збережену точку відновлення
  (`roadscout-before-overpass-batching.zip`) замість поточного стану проєкту.
