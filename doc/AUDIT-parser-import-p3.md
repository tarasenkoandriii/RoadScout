# Аудит: реализация П3 (dry-run, бюджет времени, история изменений) из `doc/TZ-parser-import-improvements.md`

Финальная фаза ТЗ — весь документ (P0–P3) реализован после этого шага.

## Что сделано

### П3.1 — Dry-run режим

- `ScraperService.dryRun(providerId, deep)` — прогоняет `adapter.discover()` (и, при
  `deep: true`, реальный геокодинг каждого элемента) **без единой записи в БД** — ни
  `CameraSourceRaw`, ни `Camera`, ни `ParserRunLog`, ни `ImportLogEntry`.
  - `deep: false` (по умолчанию) — только список найденного (быстро, без внешних вызовов кроме
    самого `discover()`).
  - `deep: true` — классифицирует каждый элемент так же, как это делал бы реальный
    `processItem()` (`IMPORTED` vs `NEEDS_REVIEW`, с причиной — нет адреса / геокодинг не
    удался / уверенность ниже порога), но по-прежнему ничего не сохраняя.
- `POST /admin/parser/dry-run/:providerId?deep=true` под `AdminGuard`.
- Кнопка «Dry-run» на `/admin/parser` рядом с «Запустить сейчас» — показывает результат в
  разворачиваемой панели (таблица найденных элементов + опциональная кнопка «Углублённая
  проверка»).

### П3.2 — Бюджет времени на проход

- В цикле обработки элементов внутри `runForProvider()` — проверка `Date.now() - startedAt` перед
  каждым элементом; при превышении `PARSER_RUN_TIME_BUDGET_MS` (по умолчанию 25с) — цикл
  аккуратно останавливается: пишется явный `WARN` в `ImportLogEntry` с числом необработанных
  элементов, финальный статус прохода — `PARTIAL` (не ложный `SUCCESS`), а не необъяснимый
  таймаут/обрыв.
- Уже обработанные элементы остаются обработанными (не откатываются) — необработанные будут
  подхвачены на следующем проходе как обычно (через `CameraSourceRaw`-дедупликацию по
  `externalId`, ничего специального для этого не потребовалось).

### П3.3 — История изменений `CameraSourceRaw`

- Выбран более лёгкий из двух вариантов, которые ТЗ явно допускало ("второй вариант проще и,
  вероятно, достаточен") — **не** отдельная таблица истории, а `WARN`-запись в уже существующем
  `ImportLogEntry` (стадия `PARSE_ITEM`), когда `rawStreamUrl`/`rawTitle` при повторном
  обнаружении отличаются от того, что было раньше, — с обоими значениями (старым и новым) в
  `metadata`. Записывается **до** того, как `cameraSourceRaw.update()` затирает старые значения.
- Никакой записи не создаётся, если ничего не изменилось (не раздувает лог впустую).

## Реально прогнанные тесты (ts-node, настоящее выполнение логики)

5 сценариев с фейковыми `PrismaService`/`GeocodingService`/`AzimuthHeuristicService`:

1. **Shallow dry-run** — 4 тестовых элемента (с адресом/без, с провальным геокодингом и т.д.)
   корректно обнаружены; **подтверждено счётчиками, что абсолютно ноль записей** появилось в
   `runs`/`sourceRaw`/`cameras`/`logEntries` фейковой БД. **Пройден.**
2. **Deep dry-run** — все 4 элемента классифицированы верно: хороший адрес+высокая уверенность
   → `IMPORTED`; провальный геокодинг → `NEEDS_REVIEW` с причиной "не вернул результата";
   низкая уверенность (0.3 < порога 0.6) → `NEEDS_REVIEW` с причиной, включающей конкретные
   цифры; отсутствие адреса → `NEEDS_REVIEW` с причиной "нет текста адреса". **И снова — ноль
   записей в БД**, несмотря на реальные вызовы геокодинга. **Пройден.**
3. **Бюджет времени** — с намеренно жёстким лимитом (50мс) и эвристикой азимута, искусственно
   занимающей ~30мс на элемент, из 20 элементов реально обработалось только 2 — подтверждено,
   что проход остановился **до** обработки всех элементов (не после, что было бы бессмысленной
   проверкой), финальный статус — именно `PARTIAL`, и в логе есть явная запись с объяснением
   причины остановки. **Пройден.**
4. **История изменений: обнаружение** — существующая запись с `rawStreamUrl: 'old-url'`/
   `rawTitle: 'Old Name'`, новый проход находит `'new-url'`/`'New Name'` для того же
   `externalId` → создаётся `WARN`-запись с `metadata.previousStreamUrl`/`newStreamUrl` (и
   аналогично для title), оба значения корректны. **Пройден.**
5. **История изменений: отсутствие ложных срабатываний** — тот же сценарий, но новый проход
   находит **точно те же** `streamUrl`/`title` → подтверждено, что запись об изменении **не**
   создаётся. **Пройден.**

Плюс `tsc --noEmit` над изменёнными файлами модуля scraper вместе с `app.module.ts` — 0 ошибок,
относящихся к этим файлам.

## Не проверено / известные ограничения

- Фронтенд-изменения (`/admin/parser` — панель dry-run) — проверены балансом скобок и вручную
  вычитаны, не прогонялись через `tsc`/визуально в браузере (та же, уже неоднократно
  задокументированная в предыдущих аудитах этого проекта причина нестабильности самодельной
  заглушки `@types/react` конкретно в этой песочнице).
- Реальный `prisma db push` — не прогонялся против настоящего Postgres (в этой фазе схема не
  менялась, только код — риск ниже, чем в предыдущих фазах).
- Значение бюджета времени по умолчанию (25с) подобрано "на глаз" с расчётом на типичные лимиты
  serverless-функций (Vercel Hobby/Pro) — не откалибровано под реальный размер каталога (сам
  размер неизвестен до починки П0.1, см. предыдущие аудиты).
- `deep`-режим dry-run расходует реальные запросы геокодинга (как и предупреждено в UI) — не
  учитывается отдельно в rate-limit/квотах Google Geocoding API, если таковые лимиты когда-либо
  будут добавлены на сам геокодинг-сервис.
