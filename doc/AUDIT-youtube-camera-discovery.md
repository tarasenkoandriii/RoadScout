# Аудит: реалізація ТЗ пошуку камер через YouTube Search API

## Контекст

Реалізація `doc/TZ-youtube-camera-discovery.md` — окреме джерело камер, доповнення до
webcam.guru.ua, пошук через YouTube Data API v3 `search.list`.

## Що зроблено

### П0 — Провайдер і конфігурація
- `YoutubeSearchAdapter` (`src/scraper/providers/youtube-search.adapter.ts`) — один екземпляр
  на одне місто, `adapterKey: youtube-search-{citySlug}`.
- `sql/youtube-search-providers-seed.sql` — по одному `CameraProvider` на кожне `City` з
  `countryCode = 'UA'` (на відміну від webcam-guru, не потребує окремого slug-поля — досить
  `lat`/`lng`, які вже є в кожного міста). Ідемпотентно, підключено в `docker-entrypoint.sh`.
- Нові env: `YOUTUBE_DATA_API_KEY`, `YOUTUBE_SEARCH_RADIUS_KM` (25км), `YOUTUBE_SEARCH_MAX_RESULTS` (50).

### П1 — `discover()`
- Дворівневий запит (гео-фільтр `location`/`locationRadius` + текстовий без гео) — обидва
  `Promise.all`, дедуплікація за `videoId`.
- **403 (квота вичерпана) — явне кидання помилки**, не мовчазний провал: вже існуючий
  `catch()` у `ScraperService.runForProvider()` коректно позначає прохід `FAILED` з чітким
  повідомленням — жодного нового коду для цього не знадобилось.
- Інші не-200 статуси — порожній результат, без падіння.

### П2 — `fetchDetails()` не потрібен
`search.list` з `part=snippet` одразу дає повний набір полів — `discover()` повертає готові
`RawCameraItem` без другої фази (на відміну від webcam.guru.ua).

### П3 — AI-фільтр релевантності (ОБОВ'ЯЗКОВИЙ крок)
- Новий опціональний метод `ProviderAdapter.isRelevant()` — інтегровано в
  `ScraperService.processItem()`, викликається **тільки для нових елементів** (не існуючих),
  **до** створення `CameraSourceRaw` — нерелевантний елемент не потрапляє в чергу ревʼю взагалі.
- `GrokCameraAssistService.isLikelyCityCamera()` — текстовий Grok-запит, безпечний фолбек
  «релевантно» при недоступності AI.
- Це **єдиний свідомий виняток** із принципу «AI не автоматично в парсері»
  (`doc/AUDIT-ai-assist-manual-review-only.md`) — задокументовано в `.env.example` явно.

### Взаємне виключення розкладів (виявлено й виправлено під час реалізації)
`ScraperService.runAll()` розширено опціями `adapterKeyPrefix`/`excludeAdapterKeyPrefix` —
загальний `run-all` (уже існуючий, щоденний) тепер явно **виключає** `youtube-search-*`, а
новий, окремий `run-all-youtube` явно **включає тільки** його — без цього виправлення нові
YouTube-провайдери тригерились би ДВІЧІ (загальним проходом і власним), подвоюючи витрату
квоти. Новий cron-запис `parser-run-all-youtube-daily` (03:15, одразу після основного о 03:00).

## Реально прогнані тести (ts-node, справжнє виконання)

**`YoutubeSearchAdapter`** (21 перевірка): відсутність ключа → порожній результат без жодного
мережевого виклику; успішний пошук (гео+текст) → коректний парсинг усіх полів
(`streamType: YOUTUBE_LIVE`, `streamUrl` у форматі `watch?v=`), **коректна дедуплікація за
videoId**; **403 → явне кидання помилки** з назвою міста в повідомленні; інші помилки → порожній
результат без падіння; елементи без `videoId` відфільтровані.

**`isRelevant()`** (3 перевірки, ключова частина): відсутність AI-ключа → безпечний дефолт
`true` (ніколи не втрачаємо камеру через недоступність AI); **реальний приклад релевантної
камери** («Веб камера Майдан Незалежності») → `true`; **точний реальний приклад шуму з
власного скріншота користувача** («КОРОЛЬ И ШУТ ЛУЧШИЕ ПЕСНИ ТОП 50») → коректно `false`.

**Інтеграція в `ScraperService`** (9 перевірок): `isRelevant()` викликається для обох нових
елементів; релевантний елемент створює `CameraSourceRaw`; **шумовий елемент — НЕ створює
запис узагалі** (не просто позначається, а відсутній як клас); чіткий лог-запис із поясненням;
`stats.newCount` рахує тільки релевантні; адаптер БЕЗ `isRelevant()` (webcam-guru-подібний) —
працює як і раніше, без жодних змін поведінки; **взаємне виключення `runAll()`** — загальний
прохід зачіпає тільки webcam-guru, youtube-специфічний — тільки youtube-search, **жоден
провайдер не тригериться обома викликами одночасно**.

Разом **33 нові перевірки**, усі пройшли. Плюс `tsc --noEmit` по всьому графу застосунку — 0
помилок у змінених файлах (2 залишкові — той самий, вже неодноразово підтверджений у
попередніх аудитах цього проєкту артефакт спрощеної заглушки типів у `lookahead.controller.ts`/
`monitoring.controller.ts`, не пов'язаний із цими змінами).

## Оновлення: доступ через VPN

За прямим запитом користувача — `YoutubeSearchAdapter` тепер приймає опціональний
`RegistryProxyService` (той самий механізм, що вже використовує `WebcamGuruAdapter`), і
`ScraperService.resolveAdapter()` передає його автоматично. Запити до `googleapis.com` тепер
ідуть через VPN, якщо `REGISTRY_SCAN_PROXY_URL` налаштований, з автоматичним фолбеком на прямий
запит, якщо сам проксі недоступний ("VPN не подключён") — той самий, уже перевірений принцип,
не новий код з нуля.

**Реально протестовано** (6 перевірок): без переданого проксі — адаптер працює як і раніше
(зворотна сумісність); з переданим проксі — `RegistryProxyService.request()` дійсно
викликається (по разу на геозапит і текстовий запит), axios отримує коректний конфіг проксі
(`httpAgent`/`httpsAgent`/`proxy: false`); **обробка вичерпаної квоти (403) коректно працює і
через проксі-обгортку** (не ковтається мовчки); успішна відповідь коректно парситься незалежно
від того, проходить вона через проксі чи ні. Усі 6 — **пройдені**.

## Не перевірено / відомі обмеження

- **Реальний виклик YouTube Data API з живим ключем** — мережа недоступна в цій пісочниці;
  перевірена лише логіка обробки відповіді (парсинг, дедуплікація, обробка квоти), не фактична
  якість/кількість результатів на реальних українських містах.
- **Реальна частка геотегованих відео** серед live-трансляцій невідома — саме це й було
  запропоновано перевірити вручну перед повноцінним запуском (див. попереднє обговорення,
  «Крок 1-2» валідації ідеї).
- Індор/аутдор-класифікація і періодична перевірка доступності — жодних змін не знадобилось,
  повністю перевикористовують уже готову інфраструктуру (`GrokCameraAssistService.
  suggestAddressAndType()`, `MonitoringService.checkContentAvailability()` — обидва фільтрують
  за `streamType`, не за провайдером).
- `prisma db push` з новим `youtube-search-providers-seed.sql` не прогонявся проти живої БД.
